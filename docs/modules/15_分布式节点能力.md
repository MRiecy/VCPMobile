# 15. 分布式节点能力 (Distributed Node)

## 1. 概述

### 1.1 模块定位

`distributed/` 是 **VCP Mobile** Rust 核心层中一个**完全独立**的模块，位于 `src-tauri/src/distributed/`，与 `vcp_modules/` 同级。其设计目标是将 VCP Mobile 物理设备转化为 VCPChat 分布式网络中的一个**可感知、可调用、可监控**的移动端节点。

该模块的核心职责包括：

- **节点身份注册**：通过 WebSocket 向 VCPToolBox 主服务器注册自身，上报设备名称、IP 地址与可用工具清单
- **工具能力暴露**：显式扫描 13 个 Android 设备工具与 1 个 `VCPMobileCLI` 适配器；只有用户授权且当前可发布的工具才会注册给主服务器
- **双向状态同步**：持续推送设备状态（电池、CPU、内存、位置等），并接收主服务器的工具执行指令
- **前端状态透传**：通过 Tauri 事件将连接状态实时反馈给 Vue 前端，支持 UI 层的在线/离线指示

### 1.2 与 `vcp_modules/` 的架构边界

`distributed/` 是 WebSocket transport、工具 catalog 与授权策略的唯一 owner。P3 之后它不再是与 `vcp_modules/` 完全无依赖的飞地；`tools/vcp_mobile_cli.rs` 是一条受控的单向适配缝：

```
┌─────────────────────────────────────────────┐
│              src-tauri/src/                  │
│  ┌─────────────┐    ┌─────────────────────┐ │
│  │ distributed/│    │   vcp_modules/      │ │
│  │ transport +  │───►│ cli protocol/runtime│ │
│  │             │    │                     │ │
│  │ • client    │    │ • cli protocol      │ │
│  │ • telemetry_center │  │ • cli runtime       │ │
│  │ • registry  │    │   (唯一事实源)      │ │
│  │ • tools     │    │                     │ │
│  │ • types     │    │                     │ │
│  └─────────────┘    └─────────────────────┘ │
│           ▲                                 │
│           │ 仅通过 lib.rs 的 app.manage()   │
│           ▼                                 │
│  ┌─────────────────────────────────────┐   │
│  │  lib.rs — Tauri State + Command 注册 │   │
│  └─────────────────────────────────────┘   │
└─────────────────────────────────────────────┘
```

- **通用 transport 不识别 CLI 内部状态**：`client.rs` 只处理连接 epoch、ACK 身份、请求去重、有界 `_vcpContext` 和回包；业务执行经 `ToolRegistry` 分发。
- **CLI 不复制业务 owner**：`vcp_mobile_cli.rs` 复用 canonical manifest、`RawVcpToolRequest` validator、`MobileCliRuntimeState` 与结果投影，不创建第二份 Shell、Job ledger 或进程生命周期。
- **通用设备工具仍保持模块内自洽**：传感器数据仍来自 Android Plugin IPC、`TelemetryCenter` 或受控 procfs/sysfs 读取，不读写 CLI ledger。
- **生命周期分工**：连接启停由 `DistributedState` 和 lifecycle reconciler 管理；已被 Runtime 接收的 CLI Job 不归 WebSocket session 所有，断线只丢弃本次回包 waiter，不终止 Job。

## 2. 节点客户端 (`client.rs`)

`client.rs` 是分布式节点的连接 owner，负责与 VCPToolBox 主服务器建立并维护 WebSocket 长连接。其协议与 VCPChat 的 `VCPDistributedServer.js` 对齐，同时增加移动端连接 epoch、有界输入与请求所有权门。

### 2.1 连接状态机 (Connection State Machine)

v1.0.3 引入了严格的 4 状态 `ConnectionState` 枚举，防止重复启停和状态混乱：

```
 Disconnected ──start()──► Connecting ──connection_ack──► Connected
      ▲                        │                              │
      │                        │ connection failed            │ session ends / error
      │                        ▼                              │
      └────stop() cleanup──── Disconnecting ◄──stop()─────────┘
                                   │
                                   └── safety net: Disconnected
```

| 状态 | 含义 | 进入条件 | 退出条件 |
|------|------|----------|----------|
| `Disconnected` | 未连接（默认） | 初始状态；session 清理后 | `start()` 调用 |
| `Connecting` | 正在建立连接 | `start()` 设置 | connection_ack 或连接失败 |
| `Connected` | 已连接并注册 | connection_ack 处理完成 | session 断开或 stop() |
| `Disconnecting` | 正在断开 | `stop()` 设置 | session 清理完成 |

**关键守卫逻辑**：

- `start()` 与 `stop()` 共享一个 lifecycle mutex，整个状态转换（包括跨 await 的旧任务 join、Android keepalive 与新 handle 安装）严格串行；
- `start()` 在 `state == Connected || state == Connecting` 时直接返回 `Ok(())`，拒绝重复启动
- `start()` 始终先 `take()` 旧 session，取消其 `CancellationToken` 并 `await` task_handle，确保旧连接完全清理后再创建新连接
- **零状态复用**：每次 `start()` 创建全新的 `CancellationToken` 和 `mpsc::channel(1)`，不继承上一个生命周期的任何状态
- `stop()` 无论当前是否已连接都会先推进 `session_id` generation、清空 connected/server/client，再取消并 await 当前主任务；因此 start 安装前窗口和迟到 ACK 都无法把状态复活；
- `connection_ack` 提交前校验自己的 `session_id`。旧 session 的 ACK、退出 finally 与状态事件没有当前 generation 的写权限；
- **安全兜底**：session drop 后，只有 stop generation 仍为当前 owner 才提交最终 `Disconnected` 并 emit 状态。

每个已连接 session 还持有自己的 `SessionTaskTracker` 与单一 WebSocket writer：工具执行、IP 上报、非空 `StreamingScheduler` 都由 tracker 收编。session 退出先 cancel 子 token，再 join 全部子任务；所有业务发送进入同一个有界 writer并使用 5 秒完成 deadline。

### 2.2 连接生命周期

```
前端调用 start_distributed_node
         │
         ▼
┌─────────────────────┐
│  状态守卫检查        │──> Connected/Connecting → 直接返回
│  take() 旧 session  │──> 若存在，cancel + await 清理
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ 创建 CancellationToken│──> 全新 token，零状态复用
│ + reconfigure/rx    │
│ + reconnect/rx      │
└──────────┬──────────┘
           ▼
┌─────────────────────┐
│ spawn connection_loop│──> 在独立 tokio 任务中运行
└──────────┬──────────┘
           ▼
    ┌──────────────┐
    │  连接主循环   │ ← `distributed:connect` lease 只覆盖 connect_async await
    └──────┬───────┘
           │
    ┌──────┴──────┐
    ▼             ▼
  成功          失败
    │             │
    ▼             ▼
┌────────┐  ┌─────────────────────┐
│run_session│ │指数退避等待           │
│(会话处理) │ │(5s → 60s)             │
└───┬────┘  │或 reconnect_rx 立即触发 │
    │       └─────────────────────┘
    ▼             │
断开/错误    ┌─────┘
    │        ▼
    └──► 循环重连直到 cancel_token.cancelled()
```

### 2.3 Struct 架构

三个 struct 实现连接生命周期的清晰分离：

| Struct | 职责 | 数据类型 |
|--------|------|----------|
| `ConnectionConfig` | 不可变连接参数 | `ws_url: String`, `vcp_key: String`, `device_name: String` |
| `SessionContext` | 运行时通道与共享状态 | `status: Arc<RwLock<DistributedStatus>>`, `registry: Arc<ToolRegistry>`, `reconfigure_rx`, `reconnect_rx`, `session_id: u64` |
| `ConnectionSession` | 活跃会话句柄 | `cancel_token: CancellationToken`, `reconfigure_tx`, `reconnect_tx`, `task_handle: JoinHandle<()>` |

### 2.4 通道架构 (Channel Architecture)

`DistributedClient` 使用两对 `tokio::sync::mpsc::channel(1)` 实现带外控制：

| 通道 | 容量 | 发送方 | 接收方 | 用途 |
|------|------|--------|--------|------|
| `reconfigure_tx/rx` | 1 | `reconfigure_tools()` | `run_session` 的 `tokio::select!` 分支 | 授权变化时结束旧会话；服务端断线清理旧投影后立即以新计划重连 |
| `reconnect_tx/rx` | 1 | `trigger_reconnect()` | `connection_loop` 的退避等待 `tokio::select!` 分支 | Android 网络恢复事件触发立即重连，跳过指数退避 |

两条通道的容量均为 1（非阻塞发送），确保 `send()` 不会阻塞调用线程，且通道中最多缓存一个待处理请求。

`CancellationToken` 作为统一的关停信号：
- `connection_loop` 在每次循环迭代开始时检查 `cancel_token.is_cancelled()`
- `run_session` 的 `tokio::select!` 中监听 `cancel_token.cancelled()` → 优雅关闭 WS 发送端并退出
- connect 阶段的 `tokio::select!` 同时等待 `connect_async` 和 `cancel_token.cancelled()`，避免关停时卡在 TCP 连接超时
- `run_session` 创建 child token + `SessionTaskTracker`，所有派生任务必须经 tracker spawn；退出时 `close_and_wait()` 先取消再 join
- WebSocket 只有一个 writer task；业务分支经请求通道发送并等待最多 5 秒 ACK，不能持 sink mutex 跨无界 await

### 2.5 资源生命周期管理

连接、授权与硬件采集分别由 `DistributedClient`、`SessionToolPlan`、`StreamingScheduler` 管理：

| 阶段 | 操作 | 触发位置 | 说明 |
|------|------|----------|------|
| 后台节点租约 | `set_keepalive_mode_inner(true/false)` | `lifecycle_controller.rs` | lifecycle 是 `distributed` tag 的唯一 owner；只在后台且节点实际运行时持有，回前台或 5 分钟到期时释放 |
| TCP 连接建立 | `acquire_foreground_inner` / `release_foreground_inner` | `connection_loop` connect 前后 | 标签 `distributed:connect`，优先级 `PRIORITY_DISTRIBUTED(10)`，防止 TCP 握手期间 CPU 休眠 |
| 工具执行 | `acquire_foreground_inner` / `release_foreground_inner` | `tokio::select!` 分支内 | 标签 `distributed:tool:{request_id}`，优先级 10，工具执行前后短暂持有 |
| 遥测批次 | `sample_sensor_data()` | `StreamingScheduler` | 只在至少一个已授权 streaming tool 到期时获取 `distributed:telemetry:*` lease；按本批需求采样并发送后立即释放 |

> **零工具物理边界**：`enabledTools=[]` 或只有 OneShot 工具时不创建 `StreamingScheduler`，不会调用原生传感器，也不会产生周期性 Foreground lease。

`distributed:connect` lease 的作用域必须严格止于 `connect_async` 返回，不能覆盖整个 `run_session` 或退避等待；长期后台保活只能由 lifecycle controller 的 `distributed` tag 表达，避免两个 owner 互相提前释放。

### 2.6 连接 URL 构造

WebSocket 连接地址基于用户传入的 `ws_url`（如 `ws://192.168.1.100:5800`），拼接固定路径：

```
{ws_url}/vcp-distributed-server/VCP_Key={vcp_key}
```

- `ws_url` 中的尾部斜杠会被 `trim_end_matches('/')` 移除，避免双斜杠
- `vcp_key` 用于服务器端的节点认证，日志输出时会替换为 `***` 防止泄露

### 2.6 会话处理 (`run_session`)

成功建立 WebSocket 后，入口先冻结不可变 `SessionToolPlan`。主会话循环监听三个事件源，遥测调度作为受 `SessionTaskTracker` 管理的子任务运行：

| 事件源 | 触发条件 | 处理逻辑 |
|--------|----------|----------|
| WS 接收 | 主服务器发来 Text/Ping/Close | Text → `handle_incoming()`；Ping → 自动回复 Pong；Close → 退出会话 |
| 授权重配置 | `reconfigure_rx.recv()` 收到信号 | 关闭当前 WS；VCPToolBox 清理旧工具与占位符后立即重连，构造新的授权快照 |
| 取消信号 | `cancel_token.cancelled()` | 优雅关闭 WS 发送端并退出 |

`StreamingScheduler` 使用每个工具真实的 `poll_interval_secs()`，等待最近 deadline，合并同批工具的 `SensorDemand`，完成一次有界采样后只发送本批到期占位符。不存在全局 30 秒空转门禁。

### 2.7 入站消息处理 (`handle_incoming`)

所有入站消息先反序列化为 `IncomingEnvelope`，再匹配为 `IncomingMessage` 变体：

| 消息类型 | 对应 `IncomingMessage` | 动作 |
|----------|------------------------|------|
| `connection_ack` | `ConnectionAck { server_id, client_id }` | 更新状态为已连接，发布会话工具清单、上报 IP；存在 streaming plan 时才启动调度器 |
| `execute_tool` | `ExecuteTool { request_id, tool_name, tool_args }` | 在 `ToolRegistry` 中查找并执行工具，通过 WS 返回 `tool_result` |
| 其他 | `Unknown(String)` | 记录 debug 日志，忽略 |

### 2.8 指数退避重连与即时重连

连接失败或会话断开后，客户端不会立即重连，而是采用指数退避策略：

- 初始间隔：**5 秒**
- 每次失败后翻倍，上限：**60 秒**
- 成功连接后重置为 5 秒
- 工具授权变化产生 `Reconfigured` 会话出口：跳过退避、立即重连
- 退避期间通过 `tokio::select!` 同时监听 `cancel_token.cancelled()` 和 `reconnect_rx.recv()`：
  - `cancel_token.cancelled()` → 退出循环（正常关停）
  - `reconnect_rx.recv()` → **立即跳过退避等待，马上重连**（Android 网络恢复事件触发）

`reconnect_rx` 通道的发送方 `trigger_reconnect()` 由 Android 原生 `ConnectivityManager.NetworkCallback` 通过 `vcp-network-status-changed` 事件触发。`lib.rs` 监听该事件，当 `connected=true` 时调用 `distributed_state.client.trigger_reconnect()`。当设备从离线恢复在线时，无需等待最长 60 秒的退避延迟，实现秒级重连。

### 2.9 状态透传

`DistributedClient` 维护一个 `Arc<RwLock<DistributedStatus>>` 状态对象。`DistributedStatus` 包含 `state: ConnectionState`（枚举）、`connected: bool`（布尔）以及 `session_id: u64`（会话版本号），前者用于状态机守卫，后者用于前端 UI 展示，`session_id` 用于识别当前生命周期以避免旧会话的脏写。任何连接状态变化都会通过 Tauri 事件推送给前端：

```rust
app.emit("vcp-distributed-status", &status)
```

前端通过 `window.addEventListener("vcp-distributed-status", ...)` 或 Tauri 的事件监听 API 接收，用于更新 UI 中的节点在线指示器。

### 2.10 公共方法

| 方法 | 用途 | 返回值 |
|------|------|--------|
| `start(app, ws_url, vcp_key, device_name, registry)` | 启动分布式节点连接 | `Result<(), String>` |
| `stop(app)` | 停止分布式节点 | void（幂等） |
| `get_status()` | 获取当前状态快照 | `DistributedStatus` |
| `is_running()` | 检查连接任务是否活跃（非 Disconnected） | bool |
| `reconfigure_tools()` | 授权变化后替换当前连接会话（通过 reconfigure_tx 发送） | void（非阻塞） |
| `trigger_reconnect()` | 触发即时重连（通过 reconnect_tx 发送） | void（非阻塞） |

> `is_running()` 在 `Connecting`、`Connected`、`Disconnecting` 状态下均返回 true，用于生命周期调和与授权变化覆盖 TCP 握手窗口。
>
> **v1.1.3 生命周期变更**：`start()` / `stop()` 不再通过前端 Tauri Command 直接调用，而是由 `vcp_modules/infra/lifecycle_reconciler.rs` 根据 `settings.distributed_enabled` 自动决策调用。前端仅通过设置持久化开关与 `reconcile_distributed_node_cmd` 触发状态对齐。

## 3. 工具注册表 (`tool_registry.rs`)

`tool_registry.rs`（158 行）是工具能力的中央调度器， mirrors VCPChat 中的 `Plugin.js`（`PluginManager` 类）。其核心设计是**三模式工具 trait 系统**。

### 3.1 三种执行模式

| 模式 | Trait | 特征 | 典型代表 |
|------|-------|------|----------|
| **OneShot** | `OneShotTool` | 调用即返回，无前端参与，纯 Rust 侧执行 | `MobileDeviceInfo`、`MobileClipboard` |
| **Interactive** | `InteractiveTool` | 需要前端 UI 参与（相机、生物识别等），触发 Tauri 事件 → Vue 展示 UI → 结果返回 | 预留，Phase 3 实现（如拍照） |
| **Streaming** | `StreamingTool` | 持续产生数据，通过 `update_static_placeholders` 定期推送到主服务器 | `MobileBatteryInfo`、`MobileCPUInfo`、`MobileLocation` |

三种 trait 的共同约束：

```rust
fn manifest(&self) -> ToolManifest;  // 工具元数据
```

OneShot 与 Interactive 额外要求：

```rust
async fn execute(&self, args: Value, app: &AppHandle) -> Result<Value, String>;
```

Streaming 额外要求：

```rust
fn placeholder_key(&self) -> &str;      // 占位符标识，如 "{{MobileBattery}}"
fn poll_interval_secs(&self) -> u64;    // 调度器实际采用的轮询间隔
fn sensor_demand(&self) -> SensorDemand; // 默认无物理传感器需求
fn read_current(&self, app: &AppHandle) -> Result<String, String>;  // 读取当前快照（必须快/非阻塞）
```

### 3.2 统一包装与注册

由于 Rust trait object 要求类型统一，`ToolRegistry` 内部使用 `ToolEntry` 枚举包装三种工具：

```rust
pub enum ToolEntry {
    OneShot(Arc<dyn OneShotTool>),
    Interactive(Arc<dyn InteractiveTool>),
    Streaming(Arc<dyn StreamingTool>),
}
```

`ToolRegistry` 以 `HashMap<String, ToolEntry>` 存储工具，键为 `manifest().name`。提供三类注册方法：

```rust
pub fn register_oneshot<T: OneShotTool + 'static>(&mut self, tool: T);
pub fn register_interactive<T: InteractiveTool + 'static>(&mut self, tool: T);
pub fn register_streaming<T: StreamingTool + 'static>(&mut self, tool: T);
```

### 3.3 动态发现与调用分发

- **`build_session_plan(app)`**：在配置锁内同时冻结注册 manifest 与 streaming plan，避免一个会话观察到两套授权状态。
- **`build_streaming_plan_for(enabled)`**：只为已授权的 Streaming 工具生成 interval、placeholder 和 `SensorDemand`；空集不会启动调度器。
- **`execute(tool_name, args, app)`**：按名称查找工具，根据 `ToolEntry` 变体路由到对应执行器。若工具为 Streaming 类型，`execute` 返回当前 `read_current()` 的快照值（字符串包装为 `Value::String`）

### 3.4 工具注册表持久化

`ToolRegistry` 使用 `app_config_dir/distributed_tools.json` 持久化显式启用 allowlist：

| 方法 | 用途 | 行为 |
|------|------|------|
| `ensure_enabled_config_loaded(app)` | 幂等加载 v2 `enabledTools` allowlist | 在连接裁决前离线加载；目录/状态 command 也会自行 ensure，不依赖 Distributed 已开启 |
| `persist_and_update_enabled(app, names)` | 持久化并切换启用 allowlist | 拒绝未知或重复名称；blocking worker 执行 temp + fsync + rename，只有持久化成功才替换内存策略 |
| `reset_all_disabled(app)` | 显式恢复入口 | 原子写入全部禁用策略，再替换已连接会话 |

**Opt-in 设计**：首次运行时，所有已扫描工具默认未授权。用户必须在 `DistributedView.vue` 的"插件列表"标签页中手动启用需要的工具。这一设计确保：
- 用户对哪些设备数据被暴露给主服务器有明确意识
- 耗电传感器（如 GPS 位置）不会在用户不知情时启用
- 变更先完成原子持久化，随后才切换运行时策略；失败时 UI 回滚开关

**会话替换机制**：`persist_and_update_enabled()` 返回 `true` 时，`update_enabled_tools` 向当前 session 发送 `reconfigure_tx`。旧 WS 主动关闭，VCPToolBox 的 disconnect handler 清理该节点全部工具与占位符，然后 Mobile 立即重连并发布最新 `SessionToolPlan`。这避免了服务端同连接 `register_tools` 非替换语义造成的同名冲突和陈旧占位符。

### 3.5 前端元数据接口

`get_tools_metadata()` 为 `DistributedView.vue` 提供增强的工具元数据。它在序列化后的 `ToolManifest` 上追加 `category`（`"oneshot"` / `"interactive"` / `"streaming"`）、`enabled`（布尔）、`placeholder`（可选）字段，并显式放入 `display_name`。v1.1.3 的 `ToolManifest` 已移除 `parameters` / `tool_type` 字段，改为通过 `invocation_commands` 描述可执行命令。

## 4. 类型系统 (`types.rs`)

`types.rs` 定义分布式节点与主服务器之间的协议消息契约。`register_tools.tools[]` 使用 `serde_json::value::RawValue`；`execute_tool.data._vcpContext` 作为受信任的顶层元数据与 `toolArgs` 分离解析。

### 4.1 出站消息 (`OutgoingMessage`)

```rust
#[serde(tag = "type", content = "data")]
pub enum OutgoingMessage {
    RegisterTools { server_name, tools },
    ReportIp { server_name, local_ips, public_ip },
    ToolResult { request_id, status, result, error },
    UpdateStaticPlaceholders { server_name, placeholders },
}
```

| 变体 | 序列化后 `type` 字段 | 发送时机 |
|------|---------------------|----------|
| `RegisterTools` | `"register_tools"` | 收到 `connection_ack` 后 |
| `ReportIp` | `"report_ip"` | 注册工具后 |
| `ToolResult` | `"tool_result"` | 完成 `execute_tool` 后 |
| `UpdateStaticPlaceholders` | `"update_static_placeholders"` | 至少一个已授权 Streaming 工具到达自身 deadline 后；只发送本批到期键 |

### 4.2 入站信封与消息 (`IncomingEnvelope` / `IncomingMessage`)

`IncomingEnvelope` 是原始 JSON 的弱类型表示：

```rust
pub struct IncomingEnvelope {
    pub msg_type: String,   // JSON 中的 "type"
    pub data: Option<Value>,
    pub message: Option<String>,
}
```

通过 `parse()` 方法转换为强类型的 `IncomingMessage`：

```rust
pub enum IncomingMessage {
    ConnectionAck { server_id, client_id },
    ExecuteTool { request_id, tool_name, tool_args },
    Unknown(String),
}
```

`Unknown` 变体确保协议前向兼容——主服务器未来新增消息类型不会导致节点崩溃。

### 4.3 工具清单 (`ToolManifest`)

```rust
pub struct ToolManifest {
    pub name: String,
    pub description: String,
    #[serde(default)]
    pub display_name: String,
    #[serde(default, skip_serializing_if = "Option::is_none")]
    pub placeholder: Option<String>,  // 有 placeholder 的工具为 Streaming 静态占位符工具
    #[serde(default)]
    pub invocation_commands: Vec<InvocationCommand>,  // OneShot 工具的调用命令说明
}

pub struct InvocationCommand {
    pub command_identifier: String,
    pub description: String,
    pub example: String,
}
```

v1.1.3 的 manifest 已改为与 VCPToolBox 插件格式严格对齐：

- 可执行工具（无 `placeholder`）序列化时 `pluginType="synchronous"`，`capabilities.invocationCommands` 填充完整命令示例；
- 静态占位符工具（有 `placeholder`）序列化时 `pluginType="static"`，`capabilities.systemPromptPlaceholders` 填充占位符信息，`invocationCommands` 为空数组。

`display_name` 供前端 UI 展示，`invocation_commands` 描述 OneShot 工具的调用方式。

### 4.4 连接状态与状态机 (`ConnectionState` / `DistributedStatus`)

```rust
#[derive(Default, Serialize, Deserialize)]
#[serde(rename_all = "lowercase")]
pub enum ConnectionState {
    #[default] Disconnected,
    Connecting,
    Connected,
    Disconnecting,
}

pub struct DistributedStatus {
    pub state: ConnectionState,    // 状态机当前状态
    pub connected: bool,           // 面向前端的简化布尔标志
    pub server_id: Option<String>,
    pub client_id: Option<String>,
    pub registered_tools: usize,       // 已交给当前本地 WS writer 的数量，非服务端 ACK
    pub last_error: Option<String>,
    pub session_id: u64,           // 会话版本号，v1.1.3 新增
}
```

`ConnectionState` 是 Rust 侧用于状态机守卫的精确状态枚举。`connected: bool` 是面向前端 UI 的简化标志——前端仅需知道"是否在线"，无需理解 Connecting/Disconnecting 过渡态。两者由 `emit_status()` 同步更新，保证前后端状态一致性。

## 6. 关键工具详解

### 6.1 `device_info.rs` — 设备基本信息 (OneShot)

> 源码：`src-tauri/src/distributed/tools/device_info.rs`（36 行）

`MobileDeviceInfo` 是最简单的 OneShot 工具， mirrors VCPChat 的 `WindowSensor` 插件。它不读取任何传感器，仅返回编译期常量：

```rust
async fn execute(&self, _args: Value, _app: &AppHandle) -> Result<Value, String> {
    Ok(json!({
        "os": std::env::consts::OS,       // 如 "android"
        "arch": std::env::consts::ARCH,   // 如 "aarch64"
        "family": std::env::consts::FAMILY // 如 "unix"
    }))
}
```

**设计意图**：在节点首次注册时，让主服务器快速了解该节点的操作系统与指令集架构，为后续工具调用策略提供上下文（例如，知晓是 Android 后不会调用桌面端的 `WindowSensor`）。

---

### 6.2 `battery.rs` — 电池状态 (Streaming)

> 源码：`src-tauri/src/distributed/tools/battery.rs`（85 行）

`MobileBatteryInfo` 是典型的 **Phase 1 Streaming 工具**，完全通过 Android sysfs 读取，不依赖前端。

**读取路径**：

| 数据项 | sysfs 路径 | 处理逻辑 |
|--------|-----------|----------|
| 电量 | `/sys/class/power_supply/battery/capacity` | 原样输出，追加 `%` |
| 状态 | `/sys/class/power_supply/battery/status` | 映射为中文：`Charging`→充电中、`Discharging`→放电中、`Full`→已充满、`Not charging`→未充电 |
| 温度 | `/sys/class/power_supply/battery/temp` | 单位是 0.1°C（如 `320` → `32°C`），除以 10 后格式化 |

**降级策略**：若 sysfs 路径不存在（如部分 OEM 屏蔽电池节点），三个值均返回 `N/A` / `未知`，最终输出 `"电池信息不可用"`，避免 panic 或错误上报。

**占位符**：`{{MobileBattery}}`，推送间隔：60 秒。

---

### 6.3 `location.rs` — GPS 位置 (Streaming)

> 源码：`src-tauri/src/distributed/tools/location.rs`（39 行）

`MobileLocation` 是典型的 **Phase 2 Streaming 工具**，代表 Android 原生传感器协作的设计模式。

**为什么需要 Android 原生？** Android 的精确 GPS 定位需要 `ACCESS_FINE_LOCATION` 权限。`StreamingScheduler` 只在该工具到期且仍获授权时，通过 `sample_sensor_data` 请求一次有界原生采样；未授权时不会触碰 `LocationManager`。

**数据流**：

```
StreamingScheduler
    │ 到达 MobileLocation 的 120 秒 deadline
    │ 合并本批 SensorDemand
    ▼
Android 原生 (SensorStatusManager.kt)
    │ sampleSensorData(location=true)
    │ 最多 2 秒内获取 last-known / single update，随后注销 listener
    ▼
TelemetryCenter
    │ 保存最近一次有界采样结果
    ▼
location.rs::read_current()
    │ 纯读取缓存并生成 {{MobileLocation}}
```

**最大容忍陈旧度**：300 秒（5 分钟）。GPS 在室内可能无法更新，过长的容忍期确保即使信号弱，仍能提供最近一次有效定位。

**占位符**：`{{MobileLocation}}`，推送间隔：120 秒。

---

### 6.4 Plugin IPC 通道 — 按需传感器批次

> 原 `frontend_bridge.rs`（43 行）已删除。传感器数据通信现已升级为 Android 原生 Plugin IPC 通道。

`plugin:vcp-mobile|sample_sensor_data` 是物理传感器的唯一采集入口。它接收三位需求 `{ location, motion, ambient }`，只注册本批需要的硬件，并在 2 秒采样窗口结束时统一注销 listener、返回快照。

**核心设计**：

```
SessionToolPlan（不可变授权快照）
    │ 每个工具的 interval + SensorDemand
    ▼
StreamingScheduler（单任务）
    │ 合并同批需求；零 streaming tool 时不创建
    ▼
Plugin IPC: sample_sensor_data
    │ Kotlin 有界采样、统一释放
    ▼
TelemetryCenter → 各 StreamingTool::read_current()
    ▼
VCPToolBox（逐键合并 update_static_placeholders）
```

**API**：

| 函数 | 调用方 | 作用 |
|------|--------|------|
| `sample_sensor_data(demand)` (IPC) | `StreamingScheduler` | 一次刷新本批需要的位置/运动/环境读数 |
| `read_current(app)` (同步) | 到期 streaming batch | 从 `TelemetryCenter` 或 sysfs 读取，不再直接启动传感器 |

**关键约束**：Kotlin 采样始终有界并在所有完成路径注销 listener；Rust 使用 blocking worker 等待 PluginHandle 回调，不阻塞 WebSocket writer。工具频率由各自 `poll_interval_secs()` 决定，不再被统一 30 秒覆盖。

---

### 6.5 `device_status_summary.rs` — 状态聚合摘要 (Streaming)

> 源码：`src-tauri/src/distributed/tools/device_status_summary.rs`（205 行）

`MobileStatusSummary` 是 **Phase 3 聚合工具**，不直接读取新的传感器，而是综合其他工具的数据源，生成一行人类可读的状态摘要。

**聚合策略**：

| 子系统 | 数据来源 | 摘要格式 |
|--------|----------|----------|
| CPU | `/proc/stat` 单点采样 + 热区温度 | `CPU:使用率%/温度°C` |
| GPU | Adreno `gpu_busy_percentage` 或 Mali `utilization` | `GPU:使用率%` |
| 内存 | `/proc/meminfo` | `内存:已用%` |
| 电池 | `/sys/class/power_supply/battery/*` | `电量:XX%[充电中/已满]` |
| 网络 | `/proc/net/route` 默认路由 | `WiFi` / `移动数据` / `离线` |
| 位置 | `location.rs` 通过 IPC 获取（max_age=300s） | 坐标简写 |
| 运动 | `motion_sensor.rs` 通过 IPC 获取（max_age=120s） | 运动状态简写 |

**设计意图**：主服务器若只想快速了解设备概况，无需分别调用 6 个工具，直接读取 `{{MobileStatus}}` 占位符即可。这显著降低了协议开销与 LLM 上下文占用。

**占位符**：`{{MobileStatus}}`，推送间隔：60 秒。

## 7. 生命周期与命令接口

v1.1.3 中，分布式节点的**启停不再由前端直接调用 Tauri Command 控制**，而是交给 `vcp_modules/infra/lifecycle_reconciler.rs` 统一根据 `settings.distributed_enabled` 自动调和。`distributed/mod.rs` 仅暴露查询、配置与调试类命令。

### 7.1 自动调和机制

```
前端保存设置
    │ distributedEnabled / distributedWsUrl / distributedVcpKey / distributedDeviceName 变化
    ▼
settings_manager::save_settings()
    │ 计算 should_reconcile_dist / force_reconnect_dist
    ▼
lifecycle_reconciler::reconcile_distributed_node(app, enabled, force_reconnect)
    │
    ├── enabled=true, not running, params valid ──► client.start(...)
    │
    ├── enabled=false, running ───────────────────► client.stop()
    │
    └── params changed + enabled ─────────────────► client.stop() → client.start(...)
```

- `distributed_enabled` 是连接开关；连接只读取独立的 `distributed_ws_url` / `distributed_vcp_key` / `distributed_device_name`，不再从 VCPLog 字段隐式回退。
- `bootstrap()` 在任何网络调和前调用 `ensure_enabled_config_loaded(app)`。因此 Distributed 关闭时，插件中心仍能准确显示持久授权与恢复警告。
- `force_reconnect` 用于 URL/Key/名称变更时先停止旧连接再启动新连接。
- `mobileCliAgentRoute` 单独变更只重注册当前 manifest 集，不重连 WebSocket，也不替用户开启 Distributed 或授权 CLI。

### 7.2 `distributed/mod.rs` 注册的 7 个命令

| 命令 | 签名 | 用途 |
|------|------|------|
| `get_distributed_status` | `async fn(state) -> Result<DistributedStatus, String>` | 查询当前连接状态（含 `session_id`） |
| `get_registered_tools_metadata` | `async fn(app, state) -> Result<Vec<Value>, String>` | 离线 ensure 授权策略后，返回全 catalog（含 `category`/`enabled`/`placeholder`/`display_name`） |
| `get_distributed_tool_config_status` | `async fn(app, state) -> Result<ToolConfigStatus, String>` | 离线 ensure 并返回 ready / recovered_disabled / persistence_error 状态 |
| `update_enabled_tools` | `async fn(app, state, enabled_names: Vec<String>) -> Result<(), String>` | 持久完整启用 allowlist；若连接任务正在运行则替换会话，覆盖 Connecting/Connected 窗口 |
| `reset_distributed_tools_disabled` | `async fn(app, state) -> Result<(), String>` | 原子恢复为全部禁用并替换连接会话 |
| `execute_distributed_tool` | `async fn(app, state, name: String) -> Result<String, String>` | 手动执行指定工具，用于 UI 调试 |
| `reconnect_distributed_client` | `async fn(state) -> Result<(), String>` | 立即触发 WebSocket 重连（跳过指数退避） |

### 7.3 `lifecycle_manager` 提供的调和命令

| 命令 | 签名 | 用途 |
|------|------|------|
| `reconcile_distributed_node_cmd` | `async fn(app_handle) -> Result<bool, String>` | 前端手动触发一次分布式节点状态对齐；读取当前 settings 后调用 `reconcile_distributed_node(..., true)` |

### 7.4 `sample_sensor_data`（Rust→Kotlin 内部桥）

| 属性 | 值 |
|------|-----|
| 函数签名 | `async fn sample_sensor_data(location, motion, ambient) -> Result<SensorSample, String>` |
| 参数 | 三个布尔需求位，只允许采集本批已授权工具真正依赖的硬件 |
| 返回值 | 仅包含请求字段的 `SensorSample` |
| 副作用 | 通过内部 `PluginHandle` 调用 Android `sampleSensorData`，注册相应 listener 并在 2 秒内统一释放 |
| 调用时机 | `StreamingScheduler` 找到至少一个到期且有传感器依赖的工具批次时 |

> **架构变更**：常驻式 `start_sensor_collection` / `stop_sensor_collection` / `get_sensor_data` 已删除。节点在线不再意味着硬件采集；只有授权且到期的 streaming batch 才能进入原生采样。
> `sample_sensor_data` 不注册为 WebView Tauri command，也不进入 permission/Guest JS；前端无法绕过工具 allowlist 直接采样。

### 7.5 前端调用示例

// Android 原生 SensorStatusManager.kt 负责传感器采集和缓存
```

        └── vcp_mobile_cli.rs ──► tool_registry.rs + canonical cli protocol/runtime + typed route
```

### 8.2 与 `vcp_modules/` 的受控跨层依赖

通用 transport、registry 与设备工具不应反向依赖聊天、同步或数据库领域。唯一例外是 `tools/vcp_mobile_cli.rs` 与其契约测试，它显式导入 `vcp_modules::cli` 与 typed route 读取缝。

| 路径前缀 | 出现次数 | 说明 |
|----------|----------|------|
| `crate::distributed::` | ~40 | 仅模块内部引用 |
| `std::` | ~30 | 标准库 |
| `tokio::` | ~10 | 异步运行时 |
| `tauri::` | ~8 | Tauri 框架 |
| `serde_json::` / `serde::` | ~15 | 序列化 |
| `futures_util::` | ~2 | Stream/Sink trait |
| `tokio_tungstenite::` | ~3 | WebSocket 客户端 |
| `reqwest::` | ~1 | 公网 IP 查询 |
| `async_trait::` | ~4 | trait 异步方法 |
| `libc::` | ~1 | `statvfs`（`storage_info.rs`） |
| `crate::vcp_modules::cli` | 受限 | 仅 CLI adapter 复用 canonical manifest、validator、Runtime 与 result projection |
| `crate::vcp_modules::settings_manager` | 受限 | 仅读取一次 turn/registration route 事实 |

**仍禁止下列跨域依赖**：

- `crate::db_manager::`
- `crate::chat_manager::`
- `crate::sync_service::`

该边界保证 Distributed 仍可单独测试 transport/registry，同时确保 CLI 只有一份协议、Runtime 和 Job 事实源。

### 8.1 VCPMobileCLI 运行语义收口

以下语义由 `vcp_modules/cli` Runtime 与 Kotlin `CliProcessHost` 的哑执行器边界共同保证（详见 `docs/plugins/01_插件初始化与命令路由.md` §7.1）：

- **Job 状态机含 `Stopping` 中间态**：`terminal_intent` 一旦持久化（首次落盘即把状态置 `Stopping`），任何后续 Running 事实都不会把状态回退为 Running；只有 Kotlin 确认进程树消失（Exited）后才由 `claim_terminal_intent` 发布目标终态（`Cancelled`/`TimedOut`/`Failed`/`Interrupted`）。`Stopping` 非终态。
- **`list` 的可见性按调用方会话过滤**：带 `session_id` 的调用方看到本会话 + 无主 job；无会话的调用方（本地 UI）只看到无主 job。`session_id` 由分布式 adapter（`dist-session:<sha256(remote_identity)>`）注入，模型不可见。
- **lease-loss 收口归 Rust**：Kotlin 在租约丢失时只置 `background_lease_lost` 事实位；Rust monitor 观察到事实后写入 `TerminalIntentTarget::Interrupted`，经 `cancelCliProcess` 通道收口进程树。App 进程重启时 `load_and_reconcile` 将非终态 job 直接置 `Interrupted`（ProcessHost 状态是进程本地的，持久化 intent 不构成旧进程树已消失的证据）。
- **托管环境变量**：前台/后台 job 的 guest 环境经 `env -i` 全量清空后注入 `VCP_CLI_WORKSPACE=/workspace`；带 session 的 job 另注入 `VCP_CLI_SESSION_ID`。PTY 路径只注入静态 `VCP_CLI_WORKSPACE`。

## 9. 分布式工具三层数据策略

The distributed tools use a four-tier data acquisition strategy (v1.1.3 新增 Root 命令层)：

| Tier | Source | Method | Tools | Fallback |
|------|--------|--------|-------|----------|
| **Layer 1: Root sysfs via libsu** | `/sys/class/*`, `/proc/*` | `sysfs_utils::execute_root_command_safe(app, cmd)` | battery, cpu_info, gpu_info, memory_info, network_info, storage_info | Root 不可用 → Layer 2 |
| **Layer 2: Direct sysfs** | `/sys/class/*`, `/proc/*` | Direct file I/O via `sysfs_utils::read_sysfs*` | battery, cpu_info, gpu_info, memory_info, network_info, storage_info | If file missing → Layer 3 or "N/A" |
| **Layer 3: JNI Plugin** | Android `SensorStatusManager.kt` / `CpuStatusManager.kt` / `GpuStatusManager.kt` / `NetworkStatusManager.kt` / `TelemetryCenter` | Plugin IPC via `run_mobile_plugin` | location, motion_sensor, ambient_sensor, cpu_info (thermal), gpu_info (renderer), network_info (status) | If plugin unavailable → Layer 4 |
| **Layer 4: 降级 (Degradation)** | Hardcoded defaults | Static strings in `#[cfg(not(target_os = "android"))]` blocks | All tools | Mock/demo data (e.g., "正常", "N/A") |

Priority chain: Root command (highest accuracy when device rooted) → Direct sysfs → JNI Plugin → Degradation (safe defaults, never panics).

The `cpu_info.rs` tool exemplifies this: `execute_root_command_safe("cat /proc/stat")` for usage → direct sysfs fallback → JNI Plugin for thermal status → degradation to "正常" on desktop.

## 10. 通道架构 (Channel Architecture)

The distributed client uses a `CancellationToken` plus 2 `tokio::sync::mpsc` channels for lifecycle management:

| 机制 | 类型 | 方向 | 用途 |
|------|------|------|------|
| `cancel_token` | `tokio_util::sync::CancellationToken` | Internal | 统一的关停信号。`stop()` 调用 `cancel()`；`connection_loop` / `run_session` 通过 `cancel_token.cancelled()` 优雅退出。 |
| `reconfigure_tx` / `reconfigure_rx` | `tokio::sync::mpsc` | Internal | 工具授权变化后结束旧 session；服务端清理远端投影后立即重连。 |
| `reconnect_tx` / `reconnect_rx` | `tokio::sync::mpsc` | Internal | 触发即时重连。`trigger_reconnect()` 发送 `()`；`connection_loop` 的退避等待 `select!` 收到后立即重连。 |

```
                     ┌─────────────────────┐
  stop() ──────────► │   cancel_token      │ ──► connection_loop / run_session select!
                     │ (CancellationToken) │
                     └─────────────────────┘

  reconfigure_tools() ─► │reconfigure_tx │ ──► run_session close → immediate reconnect
                         │    (mpsc)     │
                         └───────────────┘

  trigger_reconnect()──► │ reconnect_tx  │ ──► connection_loop select!
                         │   (mpsc)      │
                         └──────────────┘
```

`CancellationToken` 与两条 mpsc 通道均在 `tokio::select!` 中监听，确保无轮询的干净关停。

## 12. vcp_fold 渐进式内容展开协议

The `vcp_fold` protocol is a progressive content expansion format used by Streaming tools to provide multi-granularity device status reports. It allows the LLM to receive a brief summary first, then expand into detailed metrics only when needed.

### Format

```
[===vcp_fold: LEVEL ::desc: DESCRIPTION===]
CONTENT
```

| Component | Format | Example |
|-----------|--------|---------|
| LEVEL | Float 0.0–1.0 | `0.0` (brief), `0.40` (moderate detail), `0.50` (full detail) |
| DESCRIPTION | Chinese description | `CPU芯片当前温度与发热情况` |
| CONTENT | Single-line status string | `CPU 温度: 45°C` or full detail string |

### Fold Level Semantics

| Level Range | Meaning | Consumer Behavior |
|-------------|---------|-------------------|
| 0.0 – 0.20 | Brief overview | Always expanded by default |
| 0.20 – 0.40 | Moderate detail | Expanded on tool invocation or user request |
| 0.45 – 0.60 | Full sensor detail | Expanded only when deep analysis needed |
| 0.60+ | Reserved | For future high-frequency raw data |

### Producers (who generates vcp_fold)

| Tool | Fold Levels | Description |
|------|-------------|-------------|
| `MobileCPUInfo` | 0.0 (thermal), 0.40 (usage+freq+temp) | CPU status with thermal sensation |
| `MobileMotion` | 0.0 (state only), 0.50 (full accelerometer metrics) | Motion state + peak acceleration |
| `MobileAmbient` | 0.0 (light level), 0.45 (lux+hPa) | Ambient light + pressure |
| `MobileStatusSummary` | 0.0 (basic status), 0.35 (performance), 0.45 (sensors+location) | Aggregated device summary |
| Android `SensorStatusManager.kt` | 0.0 / 0.45 (ambient), 0.0 / 0.50 (motion) | Native sensor output |

### Consumers

- **VCP Server (LLM context)**: Parses fold blocks, initially presents brief (level 0.0) to LLM. When LLM requests more detail, expands higher-level blocks.
- **Frontend `DistributedView.vue`**: Renders fold blocks as expandable sections in the placeholder tab.
- **`device_status_summary.rs`**: Aggregates brief folds from multiple tools into a single multi-granularity response.

### Design Rationale
- Saves LLM context window by providing progressive disclosure
- Single `read_current()` call produces all levels (no extra I/O)
- Backward compatible: if consumer doesn't understand vcp_fold, it sees the full text with fold markers as plain text

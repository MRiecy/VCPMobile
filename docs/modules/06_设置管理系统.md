# 06_设置管理系统 (Settings Manager)

## 1. 概述

### 1.1 模块定位

`settings_manager.rs` 管理 SQLite 中的用户身份、连接、同步、分布式、对话辅助、语音和排序配置。它提供一个持久化 owner、一份不可变配置快照，以及提交后的运行时通知。主题、聊天呈现、更新偏好等 localStorage 数据仍由前端各自的 Store 管理，不属于本模块。

### 1.2 源码导航

| 文件 | 职责 |
|------|------|
| `infra/settings_manager.rs` | IPC、Rust 读取入口、提交事件、运行时连接协调和旧语音样本回收 |
| `infra/settings_manager/types.rs` | 八个领域、唯一默认值、枚举、IPC DTO 与字段描述类型 |
| `infra/settings_manager/schema.rs` | 从领域默认结构枚举字段，定义校验组、约束、备份资格与生效时机 |
| `infra/settings_manager/repository.rs` | SQLite 读写、版本冲突、局部修复、缓存发布和取消边界 |
| `infra/settings_manager/migration.rs` | 旧 `settings/global` 的一次性搬运 |
| `infra/settings_manager/backup.rs` | v2 备份解析与可导出字段投影 |
| `migrations/0103_config_domains.sql` | 领域、恢复归档、搬运元数据三张表 |
| `crates/config-export/` | host 开发期契约导出工具，不启动应用或访问用户配置 |

### 1.3 调用方向

```text
Vue 编辑会话 → settingsStore → read_settings / update_settings
                                     ↓
                         SettingsState / repository
                          ↓                    ↓
                DbState 写事务           已提交快照
                                               ├→ Rust 业务读取
                                               ├→ vcp-config-changed
                                               └→ 日志/分布式协调、样本回收
```

### 1.4 核心边界

- 类型、默认值与校验语义归 Rust；Vue 负责文案、布局和交互。
- 每领域一行 JSON，一次请求可以在一个事务中修改多个领域。
- 读取损坏字段只产生运行时投影，不把临时默认值写回用户原文。
- 提交、缓存发布与提交后 hook 由同一持久任务完成，调用方离开不截断已接纳保存。
- 配置已保存和远程连接成功分别报告；网络协调锁不阻塞配置保存。

## 2. Settings 结构体字段详解

### 2.1 领域总览

`Settings` 使用嵌套类型，序列化键仍为 camelCase。下面是实际 JSON 路径，不再是旧的顶层字段：

| 领域 | Rust 类型 | 主要内容 |
|------|-----------|----------|
| `identity` | `IdentityConfig` | `userName` |
| `server` | `ServerConfig` | `url`、`apiKey`、`endpointMode`、管理员凭据、`fileKey` |
| `log` | `LogConfig` | VCPLog / VCPInfo 共用 `url` 与 `key` |
| `sync` | `SyncConfig` | `serverUrl`、`httpUrl`、`token`、`logLevel`、`prerenderEnabled` |
| `distributed` | `DistributedConfig` | 启用状态、WebSocket 地址、密钥与设备名 |
| `conversation` | `ConversationConfig` | `topicSummaryModel` |
| `voice` | `VoiceConfig` | `connection`、`asr`、`tts`、`guidance`、`vad` 五个子结构 |
| `navigation` | `NavigationConfig` | `agentOrder`、`groupOrder` |

语音子结构共用一个领域版本和存储行；校验按叶字段及关联组隔离。TTS 模式只有 `builtin` 与 `clone`。克隆样本音频仍位于独立文件目录，配置只保存 `voice.tts.cloneSampleId`。

`currentThemeMode` 与 `set_theme` 已移除；真正主题仍归 localStorage。`lastAutomaticMaintenance` 不再是用户配置，维护模块使用原 `settings` 表中的 `last_automatic_maintenance` 独立记录。

### 2.2 默认值与字段规则

每个领域通过同一 `Default` 定义新安装、缺字段和恢复投影的默认值。`schema.rs` 遍历这些类型默认值产生叶字段清单，再补充枚举选项、数值/长度范围、`required`、`secret`、`backup`、`validationGroup` 与 `effect`。

未知提交字段会被拒绝，不再使用 `flatten extra` 接纳任意配置。已存 JSON 的未知字段仍保留原文，修改已知字段不会顺手删除它们；未知领域行也不会被本版本重写。它们不进入类型快照或配置备份。

## 3. SettingsState 与并发控制

### 3.1 状态所有权

`SettingsState` 是可克隆的 Arc owner，内部保存：

| 成员 | 作用 |
|------|------|
| `cache: RwLock<Option<Arc<LoadedConfig>>>` | 同时缓存 `Arc<Settings>` 与带领域状态的 `Arc<ConfigSnapshot>` |
| `writer: Arc<Mutex<()>>` | 串行化冷加载、配置合并和唯一快照发布 |
| `runtime_generation: AtomicU64` | 丢弃等待中的过期运行时协调任务 |
| `runtime_pending: AtomicU8` | 累积日志与分布式待处理变更，避免后一次保存覆盖前一次待办 |
| `runtime_reconcile: Arc<Mutex<()>>` | 仅串行化运行时副作用，不参与配置保存入场 |

真正的 SQLite 写入入场仍由 `DbState::write_transaction` 管理，没有第二套物理数据库写队列。

### 3.2 读取与提交顺序

缓存命中只取读锁并克隆 Arc；冷加载取得 writer 后再次检查缓存。冷加载和保存取得 writer 后进入独立的 `tokio::spawn` owner，等待者被取消不会把已开始的数据库提交留在“DB 已更新、内存未发布”的中间状态。等待 writer 入场的调用仍可取消。

保存读取版本、合并原始 JSON、校验和写入均处于同一数据库事务；成功 commit 后发布缓存，再释放 writer、同步执行调度 hook。连接重建和文件清理由 hook 启动异步任务，不在 writer 内等待网络或样本锁。

### 3.3 生命周期挂载

`lib.rs` setup 仍以 `app.manage(SettingsState::new())` 注册状态。业务模块使用 `read_config` 获得 `Arc<Settings>`；需要诊断和版本信息时使用 `read_config_snapshot`。业务消费者不直接读取配置表，也不维护第二份可写配置镜像。

## 4. 读取流程 (read_settings)

### 4.1 领域快照

`read_settings` 返回 `ConfigSnapshot`：

```text
data: Settings
domains:
  <领域名>:
    revision: 十进制字符串
    schemaVersion: 当前存储结构版本
    health: ready | recovered | unavailable
    issues: [{ domain, field, code, message }]
```

版本以字符串经过 IPC，避免 JavaScript 整数精度丢失。每个已知领域都有状态；尚无该领域记录时使用默认投影与 revision `"0"`。

### 4.2 损坏隔离

| 情况 | 读取行为 |
|------|----------|
| 缺少已知字段 | 使用唯一默认值 |
| 某叶字段类型/取值非法 | 原文保留；有效字段继续使用，坏字段及其受影响关联组使用临时默认投影 |
| 某领域不是对象或 JSON 无法解析 | 仅该领域标记 `unavailable`，提供默认运行时投影并报告问题 |
| 领域 schema 版本不支持 | 保留原记录，标记不可正常编辑，要求明确修复或使用支持版本 |
| 数据库/IO 失败 | 返回存储错误，不伪装为配置损坏，不写默认值 |
| 网络不通或克隆样本缺失 | 由实际功能执行方报告，读取不删除用户配置 |

`recovered` 表示当前快照使用了局部恢复投影，**不代表磁盘原文已经被修复**。修改其他字段仍从原始 JSON 合并，未处理的坏值不会被默认值覆盖。

### 4.3 一次性搬运

首次读取先检查 `config_metadata/global_domains_v1`。没有完成标记时，在一个 `DbState` 事务中：

1. 读取旧 `settings/global`，把完整原文归档到 `config_recovery` 的 `legacy.global`。
2. 把已知字段拆到八个领域；维护时间搬到 `last_automatic_maintenance`。
3. 写入领域记录与完成标记，删除旧 `global` 行，提交事务。

已存在领域记录不会被搬运覆盖。旧端点模式缺失时，仅在这个一次性边界恢复历史端点行为；新安装仍使用统一默认值。旧 JSON 整体损坏时保留原文并建立不可用领域记录，避免静默重置。完成后只读写新领域结构；原 `settings` 表继续服务缓存和任务状态，不被删除。

## 5. 写入流程与存储表

### 5.1 唯一写入路径

生产通用写入口为 `update_settings(request: ConfigUpdate)`。旧 `write_settings`、`internal_write_settings` 和主题快捷写入口已移除。

```text
取得 writer
→ 持久任务接管
→ DbState 写事务
→ 读取原始记录和 revision
→ 合并、检查冲突、校验受影响组
→ 如需修复，事务内先归档原文
→ 写所有受影响领域、递增各自 revision
→ 生成可发布快照
→ COMMIT
→ 发布缓存
→ 释放 writer
→ 发变更事件并调度运行时副作用
```

任一领域被拒绝或冲突时，本请求的其他领域也不写入。没有真实变化的提交不递增版本。缓存刷新发生在 commit 之后，投影检查发生在 commit 之前。

### 5.2 表结构

| 表 | 关键列 | 用途 |
|----|--------|------|
| `config_domains` | `domain` 主键、`schema_version`、`revision`、`value`、`updated_at` | 每领域一行 JSON |
| `config_recovery` | `id`、`domain`、`schema_version`、`revision`、`value`、`reason`、`created_at` | 一次性搬运与明确修复前的原文归档 |
| `config_metadata` | `key` 主键、`value` | 搬运完成标记 |
| 原 `settings` | `key` 主键、`value`、`updated_at` | 模型缓存、维护时间等既有非全局配置记录 |

SQLite 事务保证提交边界，不提供配置加密。凭据仍以字符串保存；配置导出也会包含获准导出的凭据。

## 6. 增量更新 (update_settings)

### 6.1 请求契约

`ConfigUpdate.patches` 每个领域最多一份 `DomainPatch`：

```json
{
  "patches": [{
    "domain": "voice",
    "expectedRevision": "4",
    "changes": { "asr.language": "zh" },
    "baseValues": { "asr.language": "auto" },
    "repair": false
  }]
}
```

`changes` 是相对领域的叶路径映射，不是任意 JSON Merge Patch；`baseValues` 保存实际编辑基线。非设置页也通过同一契约写入，不能绕过版本与校验。

### 6.2 并发与校验

- revision 相同：在当前原始记录上合并修改。
- revision 不同：逐个修改字段核对基线；当前值仍等于基线可合并，当前值已等于目标值则幂等接受。
- 同字段被其他操作改为第三个值：返回 `conflict`、最新快照及字段问题，不静默覆盖。
- 未知字段、重复领域、非法值或关联组规则失败：返回 `rejected`，整次请求不落盘。
- 无关旧错误可以继续留存；提交只校验受影响组及新引入问题，避免一个旧坏值阻塞整个应用。

例如 `voice.guidance.autoGuidance` 与 `guidanceRules` 属于同一校验组；修改自动指导开关会同时检查所需规则，而修改 TTS 音色不会自动覆盖这组旧原文。

### 6.3 明确修复

正常修改一个坏叶字段会先归档该领域原文，再写入修正值。若 JSON、schema 或父节点结构无法正常编辑，必须提交 `repair: true`：JSON/schema 整体不可用时以领域默认值重建；仍是当前版本对象时提交其有效投影，只将坏叶字段或关联组恢复默认，保留其他有效配置。之后叠加用户确认的修改。

修复要求匹配当前 revision，不对过期修复请求自动合并。归档与新值处于同一事务；前端保留草稿和字段错误，用户确认后才发修复请求。读取本身从不执行这个操作。

## 7. 默认值、校验与 TypeScript 导出

### 7.1 单一语义来源

`types.rs` 的领域 `Default` 同时供新安装、Serde 缺字段、运行时恢复投影、恢复默认和开发期导出使用；不再维护独立的 `create_default_settings` 字段清单。

`schema.rs` 从嵌套默认结构发现字段，不在 Vue 重写字段白名单。枚举选项来自 Rust 枚举列表，VAD 范围来自原生共享配置常量。基本类型/范围/枚举/长度约束和关联组校验由 Rust 用于读取投影、提交与备份解析；执行功能所需的完整连接、样本存在性仍由具体业务入口检查。

### 7.2 显式生成

`crates/config-export` 是 host 开发工具，直接编译生产 `types.rs` / `schema.rs`，通过可选 `config-export` feature 使用 `ts-rs`：

```powershell
pnpm config:generate
pnpm config:check
```

输出为已提交的：

- `src/core/config/generated/config.ts`：领域类型、枚举、IPC DTO。
- `src/core/config/generated/defaults.ts`：`SETTINGS_DEFAULTS`。
- `src/core/config/generated/metadata.ts`：`SETTINGS_FIELDS`。

`config:check` 只检查是否过期，不写文件，并已接入 `pnpm check` 的首步。移动端默认构建不启用导出 feature；导出不启动 Tauri、不读取数据库、密钥或设备资源。前端 `core/config/fields.ts` 使用生成契约提供字段路径与补丁工具，页面仍自行定义展示顺序和交互。

## 8. 函数接口表

### 8.1 Tauri Commands

| 命令 | 输入 | 输出 |
|------|------|------|
| `read_settings` | 无 | `ConfigSnapshot` |
| `update_settings` | `{ request: ConfigUpdate }` | `ConfigSaveResult`：`saved` / `rejected` / `conflict` |
| `export_config_domains` | 无 | 当前已提交配置中允许备份的嵌套领域对象 |
| `parse_config_backup` | `{ path: string }` | 已验证的 `domains`、`preferences`、`exportedAt` |

应用命令统一注册在 `commands.rs` 的 `app_command_handler!` 中，由 `lib.rs` 调用。原 `get_settings_recovery_status` 已由快照中的领域状态替代。

### 8.2 Rust 内部读取

| 入口 | 返回值 | 用途 |
|------|--------|------|
| `read_config` | `Arc<Settings>` | 一次任务所需的跨领域一致配置 |
| `read_config_snapshot` | `ConfigSnapshot` | 需要版本、修复状态或字段错误的调用方 |
| `SettingsState::apply` | `ConfigSaveResult` | 唯一持久提交与提交后 hook |

### 8.3 配置备份 v2

`.vcpcfg.json` 保持 version `2`，内容采用嵌套 `domains` 与独立 `preferences`；保留 v1 文件的单向导入转换，旧平铺 v2 不再接受。v1 只把实际提供的字段转为领域补丁，不注入缺失字段的默认值，也不恢复旧数据库读写路径。

`backup` 元数据决定导出和导入资格：当前包括身份、主服务器、日志、同步连接、分布式、总结模型及语音；不包含侧栏排序，也不包含同步日志级别和预渲染选项。克隆样本仅保存 ID，不包含音频文件。

Rust 拒绝未知领域/字段、不可恢复字段、非法值、非法版本以及超过 1 MiB 的文件。导出遇到可备份字段的恢复问题时拒绝把临时默认值当成用户配置导出。导入保留缺项；实际选中字段仍经过 `update_settings` 的关联组与版本检查，在一个 SQLite 事务内提交。

主题和聊天偏好继续使用已有 localStorage owner；其成功、跳过和失败分别报告，不能宣称 SQLite 与 localStorage 整份备份原子提交。

## 9. 提交后运行时联动

### 9.1 配置事件

成功提交后发出 `vcp-config-changed`，载荷为完整 `ConfigSnapshot`。前端 Store 按领域 revision 接纳新状态，迟到的旧领域版本不会覆盖新快照。事件是已提交配置通知，不证明网络连接或播放已成功。

### 9.2 日志、Info 与分布式

`classify_runtime_settings_changes` 比较旧快照与新快照：

- `log.url` / `log.key` 改变：调度 VCPLog 和 VCPInfo。
- 分布式启用状态改变，或启用时连接参数改变：调度分布式 owner。
- 其他配置变化不触发这些连接重建。

提交后将待处理类别 OR 入 `runtime_pending`，推进 generation 并调度任务。任务取得独立运行时锁、淘汰过期 generation，再提取累积待办并读取最新快照。等待期间多次保存的类别不会因后一任务只改变另一类别而丢失；运行时锁不会挡住 SQLite 保存。

连接 owner 仍负责真实连接状态；失败记录在各自路径，不把已完成数据库保存反报为失败。

### 9.3 语音与其他生效边界

| 配置 | 消费边界 |
|------|----------|
| 主连接、身份、总结模型 | 下一次相应请求 |
| 同步配置 | 下一次同步 |
| 语音连接 | 下一次语音任务 |
| ASR / 输入编码 | 下一次输入服务 |
| TTS / 风格指导 | 下一条回复或朗读任务 |
| VAD | 下一次通话 |
| 侧栏排序 | 已提交快照即时反映 |

`VoiceReplyPolicy` 继续从同一次已提交 `Settings` 读取 TTS 与注入规则，避免分段朗读混用配置。旧克隆样本回收在提交且释放配置 writer 后执行；样本 owner 会重新检查当前引用，回收失败只记录，不改写成功保存结果。

## 10. 维护入口

新增配置时先确定所属领域与消费时机，在 `types.rs` 增加类型和默认值，在 `schema.rs` 补充必要约束、备份与生效策略，再显式生成 TypeScript 契约。Vue 页面字段集合只负责该页能编辑什么，不作为另一份类型或默认值来源。

修改存储或 IPC 时，沿 `repository → settingsStore → 编辑会话/其他实际消费者` 检查；修改连接副作用时，沿提交 hook 和实际网络 owner 检查。新增数据库领域或字段不应恢复旧 `global` 双写，也不应把 localStorage 偏好悄悄搬入本模块。

# 权限与系统控制

## 1. 功能概述

提供 Android 运行时权限查询与请求、应用电池与后台设置、厂商自启动设置、通知访问权和存储空间检测。运行时权限覆盖通知、存储、麦克风、相机与定位。

> **v1.1.2 新增**：4 条 OEM/存储命令（`request_auto_start_permission`、`request_power_management_permission`、`check_auto_start_permission`、`get_free_disk_space`）+ OomScoreGuard 进程保护。WakeLock/WifiLock 保活已整合至 [ForegroundGuardian](11_ForegroundGuardian_前台守护者.md)。
> **v1.1.3 新增**：通知栏监听权限命令（`check_notification_listener_permission`、`request_notification_listener_permission`）、`start_helper_service`、`get_pending_notification`，并在 `AndroidManifest.xml` 中声明 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 与 `BIND_NOTIFICATION_LISTENER_SERVICE`。

### 1.1 当前 iOS 通知权限与本 App 通知

Android 的 `PermissionStatus` 和 `check_all_permissions` 不用于 iOS。iOS 已接入的通知权限链由 `src/system.rs` → `src/ios.rs::run_async` → `ios/Sources/Notifications/NativeNotifications.swift` 持有：

| Rust 命令/入口 | Swift selector | 实际结果 |
|---|---|---|
| `get_notification_permission` / `request_notification_permission` | `getNotificationPermission` / `requestNotificationPermission` | `{authorization}`：`notDetermined`、`denied`、`authorized`、`provisional`、`ephemeral` 或 `unknown`；请求结束后重新查询系统状态 |
| `open_notification_settings` | `openNotificationSettings` | 打开本应用的系统通知设置。返回引导时重新读取授权 |
| 内部 `send_notification_native` | `sendLocalNotification` | 输入 `title/body`；未授权明确报错，系统接受请求后才成功返回，不在工具执行时自动申请权限 |
| 内部 `notify_committed_reply` | `sendLocalNotification` | 回复入库后传入标题和消息位置。应用在后台时将位置随本地通知交给系统 |
| `get_pending_notification` | `getPendingNotification` | 取出并清空最近一次待处理点击，若无点击则返回空对象。普通通知为 `kind:"app"`，回复通知为 `kind:"chat"` 并携带 `ownerType/ownerId/topicId/messageId` |

`NativeNotifications` 在插件 init 安装 `UNUserNotificationCenterDelegate`，持有前台呈现与点击数据；`NativeNotificationSceneBridge` 将冷启动 Scene 参数送入同一 owner。它们只处理本 App 本地通知，不读取其他 App 通知，也没有 APNs 注册。实时点击及 Android 的独立路径见 [总览中的事件映射](00_总览与导航.md#请求与事件的实际路径)。下文 OEM、自启动、电池豁免和通知栏监听继续描述 Android 实现。

### 通话麦克风权限

麦克风由独立通话的原生采集 owner `voice/NativeVoiceAudio.kt` 按次申请。通用 `requestAndroidPermission` 不再接受 `microphone`；权限快照继续报告真实的麦克风授权状态。

```text
start_voice_microphone → Rust 语音服务 → 原生 startVoiceAudio
    → NativeVoiceAudio 校验通话、会话与前台条件
    → requestPermissionForAlias("microphone", invoke, "onVoiceAudioPermissionResult")
    → 系统授权结果
    → VcpMobilePlugin.onVoiceAudioPermissionResult
    → NativeVoiceAudio.onPermissionResult
    → 按原等待会话身份继续采集，或完成拒绝/取消清理
```

授权等待、迟到回调和采集资源归同一 owner，不使用通用权限回调接管通话。

**Manifest 声明**：
```xml
<uses-permission android:name="android.permission.RECORD_AUDIO" />
<uses-permission android:name="android.permission.MODIFY_AUDIO_SETTINGS" />
```

`MODIFY_AUDIO_SETTINGS` 用于独立语音通话的音频路由控制。

## 3. 权限检查

### 3.1 接口

`plugin:vcp-mobile|check_all_permissions` 返回本次查询的 `PermissionStatus` 快照。Android 启动和引导页读取同一组门禁字段。

| 属性 | 说明 |
|------|------|
| 前端命令 | `plugin:vcp-mobile\|check_all_permissions` |
| 参数 | 无 |
| 返回值 | `PermissionStatus` JSON 对象，包含四个可空的门禁字段和四个按需权限字段 |
| 桌面端行为 | 始终返回所有字段为 `true` |

**新增字段说明（v1.0.3）**：

| 字段 | 含义 | 检查方式 |
|------|------|----------|
| `camera` | 相机权限 | `ContextCompat.checkSelfPermission(CAMERA)` |
| `location` | 定位权限 | `ACCESS_FINE_LOCATION` 或 `ACCESS_COARSE_LOCATION` 任一授予即视为已授权 |

### 3.2 Kotlin 实现

| 门禁字段 | 系统检测 | 用户操作 |
|----------|----------|----------|
| `notification` | `NotificationManager.areNotificationsEnabled()` | 通过 `notificationSettings` 打开本应用的通知设置 |
| `battery` | `PowerManager.isIgnoringBatteryOptimizations(packageName)` | 申请本应用的 Doze 电池优化豁免 |
| `backgroundAllowed` | API 28 起读取 `!ActivityManager.isBackgroundRestricted`，API 26–27 返回 `null` | 在本应用详情中调整后台限制 |
| `notificationListener` | 检查 `VcpNotificationListenerService` 的通知访问授权，详见 §4.5 | 在系统通知访问设置中授权 |

`false` 表示设备已确认该项未开启，启动会停在权限引导。系统无法判定或该能力不适用于当前设备、用户配置时返回 `null`，引导页隐藏对应项。

#### 版本分支详解

| 权限 | Android 14+ (API 34+) | Android 13 (API 33) | Android 10-12 (API 29-32) | Android 9 及以下 (API ≤28) |
|------|----------------------|---------------------|---------------------------|---------------------------|
| **通知** | `areNotificationsEnabled()` | 同上 | 同上 | 同上 |
| **存储** | `READ_MEDIA_IMAGES` **或** `READ_MEDIA_VISUAL_USER_SELECTED` | `READ_MEDIA_IMAGES` 细分权限 | `READ_EXTERNAL_STORAGE` | `READ_EXTERNAL_STORAGE` + `WRITE_EXTERNAL_STORAGE` |
| **电池优化** | `PowerManager.isIgnoringBatteryOptimizations()` | 同上 | 同上 | 同上 |

> **Android 14 存储权限变化**：API 34 引入 `READ_MEDIA_VISUAL_USER_SELECTED`，允许用户仅授权部分图片/视频。`checkAllPermissions` 中同时检查 `READ_MEDIA_IMAGES` 和 `READ_MEDIA_VISUAL_USER_SELECTED`，任一满足即视为已授权。

> **注意**：电池优化检查**不是**标准的 Android 运行时权限模型，而是通过 `PowerManager` API 查询应用是否被列入系统电池优化白名单。

## 4. 权限请求

### 4.1 接口

```rust
#[tauri::command]
pub fn request_android_permission<R: Runtime>(app: AppHandle<R>, p_type: String) -> Result<(), String>;
```

| 属性 | 说明 |
|------|------|
| 前端命令 | `plugin:vcp-mobile\|request_android_permission` |
| 参数 | `p_type: String`。权限类型可传 `"notification"`、`"storage"`、`"camera"`、`"location"`、`"battery"`。`"notificationSettings"` 用于打开本应用的通知设置 |
| 返回值 | `Result<(), String>`。设置页在用户返回后完成调用，授权状态由新的权限快照报告 |
| 桌面端行为 | 空操作 |

### 4.2 Kotlin 实现

```kotlin
@TauriPlugin(permissions = [
    Permission(strings = ["android.permission.POST_NOTIFICATIONS"], alias = "notification"),
    Permission(strings = ["android.permission.READ_MEDIA_IMAGES"], alias = "storage"),
    Permission(strings = ["android.permission.READ_EXTERNAL_STORAGE", "android.permission.WRITE_EXTERNAL_STORAGE"], alias = "storageLegacy"),
    Permission(strings = ["android.permission.RECORD_AUDIO"], alias = "microphone"),
    Permission(strings = ["android.permission.CAMERA"], alias = "camera"),
    Permission(strings = ["android.permission.ACCESS_FINE_LOCATION", "android.permission.ACCESS_COARSE_LOCATION"], alias = "location")
])
class VcpMobilePlugin(private val activity: Activity) : Plugin(activity) {
    // ...
}
```

`@TauriPlugin` 注解中通过 `@Permission` 定义了**五个权限别名**（v1.0.3 新增 `camera` 和 `location`），将 Android 权限字符串映射为易用的别名：

| 别名 | Android 权限字符串 | 适用版本 |
|------|-------------------|----------|
| `notification` | `POST_NOTIFICATIONS` | Android 13+ |
| `storage` | `READ_MEDIA_IMAGES` | Android 13+ |
| `storageLegacy` | `READ_EXTERNAL_STORAGE` + `WRITE_EXTERNAL_STORAGE` | Android 12 及以下 |
| `camera` | `CAMERA` | 全部版本 |
| `location` | `ACCESS_FINE_LOCATION` + `ACCESS_COARSE_LOCATION` | 全部版本 |

> **注意**：`READ_MEDIA_VISUAL_USER_SELECTED`（Android 14+）不在 `@TauriPlugin` 注解中声明，因为 `requestPermissionForAlias` 机制无法处理「部分授权」语义。`checkAllPermissions` 中通过 `ContextCompat.checkSelfPermission` 手动检测该权限。

#### 回调与事件推送

`onPermissionResult` 处理运行时权限对话框的结果。`onPermissionSettingsResult` 处理门禁四个设置入口的返回。两者都重新采集权限快照并发出 `vcp-permission-change`，门禁据此刷新。直接按返回键也会完成调用，是否授权取决于系统查询结果。

### 4.3 BatteryStatusManager

`BatteryStatusManager.kt` 是独立的设备电量与系统省电状态检测模块，与权限系统共用 `PowerManager` 但职责分离：前者负责**检测**，后者负责**白名单状态查询与请求**。

#### 接口

```rust

pub struct BatteryStatus {
    pub level: i32,
    pub is_power_save_mode: bool,
    pub status: Option<String>,
    pub temperature: Option<f64>,
}

#[tauri::command]
pub fn get_battery_status<R: Runtime>(app: AppHandle<R>) -> Result<BatteryStatus, String>;
```

| 属性 | 说明 |
|------|------|
| 前端命令 | `plugin:vcp-mobile\|get_battery_status` |
| 参数 | 无 |
| 返回值 | `BatteryStatus` JSON 对象（`level` 为 0-100，`status` 为充电状态字符串，`temperature` 为摄氏度，`isPowerSaveMode` 为布尔值） |
| 桌面端行为 | 始终返回 `{ level: 100, status: "未充电", temperature: 25.0, isPowerSaveMode: false }` |

#### 6 层 OEM 省电模式检测逻辑

```kotlin
class BatteryStatusManager(private val context: Context) {
    fun isPowerSaveMode(): Boolean {
        // 1. 原生 PowerManager 状态检测
        val powerManager = context.getSystemService(Context.POWER_SERVICE) as PowerManager
        if (powerManager.isPowerSaveMode) return true

        val resolver = context.contentResolver

        // 2. 原生 Android 广播全局低电量标记
        if (android.provider.Settings.Global.getInt(resolver, "low_power", 0) == 1) return true

        // 3. 通用系统省电标记
        if (android.provider.Settings.System.getInt(resolver, "power_save_mode", 0) == 1) return true

        // 4. 小米 (MIUI / HyperOS) 专用标记
        if (android.provider.Settings.System.getInt(resolver, "POWER_SAVE_MODE_OPEN", 0) == 1) return true

        // 5. 华为 (EMUI / HarmonyOS) 专用标记
        // SmartModeStatus: 1=正常, 2=省电, 3=超级省电, 4=性能
        val hwPowerSave = android.provider.Settings.System.getInt(resolver, "SmartModeStatus", 1)
        if (hwPowerSave == 2 || hwPowerSave == 3) return true

        // 6. Vivo / Oppo 等其他定制 ROM Global 标记
        if (android.provider.Settings.Global.getInt(resolver, "power_save_mode", 0) == 1) return true

        return false
    }
}
```

| 层级 | 检测目标 | 数据来源 | 说明 |
|------|---------|----------|------|
| 1 | 原生 Android | `PowerManager.isPowerSaveMode()` | AOSP 标准 API，Google / 三星 / 索尼等原生或类原生系统 |
| 2 | 全局低电量广播 | `Settings.Global.low_power` | Android 全局低电量模式标记 |
| 3 | 通用系统省电 | `Settings.System.power_save_mode` | 部分国产 ROM 复用的通用键 |
| 4 | 小米 MIUI/HyperOS | `Settings.System.POWER_SAVE_MODE_OPEN` | MIUI 私有 Settings 键，HyperOS 兼容 |
| 5 | 华为 EMUI/HarmonyOS | `Settings.System.SmartModeStatus` | 华为四态电源管理：1=正常, 2=省电, 3=超级省电, 4=性能 |
| 6 | Vivo/OPPO 等 | `Settings.Global.power_save_mode` | 部分 ROM 将省电标记放在 Global 命名空间 |

#### 与前端权限门禁的联动

`get_battery_status` 的 `isPowerSaveMode` 用于同步前的设备状态提示。启动门禁独立检测本应用的 Doze 豁免和后台限制，分别提供申请豁免和打开应用详情的入口。

### 4.4 `open_file_native` — Android 原生文件打开与分享桥接

`open_file_native` 是 Rust→Kotlin 桥接命令，**已加入 `default.toml` 白名单**。它保留原有 `ACTION_VIEW` 文件打开行为，同时接受可选的 `action: "view" | "share"`；`share` 使用 Android `ACTION_SEND` 打开系统分享面板。Guest JS 分别暴露 `openFileNative(path)` 与 `shareFileNative(path)`，业务层无需直接拼接 action。

#### 接口

```rust
#[tauri::command]
pub fn open_file_native<R: Runtime>(
    app: AppHandle<R>,
    path: String,
    action: Option<String>,
) -> Result<(), String>;
```

| 属性 | 说明 |
|------|------|
| 前端命令 | `plugin:vcp-mobile\|open_file_native`（也可通过 `file_manager.rs` 的 `open_file` 间接调用） |
| 参数 | `path: String` —— 本地文件绝对路径；`action?: "view" \| "share"`，缺省为 `view` |
| 返回值 | `Result<(), String>` |

#### Kotlin 实现

```kotlin
@Command
fun openFile(invoke: Invoke) {
    val args = invoke.parseArgs(OpenFileArgs::class.java)
    val file = File(args.path)
    val uri = FileProvider.getUriForFile(
        activity,
        "${activity.packageName}.fileprovider",
        file,
    )
    val intent = if (args.action == "share") {
        val send = Intent(Intent.ACTION_SEND).apply {
            type = resolvedMimeType
            putExtra(Intent.EXTRA_STREAM, uri)
            clipData = ClipData.newRawUri(file.name, uri)
            addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
        }
        Intent.createChooser(send, "分享文件")
    } else {
        Intent(Intent.ACTION_VIEW).apply {
            setDataAndType(uri, resolvedMimeType)
            addFlags(Intent.FLAG_GRANT_READ_URI_PERMISSION)
        }
    }
    activity.startActivity(intent)
}
```

- **FileProvider**：生成 `content://` 临时授权 URI，避免直接暴露 `file://` URI（Android 7.0+ 禁止）。
- **分享语义**：文件放入 `EXTRA_STREAM`，并同步设置 `ClipData` 与 `FLAG_GRANT_READ_URI_PERMISSION`，接收应用获得临时只读访问；`.log` / `.txt` 使用 `text/plain` MIME。
- **双 authority 回退**：优先使用 `.fileprovider`，失败时回退到 `.opener.fileprovider`。
- **沙箱边界校验**：`isSafeLocalPath()` 仅允许处理 `cacheDir`、`filesDir`、`externalFilesDir`、`externalCacheDir` 内的文件，防止路径遍历。业务侧仍需约束可分享的数据源；例如同步日志必须先由 `prepare_sync_log_share_file` 校验 `sync_logs` 来源并暂存到 cache。
- **权限要求**：打开与分享应用私有文件均不需要存储运行时权限，但应用 Manifest 中必须声明 `FileProvider`：
  ```xml
  <provider
      android:name="androidx.core.content.FileProvider"
      android:authorities="${applicationId}.fileprovider"
      android:exported="false"
      android:grantUriPermissions="true">
      <meta-data android:name="android.support.FILE_PROVIDER_PATHS" android:resource="@xml/file_paths" />
  </provider>
  ```

#### 与 `08_文件选择与缩略图生成.md` 的关系

| 功能 | 对应命令 | 职责 |
|------|---------|------|
| **选择文件** | `pick_file` → `pickFile` | 文件/配置使用 `ACTION_OPEN_DOCUMENT`，相册/头像优先使用照片选择器，不可用时回退图片文档选择（分别多选/单选）；选中 URI 后流式拷贝至 `cacheDir/uploads`，头像另派生裁剪工作图 |
| **打开文件** | `open_file` → `openFile`（本小节） | 对**已保存到本地的文件**（如聊天记录中的附件），用系统默认应用（如 WPS、图片浏览器）打开 |

两者使用相同的 `fileIoExecutor` 单线程池避免并发冲突，但生命周期完全不同：`pickFile` 是「摄入」，`openFile` 是「输出」。

```kotlin
private fun checkAutoStartStatus(): String {
    val manufacturer = Build.MANUFACTURER.lowercase(Locale.ROOT)
    if (manufacturer.contains("xiaomi") || manufacturer.contains("redmi")) {
        val ops = activity.getSystemService(Context.APP_OPS_SERVICE) as? android.app.AppOpsManager
        if (ops != null) {
            try {
                val method = ops.javaClass.getMethod(
                    "checkOpNoThrow",
                    Int::class.javaPrimitiveType,
                    Int::class.javaPrimitiveType,
                    String::class.java

                    ops,
                    10008,
                    activity.applicationInfo.uid,
                    activity.packageName
                ) as Int
                return if (mode == android.app.AppOpsManager.MODE_ALLOWED) "true" else "false"
            } catch (e: Exception) {
                Log.e(TAG, "checkAutoStartStatus: reflection failed", e)
            }
        }
    }
    return "unsupported"
}

@Command
```
```kotlin
fun getFreeDiskSpace(invoke: Invoke) {
    try {
        val path = Environment.getDataDirectory()
        val stat = android.os.StatFs(path.path)
        val blockSize = stat.blockSizeLong
        val availableBlocks = stat.availableBlocksLong
        val totalBlocks = stat.blockCountLong

        val freeBytes = availableBlocks * blockSize
        val totalBytes = totalBlocks * blockSize

        val freeGB = freeBytes.toDouble() / (1024.0 * 1024.0 * 1024.0)
        val totalGB = totalBytes.toDouble() / (1024.0 * 1024.0 * 1024.0)

        val result = JSObject()
        result.put("freeBytes", freeBytes.toDouble())
        result.put("freeGb", freeGB)
        result.put("totalBytes", totalBytes.toDouble())
        result.put("totalGb", totalGB)
        invoke.resolve(result)
    } catch (e: Exception) {
        Log.e(TAG, "getFreeDiskSpace failed", e)
        invoke.reject(e.message ?: "Failed to get free disk space")
    }
}
```

## 11. 关键约束

1. **`pType` 命名**。启动门禁传入 `"notificationSettings"` 或 `"battery"`。其他功能按 §4.1 的类型请求各自的运行时权限。

2. **事件通道依赖 `webViewRef`**：`emitPermissionsToWebView()` 需要在 `load(webView)` 时保存 WebView 引用。若插件加载失败或 WebView 未初始化，事件将静默丢失（前端仍可通过 `visibilitychange` 和兜底轮询恢复）。

3. **权限请求按 owner 使用对应回调**：
   - 系统运行时权限使用 `onPermissionResult` 回调。
   - 门禁的通知设置、电池优化豁免、后台限制和通知访问设置统一使用 `onPermissionSettingsResult`。
   - 通话麦克风使用 `onVoiceAudioPermissionResult`，由 `NativeVoiceAudio` 继续采集或处理拒绝。

4. **`open_file_native` 的权限边界**：
   - 该函数通过 `FileProvider` 分享应用私有文件，**不需要** `READ_EXTERNAL_STORAGE` 或 `MANAGE_EXTERNAL_STORAGE` 运行时权限。
   - 但如果试图打开的文件位于应用私有目录之外（如用户通过 `pick_file` 选择后未拷贝到 `cacheDir` 的文件），`FileProvider` 会抛出 `IllegalArgumentException`，此时会回退到第二个 authority 尝试。
   - 参见 `docs/ANDROID_PLUGIN_MANAGEMENT.md` §3.1 关于 `FileProvider` 的路径配置规范。

5. **与规范文档的交叉引用**：
   - `POST_NOTIFICATIONS` 血训：参见 `docs/ANDROID_PLUGIN_MANAGEMENT.md` §3.1 / §7.2。
   - Tauri 权限回调机制官方文档：参见 `docs/ANDROID_PLUGIN_MANAGEMENT.md` §5.2。

6. **传感器采集生命周期**：
   - 分布式连接本身不再启动任何物理传感器。
   - `StreamingScheduler` 只在获授权的传感器工具到达自身 deadline 时调用 `sample_sensor_data`。
   - Kotlin 只注册本批需求中的 listener，并在 2 秒有界窗口结束时统一释放；空白名单和仅 OneShot 白名单不会进入原生采样。

7. **定位权限检查边界**：
   - `SensorStatusManager.startLocationSample()` 在采样前检查 `ACCESS_FINE_LOCATION` 和 `ACCESS_COARSE_LOCATION`。**两项均未授予时，定位采集静默降级**（返回"未获得定位权限"），不阻塞运动和环境的采集。
   - 定位权限请求**不在** `SensorStatusManager` 内部触发，而是由插件中心在用户开启需要定位权限的工具时，通过既有权限通道统一处理。

## 12. SensorStatusManager —— Android 原生传感器采集

> 源码：`src-tauri/plugins/vcp-mobile/android/src/main/java/com/vcp/mobile/device/SensorStatusManager.kt`（319 行）

### 12.1 架构概览

`SensorStatusManager` 由 `VcpMobilePlugin.kt` 唯一持有，但不再随分布式连接常驻运行。Rust 每个遥测批次提交 `{ location, motion, ambient }` 需求；Kotlin 只注册所需 listener，在 2 秒窗口结束时构造快照并统一释放。

```
VcpMobilePlugin.kt
├── sensorStatusManager: SensorStatusManager     ← 唯一持有者
│
SensorStatusManager.kt
├── sensorManager: SensorManager                 ← Android 系统传感器服务
├── locationManager: LocationManager             ← Android 系统定位服务
├── mainHandler: Handler(Looper.getMainLooper()) ← 主线程定时器
│
├── @Volatile latestLocationStr                  ← 缓存的定位信息字符串
├── @Volatile latestMotionStr                    ← 缓存的运动状态字符串
├── @Volatile latestAmbientStr                   ← 缓存的环境传感器字符串
│
├── sample(location, motion, ambient, callback)  ← 一次有界按需采样
├── finishActiveSample()                         ← 统一注销并返回快照
├── shutdown()                                   ← Plugin 销毁兜底
│
├── 定位监听器 (locationListener)
├── 运动突发监听器 (motionListener)
└── 环境批次监听器 (ambientListener)
```

### 12.2 按需采样策略

| 需求位 | 数据源 | 本批行为 |
|--------|--------|----------|
| `location` | GPS / Network Provider | 读取 last-known 并请求 single update；批次结束统一 `removeUpdates`；无权限则返回明确降级值 |
| `motion` | 加速度计、陀螺仪、磁力计 | 10Hz 采样 2 秒，计算平均值/峰值/运动分类，随后注销 listener |
| `ambient` | 光照、气压 | 仅在 2 秒窗口内以 `SENSOR_DELAY_NORMAL` 注册，结束后生成 lux/hPa 描述并注销 |

未设置的需求位不会注册对应硬件。物理传感器不再存在“2 秒活跃 + 28 秒常驻调度”的后台循环。

### 12.3 并发与缓存

- `sample()` 和 `finishActiveSample()` 使用同一对象锁；意外重叠时先完整结束上一批并回调，避免悬挂 Plugin Invoke。
- 三类最新字符串仍使用 `@Volatile`，但只作为一次批次的结果缓存，不再驱动常驻采集。
- Rust 收到 `SensorSample` 后写入 `TelemetryCenter`；随后各 StreamingTool 的 `read_current()` 只读 Rust 缓存。
- `shutdown()` 在 Plugin 销毁时收尾仍在进行的批次。

### 12.4 批次生命周期

```
已授权 StreamingTool 到期
    → StreamingScheduler 合并 SensorDemand
    → 获取短时 distributed:telemetry:* Foreground lease
    → sample_sensor_data(location, motion, ambient)
    → SensorStatusManager.sample(...)
    → 只注册所需 listener
    → 最多 2 秒后 finishActiveSample()
    → 注销 Location/Sensor listener
    → 返回 SensorSample 并更新 TelemetryCenter
    → 生成本批占位符并发送
    → 释放 Foreground lease
```

- 空白名单或仅 OneShot 工具：不创建调度器，也不进入 Plugin IPC。
- 多个同批工具共享一次传感器采样，例如 `MobileMotion + MobileStatusSummary` 不会重复注册运动传感器。
- 重叠采样会先完整结束上一批并回传结果，不允许悬挂 Invoke。
- Plugin 销毁时 `shutdown()` 是最终资源释放兜底。

## 14. 定位权限（ACCESS_FINE_LOCATION / ACCESS_COARSE_LOCATION）

### 14.1 Manifest 声明

v1.0.3 在 `AndroidManifest.xml` 中新增了两项定位权限声明：

```xml
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
<uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION" />
```

| 权限 | 定位精度 | 数据来源 | 调用 API |
|------|---------|----------|----------|
| `ACCESS_FINE_LOCATION` | ~3m--30m | GPS 卫星 + 精确 WiFi | `LocationManager.requestLocationUpdates(GPS_PROVIDER)` |
| `ACCESS_COARSE_LOCATION` | ~50m--500m | 基站 + WiFi 指纹 | `LocationManager.requestLocationUpdates(NETWORK_PROVIDER)` |

**权限关系**：`ACCESS_FINE_LOCATION` **包含** `ACCESS_COARSE_LOCATION` 的全部能力。若用户仅授予 `ACCESS_COARSE_LOCATION`，GPS Provider 仍然无法使用，仅 Network Provider 可用。

### 14.2 权限检查流程

```
StreamingScheduler 发现含 location 的到期批次
    │
    ▼
sampleSensorData(location=true)
    │
    ▼
startLocationSample()
    │
    ├── checkSelfPermission(ACCESS_FINE_LOCATION) → hasFine: Boolean
    ├── checkSelfPermission(ACCESS_COARSE_LOCATION) → hasCoarse: Boolean
    │
    ├── !hasFine && !hasCoarse ?
    │   ├── YES → latestLocationStr = "位置信息: 未获得定位权限"
    │   │         Log.w(TAG, "Location permissions not granted.")
    │   │         return (静默降级，继续启动运动和环境的采集)
    │   │
    │   └── NO → 继续注册 Provider
    │            ├── 读取 last-known
    │            └── 对可用 Provider 请求 single update
    │
    ▼
2 秒批次结束后 removeUpdates；其他需求位独立处理
```

### 14.3 降级语义对照表

| 权限状态 | hasFine | hasCoarse | 定位行为 | latestLocationStr 内容 |
|----------|---------|-----------|----------|----------------------|
| 两项均未授予 | false | false | 不注册任何 Provider | `"位置信息: 未获得定位权限"` |
| 仅粗略位置 | false | true | Network Provider 工作，GPS 跳过 | 格式化坐标（精度较低） |
| 精确位置已授予 | true | true (隐式) | 双 Provider 均工作 | 格式化坐标（GPS 精度优先） |
| 任一 Provider 异常 | -- | -- | `catch SecurityException` | `"位置信息: 获取异常 (msg)"` |
| 定位服务未开启 | -- | -- | `isProviderEnabled() == false` | `"位置信息: 未开启定位服务"` |

> **与现有权限系统的关系**：`@TauriPlugin` 注解中已为定位声明别名 `location`，前端也可通过 `request_android_permission({ type: 'location' })` 主动请求。`SensorStatusManager` 本身遵循"被动检查 + 静默降级"模式，不在内部触发权限弹窗，只做状态检查。

### 14.4 与分布式工具层的映射

| 权限 | 涉及的 Rust 工具 | 数据流 |
|------|-----------------|--------|
| `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION` | `MobileLocation` (`location.rs`) | 到期计划 → `sample_sensor_data(location=true)` → `LocationManager` 有界采样 → `TelemetryCenter` → 主服务器 |
| 无（硬件访问无需运行时权限） | `MobileMotion` (`motion_sensor.rs`) | 到期计划 → `sample_sensor_data(motion=true)` → 2 秒 Burst → `TelemetryCenter` |
| 无（硬件访问无需运行时权限） | `MobileAmbient` (`ambient_sensor.rs`) | 到期计划 → `sample_sensor_data(ambient=true)` → 2 秒光照/气压采样 → `TelemetryCenter` |

> 运动传感器（加速度计）和环境传感器（光/气压）在 Android 上**不需要运行时权限**，仅需 Manifest 声明或默认可用。因此 `SensorStatusManager` 的运动和环境采集不受权限检查影响，总是能正常启动。

### 14.5 定位权限数据流

```
用户授予定位权限（系统设置或首次弹窗）
    │
    ▼
Android 系统记录权限状态
    │
    ▼
StreamingScheduler 合并本批 SensorDemand
    ├── ContextCompat.checkSelfPermission(ACCESS_FINE_LOCATION) → GRANTED
    ├── ContextCompat.checkSelfPermission(ACCESS_COARSE_LOCATION) → GRANTED
    │
    ▼
LocationManager 读取 last-known 并请求 single update
    │
    ▼
onLocationChanged(location) 回调
    ├── updateLocationString(location) → @Volatile latestLocationStr 更新
    │
    │  (本工具 120 秒 deadline)
    ▼
Plugin IPC: sample_sensor_data({ location: true })
    │
    ▼
TelemetryCenter 更新 → location.rs::read_current()
    │
    ▼
Rust client.rs → 主服务器 update_static_placeholders → LLM Context
```

## 16. GpuStatusManager —— GPU 硬件信息拉取

> 源码：`src-tauri/plugins/vcp-mobile/android/src/main/java/com/vcp/mobile/device/GpuStatusManager.kt`（84 行）

### 16.1 概述

`GpuStatusManager` 是 v1.0.3 新增的独立模块，通过**动态创建临时 EGL 上下文**读取 GPU 渲染器型号（例如 "Adreno (TM) 740"）。GPU 型号信息仅需查询一次，使用双重检查锁定（Double-Checked Locking）+ `@Volatile` 缓存避免重复的 EGL 初始化开销。

### 16.2 Rust 接口

```rust
#[derive(Serialize, Deserialize)]
#[serde(rename_all = "camelCase")]
pub struct GpuStatus {
    pub renderer: String,
    pub restricted: bool,
}

#[tauri::command]
pub fn get_gpu_status<R: Runtime>(app: AppHandle<R>) -> Result<GpuStatus, String>;
```

| 属性 | 说明 |
|------|------|
| 前端命令 | `plugin:vcp-mobile\|get_gpu_status` |
| 参数 | 无 |
| 返回值 | `GpuStatus { renderer, restricted }` —— `restricted` 固定为 `true`，表示 GPU 信息受限（无 sysfs 功耗/温度数据） |
| 桌面端行为 | 返回 `{ renderer: "PC Mock GPU", restricted: true }` |

### 16.3 EGL 临时上下文技术

GpuStatusManager 采用轻量级 EGL Pbuffer Surface 方案读取 GPU 型号，避免需要 GLSurfaceView 或 Activity：

```
fetchGpuRendererFromEgl()
    │
    ├── EGLContext.getEGL() as EGL10
    ├── eglGetDisplay(EGL_DEFAULT_DISPLAY)
    ├── eglInitialize(dpy, vers)
    │
    ├── eglChooseConfig(dpy, configAttr, configs, 1, numConfig)
    │   └── configAttr: [RED_SIZE=8, GREEN_SIZE=8, BLUE_SIZE=8]
    │
    ├── eglCreatePbufferSurface(dpy, config, [WIDTH=1, HEIGHT=1])
    │   └── 1x1 像素 Pbuffer Surface，最小化 GPU 资源占用
    │
    ├── eglCreateContext(dpy, config, EGL_NO_CONTEXT, [EGL_CONTEXT_CLIENT_VERSION=2])
    │   └── GLES 2.0 上下文
    │
    ├── eglMakeCurrent(dpy, surf, surf, ctx)
    │
    ├── GLES20.glGetString(GLES20.GL_RENDERER) → "Adreno (TM) 740"
    │
    └── 清理（严格按顺序）
        ├── eglMakeCurrent(dpy, EGL_NO_SURFACE, EGL_NO_SURFACE, EGL_NO_CONTEXT)
        ├── eglDestroyContext(dpy, ctx)
        ├── eglDestroySurface(dpy, surf)
        └── eglTerminate(dpy)
```

**为什么 `restricted` 固定为 `true`？**
在大多数 Android 设备上，`/sys/class/kgsl/` 或 `/sys/class/devfreq/` 等 GPU 性能计数器路径需要 Root 权限读取。`GpuStatusManager` 仅通过 EGL 读取渲染器名称字符串，无法获取 GPU 使用率、频率、温度等运行时指标。`restricted: true` 向前端明确告知此限制。

### 16.4 双重检查锁定缓存

```kotlin
@Volatile
private var cachedGpuRenderer: String? = null

fun getGpuRenderer(): String {
    cachedGpuRenderer?.let { return it }     // 第一次检查（无锁，快速路径）
    synchronized(this) {
        cachedGpuRenderer?.let { return it } // 第二次检查（持锁，防止竞争）
        val renderer = fetchGpuRendererFromEgl()
        cachedGpuRenderer = renderer
        return renderer
    }
}
```

| 场景 | 行为 |
|------|------|
| 首次调用 | `cachedGpuRenderer == null` → 进入 `synchronized` → 创建 EGL → 读取 GL_RENDERER → 写入缓存 |
| 并发调用（首次） | 第二个线程在 `synchronized` 外的 `?.let` 返回 `null` → 等待锁 → 持锁后第二次检查 → 发现已缓存 → 直接返回 |
| 后续调用 | `@Volatile` 保证可见性 → 无锁快速路径返回缓存值 → 零 EGL 开销 |

```kotlin
fun getNetworkStatus(): JSObject {
    val cm = context.getSystemService(Context.CONNECTIVITY_SERVICE) as ConnectivityManager
    val activeNetwork = cm.activeNetwork
    if (activeNetwork == null) {
        // 无活跃网络
        return { connected: false, type: "未连接", downSpeedKbps: 0, upSpeedKbps: 0, ip: "未分配" }
    }

    val capabilities = cm.getNetworkCapabilities(activeNetwork) ?: return /* 同上 */

    val type = when {
        capabilities.hasTransport(NetworkCapabilities.TRANSPORT_WIFI)     -> "WiFi"
        capabilities.hasTransport(NetworkCapabilities.TRANSPORT_CELLULAR) -> "移动数据"
        capabilities.hasTransport(NetworkCapabilities.TRANSPORT_ETHERNET) -> "以太网"
        else -> "未知"
    }

    val downSpeed = capabilities.linkDownstreamBandwidthKbps  // 下行估计带宽 (Kbps)
    val upSpeed   = capabilities.linkUpstreamBandwidthKbps    // 上行估计带宽 (Kbps)
    val ip        = getLocalIpAddress()                       // 本地 IPv4 地址
}
```

| 字段 | 来源 | 说明 |
|------|------|------|
| `connected` | `ConnectivityManager.activeNetwork` | `null` 表示无网络连接 |
| `type` | `NetworkCapabilities.hasTransport()` | 优先级：WiFi > 移动数据 > 以太网 |
| `downSpeedKbps` | `linkDownstreamBandwidthKbps` | 链路层估计值，非实时测速 |
| `upSpeedKbps` | `linkUpstreamBandwidthKbps` | 链路层估计值，非实时测速 |
| `ip` | `NetworkInterface.getNetworkInterfaces()` | 非回环 `Inet4Address` 的第一个地址 |

### 17.4 本地 IP 获取

```kotlin
private fun getLocalIpAddress(): String? {
    val en = NetworkInterface.getNetworkInterfaces()
    while (en.hasMoreElements()) {
        val intf = en.nextElement()
        val enumIpAddr = intf.inetAddresses
        while (enumIpAddr.hasMoreElements()) {
            val inetAddress = enumIpAddr.nextElement()
            if (!inetAddress.isLoopbackAddress && inetAddress is Inet4Address) {
                return inetAddress.hostAddress
            }
        }
    }
    return null
}
```

- 遍历所有网络接口，返回**第一个非回环 IPv4 地址**。
- 如无可用 IPv4 地址，`ip` 字段设为 `"未分配"`。

### 17.5 桌面端与异常 fallback

| 场景 | connected | type | downSpeedKbps | upSpeedKbps | ip |
|------|-----------|------|---------------|-------------|-----|
| 正常连接（WiFi） | true | "WiFi" | 链路估计值 | 链路估计值 | 实际 IPv4 |
| 正常连接（移动数据） | true | "移动数据" | 链路估计值 | 链路估计值 | 实际 IPv4 |
| 无活跃网络 | false | "未连接" | 0 | 0 | "未分配" |
| capabilities 为 null | false | "未连接" | 0 | 0 | "未分配" |
| 异常 | false | "未连接" | 0 | 0 | "未分配" |
| 桌面端 | true | "以太网" | 100000 | 100000 | "127.0.0.1" |

## 18. Root 访问体系

> 源码：`VcpMobilePlugin.kt`（`checkRootAccess` / `runRootCommand` / `launchRootManager`）、`system.rs`

### 18.1 概述

Root 访问体系基于 [libsu](https://github.com/topjohnwu/libsu)（`com.topjohnwu.superuser`）库提供三项能力：Root 状态检测、Root 命令执行、Root 管理器应用启动。Root 操作在独立有界单线程 `rootExecutor` 上执行，与串行文件 I/O 和 OOM scheduler 隔离。

### 18.2 check_root_access —— Root 状态检测

### 18.3 run_root_command —— 以 Root 身份执行 Shell 命令


| 属性 | 说明 |
|------|------|

| 参数 | `command: String` —— 要执行的 Shell 命令 |

**Kotlin 实现**：

```kotlin
@Command
fun runRootCommand(invoke: Invoke) {
    val args = invoke.parseArgs(RunRootCommandArgs::class.java)
    executePluginTask(executorDomains.rootExecutor, invoke, "runRootCommand") {
        try {
            val output = Shell.cmd(args.command).exec().out
            val result = JSObject().apply {
                put("success", true)
                put("output", output.joinToString("\n"))
            }
            invoke.resolve(result)
        } catch (e: Exception) {
            val result = JSObject().apply {
                put("success", false)
                put("output", e.message ?: "Unknown Shell execution error")
            }
            invoke.resolve(result)
        }
    }
}
```

- `Shell.cmd(command).exec().out`：通过 libsu 以 Root 身份执行命令，返回标准输出行列表。
- 在 `rootExecutor` 上运行，避免阻塞 UI 且不会饿死文件任务。
- 参数解析失败直接 `invoke.reject()`，不上报执行级错误。

### 18.4 launch_root_manager —— 启动 Root 管理器应用

| 属性 | 说明 |

| 前端命令 | `plugin:vcp-mobile\|launch_root_manager` |
| 参数 | 无 |
| 返回值 | `LaunchRootManagerResult { success, manager, message }` |

**Kotlin 实现**：

```kotlin
@Command
fun launchRootManager(invoke: Invoke) {
    val managers = listOf(
        "com.topjohnwu.magisk" to "Magisk",
        "me.weishu.kernelsu" to "KernelSU",
        "me.tool.apatch" to "APatch"
    )
    for ((pkg, name) in managers) {
        try {
            val intent = activity.packageManager.getLaunchIntentForPackage(pkg)
            if (intent != null) {
                intent.addFlags(Intent.FLAG_ACTIVITY_NEW_TASK)
                activity.startActivity(intent)
                invoke.resolve(JSObject().apply {
                    put("success", true)
                    put("manager", name)
                })
                return
            }
        } catch (e: Exception) { /* 尝试下一个 */ }
    }
    // 未找到任何已安装的 Root 管理器
    invoke.resolve(JSObject().apply {
        put("success", false)
        put("message", "未找到支持的 Root 管理器 (Magisk, KernelSU, APatch)。")
    })
}
```

**支持的 Root 管理器**：

| 包名 | 显示名称 | 说明 |
|------|---------|------|
| `com.topjohnwu.magisk` | Magisk | 最主流的 Android Root 方案 |
| `me.weishu.kernelsu` | KernelSU | 基于内核的 Root 方案 |
| `me.tool.apatch` | APatch | 新一代内核级 Root 方案 |

- 按顺序遍历三个包名，使用 `packageManager.getLaunchIntentForPackage()` 查找启动 Intent。
- 找到第一个已安装的管理器即启动并立即返回。
- 全部未找到返回 `success: false` + 错误消息。

### 18.5 AndroidManifest.xml 包可见性声明

Android 11 (API 30) 引入了包可见性限制，默认情况下应用无法查询其他已安装应用。为支持 `launch_root_manager` 中通过 `getLaunchIntentForPackage` 查询 Root 管理器，需在 `AndroidManifest.xml` 中声明 `<queries>`：

```xml
<queries>
    <package android:name="com.topjohnwu.magisk" />
    <package android:name="me.weishu.kernelsu" />
    <package android:name="me.tool.apatch" />
</queries>
```

> **不声明 `<queries>` 的后果**：`getLaunchIntentForPackage()` 始终返回 `null`，`launch_root_manager` 会错误报告"未找到支持的 Root 管理器"，即使设备上已安装了 Magisk/KernelSU/APatch。

## 20. WakeLock/WifiLock 保活机制（v1.1.2: 委托 ForegroundGuardian）

> 源码：`VcpMobilePlugin.kt`, `system.rs`, `ForegroundGuardian.kt`

### 20.1 概述

v1.0.3 引入的 WakeLock + WifiLock 双锁保活机制，在 v1.1.2 中已**委托给 `ForegroundGuardian`** 统一管理。`acquire_wake_lock` / `release_wake_lock` 命令现在通过 `ForegroundGuardian.acquire(tag="manual_keepalive", priority=10)` / `release(tag="manual_keepalive")` 实现，不再直接操作 `PowerManager` / `WifiManager` API。完整的锁管理机制请参见 [11_ForegroundGuardian 前台守护者](11_ForegroundGuardian_前台守护者.md)。

#### 分布式节点的三阶段调用

在 `distributed/client.rs` 中，WakeLock/WifiLock 由 helper 函数成对自动调用，无需前端介入：

| 阶段 | 位置 (client.rs) | 锁持有时长 | 目的 |
|------|------------------|-----------|------|
| WebSocket 连接 | `connection_loop` connect 前后 | 毫秒级 | 防止 TCP 握手期间 CPU 休眠 |
| 工具执行 | `tokio::select!` 内 `execute_tool` 前后 | 取决于工具（硬上限 5 分钟） | 保证工具执行期间 CPU+WiFi 不中断 |
| 占位推送 | `tokio::select!` 内 `push_static_placeholders` 前后 | 毫秒级 | 30 秒定时推送不被 Doze 模式阻断 |

#### 与前台保活服务的协同

`StreamKeepaliveService` 与 WakeLock/WifiLock 构成**双重保活**体系：

| 层级 | 触发 | 停止 |
|------|------|------|
| Service 层 | `DistributedClient::start()` → `set_keepalive_mode(true)` | `DistributedClient::stop()` → `set_keepalive_mode(false)` |
| 锁层 | 上述三阶段操作开始前 | 对应操作完成后立即释放 |

锁仅在关键操作期间**短暂持有**，操作完成后立即释放。Service 提供通知栏可见性与进程优先级。两者协同确保分布式长连接在 Android Doze/App Standby 模式下可靠运行。

### 20.2 acquire_wake_lock —— 获取双锁


## 21. 网络监控与自动重连

> 源码：`VcpMobilePlugin.kt` (lines 524--563), `system.rs` (lines 787--804)

### 21.1 概述

v1.0.3 新增基于 Android `ConnectivityManager.NetworkCallback` 的原生网络状态监控，在网络可用/丢失/能力变化时自动触发事件推送到 WebView。相比前端 `navigator.onLine` + `online`/`offline` 事件，原生回调更可靠且能感知网络能力变化（如从 WiFi 切换到移动数据）。

**自动激活时机**：网络监控由 `lifecycle_manager.rs` 的 `bootstrap()` 在**步骤 10** 自动启动——在 `CoreStatus::Ready` 发射之后，通过 `tauri::async_runtime::spawn` 异步调用。延迟激活是为了规避冷启动时 JNI WebView 尚未完全就绪导致的死锁——此时所有 Rust 业务服务已就绪，Native 回调可安全触发分布式节点自动重连。前端无需手动调用 `start_network_monitoring`。

### 21.2 start_network_monitoring —— 启动网络监控

```rust
#[tauri::command]
pub fn start_network_monitoring<R: Runtime>(app: AppHandle<R>) -> Result<(), String>;
```

| 属性 | 说明 |
|------|------|
| 前端命令 | `plugin:vcp-mobile\|start_network_monitoring` |
| 参数 | 无 |
| 桌面端行为 | 空操作 |
| 幂等性 | `isNetworkMonitoringStarted` 标志位防止重复注册 |

**Kotlin 实现**：

```kotlin
private var networkCallback: ConnectivityManager.NetworkCallback? = null
private var lastConnected: Boolean? = null
private var isNetworkMonitoringStarted = false

@Command
fun startNetworkMonitoring(invoke: Invoke) {
    if (isNetworkMonitoringStarted) {
        invoke.resolve()
        return
    }
    val cm = activity.getSystemService(Context.CONNECTIVITY_SERVICE) as ConnectivityManager
    val request = NetworkRequest.Builder()
        .addCapability(NetworkCapabilities.NET_CAPABILITY_INTERNET)
        .build()
    networkCallback = object : ConnectivityManager.NetworkCallback() {
        override fun onAvailable(network: Network) {
            emitNetworkStatusToWebView()
        }
        override fun onLost(network: Network) {
            emitNetworkStatusToWebView()
        }
        override fun onCapabilitiesChanged(network: Network, caps: NetworkCapabilities) {
            emitNetworkStatusToWebView()
        }
    }
    cm.registerNetworkCallback(request, networkCallback!!)
    isNetworkMonitoringStarted = true
    invoke.resolve()
}
```

### 21.3 回调触发条件

| 回调方法 | 触发时机 | 典型场景 |
|----------|----------|----------|
| `onAvailable` | 满足 `NET_CAPABILITY_INTERNET` 的网络变为可用 | WiFi 连接成功、移动数据开启 |
| `onLost` | 之前可用的网络丢失 | WiFi 断开、飞行模式 |
| `onCapabilitiesChanged` | 网络能力发生变化 | WiFi → 移动数据切换、带宽限制变化 |

### 21.4 变化检测与事件推送

`emitNetworkStatusToWebView()` 在推送事件前进行连接状态变化检测，避免重复通知：

```kotlin
private fun emitNetworkStatusToWebView() {
    val status = networkStatusManager.getNetworkStatus()
    val connected = status.optBoolean("connected", false)
    if (connected != lastConnected) {
        lastConnected = connected
        trigger("vcp-network-status-changed", status)
    }
}
```

| 变量 | 类型 | 说明 |
|------|------|------|
| `lastConnected` | `Boolean?` | 上次已知的连接状态。初始 `null`，首次回调必定触发事件 |
| `vcp-network-status-changed` | Tauri Plugin `trigger` 事件 | 携带完整 `NetworkStatus` JSON 对象 |

### 21.5 事件监听（前端）

```typescript
// 前端通过 Tauri event system 监听网络状态变化
import { listen } from '@tauri-apps/api/event';

listen('vcp-network-status-changed', (event) => {
    const status = event.payload as NetworkStatus;
    if (status.connected) {
        console.log(`网络已连接: ${status.type}, IP: ${status.ip}`);
        // 触发 WebSocket 重连 / SSE 重连逻辑
    } else {
        console.log('网络已断开');
        // 暂停连接尝试，UI 显示离线状态
    }
});
```

### 21.6 生命周期清理

```kotlin
override fun onDestroy(activity: AppCompatActivity) {
    try {
        if (networkCallback != null) {
            val cm = activity.getSystemService(Context.CONNECTIVITY_SERVICE) as ConnectivityManager
            cm.unregisterNetworkCallback(networkCallback!!)
            networkCallback = null
            isNetworkMonitoringStarted = false
        }
    } catch (_: Exception) {}
    // ...
}
```

- `unregisterNetworkCallback` 必须在 Activity 销毁前调用，否则会导致内存泄漏。
- `networkCallback` 和 `isNetworkMonitoringStarted` 重置为初始状态，确保 Activity 重建后可以重新注册。

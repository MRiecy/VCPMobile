# 屏幕常亮控制

## 1. 功能概述

Android 的常亮最终由 `ScreenKeepOnArbiter` 写入当前 Activity 的 Window。Rust `screen.rs` 经 **Raw JNI** 调用 Kotlin `setManualRequested(activity, requested)`，只提交手动意图；业务任务的常亮意图来自 `ForegroundGuardian` 持有的消费者集合。

仲裁条件为 `appInForeground && (manualRequested || guardianRequested)`。Activity 暂停时清除窗口标志，恢复后重新按当前请求应用；释放手动请求不会清除仍由 Guardian 持有的常亮请求。这里的 `appInForeground` 来自该 Activity 的回调，是窗口可见性条件，与 `LifecycleBridge` 的进程级业务 phase 各有用途。

> **所有权边界**：窗口标志只由仲裁器应用。任务租约、取消与业务完成归原来的 Rust/Guardian owner；不通过新的前端引用计数复制任务状态。当前源码已没有 `useScreenKeeper.ts`。

## 3. 接口详解

### 3.1 `set_keep_screen_on`

```rust
#[tauri::command]
pub fn set_keep_screen_on<R: Runtime>(app: AppHandle<R>) -> Result<(), String> {
    #[cfg(target_os = "ios")]
    crate::ios_not_implemented::<()>("set_keep_screen_on")?;

    #[cfg(target_os = "android")]
    {
        set_manual_screen_owner(&app, true)?;
    }
    Ok(())
}
```

| 属性 | 说明 |
|------|------|
| 前端命令 | `plugin:vcp-mobile\|set_keep_screen_on` |
| 参数 | 无 |
| 返回值 | `Result<(), String>`；窗口查找/调度失败返回错误，内部 JNI 失败仅记日志，见 §5 |
| iOS 行为 | 该手动命令返回 `not_implemented`；不代表 iOS 的业务后台资源租约未实现 |
| host 开发行为 | 空操作；不构成桌面产品能力 |
| 当前前端授权 | 包装与注册入口仍存在，但 `android-main.json` 未授予这两个命令，生产 Vue 无直接消费者 |

### 3.2 `clear_keep_screen_on`

与 `set_keep_screen_on` 对称，向仲裁器提交 `manualRequested=false`。仅当没有 Guardian 常亮请求，或 Activity 已不在前台时，仲裁结果才清除 `FLAG_KEEP_SCREEN_ON`。

## 4. JNI 调用链拆解

```rust
let window = app
    .get_webview_window("main")
    .ok_or("main window not found")?;

window
    .as_ref()
    .with_webview(move |webview| {
        webview.jni_handle().exec(move |env, activity, _webview| {
            if let Err(error) = env.call_static_method(
                "com/vcp/mobile/ScreenKeepOnArbiter",
                "setManualRequested",
                "(Landroid/app/Activity;Z)V",
                &[
                    JValue::Object(activity),
                    JValue::Bool(if requested { 1 } else { 0 }),
                ],
            ) {
                log::error!(
                    "[VcpMobilePlugin] ScreenKeepOnArbiter.setManualRequested failed: {:?}",
                    error
                );
            }
        });
    })
    .map_err(|e| format!("with_webview failed: {:?}", e))?;
```

| 步骤 | JNI 签名 | 说明 |
|------|----------|------|
| Kotlin 类 | `com/vcp/mobile/ScreenKeepOnArbiter` | FQCN 固定；抽成独立文件后仍保留原 package |
| `setManualRequested` | `(Landroid/app/Activity;Z)V` | `@JvmStatic` 方法接收 Activity 与请求布尔值 |
| `apply(activity)` | Kotlin 内部调用 | 切主线程、检查 Activity 身份，再添加或清除 `FLAG_KEEP_SCREEN_ON` |

`detach(activity)` 只清理当前持有的 Activity，重置手动意图并清除旧窗口标志；Guardian 请求仍由 Guardian 消费者集合决定，不在 Activity 销毁时伪造任务完成。

## 5. 错误处理

| 错误来源 | 错误信息 | 触发条件 |
|----------|----------|----------|
| `get_webview_window` | `"main window not found"` | 名为 `"main"` 的 WebView 窗口不存在 |
| `with_webview` | `"with_webview failed: ..."` | JNI 执行环境异常 |
| `setManualRequested` | 日志输出 `[VcpMobilePlugin] ScreenKeepOnArbiter.setManualRequested failed: ...` | JNI 静态方法调用失败 |

> **返回值范围**：内部 JNI 调用错误仅通过 `log::error!` 记录，不回传外层 `Result`；Kotlin 应用窗口标志还会切到 UI 线程。`Ok(())` 不能作为窗口标志或设备常亮已经生效的证明。

## 6. 当前业务任务的资源所有权

当前 Rust `ForegroundLease` 为每个操作生成独立 tag；正常结束显式释放，future 被取消时由 Drop 安排释放。`ForegroundGuardian` 汇总仍存活的消费者，`setScreenStateListener` 把其常亮需求交给仲裁器。

```text
Rust 业务操作 → ForegroundLease / ForegroundTask
             → Kotlin ForegroundGuardian 消费者集合
             → ScreenKeepOnArbiter.setGuardianRequested
             → 当前 Activity 的 Window flag
```

### 6.1 已核对的任务策略

| 任务 | 实际消费者 | `screenKeepOn` |
|------|------------|----------------|
| `Stream` | `agent_chat_application_service.rs`、`group_chat_application_service.rs` | `false`；流式后台资源租约不要求点亮屏幕 |
| `Sync` | `sync/sync_service.rs` | `true` |
| `Prerender` | `persistence/message_repository.rs` | `true` |

### 6.2 历史前端引用计数

旧 `useScreenKeeper`、`withScreenKeep` 与聊天 Store 全局归零释放方案已不在当前生产调用链中。不能按旧场景列表推断所有维护操作都会申请常亮，也不应恢复第二份前端任务引用计数。新增任务是否需要常亮，应由其真实业务 owner 选择现有租约策略。

## 7. 与 Kotlin 侧的对照

Kotlin 插件保留同名原生命令入口，提交的仍是同一仲裁器的手动意图：

```kotlin
@Command
fun setKeepScreenOn(invoke: Invoke) {
    ScreenKeepOnArbiter.setManualRequested(activity, true)
    invoke.resolve()
}
```

Rust `screen.rs` 当前直接走 JNI 静态入口；Kotlin `@Command` 的存在不表示 Vue 已获调用授权。两条入口都不能直接绕过仲裁器写 Window flags；原生方法、公开插件命令与前端 capability 是不同层的声明。

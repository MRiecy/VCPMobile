### 请求与事件的实际路径

- Android `registerNativeEvents` 保存 Rust 提供的 Channel，`emitNativeEvent` 在主线程发送 `{event,payload}`；Swift 使用同一封装。两者由 [src/events.rs](../../src-tauri/plugins/vcp-mobile/src/events.rs) 解码，并在应用 [lifecycle_manager.rs](../../src-tauri/src/vcp_modules/infra/lifecycle_manager.rs) 分派。当前生命周期没有使用 `plugin.trigger`。
- `lifecycle` 进入 Rust 生命周期 owner；`network` 在 Android 提示 Distributed 重连，在 iOS 发 `vcp-network-changed` 供现有恢复逻辑消费。它与按次查询的完整网络 DTO 是不同路径。
- iOS `notificationClick` 经 Channel → Rust → `vcp-notification-click`；原生 `getPendingNotification` 返回同一最近点击快照，读取不清除，Vue 按 `clickId/sequence` 去重。Android 通知点击仍使用 `evaluateJavascript` 的 DOM `vcp-notification-click`，并由 Android pending getter 取走待处理数据。
- Android 权限变化、Insets 和文件选择仍各自沿现有 WebView 事件发送；不能把所有原生事件统称为 Channel 或 `plugin.trigger`。本地通知发送和剪贴板的 Rust 内部工具调用不因此新增前端接口。

## 插件模块依赖关系

Android 保留单一 Gradle 插件；`VcpMobilePlugin` 接入框架命令和生命周期，功能实现按包组合。`service/SseProxyService` 将 helper 会话交给 `sse/SseSessionCoordinator`；主进程租约继续由 `ForegroundGuardian` 持有。

具体目录、资源归属、跨层符号和验证边界见 [功能分包与资源所有权](13_Android功能分包与资源所有权.md)。iOS Swift owner 不依赖 Android Service。

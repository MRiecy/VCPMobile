# 日志系统与可观测性

## 1. 引言

在分布式同步系统中，日志（Log）不仅是调试（Debugging）的核心依据，更是运行时可观测性（Observability）的唯一数据源。VCP Mobile 的同步链路横跨 Rust 移动端、Node.js 桌面服务端与 Vue 前端三层，任何一层的状态漂移都可能导致数据不一致。通过结构化的三级日志体系——Session（会话）→ Phase（阶段）→ Operation（操作）——开发者可以精准定位一次同步请求在全链路中的执行轨迹，快速诊断网络延迟、哈希冲突、数据库锁竞争等典型问题。

本文档同时覆盖移动端（Rust）与桌面端（Node.js）的日志实现，并基于真实日志样本解读关键模式。

---

## 2. Session → Phase → Operation 三级结构

VCP Mobile 的日志系统采用严格嵌套的三级树形结构，两端实现保持一致。

### 2.1 概念定义

| 层级 | 英文术语 | 中文释义 | 生命周期 | 标识符示例 |
|------|----------|----------|----------|------------|
| 一级 | Session | 同步会话 | 一次完整的同步连接（WebSocket 握手到断开） | `sync_1778537156425` |
| 二级 | Phase | 同步阶段 | 会话内的逻辑分段，按数据类型划分 | `owner_metadata`、`messages` |
| 三级 | Operation | 单个操作 | 阶段内的最小原子单元（单条实体处理） | `diff:agent`、`upload_messages_batch_stream` |

### 2.2 嵌套关系与约束

- 一个 **Session** 包含多个 **Phase**，Phase 按固定顺序串行执行：`owner_metadata` → `topic_metadata` → `messages`。
- 一个 **Phase** 包含任意数量的 **Operation**，Operation 在 Phase 内可并行或串行执行。
- Phase 具备自动收尾机制：桌面端（`logger.js`）在启动新 Phase 时，若检测到前一个 Phase 未完成，会自动调用 `completePhase` 强制关闭（`src-tauri/src/vcp_modules/sync/sync_logger.rs` 与 `logger.js` 均实现了此语义）。
- 每个 Phase 维护独立的计数器：`expected`（预期总量）、`success`（成功数）、`errors`（错误数）。

### 2.3 标识符与追踪

| 属性 | 来源 | 说明 |
|------|------|------|
| Session ID | 单调递增 `u64` / `Date.now()` 时间戳 | 移动端由 `SyncState` 分配并写入文件名与文件头；桌面端由 `startSession(prefix)` 生成 |
| Phase 名称 | 硬编码枚举 | 两端共享同一组阶段名，确保日志可交叉比对 |
| Operation ID | 实体类型 + 实体 ID | 如 `topic_1773214887121`、`agent_xxx` |

## 3. Rust 端 SyncLogger

### 3.1 结构与核心方法

`SyncLogger`（`src-tauri/src/vcp_modules/sync/sync_logger.rs`）负责级别过滤和可选文件原文持久化：

| 结构成员 | 类型 | 职责 |
|----------|------|------|
| `log_level` | `LogLevel` | 过滤阈值，低于此级别的日志被丢弃 |
| `log_file` | `Option<std::fs::File>` | 可选的日志文件句柄 |
| `log_path` | `Option<PathBuf>` | 日志文件路径 |
| `initialization_error` | `Option<String>` | 日志目录或文件创建失败的完整原因；失败不阻断同步 |

**核心方法清单：**

| 方法 | 级别 | 作用 |
|------|------|------|
| `new_session(log_level, log_dir, session_id)` | — | 创建当前 Session 独占文件，并写入 Session ID 文件头 |
| `log(level, phase, message)` | 由参数决定 | 按阈值过滤并原样写入日志 |
| `log_direct(level, phase, message)` | 由参数决定 | 写入会话必要记录 |
| `end_session()` | Info | 收尾并刷盘 |

### 3.2 日志级别定义

Rust 端定义五级枚举（`src-tauri/src/vcp_modules/sync/sync_logger.rs`）：

| 级别 | 数值 | 用途 |
|------|------|------|
| `Trace` | 0 | 最细粒度协议追踪，生产环境默认关闭 |
| `Debug` | 1 | 高频操作日志（单条实体处理），生产环境默认关闭 |
| `Info` | 2 | 阶段起止、连接事件、统计摘要 |
| `Warning` | 3 | 可继续运行的降级与自动重试（文件标签为 `WARN`） |
| `Error` | 4 | 操作失败、数据库锁、网络异常 |

**级别过滤规则**：普通日志仅当 `level >= self.log_level` 时写入。运行时读取现有 `syncLogLevel` 设置，大小写不敏感；非法值回退 `INFO` 并记录一条 `WARN`。生产环境默认 `INFO`，调试时可设为 `DEBUG` 或 `TRACE`。Session 文件头与结尾属于必要记录，通过 `log_direct` 保留；数据库 writer 指标遵守同一阈值，Bridge 缓存会话阈值并在字符串格式化和 Logger 加锁前丢弃低级别指标。默认 `INFO` 只保留慢写 `WARN` 与失败 `ERROR`，完整成功事务时序需在下一次会话前设为 `DEBUG`。

### 3.3 日志格式

Rust 端采用 ISO-8601 带毫秒偏移的格式：

```
[2026-08-25T05:09:48.123+08:00] [INFO] [messages] === Phase 3: Messages ===
```

字段依次为：**时间戳**、**级别**、**Phase 名**、**消息体**。

### 3.4 与前端事件的集成

移动端严格区分“用户过程日志”和“诊断日志”。`SyncLogger` 只负责控制台与持久文件，不把原始诊断行逐条发往 WebView。同步面板的阶段/完成记录由结构化状态与进度事件生成；仅自动重试、日志文件不可用等安全提示通过 `vcp-log` 发出，并要求 `audience="operator" + sessionId`。

| 事件名称 | 触发时机 | payload 关键字段 |
|----------|----------|------------------|
| `vcp-sync-status` | 连接状态或类型化错误 | `{ sessionId, status, error? }` |
| `vcp-sync-progress` | 阶段进度与汇总计数 | `{ sessionId, phase, total, completed, ... }` |
| `vcp-sync-completed` | 经过最终 ACK 的唯一成功终态 | `{ sessionId, status, summary }` |
| `vcp-log` | 少量用户过程提示 | `{ audience:"operator", sessionId, level, message }` |

同步状态不再镜像到全局 `vcp-system-event`，也不发送重复完成 Toast；同步面板是唯一用户展示面。移动端持久日志目录为 Tauri `app_log_dir()/sync_logs/`。

### 3.5 SQLite writer 指标桥

Persistence 只发布中性的 `DbWriteMetric`，同步会话通过固定容量 broadcast receiver 观察“本会话存活期间完成的 writer”。独立 `DbWriteMetricLogBridge` 消费指标后才锁 `SyncLogger` 和刷文件；`WriteLease` 在发送前已经释放全局 writer guard，因此日志磁盘 I/O 不计入 Gate hold，也不会阻塞后续 SQLite writer。

```text
[2026-08-30T12:34:56.789+08:00] [DEBUG] [db_write] operation=sync.queue outcome=committed wait_ms=1.231 begin_ms=0.542 hold_ms=18.430 finish_ms=2.114
```

字段语义：

| 字段 | 起止边界 |
|------|----------|
| `operation` | 静态 writer 类别，不含实体 ID、SQL 或路径 |
| `outcome` | `committed`、`rolled_back`、`*_failed*`、`*_closed` 等物理结局 |
| `wait_ms` | 请求进入公平队列至取得 process-local writer guard |
| `begin_ms` | 取得 guard 后至 `BEGIN IMMEDIATE` 成功；Queue 包含 blocking 调度与连接准备 |
| `hold_ms` | 取得 guard 至物理事务结束并准备释放 guard |
| `finish_ms` | COMMIT、ROLLBACK 或不确定连接关闭本身的耗时 |

正常项写为 `DEBUG`，等待或持有达到 500ms 写为 `WARN slow`，失败写为 `ERROR`，三者均服从 `syncLogLevel`。指标缓冲区落后时按日志阈值记录 `metric stream lagged; skipped=N`；丢失诊断不能改变事务、Queue Flush 或同步终态。会话退出顺序为 Queue 最终 Flush → 固定当时 backlog 截止线 → 排空该有限快照 → `Session ended`，因此最后一个会话内 `sync.queue` 指标不会落在会话结尾之后，截止线后持续产生的普通业务指标也不会拖住 `stop_sync()`。

## 4. Node 端 SyncLogger

### 4.1 结构与核心方法

桌面端的 `SyncLogger`（`VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/core/logger.js`）在语义上与 Rust 端对齐，但增加了 **WebSocket 广播** 与 **控制台可视化边框** 能力：

| 结构成员 | 类型 | 职责 |
|----------|------|------|
| `currentSession` | `Object` | 当前会话元数据与 Phase Map |
| `currentPhase` | `String` | 当前活跃 Phase，默认 `"system"` |
| `logDir` | `String` | 固定为 `../logs/sync/` |
| `logStream` | `WriteStream` | 文件写入流 |
| `logFilePath` | `String` | 当前会话的日志文件绝对路径 |

**核心方法清单：**

| 方法 | 作用 |
|------|------|
| `startSession(prefix)` | 清理旧流，创建新会话，输出 ASCII 边框横幅 |
| `startPhase(phase, expected)` | 注册 Phase，自动结束上一个未完成的 Phase |
| `logOperation(phase, type, id, result, detail)` | 记录操作，每 100 条输出进度简报 |
| `logInfo(phase, message, level)` | 纯文本信息，不更新计数器 |
| `completePhase(phase)` | 关闭 Phase，输出耗时与统计 |
| `endSession()` | 强制完成所有 Phase，输出结束横幅 |
| `broadcast(payload)` | 通过 WebSocket 向所有在线客户端广播 JSON 事件 |

### 4.2 日志格式规范

Node 端在控制台与文件中采用两种格式：

**控制台输出（带可视化边框）：**
```
[VCPMobile] [22:05:56] ╔══════════════════════════════════════════════════════════════════════════════╗
[VCPMobile] [22:05:56] ║ SESSION START: sync_1778537156425                                            ║
[VCPMobile] [22:05:56] ╚══════════════════════════════════════════════════════════════════════════════╝
[VCPMobile] [22:05:56]
[VCPMobile] [22:05:56] ┌─── PHASE START: [owner_metadata] (expected: 0) ──────────────────────────────
[VCPMobile] [22:05:56] │ [owner_metadata] diff:owner -> success (push=0 pull=0 pull_delete=0 skip=6)
[VCPMobile] [22:05:56] └─── PHASE COMPLETE: [owner_metadata] duration: 31ms (Total:3 OK:3 ERR:0)
```

**文件持久化（精简格式）：**
```
[2026-05-11T22:05:56.426Z] === SESSION START: sync_1778537156425 ===
[2026-05-11T22:05:56.426Z] [websocket] connection:100.68.180.95 -> success (token=ok, path=/)
[2026-05-11T22:05:56.448Z] --- PHASE START: [owner_metadata] (expected: 0) ---
[2026-05-11T22:05:56.459Z] [owner_metadata] diff:owner -> success (push=0 pull=0 pull_delete=0 skip=6)
```

| 字段 | 控制台 | 文件 |
|------|--------|------|
| 前缀 | `[VCPMobile] [HH:mm:ss]` | ISO-8601 时间戳 |
| Phase 标记 | `│ [phase_name]` | `[phase_name]` |
| 边框线 | `╔═╗╚═╝┌─┐└─┘` | 无 |
| 进度简报 | `│ [PROGRESS]` | `[PROGRESS]` |

### 4.3 WebSocket 日志广播机制

桌面端通过 `setWss(wss)` 注入 WebSocket 服务器引用，在关键节点广播结构化事件：

| 广播类型 | 触发方法 | payload 字段 | 用途 |
|----------|----------|--------------|------|
| `DESKTOP_PHASE_START` | `startPhase()` | `{ type, phase, ts }` | 通知前端某阶段开始 |
| `DESKTOP_PHASE_COMPLETE` | `completePhase()` | `{ type, phase, ts }` | 通知前端某阶段结束 |
| `SYNC_LOG_EVENT` | `logOperation()` / `logInfo()` | `{ type, level, phase, message, ts }` | 移动端接收后写入持久诊断日志，不透传到 WebView |

广播范围覆盖所有 `readyState === 1`（OPEN）的 WebSocket 客户端，发送失败时静默吞掉异常，避免影响主同步流程。

## 5. 日志文件管理

### 5.1 文件命名规则

| 端 | 命名模板 | 示例 |
|----|----------|------|
| 移动端（Rust） | `{YYYYMMDD_HHMMSS_SSS}_{sessionId}_sync.log` | `20260813_120000_127_42_sync.log` |
| 桌面端（Node） | `{prefix}_{timestamp}.log` | `sync_1778537156425.log` |

移动端使用毫秒时间戳、单调 Session ID 与 `create_new`，连续重试不会追加到已有文件。

### 5.2 目录结构

桌面端的日志目录固定为插件根目录下的相对路径：

```
VCPMobileSync/
├── core/
│   └── logger.js
└── logs/
    └── sync/
        ├── sync_1778537156425.log       # 常规同步会话
        ├── sync_1778536310477.log       # 常规同步会话
        └── system_1778533765692.log     # 系统/索引扫描会话
```

移动端日志目录由 Tauri `app_log_dir()` 推导并追加 `sync_logs/`。代码和 UI 不依赖 OEM 相关的绝对路径。

### 5.3 日志分类

| 分类 | 前缀 | 典型内容 | 生命周期 |
|------|------|----------|----------|
| 同步会话日志 | 移动端 `*_sync.log` / 桌面端 `sync_*` | WebSocket 握手、三阶段 diff、消息上传下载 | 单次同步连接 |
| 系统日志 | `system_*` | 数据库初始化、轻量级索引扫描（reconcile） | 服务启动时 |

### 5.4 文件大小与轮转策略

Rust 端提供 `clear_old_sync_logs` Tauri Command，可按保留天数清理 `app_log_dir()/sync_logs/` 下的过期同步日志文件。前端或维护任务可主动调用该命令实现日志轮转；未调用时仍依赖以下被动机制控制体积：

| 机制 | 说明 |
|------|------|
| 按会话分文件 | 每个 Session 独占一个文件，连接断开即关闭句柄 |
| 进度采样 | Node 端每 100 条 Operation 才输出一次 `PROGRESS` 简报，降低高频场景下的行数 |
| 主动清理 | `clear_old_sync_logs(keep_days) -> {removed, failed}`；只统计实际删除成功的文件，部分失败单独报告 |

所有持久日志保留完整诊断原文，包括 Bearer、Token/Key/Secret/Password、URL 查询参数、IP、端口、文件路径和实体 ID。同步会话启动时会记录冻结后的 WebSocket URL、HTTP URL 与 token。若目录或文件创建失败，面板展示完整失败原因；同步本身不失败。

## 6. 前端事件监听

Vue 前端通过 Tauri 的 `listen` API 订阅同步状态事件，实现面板内进度、错误结论和历史日志浏览；同步事件不进入全局 Toast 或通知中心。

### 6.1 事件总览

| 事件名称 | 来源端 | 频率 | 典型消费者 |
|----------|--------|------|------------|
| `vcp-sync-status` | Rust（Tauri emit） | 低频（连接与终态） | 同步面板状态与错误卡 |
| `vcp-sync-progress` | Rust（Tauri emit） | 中频（阶段进度） | 进度条与去重后的阶段日志 |
| `vcp-sync-completed` | Rust（Tauri emit） | 低频（每 Session 一次） | 面板完成态与数据刷新标志 |
| `vcp-log`（`audience:"operator"`） | Rust（Tauri emit） | 低频（重试/降级） | 面板简明过程日志 |
| `DESKTOP_PHASE_START` | Node（WebSocket） | 中频 | 桌面端调试面板 |
| `DESKTOP_PHASE_COMPLETE` | Node（WebSocket） | 中频 | 桌面端调试面板 |

### 6.2 事件 Payload 结构

**`vcp-sync-status`**
```typescript
interface SyncStatusEvent {
  sessionId: number;
  status: "connecting" | "open" | "error" | "completed" | "completed_with_warnings";
  source: "Sync";
  error?: {
    code: string;
    category: "device" | "configuration" | "connection" | "compatibility" | "protocol" | "data" | "storage" | "internal";
    origin: string;
    stage: string;
    retryAction: string;
    message: string;
    guidance: string;
    failedTopicIds: string[];
    logFile: string | null;
  };
}
```

**`vcp-sync-completed`**
```typescript
interface SyncCompletedEvent {
  sessionId: number;
  source: "Sync";
  status: "completed" | "completed_with_warnings";
  summary: {
    successfulTopics: number;
    totalTopics: number;
    failedTopics: number;
    legacyAttachmentWarnings: number;
    failedTopicIds: string[];
  };
}
```

### 6.3 前端与日志的对应关系

前端事件并非日志的逐行镜像，而是日志数据的安全聚合。例如：
- Phase 3 只有 `Phase3Tracker::mark_completed` 推进成功 Topic 计数；诊断日志不反向驱动 UI 进度。
- 终态会先把稳定错误码与原始 detail 写入日志文件，再只向 WebView 发送固定的 `message + guidance`。主错误卡额外显示低显著度的 `阶段 · 来源 · code`，但不渲染原始异常或失败实体 ID；完整规则见 `16_Wire_1.5错误契约与排障规范.md`。

## 7. 实际日志样本分析

以下分析基于桌面端真实日志文件 `sync_1778537156425.log`（2026-05-12 06:05:57 生成）与 `system_1778533765692.log`。

### 样本 1：会话建立与版本协商

以下为旧版顶层版本字段时期的历史日志，仅用于说明连接事件；当前 Wire 1.5 已改为结构化 `versions` 声明，日志键为 `mobilePackageVersion`、`desktopPackageVersion` 与 `wireVersion`。

```
[2026-05-11T22:05:56.426Z] [websocket] connection:100.68.180.95 -> success (token=ok, path=/)
[2026-05-11T22:05:56.432Z] [websocket] version_check:mobile -> info (mobileVersion=0.9.13, pluginVersion=0.9.13)
```

**历史解读**：
- 移动端 IP 为 `100.68.180.95`，WebSocket 连接成功并通过 Token 校验。
- 当前实现只按 Wire 1.5 仲裁兼容性；插件包版本和桌面后端模式作为当前 session 信息记录。

### 样本 2：Owner Metadata 阶段的零变更场景

```
[2026-05-11T22:05:56.448Z] --- PHASE START: [owner_metadata] (expected: 0) ---
[2026-05-11T22:05:56.459Z] [owner_metadata] diff:owner -> success (push=0 pull=0 pull_delete=0 skip=6)
[2026-05-11T22:05:56.469Z] [owner_metadata] diff:avatar -> success (push=0 pull=0 pull_delete=0 skip=8)
[2026-05-11T22:05:56.479Z] --- PHASE COMPLETE: [owner_metadata] ---
```

**解读**：
- `expected: 0` 表示桌面端未预设具体数量，依赖实际 diff 结果动态统计。
- 三类实体（agent、group、avatar）均无推拉删操作，全部 `skip`，说明两端元数据已完全一致。
- Phase 耗时约 31ms，属于典型的快速路径（Fast Path）。

### 样本 3：Topic Metadata 阶段的批量哈希比对

```
[2026-05-11T22:05:56.521Z] [topic_metadata] diff:topic -> success (push=1 pull=0 pull_delete=0 skip=130)
[2026-05-11T22:05:56.576Z] [topic_metadata] topic_diff:summary -> success (total=131 match=113 changed=18)
```

**解读**：
- 首次 diff 发现 1 个 topic 需要 push（移动端向桌面端推送）。
- 随后进入 `SYNC_TOPIC_DIFF_REQUEST/RESULT`，对 Topic 双 Hash 进行批量比对。
- 结果：113 个完全匹配（match），18 个存在差异（changed）。这 18 个 topic 将进入下一阶段的 messages 级 diff。

### 样本 4：Messages 阶段的上传与下载

```
[messages] diff:topic_1773214887121 -> success (pull=2 pushTopic=false delete=0)
[messages] diff:topic_1778526713775 -> success (pull=0 pushTopic=true delete=0)
[2026-05-11T22:05:56.829Z] [messages] download_messages_stream:batch -> success (topics=1 success=1 error=0)
```

**解读**：
- `topic_1773214887121` 的 `pullMessageIds` 为 2 条。
- `topic_1778526713775` 的 `pushTopic=true`。
- `download_messages_stream:batch` 表明实际执行了流式下载，1 个 topic 成功，0 错误。
- 注意第 51 行的 `upload_messages_batch_stream` 出现 `error=1`，说明上传批次中存在个别失败，但 HTTP 状态码仍为 200，属于部分成功的典型模式。

### 样本 5：系统级索引扫描

```
[2026-05-11T21:09:25.692Z] === SESSION START: system_1778533765692 ===
[2026-05-11T21:09:25.703Z] [reconcile] 正在执行轻量级索引扫描...
```

## 8. 调试技巧

### 8.1 如何开启详细日志

| 端 | 操作方式 | 效果 |
|----|----------|------|
| Rust 移动端 | 将现有设置字段 `syncLogLevel` 设为 `TRACE` / `DEBUG` / `INFO` / `WARN` / `ERROR` | 下一次 Session 按该阈值生成持久日志；非法值回退 `INFO` |
| Node 桌面端 | 日志固定为全量输出，控制台天然可见 `│` 前缀的详细操作 | 通过 `logs/sync/` 目录直接查看文件 |
| Vue 前端 | 在 DevTools Console 过滤 `vcp-sync-*` 事件 | 实时观察事件流与 payload |

### 8.2 如何定位特定实体的同步历史

假设需要追踪某个 topic（如 `topic_1773214887121`）的完整同步轨迹：

1. **grep 单实体 ID**：在 `logs/sync/` 目录下搜索 `topic_1773214887121`，可快速找到涉及该实体的所有 Operation。
2. **grep Phase 边界**：搜索 `PHASE START: [messages]` 与 `PHASE COMPLETE: [messages]`，定位该实体所属会话的上下文。
3. **结合 Session ID**：确认 `{timestamp}_{sessionId}_sync.log` 文件名，确保不跨会话混淆。
4. **移动端补充**：优先在同步面板“历史”Tab 打开或复制日志；需要 ADB 时先通过设备实际 `app_log_dir` 定位，不硬编码 OEM 路径。

### 8.3 常见日志模式与问题对应关系

| 日志模式 | 可能的问题 | 诊断方向 |
|----------|------------|----------|
| `database is locked` | `WriteCoordinator` 漏接 writer 或异常外部连接 | 结合 `[db_write] operation/outcome/wait_ms/begin_ms/hold_ms/finish_ms` 定位；不要先扩大 timeout |
| `pullMessageIds>0` 但 `/messages/pull` 缺失 | 差异后未执行数据面 | 检查 Phase ACK 与连接状态 |
| `error=1` 但 HTTP `status=200` | 批次内部部分失败 | 展开批次详情，定位具体失败的 topic/消息 ID |
| Phase 耗时 > 30s | 网络延迟或大数据量传输 | 检查 `expected` 数量，确认是否处于首次全量同步 |
| `skip=N` 但 `N` 远小于预期总数 | 哈希索引未覆盖全部实体 | 检查 reconcile 扫描是否完整，索引是否损坏 |
| `VERSION_ACK` 版本不匹配 | 两端协议不兼容 | 升级移动端或桌面端插件至同一版本 |

### 8.4 性能分析速查

通过日志中的 `duration` 字段可进行轻量级性能剖析：

| 指标 | 正常范围 | 异常阈值 | 优化建议 |
|------|----------|----------|----------|
| `owner_metadata` Phase | < 100ms | > 500ms | 减少 avatar/agent 数量，或启用增量哈希 |
| `topic_metadata` Phase | < 1s | > 5s | 检查 topic 总数是否超过千级，考虑归档旧 topic |
| `messages` Phase（无变更） | < 500ms | > 2s | 优化哈希比对算法，减少不必要的批次请求 |
| `messages` Phase（有变更） | 取决于消息量 | 单条消息 > 200ms | 检查附件大小，启用流式分片传输 |

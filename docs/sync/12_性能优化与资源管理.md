# 性能优化与资源管理

## 1. 引言

在移动端同步场景中，性能（Performance）与资源管理（Resource Management）直接决定用户体验与设备稳定性。VCP Mobile 面向的是物理 Android 终端，其约束远比桌面端严苛：

| 约束维度 | 移动端限制 | 对同步的影响 |
|---------|-----------|------------|
| 内存（Memory） | 典型 4-8GB，应用可用仅数百 MB | 禁止全量缓冲，必须流式处理 |
| 网络（Network） | WiFi/5G/4G 频繁切换，高延迟抖动 | 需要有界流式处理与指数退避 |
| 存储 IO（Storage IO） | SQLite 在闪存上的 WAL 写入存在锁竞争 | 必须串行化写入并合并事务 |
| CPU（Central Processing Unit） | 大核小核架构，后台任务受限 | 预渲染等 CPU 密集型任务需控制并行度 |

本文档系统阐述 VCP Mobile 同步引擎在 Rust 后端实现的六大性能优化策略，涵盖并发控制、数据库写入队列、批量尺寸控制、NDJSON（Newline Delimited JSON，换行分隔 JSON）流式传输、附件去重以及冷启动特殊处理。

## 2. 消息 Pull 帧预算

`pull_messages_batch` 使用 `tokio::sync::Semaphore` 限制在途 NDJSON 帧内存：

- 总预算 32 MiB。
- 每帧按原始字节数以 1 MiB 为单位向上取整占用 permit。
- 处理完成后自动释放 permit。

该预算只约束消息 Pull 的 Topic 帧解析，不是全局 HTTP 并发控制器。

## 3. DB 写队列（DbWriteQueue）

> 完整、按当前代码核对的算法说明见 [`14_Persistence领域总览.md` §3](../modules/14_Persistence领域总览.md)。该章节包含 Worker 流程图、`carried_task`、Flush 时序、250 + 250 + 250 示例，以及当前双截止微批处理边界。

### 3.1 当前结构

同步 Pull 的并发解析结果不会各自直接争抢 SQLite 写锁，而是进入一个容量 32 的有界 `mpsc`。唯一 Worker 按 FIFO 收集当前预算内的最长连续前缀，再通过 `spawn_blocking` 使用持久 rusqlite 连接执行一个事务。

| 参数 | 当前值 | 准确含义 |
|------|-------:|----------|
| 通道容量 | 32 个任务 | sender 满时对 Pull 生产者施加背压 |
| 单事务任务上限 | 32 个数据任务 | 所有非 Flush 任务各计 1 |
| 单事务消息预算 | 正常路径 500 条 | 只统计 `TopicMessages.writes`；上游单任务先按 250 条切块 |
| 收集等待 | quiet 2ms / hard 10ms | quiet 捕获突发；hard 从首任务起固定且不可延长 |
| SQLite busy timeout | 2000ms | 队列连接与其他 sqlx 写连接冲突时有界退避 |

这条单消费者路径消除的是 **DbWriteQueue 内部**的写竞争；项目中的其他 sqlx 写事务仍共享同一 SQLite 文件。

### 3.2 当前批次算法

Worker 使用“有界 FIFO 最大前缀贪婪”：

1. 优先取上一轮预读但超预算的 `carried_task`，否则等待队首。
2. 首任务若是 `Flush`，直接返回并清空历史 `pending_errors`。
3. 数据任务成为本批第一项。
4. 首任务固定 10ms hard deadline，同时维护每次接收后重置的 2ms quiet deadline。
5. 遇到 Flush、任一 deadline、通道关闭或计数上限即停止。
6. 若已预读的消息任务会使本批超过 500，将它放入 `carried_task`，下一事务优先处理。
7. 一个事务严格按 FIFO 执行本批；失败回滚并累计到下一个 Flush。

在不可重排、不可跳过队首的约束下，最长前缀已经最小化事务数量，不需要优先队列或 knapsack。双截止算法让单个稀疏任务通常在 2ms quiet 后提交，同时把连续流量的整个收集期限制在首任务后的 10ms；该上界不包含 SQLite 事务执行时间。

### 3.3 Flush 与同步收尾

`flush().await` 先把一个 FIFO marker 送入同一通道，再等待 oneshot：

- marker 前的任务事务全部处理完，Worker 才返回 ACK；
- 当前或历史事务失败会聚合为 `Err`，同步阶段不得当作成功；
- Flush 不会越过旧任务，因此它是有序提交屏障，不是高优先级任务；
- 消息批次 Flush 成功后，`SyncFinalizer` 才统一更新 Topic/Owner 聚合根，避免每个 250 条块重复冒泡。

`submit().await` 仅代表入队；只有 Flush ACK 才证明 marker 之前的 SQLite `commit` 已返回。

## 4. 批量操作的尺寸控制

### 4.1 实体批次的最大数量

在 HTTP 批量拉取（Batch Pull）和推送（Batch Push）中，不同实体类型采用不同的批次尺寸（`src-tauri/src/vcp_modules/sync/sync_service.rs`）：

| 数据类型 | 批次大小 | 拉取端点 | 理由 |
|---------|---------|---------|------|
| Owner | 50 | `/entities/pull` | 配置数据相对较大 |
| Topic | 1000 | `/entities/pull` | 元数据轻量 |
| 其他 | 100 | `/entities/pull` | 默认分块 |

### 4.2 消息批次的最大数量

Phase 3（消息同步）采用**双层级批次控制**（`src-tauri/src/vcp_modules/sync/sync_service.rs`）：

**第一层：WebSocket Diff 批次**

```rust
const MAX_MESSAGES_PER_BATCH: usize = 10000;
```

- 每批最多包含 **10,000 条消息** 的哈希映射；
- 典型 Payload 约 1.5-2MB JSON，在移动端 WebSocket 安全范围内；
- `build_diff_batches` 函数按 `topic` 粒度累加，不会拆散单个 topic 的消息映射。

**第二层：HTTP NDJSON 流式批次**

- Pull：`/messages/pull` 以 Topic 为单位逐行返回；
- 处理端：每个 Topic 帧在 spawn 前按原始字节数占用 32 MiB 在途预算。

### 4.3 本地附件大小限制

| 方向 | 限制 | 代码位置 |
|-----|------|---------|
| 本机存储 | 20 MB | `file_manager.rs`（`store_file`） |
| 本机读取 | 50 MB | `file_manager.rs`（`read_local_file_base64`） |

附件二进制不进入同步网络数据面。

## 5. NDJSON 流式的内存优势

### 5.1 与传统 JSON 批量的内存对比

| 对比维度 | 传统 JSON 批量 | NDJSON 流式 |
|---------|--------------|------------|
| 内存占用 | 正比于总数据量（全量缓冲） | 正比于单个 topic（行缓冲） |
| 10,000 条消息 | ~50-100MB 峰值 | ~2-5MB 峰值 |
| 失败恢复 | 全部重试 | 单 topic 失败，不影响其他 |
| 进度反馈 | 请求结束后统一反馈 | 逐 topic 实时反馈 |

NDJSON（Newline Delimited JSON）的核心优势在于：**解析器无需等待整个响应体下载完成，只需维护一个行级缓冲区**（`src-tauri/src/vcp_modules/sync/sync_executor/pull_executor.rs`）。

### 5.2 流式读取的实现机制

移动端 `pull_messages_batch` 的实现（`src-tauri/src/vcp_modules/sync/sync_executor/pull_executor.rs`）：

```
┌─────────────────────────────────────────────────────────────┐
│              NDJSON 流式解析与并发处理管线                     │
├─────────────────────────────────────────────────────────────┤
│  HTTP Response Stream                                         │
│       │                                                      │
│       ▼                                                      │
│  ┌─────────────┐     chunk (bytes)     ┌─────────────┐     │
│  │ bytes_stream│ ───────────────────> │  Buffer Vec │     │
│  │ (futures)   │                     │  (行级累积)  │     │
│  └─────────────┘                     └──────┬──────┘     │
│                                             ▼              │
│                                   ┌─────────────────┐      │
│                                   │ 逐行查找 '\n'   │      │
│                                   │ drain(..=end)   │      │
│                                   └────────┬────────┘      │
│                                            ▼               │
│                                   ┌─────────────────┐      │
│                                   │  spawn 异步任务  │      │
│                                   │  Semaphore(6–12) │      │
│                                   │  process_topic  │      │
│                                   └─────────────────┘      │
└─────────────────────────────────────────────────────────────┘
```

关键代码逻辑：

```rust
let mut stream = res.bytes_stream();
let mut buffer = BytesMut::new();
let mut search_start = 0;

while let Some(chunk) = stream.next().await {
    // 实际实现先执行 32 MiB 上限检查；无残留时尽量复用 transport allocation。
    if buffer.is_empty() {
        buffer = chunk.try_into_mut().unwrap_or_else(|bytes| BytesMut::from(bytes.as_ref()));
    } else {
        buffer.extend_from_slice(&chunk);
    }

    while let Some(line_end) = buffer[search_start..].iter().position(|&b| b == b'\n') {
        let line = buffer.split_to(search_start + line_end + 1);
        search_start = 0;
        let topic_data = parse_topic_ndjson_frame(&line)?;
        // 解析 topicId 和 messages，spawn 并发处理
    }
    search_start = buffer.len();
}
```

**Chunk 边界跨越处理**：由于 TCP 分片，`chunk` 可能截断在任意字节位置。`buffer` 累积机制确保不丢失半行数据（`src-tauri/src/vcp_modules/sync/sync_executor/pull_executor.rs`）。

### 5.3 Flush 策略

桌面端 `pullMessagesStreamRaw` 的 Flush 策略（`VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/sync/message.js`）：

```javascript
res.setHeader("Content-Type", "application/x-ndjson");
res.setHeader("Transfer-Encoding", "chunked");
res.flushHeaders();

for (const topic of topics) {
    const history = await fs.readFile(historyPath, "utf-8");
    const messages = JSON.parse(history);
    await writer.write({ kind: "topic", ownerType, ownerId, topicId, ok: true, messages });
    // Node.js 自动 flush chunked 数据
}
res.end();
```

桌面端每处理完一个 topic 立即 `res.write()`，利用 HTTP Chunked Transfer Encoding 将数据推送到网络层。移动端因此可以**在完整响应到达之前就开始处理首批 topic**。

## 6. 附件去重策略

### 6.1 基于 Hash 的物理文件去重

附件在数据库中以 `hash` 为主键（Primary Key），采用 `INSERT ... ON CONFLICT(hash) DO UPDATE` 语义（`src-tauri/src/vcp_modules/persistence/db_write_queue.rs`）：

```sql
INSERT INTO attachments (
    hash, mime_type, size, internal_path, extracted_text, 
    image_frames, thumbnail_path, created_at, updated_at
) VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)
ON CONFLICT(hash) DO UPDATE SET
    mime_type = excluded.mime_type,
    size = excluded.size,
    ...
```

同一文件无论被多少条消息引用，物理存储仅保留一行记录。`message_attachments` 关联表维护消息与附件的多对多关系（`src-tauri/src/vcp_modules/persistence/db_write_queue.rs`）。

### 6.2 同步边界

消息 DTO 传输附件关系元数据与内容 Hash。两端只复用各自本机已存在的同 Hash CAS，不通过同步补传文件。

## 7. 首次同步（冷启动）的特殊处理

### 7.1 空数据库首次连接时的全量拉取策略

全新数据库没有 Owner、Topic 或 Message 行。桌面 Manifest 因此返回完整 PULL；每个实体在写入事务中同时生成自己的 DTO Hash。

| Phase | 行为 | 结果 |
|-------|------|------|
| Phase 1 | 桌面端对比发现所有 Agent/Group/Avatar 均缺失 | 返回全量 PULL |
| Phase 2 | 所有 Topic 元数据缺失 | 返回全量 PULL |
| Phase 2.5 | 双哈希批量比对发现所有 Topic 消息不一致 | 进入 Phase 3 |
| Phase 3 | 全量消息哈希 diff | 分批拉取所有消息 |

### 7.2 初始同步流程

```
┌─────────────────┐
│  WS 连接成功     │
└────────┬────────┘
         ▼
┌─────────────────────────┐
│ Phase 1: Owner Metadata │
│  (全量 PULL Agent/Group) │
└────────┬────────────────┘
         ▼
┌─────────────────────────┐
│ Phase 2: Topic Metadata │
│  (全量 PULL Topics)      │
```

## 8. 性能监控指标

### 8.1 日志边界

`SyncLogger` 只负责级别过滤、脱敏和持久文件写入，不维护第二份阶段计数或错误集合。Phase 边界、Diff 摘要、逐 Topic 失败和最终状态直接写入带时间戳的诊断日志；实时数字进度由会话计数器与 `Phase3Tracker` 产生。

### 8.2 前端可观测的指标

同步引擎通过 Tauri Event 向前端推送实时进度（`src-tauri/src/vcp_modules/sync/sync_service.rs`）：

| Event 名称 | 触发时机 | Payload 字段 |
|-----------|---------|-------------|
| `vcp-sync-progress` | 阶段活动或可靠计数变化 | `sessionId`, `phase`, `total`, `completed`，Phase 3 另带 Topic 汇总 |
| `vcp-sync-status` | 连接状态变化 | `sessionId`, `status`, `error?` |
| `vcp-sync-completed` | 最终 ACK 与本地 drain 完成 | `sessionId`, `status`, `summary` |
| `vcp-log` | 自动重试、日志文件降级等低频安全提示 | `audience:"operator"`, `sessionId`, `level`, `message` |

`SYNC_LOG_EVENT` 与后端详细阶段日志只写入控制台/持久诊断文件，不按行转发到 WebView。面板过程记录由 `vcp-sync-progress` 和 `vcp-sync-status` 的稳定字段生成。

**Phase 3 进度计算**：使用 `Phase3Tracker` 替代简单的 `AtomicU32` 计数器，防止同一 topic 被重复标记完成导致进度跳变（`src-tauri/src/vcp_modules/sync/sync_service.rs`）：

```rust
struct Phase3Tracker {
    completed: tokio::sync::Mutex<HashSet<String>>,
    modified: tokio::sync::Mutex<HashSet<String>>,
    total: std::sync::atomic::AtomicUsize,
}
```

`mark_completed` 方法通过 `HashSet::insert` 的返回值判断是否为首次完成，确保进度条线性增长。

## 10. CPU 与预渲染边界

### 10.1 PullExecutor `spawn_blocking`

`PullExecutor::process_topic_messages` 将消息处理循环放入 `tokio::task::spawn_blocking`：

```rust
tokio::task::spawn_blocking(move || {
    for msg in dtos {
        // fingerprinting + optional pre-rendering
    }
}).await?
```

fingerprinting 与可选 AST 编译不占用异步 IO worker；`[ProfileDetail]` / `[ProfileSummary]` 仅在 debug 日志记录处理耗时。

### 10.2 预渲染开关

`syncPrerenderEnabled` 控制同步下载阶段是否生成渲染缓存：

| 设置状态 | 同步下载行为 | `render_cache` 写入 | 消息加载行为 |
|---------|-------------|---------------------|-------------|
| 启用 | 同步 Pull 时编译渲染字节 | 批量写入 | 命中 render_cache 直接反序列化 |
| 禁用 | `blocks` 显式设为 `None`，跳过预渲染 | 本批消息的旧 cache 先失效，不写新 cache | 懒渲染缓存闭环在加载时编译 |

禁用时 `blocks` 为 `None`，旧缓存先失效，本批不写新缓存；后续消息加载按需编译。批量插入会跳过 `render_bytes` 为空的缓存项。


## 12. 运行约束

### 12.1 移动端

- **避免在同步期间触发大量 UI 重绘**：`vcp-sync-completed` 事件已聚合所有变更，前端应在收到该事件后批量刷新；
- **监听 `vcp-sync-progress` 而非轮询**：进度事件以 topic/批次为粒度推送，轮询会额外消耗 CPU 与电池；
- **日志清理策略**：`clear_old_sync_logs` 命令可按保留天数清理，建议设置为 7 天。

### 12.2 桌面端

- **NDJSON 流的逐 topic flush**：`pullMessagesStreamRaw` 中每处理完一个 topic 立即通过 `NdjsonWriter` 写出，不可缓存到数组后一次性 `res.json()` 输出，否则会失去流式内存优势；
- **`writeIntentLock` 的及时释放**：批量上传完成后必须遍历释放所有 topic 的锁，否则文件监控器（File Watcher）会停滞（`VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/sync/message.js`）。

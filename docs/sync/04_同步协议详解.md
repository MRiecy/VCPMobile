# 同步协议详解

## 1. 引言

### 1.1 协议概述

VCP Mobile 同步协议（以下简称本协议）是连接移动端（Mobile）与桌面端（Desktop）的数据同步桥梁，采用 WebSocket + HTTP REST 双协议架构（Dual-Protocol Architecture）。该设计兼顾了实时控制信令的低延迟需求与大容量数据传输的可靠性需求：

- WebSocket 层：承担同步会话的生命周期管理、阶段控制、差异比对指令交换等轻量级控制面职责。所有控制消息以 JSON 文本帧（Text Frame）传输。
- HTTP REST 层：承担实体数据、消息历史、附件文件等大容量载荷的传输职责。移动端使用 reqwest 客户端（`src-tauri/src/vcp_modules/sync/sync_service.rs`）向桌面端 Express 服务器发起调用。

双协议层共享同一套认证令牌（Sync Token），但传输方式存在差异：WebSocket 采用 Query Param 传递，HTTP 采用 Header 传递。

### 1.2 同步数据类型

本协议涉及五种核心同步数据类型（SyncDataType），定义于 `src-tauri/src/vcp_modules/sync/sync_types.rs`：

| 类型枚举 | 英文标识 | 说明 |
|---------|---------|------|
| Agent | agent | 智能体配置与元数据 |
| Group | group | 群组配置与元数据 |
| Avatar | avatar | 头像图片文件 |
| Topic | topic | 话题（会话）配置 |
| Message | message | 消息历史记录 |

### 1.3 核心设计哲学

- LWW（Last-Write-Wins，最后写入胜出）：以绝对时间戳 ts（毫秒级 Unix 时间戳）作为冲突裁决依据。
- 双哈希体系（Dual-Hash System）：V2 协议引入 configHash（配置指纹）与 contentHash（内容聚合指纹，即 Merkle Root）的分离设计，避免全量内容比对。contentHash 用于快速判定某 Agent/Group 旗下话题/消息是否发生深层变更，从而决定是否进入 Phase 3 消息同步。
- 分阶段流水线（Phased Pipeline）：同步过程被划分为四个严格顺序的阶段，通过 WebSocket 的 PHASE_START / PHASE_COMPLETED / PHASE_ACK 机制驱动流转。

## 2. 协议数据模型

### 2.1 实体状态向量（EntityState）

EntityState 是同步协议中最核心的数据结构，定义于 `src-tauri/src/vcp_modules/sync/sync_types.rs`。它代表任意同步实体在某一时刻的完整状态快照，是清单交换与差异比对的唯一依据。

| 字段 | 类型 | 序列化名 | 必填 | 说明 |
|------|------|---------|------|------|
| id | String | - | 是 | 实体唯一标识（如 agent_id、group_id、topic_id） |
| hash | Option<String> | - | 仅 Avatar | Avatar 二进制内容的 SHA-256 指纹 |
| config_hash | Option<String> | configHash | Agent/Group/Topic | 配置内容指纹，代表该实体同步 DTO 字段的哈希 |
| content_hash | Option<String> | contentHash | Agent/Group/Topic | 内容聚合指纹，代表子实体集合的 Merkle Root |
| ts | i64 | - | 是 | 最后更新时间戳（毫秒级 Unix 时间戳），LWW 裁决依据 |
| deleted_at | Option<i64> | deletedAt | 否 | 软删除时间戳。存在该字段表示实体已被删除 |
| owner_type | Option<String> | ownerType | 否 | 仅 Topic 类型使用，区分 agent 和 group |
| owner_id | Option<String> | ownerId | 否 | 仅 Topic 类型使用；与 ownerType、Topic ID 共同构成不可猜测的复合身份 |

协议 1.3 中，Agent/Group/Topic 必须携带合法的 `configHash`、`contentHash` 与非负安全整数时间戳；Topic 还必须同时携带 `ownerType` 和 `ownerId`。Avatar 使用 `hash`，并以 `owner_type:owner_id` 作为 `id`。

哈希计算规则：
- Agent/Group 配置哈希：提取 DTO 中的同步字段子集（AGENT_SYNC_FIELDS / GROUP_SYNC_FIELDS），通过确定性 JSON 序列化后计算 SHA-256（compute_deterministic_hash）。
- Topic 配置哈希：同理提取 AGENT_TOPIC_SYNC_FIELDS 或 GROUP_TOPIC_SYNC_FIELDS。
- Content Hash（聚合哈希）：对子实体哈希列表按字典序排序后连接，再次计算 SHA-256（compute_merkle_root）。Agent/Group 的 contentHash 为其旗下所有 Topic 的 configHash + contentHash 的聚合；Topic 的 contentHash 为其旗下所有消息的 contentHash 的聚合。

### 2.2 同步清单（SyncManifest）

SyncManifest 是移动端向桌面端发送的批量状态向量容器：

```rust
pub struct SyncManifest {
    pub data_type: SyncDataType,
    pub items: Vec<EntityState>,
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| data_type | SyncDataType | 清单中包含的实体类型 |
| items | Vec<EntityState> | 该类型的全量实体状态列表 |

Phase 1 构建 3 个 SyncManifest（agent、group、avatar），但严格分两波传输：agent/group 完成并 drain 后才发 avatar。Phase 2 发送 1 个 SyncManifest（topic，且附带 targetedOwners 过滤）。

### 2.3 同步数据类型枚举（SyncDataType）

```rust
pub enum SyncDataType {
    Agent,
    Group,
    Avatar,
    Topic,
    Message,
}
```

序列化时采用 rename_all = lowercase，故 JSON 中对应的字符串值为 agent、group、avatar、topic、message。

## 3. 连接建立

### 3.1 WebSocket 连接流程

移动端在启动手动同步时，由 `start_manual_sync` 命令触发同步会话。核心连接流程如下：

1. 完成后端唯一会话与消息生成前检；VCPLog 是独立日志通道，不参与同步网络准入。
2. 从 settings_manager 一次读取 WebSocket 地址、HTTP 基地址、同步令牌、日志等级和预渲染开关，在创建 session 资源前统一校验 URL、协议、非空令牌及 Android loopback。
3. 生成不可变会话配置快照：清除 WS 旧 query 后附加唯一 token，并由同一份快照服务本次会话的全部重连。
4. 创建 HTTP Client、会话日志并尝试申请 Android ForegroundGuardian lease；Guardian 是最佳努力的后台保活增强，申请失败只记录警告，不阻断 Wire 同步。
5. 通过 tokio_tungstenite::connect_async 发起异步握手；每次建连最多等待 10 秒。
6. 连接失败或建连超时时使用同一组 3 个自动重试槽，退避依次为 500ms、1s、2s。

桌面端由 startWsServer（`VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/transport/websocket.js`）在指定端口（默认 5975）监听 WebSocket 连接。

### 3.2 Token 验证机制

桌面端对同步令牌的验证存在两个入口，采用双轨验证策略：

WebSocket 入口（`VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/transport/websocket.js`）：

| 位置 | 字段名 | 格式 |
|------|--------|------|
| Query Param | token | ws://host:port?token=<sync_token> |

验证逻辑提取桌面端源码核心逻辑：连接时解析 URL Query 中的 token 参数，与 syncToken 比对，不匹配则返回 WebSocket Close Code 4001。

HTTP 入口（`VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/transport/routes.js`）：

| 优先级 | 位置 | 字段名 | 说明 |
|--------|------|--------|------|
| 1 | Header | x-sync-token | 自定义同步令牌头 |
| 2 | Header | Authorization | Bearer <sync_token> 标准格式 |
| 3 | Query Param | token | 调试入口 |

移动端在发起 HTTP 请求时，会同时携带 x-sync-token 和 Authorization: Bearer <token> 两个头部（`src-tauri/src/vcp_modules/sync/sync_executor/push_executor.rs`），以确保桌面端无论采用哪种校验方式均可通过。

### 3.3 版本校验（VERSION_CHECK / VERSION_ACK）

连接建立后，同步会话的第一条消息必须是版本握手。该机制确保移动端 App 与桌面端插件的版本兼容性。

握手时序：

```
Mobile                                  Desktop
  |                                        |
  | ---- WS: VERSION_CHECK --------------> |
  |     { type: VERSION_CHECK,             |
  |       mobileVersion: <App Version>,    |
  |       protocolVersion: "1.3" }         |
  |                                        |
  | <--- WS: VERSION_ACK ----------------- |
  |     { type: VERSION_ACK,               |
  |       pluginVersion: "1.3.0",          |
  |       protocolVersion: "1.3" }         |
  |                                        |
```

移动端校验逻辑（`src-tauri/src/vcp_modules/sync/sync_service.rs`）：

| 常量 | 值 | 说明 |
|------|-----|------|
| EXPECTED_PLUGIN_VERSION | 1.3.0 | 期望的桌面端插件协议版本 |
| WIRE_PROTOCOL_VERSION | 1.3 | 双端 wire protocol；不支持与旧 wire 混跑 |
| WS_CONNECT_TIMEOUT | 10s | 单次 WebSocket TCP/Upgrade 建连的最大等待时间 |
| VERSION_CHECK_TIMEOUT | 5s | 等待 VERSION_ACK 的超时时间 |
| WS_OPERATION_TIMEOUT | 5s | 单次 WebSocket send / close 的最大等待时间 |
| FINAL_ACK_TIMEOUT | 30s | Finalize 后等待桌面端最终完成确认的最大时间 |

校验规则：
- 只有 `pluginVersion` 与 `protocolVersion` 同时精确匹配，握手才成功。
- 缺字段、错误字段类型、畸形 JSON 或旧字段 `version` 均以 `VERSION_ACK_INVALID` 终止当前会话，不做降级。
- 若版本不一致，移动端立即断开连接，向前端报告错误，并提示用户下载最新插件。
- 若超时未收到 VERSION_ACK，视为桌面端插件过旧或不支持版本校验，同样断开连接。
- 1.1.0 引入的最终 ACK 四元身份契约在 1.3.0 中继续保持；1.3.0 另将全部错误硬切为结构化对象。1.1.0 及更旧插件会在 VERSION_ACK 阶段被拒绝。

## 4. WebSocket 消息类型完整参考

以下表格覆盖同步会话中所有 WebSocket 消息类型。方向列中 M-D 表示 Mobile-Desktop，D-M 表示 Desktop-Mobile。

### 4.1 控制面消息

| 消息名称 | 方向 | 触发时机 | Payload 关键字段 | 处理函数（Mobile） | 处理函数（Desktop） |
|---------|------|---------|-----------------|-------------------|-------------------|
| VERSION_CHECK | M-D | WS 连接建立后，由移动端主动发送 | mobileVersion: string, protocolVersion: "1.3" | run_sync_session 中直接构造发送 | index.js switch-case 处理，返回 VERSION_ACK |
| VERSION_ACK | D-M | 桌面端收到 VERSION_CHECK 后回复 | pluginVersion: "1.3.0", protocolVersion: "1.3" | run_sync_session 严格校验两个字段 | index.js 读取 plugin-manifest.json 返回 |
| PHASE_START | M-D | 各阶段开始时由移动端发送 | phase: string | run_sync_session 中通过 ws_stream.send 发送 | index.js 记录日志，返回 PHASE_ACK |
| PHASE_COMPLETED | M-D | 移动端完成阶段后发送；最终 `messages` 帧启动严格 ACK 等待 | 普通阶段：phase；最终帧：phase, sessionId, attemptId, nonce | `SyncCommand::Finalize` 发送最终帧，仅精确 ACK 可解除 30 秒 watchdog | index.js 回显最终帧身份字段 |
| PHASE_ACK | D-M | 桌面端确认收到阶段控制消息 | 普通阶段：phase；最终 ACK：phase, sessionId, attemptId, nonce | 普通 ACK 仅记录；最终 ACK 必须精确匹配当前 pending key 并仅消费一次 | index.js 回显所有身份字段 |
| SYNC_LOG_EVENT | D-M | 桌面端主动上报日志事件 | level: string, message: string | 通过 emit_sync_log 转发到前端 | 桌面端内部 logger 触发 |
| DESKTOP_PHASE_START | D-M | 桌面端报告自身阶段开始 | phase: string | 日志输出：[Desktop] Phase X started | 桌面端内部 logger 触发 |
| DESKTOP_PHASE_COMPLETE | D-M | 桌面端报告自身阶段完成 | phase: string | 日志输出：[Desktop] Phase X completed | 桌面端内部 logger 触发 |

### 4.2 清单与差异比对消息

| 消息名称 | 方向 | 触发时机 | Payload 关键字段 | 处理函数（Mobile） | 处理函数（Desktop） |
|---------|------|---------|-----------------|-------------------|-------------------|
| SYNC_MANIFEST | M-D | Phase 1 / Phase 2 开始时，移动端发送本地清单 | data: EntityState[], dataType: string, phase: number, targetedOwners: string[] (V2) | SyncCommand::StartManualSync 或 PipelineCommand::StartTopicMetadata 触发 | handleSyncManifest (sync/manifest.js) |
| SYNC_DIFF_RESULTS | D-M | 桌面端完成清单比对后返回 | data: DiffResult[], dataType: string, phase: number | run_sync_session WS 处理器中解析，派发 Pull/Push/Delete 任务 | handleSyncManifest 返回 |
| SYNC_DIFF_RESULTS_BATCH | D-M | 桌面端完成消息差异批量比对后返回 | results: Record<topicId, Phase3Decision> | 严格拒绝缺失/重复/额外 topic、字段类型错误和 `ok:false` | handleSyncMessageDiffBatch (sync/diff.js) |
| SYNC_TOPIC_HASH_BATCH_V2 | M-D | Phase 2.5 发送 topic 双哈希 | hashes: Record<topicId, { configHash, contentHash }> | PipelineCommand::StartTopicValidation 触发构造发送 | handleSyncTopicHashBatchV2 (sync/diff.js) |
| SYNC_TOPIC_HASH_RESULTS | D-M | 桌面端返回哈希比对结果 | changedTopics: string[] | 接收后设置 changed_topics，触发 SyncCommand::StartMessages | handleSyncTopicHashBatchV2 返回 |
| SYNC_MESSAGE_DIFF_BATCH | M-D | Phase 3 分批发送消息版本状态 | topics: Record<topicId, { topicHash, messages: Record<msgId, {hash,updatedAt}> }> | PipelineCommand::StartMessages 触发，按 MAX_MESSAGES_PER_BATCH（10000 条）分批次发送 | handleSyncMessageDiffBatch (sync/diff.js) |

### 4.3 实时变更通知消息

| 消息名称 | 方向 | 触发时机 | Payload 关键字段 | 处理函数（Mobile） | 处理函数（Desktop） |
|---------|------|---------|-----------------|-------------------|-------------------|
| SYNC_ENTITY_DELETE | M-D | 移动端本地实体或消息提交软删除 | id, dataType, deletedAt；Message 另需 topicId | SyncCommand::NotifyDelete / NotifyMessageDelete 触发发送 | index.js 调用 deleteEntity / deleteMessage |
| SYNC_ERROR | 双向 | 任一端遇到不可恢复错误 | `error: { code, origin, stage, kind, retry, message, failedTopicIds }` | 严格解析完整 Wire 1.3 对象；原始 message 只写诊断日志 | `error-contract.js` / `sync_error.rs` 统一构造 |
| SYNC_ACK | D-M | 桌面端确认收到 Mobile 的删除通知 | id: string | 移动端不处理 | index.js 返回 |

### 4.4 内部控制命令

| 命令/消息 | 方向 | 触发时机 | 说明 |
|----------|------|---------|------|
| `SyncCommand::Cancel` | 内部 | `stop_sync` Tauri 命令被调用 | 关闭 WebSocket 并收口当前后端会话。同步中不提供用户取消入口。 |
| `SyncCommand::SendWsMessage(Value)` | 内部 | `BatchDiffHandler` 处理完一批后需要发送下一批 | 允许内部任务将 outbound WS 消息重新入队，用于 `pending_diff_batches` 的链式触发。 |
| `stop_sync` | Tauri Command | 终态关闭面板或开始重试 | 取消并等待旧后端会话，防止旧任务跨入下一次尝试。 |

### 4.5 消息 Payload 字段详解

#### SYNC_MANIFEST Payload 结构

```json
{
  type: SYNC_MANIFEST,
  data: [
    {
      id: agent_001,
      configHash: sha256_cfg...,
      contentHash: sha256_cnt...,
      ts: 1715000000000,
      deletedAt: null,
      ownerType: null,
      ownerId: null
    }
  ],
  dataType: agent,
  phase: 1
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| type | string | 是 | 固定为 SYNC_MANIFEST |
| data | EntityState[] | 是 | 本地实体状态清单 |
| dataType | string | 是 | 实体类型：agent / group / avatar / topic |
| phase | number | 是 | 阶段标识：1 表示 Phase 1（Owner Metadata），2 表示 Phase 2（Topic Metadata） |
| targetedOwners | string[] | 否 | V2 优化：仅针对特定所有者的话题清单 |

#### SYNC_DIFF_RESULTS Payload 结构

```json
{
  type: SYNC_DIFF_RESULTS,
  data: [
    { id: agent_001, action: PULL, ownerType: agent },
    { id: agent_002, action: PUSH, mismatchedContent: true },
    { id: agent_003, action: DELETE, deletedAt: 1714000000000 },
    { id: agent_004, action: PUSH_DELETE, deletedAt: 1714000000000 }
  ],
  dataType: agent,
  phase: 1
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| id | string | 是 | 实体唯一标识 |
| action | string | 是 | 操作类型：PULL / PUSH / DELETE / PUSH_DELETE / SKIP |
| ownerType | string | 否 | 所有者类型，topic 类型时用于区分 agent_topic 和 group_topic |
| ownerId | string | 条件 | Topic 的 PUSH/PULL 决策必须携带，用于校验精确父实体，禁止从路径或 Topic 名猜测 |
| mismatchedContent | boolean | 否 | V2：内容哈希不匹配标记，用于引导后续 targeted topic sync |
| deletedAt | number | 条件 | DELETE / PUSH_DELETE 时必须，软删除时间戳 |

#### SYNC_MESSAGE_DIFF_BATCH Payload 结构

```json
{
  type: SYNC_MESSAGE_DIFF_BATCH,
  topics: {
    topic_001: {
      ownerType: agent,
      ownerId: agent_001,
      topicHash: sha256_topic...,
      messages: {
        msg_001: { hash: sha256_msg1..., updatedAt: 1700000000000 },
        msg_002: { hash: sha256_msg2..., updatedAt: 1700000000001 }
      }
    }
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| topics | object | 是 | Key 为 topicId，Value 必须包含 `ownerType + ownerId + topicHash + messages`；每个消息状态为 `{hash, updatedAt}`，墓碑的 `hash` 为 `DELETED` |

#### SYNC_DIFF_RESULTS_BATCH Payload 结构

```json
{
  "type": "SYNC_DIFF_RESULTS_BATCH",
  "results": {
    "topic_001": {
      "ok": true,
      "toPull": ["msg_003", "msg_004"],
      "toPush": false
    },
    "topic_002": {
      "ok": false,
      "error": { "code": "DESKTOP_DB", "message": "read failed" }
    }
  }
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| ok | boolean | 是 | 判别字段；禁止缺省或用 truthy 值代替 |
| toPull / toPush | string[] / boolean | `ok:true` 时 | `toPull` 必须为无重复的非空消息 ID；成功分支禁止携带 `error` |
| error.code / error.message | string / string | `ok:false` 时 | 必须为非空字符串；失败分支禁止携带 `toPull`、`toPush`，并立即终止 attempt |

响应必须逐 topic 精确覆盖本批请求。原始 JSON 中重复 topic key 也会在进入普通 `Value` 解析前被拒绝，不能依赖后写覆盖。

## 5. HTTP 端点完整参考

所有 HTTP 端点统一挂载在 /api/mobile-sync 路径前缀下（`VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/transport/routes.js`）。请求必须使用 x-sync-token 或 Authorization: Bearer 头部进行认证。

### 5.1 实体下载端点

#### POST /download-entities

| 属性 | 值 |
|------|-----|
| 方法 | POST |
| 用途 | 批量实体下载（Pull 批量，Phase 1/2 优化） |
| 请求格式 | {requests: [{id: ..., type: ...}]} |
| 响应格式 | JSON 数组，每个元素为对应实体的 DTO 或 null |
| Body 限制 | 默认 Express JSON 限制 |
| 认证方式 | Header |
| 对应处理函数 | downloadEntities (sync/entity.js) |
| 分批策略 | Mobile 端按类型分块：Agent/Group 每批 50，Topic 每批 1000（`sync_executor/diff_handler.rs:226-230`） |

## 6. 差异比对算法详解

### 6.1 清单差异计算（Manifest Diff）

桌面端收到 SYNC_MANIFEST 后，由 handleSyncManifest（`VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/sync/manifest.js`）执行差异计算。算法流程如下：

1. 加载本地清单：根据 dataType 查询桌面端本地索引数据库（entity_index 表），组装对应实体的 configHash、contentHash、ts、deletedAt；Avatar 单独使用 hash。
2. 遍历远程清单：对移动端发送的每个 EntityState：
   - 若 deletedAt 存在且本地未删除，输出 DELETE 动作
   - 若本地不存在，输出 PUSH 动作（移动端需要推送给桌面端）
   - 若本地已删除但远程未删除，输出 PUSH_DELETE 动作（告知移动端该实体在桌面端已被删除）
   - 若 Avatar 的 hash 不一致，按时间戳裁决
   - 若 configHash 不一致，按时间戳裁决：远程较新则 PUSH，否则 PULL
   - 若 contentHash 不一致（仅限 Agent/Group），标记 mismatchedContent = true，引导后续 Targeted Topic Sync
3. 遍历本地剩余：对远程清单中未包含的本地实体：
   - 若本地已删除，输出 PUSH_DELETE
   - 否则，输出 PULL（桌面端需要推送给移动端）

输出动作类型完整语义：

| 动作 | 方向 | 含义 | 后续操作 |
|------|------|------|---------|
| PULL | D-M | 桌面端数据较新或仅桌面端有，需推送给移动端 | 移动端调用 HTTP Pull 端点下载 |
| PUSH | M-D | 移动端数据较新或仅移动端有，需推送给桌面端 | 移动端调用 HTTP Push 端点上传 |
| DELETE | D-M | 移动端标记已删除，桌面端需同步删除 | 桌面端执行软删除 |
| PUSH_DELETE | M-D | 桌面端已删除，需通知移动端同步删除 | 移动端使用远端 `deletedAt` 幂等落墓碑，并发送 `SYNC_ENTITY_DELETE` 确认 |
| SKIP | - | 数据一致，无需操作 | 无 |

### 6.2 消息差异计算（Message Diff）

Phase 3 的消息差异由 handleSyncMessageDiffBatch（sync/diff.js）计算，采用双层快速路径策略：

第一层：Topic 级快速路径
- 比较移动端发送的 topicHash 与桌面端 entity_index 中的 aggregated_hash
- 若完全一致，返回 `{ok: true, toPull: [], toPush: false}`
- 该路径避免了逐消息比对，在大部分话题未变更时极大降低计算量

第二层：消息级详细比对
- 对未命中快速路径的 Topic，读取桌面端 message_index 中该话题的消息 Hash 与最终更新时间
- 构建桌面端状态映射 `Map<msgId, {hash, updatedAt}>`
- 同 ID、不同 Hash 时按 `updatedAt` 较大者优胜；时间相同则 Hash 字典序较大者优胜
- 遍历移动端消息：若桌面端无此消息，设置 toPush = true

结果处理策略：
- 先应用桌面消息墓碑，再调用 POST /download-messages-stream 拉取桌面获胜消息
- Pull 成功后等待本地写队列落库；任一 Pull 或落库失败均终止 attempt，不执行 Push
- `toPush` 为 true 时，最后调用 POST /upload-messages-batch 推送该 Topic 已合并的完整最终视图

## 7. 并发控制与流量整形

### 7.1 消息 Pull 帧预算

`pull_messages_batch` 使用 32 MiB 的在途 NDJSON 帧预算。每个 Topic 按原始帧大小占用预算，处理完成后释放，防止多个大帧同时进入解析管线。

### 7.2 移动端数据库写入队列（DbWriteQueue）

为避免高频并发写入 SQLite 导致锁竞争，移动端引入 DbWriteQueue（`src-tauri/src/vcp_modules/persistence/db_write_queue.rs`）：

- 批量缓冲：Pull 下来的实体数据先进入内存队列，而非直接写入数据库
- 定时刷盘：队列在以下时机执行批量写入：
  1. 队列长度达到阈值
  2. 阶段切换时（PHASE_COMPLETED 触发 flush()）
  3. 同步完成时
- WAL 模式：SQLite 启用 Write-Ahead Logging，进一步降低并发写入的锁竞争

### 7.3 桌面端流式传输

Phase 3 的大批量消息传输采用 NDJSON 流式格式，避免移动端内存溢出：

- 下载流（`/download-messages-stream`）：桌面端按 Topic 输出 NDJSON 帧并等待响应背压；请求与响应都携带 `ownerType + ownerId + topicId`。
- 上传流（`/upload-messages-batch`）：移动端按 Topic 快照分页序列化，桌面端逐帧处理并逐 Topic 返回结果。
- 单帧最大 32 MiB、单 attempt 总序列化预算 256 MiB、Topic 上限 10,000、消息上限 100,000；任一超限都会终止当前 attempt，而不是继续缓冲。

## 8. 同步状态机与事件系统

### 8.1 会话状态所有权

`run_sync_session` 是后端会话状态的唯一所有者，负责连接状态、attempt、阶段门和完成确认。`SyncPipeline` 只中继 Phase 2、Phase 2.5 与 Phase 3 的推进命令；Phase 3 完成后由 `SyncCommand::Finalize` 进入收尾。前端不读取后端内部状态枚举，只消费带 `sessionId` 的 Tauri 事件。

### 8.2 前端事件系统

同步模块通过 Tauri 的 Emitter 向前端 Vue 层发送多种事件，驱动 UI 状态更新：

| 事件名称 | 触发时机 | Payload 结构 |
|---------|---------|-------------|
| vcp-sync-status | 同步状态变更时 | `{ sessionId, status, error? }`；错误保留结构化 code 与有限失败 Topic |
| vcp-sync-progress | 阶段进度更新时 | `{ sessionId, phase, total, completed, successfulTopics?, totalTopics?, failedTopics?, legacyAttachmentWarnings? }` |
| vcp-sync-completed | 最终 ACK 且本地 drain 成功后 | `{ sessionId, status, summary: {successfulTopics, totalTopics, failedTopics, legacyAttachmentWarnings, failedTopicIds} }` |
| vcp-log | 仅自动重试、日志文件不可用等安全过程提示 | `{ id, level, category:"sync", audience:"operator", sessionId, message }` |

同步模块不再发射 `vcp-system-event` / `vcp-log-message`；全局 Toast 和通知中心不承担同步连接、完成或错误展示。

状态流转图：

```
[disconnected] --start_manual_sync--> [connecting]
    [connecting] --WS open--> [open]
    [open] --sync progress--> [open]
    [open] --error--> [error]
    [open] --all phases done--> [completed | completed_with_warnings]
    [error] --retry--> [connecting]
```

### 8.3 Phase3Tracker 任务追踪

Phase 3 中由于涉及大量 Topic 的并行 Push/Pull，移动端使用 Phase3Tracker（`src-tauri/src/vcp_modules/sync/sync_service.rs`）精确追踪每个 Topic 的完成状态：

| 属性 | 类型 | 说明 |
|------|------|------|
| completed | Mutex<HashSet<String>> | 已完成去重集合，防止同一 Topic 被重复计数 |
| modified | Mutex<HashSet<String>> | 数据实际发生变更的 Topic 集合，用于最终 Hash 冒泡 |
| total | AtomicUsize | 需要处理的总 Topic 数 |

mark_completed 方法采用首次标记有效策略：只有第一次调用返回 true，后续重复调用返回 false。当 completed.len() == total 时，自动触发 SyncCommand::Finalize，进入同步收尾阶段。

| Phase 3 | Messages | SYNC_MESSAGE_DIFF_BATCH | 按 10000 条与 8 MiB 序列化字节双预算分批；桌面端返回严格判别联合，随后通过 HTTP 传输数据，一批收尾后才发下一批 |

### 9.2 关键设计细节

- Phase Gate 机制（phase_gate 互斥锁）：每个 PHASE_COMPLETED 只能发送一次，防止重复触发导致流水线状态混乱（`src-tauri/src/vcp_modules/sync/sync_service.rs`）。
- 阶段推进保护：每个 reconnect attempt 拥有独立 tracker、计数器和任务集合；旧 attempt 的阶段命令会因 `attempt_id` 不匹配被丢弃。
- Phase 3 完整性：响应 Topic 集合必须与请求完全一致；Push/Pull 批错误、缺失结果或 `success=false` 会失败当前 attempt，不能继续 `mark_completed`。
- 有界等待：所有阶段均不设置基于完成数的额外看门狗；HTTP 请求由共享 Client 限制为从连接开始到响应体读取完成最多 270 秒，Phase 3 Pull 还要求相邻 NDJSON chunk 不得空闲超过 30 秒。Finalize 后 30 秒未收到桌面端最终 ACK 会失败，所有 WS send/close 为 5 秒 deadline。
- 断线重连保护：pending_diff_batches 在 Phase 3 启动前清空，旧 attempt 的任务先 cancel + join，再开始新 attempt。

## 10. 幂等性机制

### 10.1 设计目的

在移动网络环境下，HTTP 请求可能因网络抖动而超时，但服务器端实际已处理完成。若客户端盲目重试，可能导致数据重复写入。幂等性机制通过唯一操作标识（Idempotency Key）确保同一操作在 TTL 窗口内只执行一次。

### 10.2 幂等 Key 生成公式

移动端在发送 POST /upload-entity 请求时，通过 generate_idempotency_key 函数生成 Key（`src-tauri/src/vcp_modules/sync/sync_executor/push_executor.rs`）：

```rust
fn generate_idempotency_key(
    action: &str,
    entity_type: &str,
    id: &str,
    config_hash: &str,
) -> String {
    let minute = (chrono::Utc::now().timestamp() / 60).to_string();
    calculate_sha256_slices(&[
        action.as_bytes(),
        entity_type.as_bytes(),
        id.as_bytes(),
        config_hash.as_bytes(),
        minute.as_bytes(),
    ])
}
```

公式解析：

| 组成部分 | 来源 | 作用 |
|---------|------|------|
| action | 操作类型，如 push | 区分同一实体的不同操作 |
| entity_type | 实体类型，如 agent / group | 防止跨类型 ID 冲突 |
| id | 实体唯一标识 | 定位目标实体 |
| config_hash | 当前配置 DTO Hash | 区分同一分钟内的不同配置版本 |
| timestamp / 60 | UTC 时间戳按分钟取整 | 时间窗口切片，每分钟生成不同的 Key |

同一配置版本在同一分钟内重试会复用 Key；同一分钟内配置再次变化时，新的 `configHash` 会生成不同 Key。分钟切片允许跨分钟重新执行同一配置请求。

### 10.3 TTL 策略

桌面端幂等性控制实现于 `VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/core/idempotency.js`：

| 属性 | 值 |
|------|-----|
| TTL 时长 | 300000ms（5 分钟） |
| 存储结构 | Map<opId, { timestamp, result }> |
| 清理周期 | 每 60 秒执行一次自动清理 |
| 清理逻辑 | 遍历 recentOperations，删除 now - timestamp > IDEMPOTENCY_TTL 的条目 |

### 10.4 生效端点

目前幂等性机制仅在以下端点生效：

| 端点 | 方法 | 幂等头部 |
|------|------|---------|
| /upload-entity | POST | x-idempotency-key |

检测与返回逻辑（`VCPChat/VCPDistributedServer/Plugin/VCPMobileSync/transport/routes.js`）：

桌面端接收到请求后，提取 x-idempotency-key 头部，调用 checkIdempotency(opId)。若判定为重复请求，直接返回上次缓存的结果，不执行业务逻辑；若为新请求，执行业务后调用 recordOperation(opId, result) 记录结果，供后续幂等命中。

## 11. 版本兼容性策略

### 11.1 版本协商机制

本协议采用严格版本匹配策略，不支持向前/向后兼容的松散协商。

协商流程：

1. 移动端发送 `{ mobileVersion, protocolVersion: "1.3" }`。
2. 桌面端返回 `{ pluginVersion: "1.3.0", protocolVersion: "1.3" }`。
3. 移动端对两个版本字段做字符串精确匹配；任一不符或字段无效都终止会话。

### 11.2 版本不匹配处理

| 场景 | 移动端行为 | 桌面端行为 |
|------|-----------|-----------|
| 版本一致 | 继续同步流程 | 正常响应 |
| 版本不一致 | 断开 WS，状态置为 error，提示用户更新插件 | 不处理（版本校验由移动端主导） |
| 超时未收到 VERSION_ACK | 断开 WS，状态置为 error | 无有效响应 |

### 11.3 配对版本边界

- 版本号采用 SemVer（语义化版本）格式，但校验逻辑为字符串完全匹配，非语义化比较。这意味着 1.0.0 与 1.0.0-beta 会被视为不兼容。
- 当前 wire protocol 基线为 1.3，桌面插件包版本为 1.3.0，Mobile 版本为 1.1.5。桌面端对最终 `PHASE_COMPLETED` 的回复必须原样回显 `phase`、`sessionId`、`attemptId`、`nonce`；缺字段、旧会话、旧 attempt、错 nonce 或重放均不会解除最终 ACK deadline。
- 不支持 1.1/1.2 混跑；升级和回滚都必须成对交付桌面插件/CDS 与 APK。
- 中央索引是桌面端的默认路由。`MobileSyncUseCentralIndex` 优先级必须为插件显式值 > 全局 Facade 值 > 默认 `true`，因此插件显式 `false` 不得被全局默认覆盖。路由只在重启后的新 session 中决定，attempt 中不做 local/central legacy 回退。
- CDS 内部 API protocol 必须为 `2`；Mobile wire protocol 为 `1.3`，两者不是同一版本字段。Mobile 消费逐 Topic NDJSON Pull。
- 桌面端插件版本硬编码于 plugin-manifest.json，移动端期望版本硬编码于 sync_service.rs 的 EXPECTED_PLUGIN_VERSION 常量。任何版本升级必须双端同步修改。
- 在 CI/CD 流程中，建议将 EXPECTED_PLUGIN_VERSION 与 plugin-manifest.json 的版本通过构建脚本自动对齐，避免人为遗漏。

协议 golden bundle 位于 `src-tauri/src/vcp_modules/sync/fixtures/protocol_1_2_golden.json`，SHA-256 为 `0aae238ea2699b4246cf78ecd4ee044b820a0586d3821224ad59b925e531f6c0`。错误契约 fixture 为同目录的 `error_contract_1_2_golden.json`，SHA-256 为 `434279b33a86a2206c1e4f47caccb4e72f05b2f9d48e093af95d5ebae6947adb`。配对桌面仓必须复制同一字节文件并校验相同摘要；完整错误字段、分类、传输外壳和扩展规则见 `16_Wire_1.3错误契约与排障规范.md`。

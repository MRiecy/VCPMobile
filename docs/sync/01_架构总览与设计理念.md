# 架构总览与设计理念

## 1. 引言

### 1.1 文档定位

本文档描述 VCPMobile 同步模块的当前架构，回答以下问题：

- 移动端与桌面端如何通过双通道（WebSocket + HTTP）协同完成数据同步？
- 三阶段同步协议（Three-Phase Sync Protocol）的每一步如何保证数据一致性？
- 各层代码分别负责什么？

## 2. 双端架构概览

### 2.1 整体分层架构

VCPMobile 同步系统采用**双轨三层（Double-Track 3-Tier）**物理隔离架构：Rust 核心层、Tauri IPC 桥接层、Vue 3 渲染层在移动端内部隔离；移动端与桌面端之间通过 WebSocket（信令）+ HTTP（数据）双通道隔离。

## 3. 同步的核心设计原则

### 3.1 会话单一所有权

`SyncState` 继续作为唯一协调者，但不再保存一个无人接收的永久 sender。当前生命周期合同是：

- `SyncSessionHandle { session_id, cancel_token, command_tx, join_handle }` 表示唯一活跃会话；`SyncCommandRouter` 只路由到当前 owner；
- start/stop 由同一个 lifecycle mutex 串行化。start 原子安装 generation、router 与 handle；重复 start 拒绝；
- stop 先推进 generation 并清空 router，再 cancel、发送 Cancel、await 旧主任务退出。旧会话完全退出前不能启动新会话；
- 状态、logger 与 ForegroundGuardian 的提交/清理都校验 `session_id`，旧 finally 无权清掉新 owner；
- 同一会话派生的 pull/diff 写任务进入 `SyncTaskTracker`。退出时先 cancel/join 已登记子任务，再 flush 会话写队列，避免 stop 返回后旧任务继续入队。

### 3.2 确定性哈希（Deterministic Hashing）

**原则**：所有实体的指纹必须通过**规范 JSON 序列化（Canonical JSON Serialization）** + **SHA-256** 生成，确保相同数据在任何时刻、任何设备上产生完全相同的哈希值。

**代码体现**：

- 三端按原始 key 的 UTF-8 字节序排序并进行 JSON string 转义；桌面端入口为 `computeDtoHash(dto, fields)`
- 移动端消息指纹绑定消息 ID、角色、名称、内容、时间戳、发言 Agent 与排序后的附件哈希；Topic/Owner 聚合继续绑定下级实体 ID，避免无身份集合碰撞
- 双哈希体系（V2）：`config_hash`（配置指纹）与 `content_hash`（子实体 Merkle 根）分离 (`sync_service.rs`)

**伪代码示例（规范序列化核心逻辑）**：

```rust
fn write_canonical(value: &Value, sink: &mut impl Write) {
    if let Value::Object(map) = value {
        let mut keys = map.keys().collect::<Vec<_>>();
        keys.sort_unstable_by(|a, b| a.as_bytes().cmp(b.as_bytes()));
        sink.write_all(b"{");
        for (index, key) in keys.into_iter().enumerate() {
            if index > 0 { sink.write_all(b","); }
            serde_json::to_writer(&mut *sink, key); // key 必须转义
            sink.write_all(b":");
            write_canonical(&map[key], sink);
        }
        sink.write_all(b"}");
    }
    // Array 保持输入顺序，标量按固定 JSON 字节写入。
}
```

生产路径把该 sink 直接连接 SHA-256，不构造完整 canonical String。规范序列化通过
“UTF-8 key 排序 + JSON key/value 转义 + 统一空值表示”消除了语言与字段顺序噪声。

### 3.3 Merkle 树聚合（Merkle Tree Aggregation）

**原则**：层级结构（Agent/Group → Topic → Message）采用 Merkle 树（Merkle Tree）风格的层级哈希聚合，父节点的哈希由所有子节点哈希有序拼接后计算得出。

**代码体现**：

```rust
// 伪代码：Agent Root Hash 计算 (sync_hash/HashAggregator)
fn compute_agent_root_hash(agent_id) -> String {
    let topic_leaves = get_topic_config_and_content_hashes(agent_id)
        .map(|topic| hash({ topicId, configHash, contentHash }));
    sha256_concat(sort(topic_leaves))
}
```

- Legacy 桌面端：全量刷新按完整 OwnerKey 聚合一次并写入 `owners.content_hash`；增量只刷新受影响 Owner，Manifest 直接读取提交根
- 移动端：`HashAggregator::bubble_topic_hash()` → `bubble_agent_hash()` (`sync_service.rs`)

**意义**：变更只向直接 Topic 和 Owner 冒泡，不重算无关 Owner。当前未存储分层 Merkle Tree：Topic 根依然线性扫描该 Topic 的活消息，Owner 根线性扫描其活 Topic。双哈希体系的价值是区分配置变更与内容变更，不是把根计算降为 O(log n)。

### 3.4 幂等操作（Idempotent Operations）

**原则**：所有可能因网络抖动而重试的写操作必须具备幂等性（Idempotency），即多次执行与一次执行效果相同。

**代码体现**：

| 机制 | 实现位置 | 说明 |
|------|---------|------|
| 幂等键（Idempotency Key） | HTTP Header `x-idempotency-key` | `SHA256(frame(domain, ownerType, ownerId, configHash, updatedAt))` |
| Phase3Tracker | `completed: Mutex<HashSet<TopicKey>>` | 同一完整 Topic 身份的完成状态用集合去重 (`sync_service.rs`) |
| DbWriteQueue 顺序消费 | `mpsc::UnboundedSender<DbWriteTask>` | 同一实体的多次写任务按队列顺序执行，后到达的任务覆盖先到达的 (`db_write_queue.rs`) |

**幂等键生成逻辑**：

```rust
fn generate_owner_push_idempotency_key(
    owner_type: OwnerType,
    owner_id: &str,
    config_hash: &str,
    updated_at: i64,
) -> String {
    let owner_type = owner_type.as_str();
    let version = updated_at.to_be_bytes();
    let mut hasher = Sha256::new();
    hasher.update(b"VCPMobileSync.OwnerPush.Idempotency.v1");
    for field in [
        owner_type.as_bytes(),
        owner_id.as_bytes(),
        config_hash.as_bytes(),
        version.as_slice(),
    ] {
        hasher.update((field.len() as u64).to_be_bytes());
        hasher.update(field);
    }
    finalize_sha256_hex(hasher)
}
```

**语义**：Key 不读取生成时的当前时间。同一 Owner 配置快照的网络重试复用相同键；
配置内容或持久化 `updatedAt` 版本变化都会生成新键，正常的 `A → B → A` 回退不会误用
第一次 A 的缓存。桌面端内存缓存的 5 分钟 TTL 是唯一过期所有者，过期后相同 Key 可
再次执行。`updatedAt` 仍是毫秒时间而非严格单调 revision，其同值边界见冲突文档 §7.3。

### 3.5 软删除（Soft Deletion）

**原则**：删除操作不物理移除数据，而是标记 `deleted_at` 时间戳，使删除信息本身可同步。

**代码体现**：

- 移动端：`DeleteExecutor::soft_delete_agent/group/topic/avatar()` (`sync_service.rs`)
- Diff 动作使用 `DiffAction::Delete { deleted_at }` 和 `DiffAction::PushDelete { deleted_at }` 传播墓碑。
- 桌面端：`deleteEntity()` / `deleteMessage()` 写入删除索引 (`VCPMobileSync/index.js`)
- 安全期清理：Mobile 生命周期任务每日清理超过 30 天的已删消息正文与渲染缓存，但保留墓碑身份；Desktop 同步插件没有定时硬删墓碑任务

**同步语义**：

```
Mobile 有墓碑、Desktop 未删除  →  PUSH_DELETE
Desktop 有墓碑、Mobile 未删除 →  PULL_DELETE
双方均有墓碑                    →  无操作
```

`deletedAt` 用于稳定记录和幂等重放，不参与 live 数据的 LWW；墓碑存在即删除优先。

### 3.6 有界流式处理

消息 Pull 按 NDJSON 帧字节数占用在途预算，总预算为 32 MiB。数据库写入统一进入 `DbWriteQueue`，避免并发解析直接争用 SQLite 写锁。

## 4. 三阶段同步协议

### 4.1 协议总览

同步会话（Sync Session）是一次完整的端到端数据对齐过程，由移动端主动发起，通过 WebSocket 连接桌面端插件，按严格顺序执行以下相位（Phase）：

| 相位 | 名称 | 核心目标 | 数据粒度 | 代码触发点 |
|------|------|---------|---------|-----------|
| Phase 1 | Owner Metadata | 同步 Agent、Group、Avatar | 实体级 | `SyncCommand::StartManualSync` |
| Phase 2 | Topic Metadata | 拉取/推送有变动的 Owner 下的 Topic 配置 | Topic 级 | `PipelineCommand::StartTopicMetadata` |
| Phase 2.5 | Topic Validation (V2) | 双哈希批量比对，精准筛选需同步消息的 Topic | Hash 级 | `PipelineCommand::StartTopicValidation` |
| Phase 3 | Messages | 逐 Topic 同步消息内容 | 消息级 | `PipelineCommand::StartMessages` |
| Finalize | 收尾 | 全局 Hash 冒泡、计数更新、关闭连接 | 事务级 | `SyncCommand::Finalize` |

### 4.2 阶段推进

`run_sync_session` 持有连接、attempt、阶段门和最终状态，是同步会话的唯一状态所有者。`SyncPipeline` 不保存第二份状态，只把三个阶段转换命令送回主事件循环：

| 完成条件 | 下一命令 |
|---|---|
| Owner 与 Avatar 两个波次均完成并 drain | `StartTopicMetadata` |
| Topic Manifest 完成并 drain | `StartTopicValidation` |
| Topic 双 Hash 结果完成 | `StartMessages` |
| 所有消息 Topic 完成 | `SyncCommand::Finalize` |

前端阶段由 `vcp-sync-progress` 表达；完成态只由本地 Finalize 成功后的精确 `PHASE_ACK` 发布。

### 4.4 Phase 1: Owner Metadata 详解

**目标**：同步 Agent、Group、Avatar 三类实体的配置与存在性。

**流程**：

1. **Manifest 构建**：`Phase1Metadata` 从 Agent/Group 已提交表行联合构建 Owner Manifest，并独立构建 Avatar Manifest。
2. **Owner 波次**：先发统一 Owner Manifest，完整收取 Diff、执行任务并 drain 写队列。
3. **Avatar 波次**：仅在 Owner 持久化后发 Avatar，同样经过完整响应、任务归零和 drain 完成门。
4. **Diff 任务**：各波次内将 Diff 分类为 pull、push、delete；任一 HTTP、DB 或协议失败终止 attempt。
5. **靶向 Topic**：Desktop 以 `contentHashMismatch` 标出 Owner 子树差异。

**任务分类策略**：移动端收到 Diff 后按三类批处理：batch_pull（Owner chunk=50, Topic chunk=1000）、push_topics_to_fetch（先查 DB 再推送）、other_items（Avatar 单独处理）(`sync_service.rs`)

**Diff 动作语义**：

| 动作 | 移动端行为 | 桌面端行为 |
|------|-----------|-----------|
| `SKIP` | 无操作 | 无操作 |
| `PULL` | HTTP GET 拉取实体数据 | 返回实体 DTO |
| `PUSH` | HTTP POST 推送实体数据 | 写入本地文件/索引 |
| `DELETE` | 本地 soft_delete_* | 已在远程删除，无需动作 |
| `PUSH_DELETE` | 本地落墓碑后发送 `SYNC_ENTITY_DELETE` | 幂等标记桌面端删除索引 |

### 4.5 Phase 2: Topic Metadata 详解

**目标**：仅同步**内容有变动的 Owner** 下的 Topic 配置，而非全量 Topic。

**V2 改进**：在 V1 中，Topic Metadata 是全量比对；在 V2 中，利用 Phase 1 筛选出的 `changed_owners`，移动端仅构建这些 Owner 下的 Topic Manifest：

```rust
Phase1Metadata::build_targeted_topic_manifest(&db.pool, &changed_owners)
```

这极大减少了 Phase 2 的数据传输量，尤其是当用户拥有大量 Topic 但仅少数 Agent/Group 有变更时。

### 4.6 Phase 2.5: Topic Validation 详解

**目标**：在消息同步前，通过**双哈希（Dual-Hash）**精准判断哪些 Topic 真正需要进入 Phase 3。

**问题背景**：V1 中 Topic 聚合哈希变化即触发全量消息同步，但配置变更（如 title）可能不影响消息。

**V2 解决方案**：

Mobile 发送 `SYNC_TOPIC_DIFF_REQUEST`，携带每个 Topic 的双 Hash：

```json
{
  "type": "SYNC_TOPIC_DIFF_REQUEST",
  "hashes": {
    "topic_001": { "configHash": "abc...", "contentHash": "def..." },
    "topic_002": { "configHash": "ghi...", "contentHash": "jkl..." }
  }
}
```

桌面端逐 Topic 比对：
- `configHash` 不同 → 配置需同步（Phase 2 已处理）
- `contentHash` 不同 → **消息需同步**，加入 `changedTopics`

桌面端返回：

```json
{ "type": "SYNC_TOPIC_DIFF_RESULT", "changedTopics": [{"ownerType":"agent","ownerId":"agent-a","topicId":"topic_001"}] }
```

**意义**：Phase 3 的输入从"所有 Topic"缩小到"消息真正有差异的 Topic"，避免大量无效的消息哈希比对。

### 4.7 Phase 3: Messages 详解

**目标**：同步真正有差异的 Topic 下的消息。`build_diff_batches()` 同时遵守 `MAX_MESSAGES_PER_BATCH = 10000` 与 8 MiB 实际序列化字节预算，保证同一 Topic 不跨批次：

**执行顺序**：桌面端必须为当前批每个 Topic 返回严格判别联合。`ok:false`、缺失/重复/额外 Topic 或字段错类型都立即终止 attempt。`ok:true` 时移动端依次应用桌面墓碑、Pull 桌面获胜消息、等待写队列落库，再 Push 该 Topic 的完整最终视图。Pull 或落库失败时不执行 Push。

当前批的 Pull、Push 与 DB 收尾全部成功后才发送下一批，保证最多只有一个 Phase 3 批次在途。附件只随消息传输元数据与内容 Hash，二进制保留在各端本机 CAS。

**Phase3Tracker 完成判定**：

```rust
struct Phase3Tracker {
    completed: Mutex<HashSet<String>>, // 已完成的 Topic 集合
    modified:  Mutex<HashSet<String>>, // 实际发生数据变更的 Topic 集合
    total: AtomicUsize,
}
```

- `mark_modified()`：在 Push/Pull 成功后调用，记录该 Topic 需要在 Finalize 阶段重新冒泡哈希
- `mark_completed()`：首次标记返回 true，重复标记返回 false，彻底杜绝 `AtomicU32` 双重递减导致的下溢
- 当 `completed.len() == total.load()` 时，自动触发 `SyncCommand::Finalize`

### 4.8 Finalize 详解

**目标**：完成所有数据写入后，确保层级哈希一致性，并向前端报告完成。

**流程**：

1. **DbWriteQueue Flush**：强制落盘所有缓冲的写任务 (`sync_service.rs`)
2. **批量更新 Topic 派生数据**：一条 SQL 更新所有受影响 Topic 的 `msg_count`，不改动配置时间 (`sync_finalize.rs`)
3. **层级冒泡（Hash Bubble Up）**：
   - 对每个修改过的 Topic：`HashAggregator::bubble_topic_hash()`
   - 收集受影响的 Agent/Group：`HashAggregator::bubble_agent_hash()` / `bubble_group_hash()`
4. **事务提交**：所有冒泡操作在一个 SQLite 事务内完成
5. **最终提交帧**：发送 `PHASE_COMPLETED { phase: "messages", sessionId, attemptId, nonce }`，等待桌面端精确回显的 `PHASE_ACK`。
6. **前端事件与连接关闭**：仅在 ACK 原子消费且最终 drain 成功后，发射 `vcp-sync-completed` 并主动关闭 WebSocket。30 秒内未收到当前四元身份的 ACK 则进入错误终态。

## 7. 附录：术语表

| 英文术语 | 中文翻译 | 定义 |
|---------|---------|------|
| Sync Session | 同步会话 | 一次从连接到完成的完整同步过程 |
| Owner | 拥有者 | Agent 或 Group，作为 Topic 的父级容器 |
| Manifest | 清单 | 按 Owner、Topic、Avatar 分型的 live/墓碑状态集合；每项携带完整复合身份 |
| Diff | 差异 | 两端 Manifest 比对后产生的动作列表 |
| Dual-Hash / 双哈希 | 双哈希 | V2 特性，Topic 同时维护 configHash 和 contentHash |
| Hash Bubble Up | 层级冒泡 | 子实体哈希变化后逐层向上重新计算父哈希 |
| Phase Gate | 相位门 | 用 `HashSet<String>` 确保每个相位推进命令仅执行一次 |
| Idempotency Key | 幂等键 | 对 Owner 类型、ID、configHash 与持久化 updatedAt 做定长分帧后得到的 SHA-256 值 |
| Targeted Sync | 靶向同步 | V2 特性，仅同步有变动的 Owner 的 Topic |

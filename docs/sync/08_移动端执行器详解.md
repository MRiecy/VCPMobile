# 移动端执行器详解

## 1. 引言

`sync_executor` 把 Pipeline 的差异决策转换为 HTTP 请求和本地数据库操作。

本模块由三个执行器（Executor）组成，各自负责单向或双向的数据流动：

| 执行器 | 职责 | 数据流向 | 核心源文件 |
|--------|------|----------|-----------|
| **PullExecutor** | 从桌面端拉取数据到移动端 | 桌面端 → 移动端 | `pull_executor.rs` |
| **PushExecutor** | 将移动端数据推送到桌面端 | 移动端 → 桌面端 | `push_executor.rs` |
| **DeleteExecutor** | 处理双向删除传播 | 双向（以移动端为准触发） | `delete_executor.rs` |

实体按 Diff 动作执行 Pull、Push 或 Delete。Phase 3 对每个 Topic 按桌面墓碑、Pull、写队列落库、整 Topic Push 的顺序收敛；Pull 或落库失败时不执行 Push。

## 2. PullExecutor

### 2.1 职责边界

`PullExecutor`（拉取执行器）负责将桌面端（Desktop）的最新数据复制到移动端本地数据库。其处理范围涵盖：

- **实体（Entity）**：Agent、Group、AgentTopic、GroupTopic
- **消息（Message）**：按 Topic 分帧的流式消息批量下载
- **头像（Avatar）**：Agent / Group 的二进制头像图片
- **附件（Attachment）**：消息携带的附件关系元数据；拉取时仅解析 Hash 并映射本机已有 CAS 文件

所有拉取到的数据**不直接写入数据库**，而是通过 `DbWriteQueue`（数据库写入队列）异步排队，以串行化 SQLite 写入、避免 WAL（Write-Ahead Logging）模式下的并发锁竞争。

### 2.2 HTTP 调用链

#### 2.2.1 批量实体下载

```
POST /api/mobile-sync/entities/pull
Body: { "items": [{ "entityType": "owner|topic", "ownerType": "...", "ownerId": "...", "topicId": "..." }] }
```

服务端返回 `{results}`；逐项回显完整身份和 `ok/data/error`。执行器按 `entityType+ownerType` 选择具体 DTO 并提交写队列。

协议外壳不再使用 `agent_topic/group_topic`；具体 DTO 仍由 `ownerType` 选择。

#### 2.2.2 头像下载

Avatar 使用 `GET /avatars/pull?ownerType=&ownerId=`；网络波动与其他 HTTP 数据面共用 session 级整 attempt 重试，不维护第二套头像重试循环。

#### 2.2.3 流式消息批量下载

```
POST /api/mobile-sync/messages/pull
Body: { "topics": [{ "ownerType":"...", "ownerId":"...", "topicId":"...", "messageIds": ["..."] }] }
```

对应实现为 `PullExecutor::pull_messages_batch`（`pull_executor.rs`）。这是消息同步的核心路径，具备以下技术特征：

| 特征 | 实现细节 |
|------|----------|
| 传输格式 | **NDJSON**（Newline Delimited JSON，换行分隔 JSON），逐 Topic 分帧 |
| 流式消费 | 使用 `res.bytes_stream()` 逐 chunk 读取，不等待完整响应 |
| 并发处理 | 按原始帧字节加权占用 32 MiB 在途预算，permit 在 spawn 前获取 |
| 资源预算 | 单帧 32 MiB、总响应 256 MiB、消息总数 100000；响应 topic 必须与请求精确一一对应 |
| 错误语义 | `kind:streamError`、Topic `ok:false`、畸形/缺失/重复/额外 Topic 或落库错误都会失败 attempt |

**NDJSON 解析流程**：

```
while chunk = stream.next():
    buffer.extend(chunk)
    while line = buffer.extract_line():
        topic_data = parse_json(line)
        if topic_data.kind == "streamError" or topic_data.ok == false:
            fail_current_attempt(topic_data.topicId)
        
        // 通过 Semaphore 获取许可后 spawn 异步任务
        permit = sem.acquire_owned().await
        spawn process_topic_messages(topic_data)
```

#### 2.2.4 消息处理管线

`process_topic_messages`（`pull_executor.rs`）是 PullExecutor 中最复杂的内部函数，承担从原始 JSON 到可持久化消息的完整转换。其管线分为 4 个阶段：

| 阶段 | 操作 | 优化策略 |
|------|------|----------|
| 1. 入站协议规范化 | 在 DTO 前统一 flat/nested hash，校验消息 id/role/timestamp，并剥离桌面内部路径字段 | 无 hash/非法/冲突附件仅省略并计入有界 warning，消息保留 |
| 2. 附件路径预查与状态填充 | hash 分块查询 Mobile CAS；真实文件存在为 `ready`，否则保留关系为 `desktop_only` 且路径为空 | 不伪造 `file://`，不覆盖同 hash 的真实本地路径 |
| 3. 预渲染 | 对每个消息调用 `MessageRenderCompiler::compile` + `serialize`；消息正文保持明文 TEXT | `catch_unwind` 防 panic |
| 4. 提交写入队列 | 组装 `DbWriteTask::TopicMessages` 提交到 `DbWriteQueue` | `skip_bubble = true` 避免同步期间重复冒泡 |

**强类型反序列化（Type-Safe Deserialization）**：

`MessageSyncDTO` 是网络契约与核心实体的边界。NDJSON 中的消息先反序列化为该 DTO，再经 `From<MessageSyncDTO> for ChatMessage` 转换；`blocks` 设为 `None`，由消息加载路径按需生成渲染缓存。

DTO 前的 canonicalizer 统一附件 Hash、时间戳和 frame Topic 身份，并剥离桌面内部路径与发送方 `contentHash`。规范化后进入 `MessageSyncDTO`，附件 `hash` 为必填字段：

```rust
#[derive(serde::Deserialize)]
struct TopicNDJSONFrame {
    topic_id: String,
    owner_type: String,
    owner_id: String,
    messages: Vec<MessageSyncDTO>,
    error: Option<WireSyncError>,
}
```

- `MessageSyncDTO` 隔离网络契约与核心实体。
- 接收端依据规范消息重新计算指纹，不信任发送方派生 Hash。
- 单个 Topic 要么完整规范化并提交，要么失败当前 attempt，不保留逐消息失败计数。

### 2.3 重试机制

执行器不各自维护重试循环。HTTP 传输中断编码为 `HTTP_TRANSPORT_FAILED` 返回会话层；会话完成取消子任务、写队列 drain 和派生 Hash 修复后，使用与 WebSocket 相同的 3 个退避槽重新执行完整 attempt。响应畸形、预算、数据和存储错误不进入该路径。

### 2.4 并发控制

`pull_messages_batch` 的并发控制由两层机制组成：

| 层级 | 机制 | 限流值 | 作用 |
|------|------|--------|------|
| 第一层 | `tokio::sync::Semaphore` | 20 | 限制同时处理 Topic 的并发任务数 |
| 第二层 | `DbWriteQueue` 内部串行化 | 1 | SQLite 写入天然串行，避免 WAL 锁竞争 |

**网络感知调节**：当前版本尚未实现基于网络类型（WiFi / 5G / 4G）的动态并发度调整。在 WiFi 环境下，Semaphore 的 20 许可通常不会成为瓶颈；但在弱网蜂窝环境下，过大的并发可能导致请求超时风暴。

### 2.5 批量操作的归口优化

PullExecutor 的归口优化体现在三个层面：

1. **实体层**：`pull_entities_batch` 将多个 Agent / Group / Topic 的下载请求聚合为单次 HTTP POST，避免多次 TLS 握手。
2. **消息层**：`pull_messages_batch` 将多个 Topic 的消息请求聚合为单次 NDJSON 流式响应，利用 HTTP/1.1 或 HTTP/2 的持久连接。
3. **附件路径层**：`process_topic_messages` 在解析前批量查询所有附件的本地路径，将 N 次 SQL 查询降为 1 次。

### 2.6 核心函数输入输出签名表

| 函数 | 输入参数 | 输出 | 所在文件 |
|------|----------|------|----------|
| `PullExecutor::pull_entities_batch` | `app`, `client`, `http_url`, `sync_token`, `requests: Vec<Value>`, `write_queue` | `Result<(), String>` | `pull_executor.rs` |
| `PullExecutor::pull_avatar` | `app`, `client`, `http_url`, `sync_token`, `owner_type`, `owner_id`, `write_queue` | `Result<(), String>` | `pull_executor.rs` |
| `PullExecutor::pull_messages_batch` | `app`, `client`, `http_url`, `sync_token`, `requests: &[(String, Vec<String>)]`, `write_queue` | `Result<Vec<BatchPullResult>, String>` | `pull_executor.rs` |
| `process_topic_messages` | `app`, `TopicKey`, `messages`, `write_queue`, `prerender_enabled` | `Result<usize, String>` | `pull_executor.rs` |

## 3. PushExecutor

### 3.1 职责边界

`PushExecutor`（推送执行器）负责将移动端本地产生或修改的数据上传到桌面端。其处理范围涵盖：

- **实体**：Agent、Group 的配置变更
- **消息**：按 Topic 聚合的聊天记录
- **头像**：Agent / Group 的头像图片
- **附件元数据**：随消息携带名称、MIME、大小、内容 Hash 和提取文本；不上传二进制

与 PullExecutor 不同，PushExecutor **直接读取本地数据库**（通过 `agent_service`、`group_service`、`message_service`），而非接收外部传入的数据。

### 3.2 HTTP 调用链

#### 3.2.1 Topic 元数据批量上传

```
POST /api/mobile-sync/entities/push
Body: { "items": [{ "entityType":"topic", "ownerType":"...", "ownerId":"...", "topicId":"...", "data":{...} }] }
```

对应实现为 `PushExecutor::push_entities_batch`（`push_executor.rs`）。该端点只承担 Phase 2 Topic 元数据，完整 Owner + Topic 身份缺一不可。

#### 3.2.2 Owner 单实体上传

| 方法 | 端点 | 特殊头 |
|------|------|--------|
| `push_agent` | `POST /entities/push` | `x-idempotency-key` |
| `push_group` | `POST /entities/push` | `x-idempotency-key` |

Owner 与 Topic 共用 `/entities/push` 外壳；Desktop 内部仍让 Owner 单独写配置、Topic 按父 config 分组。Owner 的幂等键绑定 DTO `configHash` 与对应持久化 `updatedAt` 版本。

```
fn generate_owner_push_idempotency_key(owner_type, owner_id, config_hash, updated_at):
    fields = frame_u64_be(owner_type, owner_id, config_hash, updated_at)
    hash = SHA256("VCPMobileSync.OwnerPush.Idempotency.v1" + fields)
    return hex(hash)
```

每个字段均带 `u64` 大端长度前缀。Key 不读取当前时间；相同配置快照跨分钟重试仍稳定，
配置内容或 `updatedAt` 版本变化会生成新 Key。桌面端 5 分钟 TTL 负责缓存过期；
`updatedAt` 沿用现有毫秒级 LWW 时间，不是额外引入的单调序号。

#### 3.2.3 头像上传

```
POST /api/mobile-sync/avatars/push?ownerType={owner_type}&ownerId={owner_id}
Content-Type: {mime_type}
Body: <binary image_data>
```

对应实现为 `PushExecutor::push_avatar`（`push_executor.rs`）。直接从 `avatars` 表读取 `image_data` 和 `mime_type`，以原始二进制形式 POST。

#### 3.2.4 流式消息批量上传

```
POST /api/mobile-sync/messages/push
Content-Type: application/x-ndjson
Body: <NDJSON lines>
```

对应实现为 `PushExecutor::push_messages_batch`（`push_executor.rs`）。这是消息推送的核心路径，完整流程如下：

```
输入: topic_ids[]

1. 逐 Topic 开启稳定 SQLite 读事务，校验 live Owner，并一次统计 live 消息与墓碑数量
2. 使用 `(timestamp, msg_id)` keyset 分页，每页 100 条，避免一次 `fetch_all` 整段历史
3. 对每个 topic:
     - 直接从 SQLite 投影统一 `MessageSyncDTO`
     - 按 `attachment_order` 附加关系元数据
     - 生成携带完整 Topic 身份的 NDJSON 行
4. 有界 writer 按实际序列化字节强制单 Topic 32 MiB 上限，再组成不超过 8 MiB 的请求块；attempt 总量最大 256 MiB
5. 严格解析 NDJSON 响应；缺失、重复、额外 topic 或错误字段类型立即失败
6. 每行同时携带该 Topic 的 `deletedMessages`，与 live 最终视图共用一次提交结果
7. 附件只作为消息元数据与内容 Hash 序列化，不读取或上传本机文件
8. Topic 提交失败写入 `PushBatchResult`，当前 attempt 终止
```

消息 Wire 合同使用一套 canonical `MessageSyncDTO`；角色与 Owner 差异仍由 `role`、`agentId`、`groupId`、`topicId`、`isGroupMessage` 等实际字段表达。旧三种类型只是 Push 专用的无标签投影壳，Pull 与桌面端本来就使用统一结构。`avatarColor` 不是 Mobile 出站投影的一部分。

### 3.3 与 DbWriteQueue 的交互

PushExecutor **不直接操作** `DbWriteQueue`，它的数据源是已经由前端或本地逻辑写入数据库的"稳定状态"。两者的交互关系是间接的：

```
前端操作 → DbWriteQueue 写入 SQLite → 同步服务检测到变更 → PushExecutor 读取并上传
```

这意味着推送的数据总是数据库中已提交的版本，不存在"读取未提交"的脏读问题。

### 3.4 批量操作的归口优化

PushExecutor 的归口优化体现在：

1. **实体层**：`push_entities_batch` 聚合多个实体为单次 HTTP POST。
2. **消息层**：`push_messages_batch` 将多个 Topic 的消息编码为 NDJSON，单次上传。

### 3.5 核心函数输入输出签名表

| 函数 | 输入参数 | 输出 | 所在文件 |
|------|----------|------|----------|
| `PushExecutor::push_agent` | `app`, `client`, `http_url`, `sync_token`, `agent_id` | `Result<(), String>` | `push_executor.rs` |
| `PushExecutor::push_group` | `app`, `client`, `http_url`, `sync_token`, `group_id` | `Result<(), String>` | `push_executor.rs` |
| `PushExecutor::push_entities_batch` | `app`, `client`, `http_url`, `sync_token`, `items: Vec<Value>` | `Result<(), String>` | `push_executor.rs` |
| `PushExecutor::push_avatar` | `app`, `client`, `http_url`, `sync_token`, `owner_type`, `owner_id` | `Result<(), String>` | `push_executor.rs` |
| `PushExecutor::push_messages_batch` | `app`, `client`, `http_url`, `sync_token`, `topic_keys: &[TopicKey]` | `Result<Vec<PushBatchResult>, String>` | `push_executor.rs` |
| `generate_owner_push_idempotency_key` | `owner_type`, `owner_id`, `config_hash`, `updated_at` | `String` | `push_executor.rs` |

## 4. DeleteExecutor

### 4.1 职责边界

`DeleteExecutor` 是远端删除动作的 Mobile 适配层。它验证完整身份与 `deletedAt`，再复用 Agent、Group、Topic 和 Message 的领域删除函数；Avatar 墓碑在本模块落库。它不直接发起 HTTP，删除传播由 Manifest、`SYNC_ENTITY_DELETE` 或 Phase 3 消息墓碑负责。

协议没有恢复操作。墓碑是单调的，普通 upsert 不能清除它。

### 4.2 级联删除逻辑

级联语义属于领域删除函数，不由同步层再实现一套：

| 操作 | 终态 |
|------|------|
| `soft_delete_agent` / `soft_delete_group` | 复用 Owner 领域删除，级联 Topic、Message 及无效附属状态 |
| `soft_delete_topic` | 复用 Topic 删除事务，级联 Message、附件关系、render cache、FTS 与生成态 |
| `soft_delete_message` | 复用 Message 删除事务，清理该消息的可重建状态并更新聚合 Hash |
| `soft_delete_avatar` | 写入或保留完整 Owner 身份的 Avatar 墓碑 |

远端墓碑即使本地从未有过该实体，也会落成 tombstone-only 行，使下一轮 Manifest 稳定为 no-op。

### 4.3 安全期清理

`cleanup_old_deleted_records(app, days)` 不删除 Agent、Group、Topic 或 Message 墓碑行。它只处理超过安全期的已删消息：

- 删除对应 `render_cache`；
- 将大段消息正文置为 `[已清空]`；
- 保留完整消息主键、角色与 `deleted_at`，防止跨端幽灵复活。

生命周期管理器在启动后延迟执行，并以 24 小时为间隔重试；当前安全期为 30 天。

### 4.4 核心函数输入输出签名表

| 函数 | 输入参数 | 输出 | 所在文件 |
|------|----------|------|----------|
| `DeleteExecutor::soft_delete_agent` | `app`, `agent_id`, `deleted_at` | `Result<(), String>` | `delete_executor.rs` |
| `DeleteExecutor::soft_delete_group` | `app`, `group_id`, `deleted_at` | `Result<(), String>` | `delete_executor.rs` |
| `DeleteExecutor::soft_delete_topic` | `app`, `TopicKey`, `deleted_at` | `Result<(), String>` | `delete_executor.rs` |
| `DeleteExecutor::soft_delete_message` | `app`, `MessageKey`, `deleted_at` | `Result<(), String>` | `delete_executor.rs` |
| `DeleteExecutor::soft_delete_avatar` | `app`, `owner_type`, `owner_id`, `deleted_at` | `Result<(), String>` | `delete_executor.rs` |
| `DeleteExecutor::cleanup_old_deleted_records` | `app`, `days: i64` | `Result<(), String>` | `delete_executor.rs` |

## 5. Executor 间的协作

### 5.1 阶段执行顺序

Owner 与 Topic 元数据依 Desktop Diff 逐项执行 `PULL` / `PUSH` / `DELETE` / `PUSH_DELETE`，不存在本地 dirty 表或先全量 Pull 再全量 Push 的通用阶段。

Phase 3 才有固定的 Topic 内合并顺序：

1. 应用 Desktop 消息墓碑。
2. Pull Desktop 时间或平局 Hash 获胜的消息。
3. `DbWriteQueue::flush()` 确保 Pull 落盘。
4. 若 `pushTopic=true`，Push Mobile 已合并的整 Topic 最终视图与墓碑。

Pull 或 drain 失败时终止 attempt，不执行后续 Push。附件只随获胜消息投影元数据，没有缺失二进制上传步骤。

### 5.2 Delete 的执行与传播

| 触发场景 | 执行的操作 | 调用方 |
|----------|-----------|--------|
| Mobile 用户删除 Owner / Topic / Message | 领域服务事务内落墓碑，在线时发送 `SyncCommand::Notify*` | Agent / Group / Topic / Message 领域服务 |
| Desktop Diff 返回删除动作 | 对应的 `DeleteExecutor::soft_delete_*` | 同步服务 |
| 应用启动 / 定时任务 | `cleanup_old_deleted_records(30)` | 生命周期管理器 |

**删除传播到桌面端的流程**：

```
Mobile 领域删除事务落墓碑
    → 在线会话通过 SYNC_ENTITY_DELETE 低延迟通知 Desktop
    → 若当时离线，下一轮 Manifest / Phase 3 仍会重放墓碑
    → Desktop 墓碑通过后续 Diff 返回 Mobile，最终成为稳定 no-op
```

### 5.3 批量操作的协调

三个执行器的批量操作在数据层面通过 `DbWriteQueue` 间接协调：

| 执行器 | 批量操作 | DbWriteQueue 交互 | 并发模型 |
|--------|----------|-------------------|----------|
| PullExecutor | `pull_entities_batch` | 提交 `DbWriteTask::AgentBatch`, `GroupTopicBatch` 等 | 并行解析，串行写入 |
| PullExecutor | `pull_messages_batch` | 提交 `DbWriteTask::TopicMessages` | 32 MiB 加权帧预算限制在途解析 |
| PushExecutor | `push_entities_batch` | 无直接交互（读取已提交数据） | 单次 HTTP 请求 |
| PushExecutor | `push_messages_batch` | 无直接交互 | 分页序列化并按 8 MiB 请求块发送 |
| DeleteExecutor | 各 `soft_delete_*` | 直接执行 SQL（事务内） | 串行（SQLite 特性） |

## 6. 错误处理策略

### 6.1 单个操作失败时的回退

#### 6.1.1 Pull 侧回退

| 失败场景 | 回退行为 | 影响范围 |
|----------|----------|----------|
| `pull_entities_batch` HTTP 或逐项失败 | 返回 `Err(String)` 并终止当前 attempt | 当前实体批次 |
| `pull_avatar` 网络失败 | 返回 `HTTP_TRANSPORT_FAILED`，由会话重跑完整 attempt | 当前 attempt |
| `pull_avatar` MIME/解码失败 | 返回 `Err`，不自动重试 | 单个头像 |
| `pull_messages_batch` 流级错误 | 解析 `kind:streamError` 的完整 Wire 1.4 对象 | 整个消息批次 |
| `pull_messages_batch` 单 Topic 错误 | 解析 `kind:topic,ok:false,error` 并终止 attempt | 当前 attempt |
| `process_topic_messages` 解析失败 | `TopicNDJSONFrame` 强类型反序列化消除此类失败；若发生则整个 Topic 失败 | 整个 Topic |

**关键设计**：传输仍可逐 Topic 处理，但完成语义是严格的。只要有一个 Topic 失败，调用方就发出终态 error、取消并 join 当前 attempt；已落盘 Topic 在 attempt 收口时重算派生 Hash，绝不发 `vcp-sync-completed`。

#### 6.1.2 Push 侧回退

| 失败场景 | 回退行为 | 影响范围 |
|----------|----------|----------|
| `push_entities_batch` HTTP 失败 | 返回 `Err(String)` | 整个实体批次 |
| `push_messages_batch` HTTP 失败 | 返回 `Err(String)` | 整个消息批次 |
| 单 Topic 上传失败（`ok=false`） | 记录到 `PushBatchResult`，已完成 Topic 不回滚，但当前 attempt 失败 | 当前 attempt |

**幂等性兜底**：单 Owner Push 使用 `x-idempotency-key`；消息按 Topic/Message ID 幂等合并，墓碑随 Topic 一起重放。

### 6.2 批量操作中部分失败的隔离

**Pull 侧**：`pull_messages_batch` 返回 `Vec<BatchPullResult>`，每个元素包含完整 Topic 身份、`success`、附件元数据告警数和 `error`。任一失败都会终止当前 attempt。

**Push 侧**：`push_messages_batch` 返回 `Vec<PushBatchResult>`，每个元素包含完整 Topic 身份、`success` 和 `error`。消息墓碑失败按所属 Topic 传播；调用方随后终止 attempt。

```
// 部分失败隔离的调用范式
let results = PullExecutor::pull_messages_batch(...).await?;
for r in results:
    if !r.success:
        failed_topics.push(r.topic_id)
        log_error(r.error)
    else:
        success_topics.push(r.topic_id)

// failed_topics 可在下一轮同步中单独重试
```

### 6.3 网络中断时的状态保留

同步执行器在网络中断场景下遵循以下状态保留原则：

| 层级 | 状态保留机制 | 说明 |
|------|-------------|------|
| HTTP 请求层 | `reqwest::Client` 内部连接池 | 短连接，无长连接状态 |
| 数据解析层 | 无中间状态 | `pull_messages_batch` 的 NDJSON 解析是流式的，网络中断会导致整个批次失败，已处理的部分已提交到 `DbWriteQueue` |
| 数据库层 | SQLite 事务 + WAL | `DeleteExecutor` 的每个操作都在显式事务内；`PullExecutor` 通过 `DbWriteQueue` 串行写入，天然原子 |

**重要约束**：当前执行器的设计**不保证跨进程重启的断点续传**。如果应用在网络中断后被系统回收或用户手动关闭，下次启动时将从头开始新的同步周期。这是由移动端的资源受限环境决定的——维护复杂的断点状态机会增加内存和存储开销。

## 7. 设计决策与权衡

### 7.1 为什么使用 DbWriteQueue 而非直接写入

`PullExecutor` 和 `process_topic_messages` 选择将数据提交到 `DbWriteQueue` 而不是直接执行 `INSERT`/`UPDATE`，这一决策基于以下考量：

| 方案 | 优点 | 缺点 | 本模块选择 |
|------|------|------|-----------|
| 直接写入 | 简单、时序直观 | SQLite 并发写入会触发 WAL 锁竞争，导致 `database is locked` | ❌ |
| `DbWriteQueue` 串行写入 | 消除锁竞争、统一事务边界、便于日志追踪 | 引入异步延迟，数据非即时落盘 | ✅ |
| 批量事务写入 | 性能最优 | 实现复杂，失败回退成本高 | 部分采用（Queue 内部） |

`DbWriteQueue` 本质上是一个单消费者（Single-Consumer）的异步通道，所有写入任务按提交顺序执行。这种"漏斗"设计牺牲了极低的写入延迟，换取了移动端恶劣环境下的稳定性。

### 7.2 流式 NDJSON vs 传统 JSON 数组

`pull_messages_batch` 和 `push_messages_batch` 均采用 NDJSON 格式，而非传统的 JSON 数组 `[]`。这一选择的权衡如下：

| 维度 | NDJSON | JSON Array |
|------|--------|------------|
| 内存占用 | 低（逐行解析，无需缓冲整个响应） | 高（需完整加载到内存） |
| 解析启动延迟 | 零（收到第一行即可开始处理） | 需等待 `]` 闭合 |
| 错误隔离 | 可精确指出失败 Topic；任一畸形帧仍 fail-closed 终止 attempt | 整体解析失败 |
| 服务端实现 | 需支持流式序列化 | 简单（一次性 `json.dumps`） |
| 带宽效率 | 略低（每行重复字段名） | 略高（可共享结构） |

对于移动端而言，**内存占用**和**启动延迟**是决定性因素。一条 Topic 可能包含数千条消息，传统 JSON 数组很容易导致 OOM（Out of Memory，内存溢出）。

### 7.3 Push 为什么必须检查逐项结果

所有数据面操作必须同时满足 HTTP 成功、响应合法、逐项 `ok:true` 和完整身份回显。HTTP 非 2xx、`ok:false` 与 NDJSON 错误帧都必须携带完整 Wire 1.4 错误对象。

### 7.4 软删除的存储成本权衡

`DeleteExecutor` 采用软删除而非即时物理删除，是为了支持以下场景：

- **跨端传播**：墓碑让离线删除能在下一次同步继续传播。
- **删除优先**：残留物理文件或旧快照不能隐式复活同 ID 实体。
- **安全期清理**：正文和可重建缓存可延后清理，而墓碑身份继续保留。

代价是墓碑行会长期保留。`cleanup_old_deleted_records` 只在 30 天安全期后清空已删消息正文和渲染缓存，不删除墓碑身份，也不提供恢复功能。

## 8. 性能特征

### 8.1 当前性能特征

基于代码分析，各执行器的理论性能特征如下：

| 操作 | 时间复杂度 | 网络往返数（RTT） | 主要瓶颈 |
|------|-----------|------------------|----------|
| `pull_entities_batch` | O(n) n=实体数 | 1 | 服务端序列化 + 网络带宽 |
| `pull_messages_batch` | O(m) m=消息总数 | 1 | NDJSON 解析 + 预渲染 CPU |
| `pull_avatar` | O(1) | 单 attempt 1 次 | 网络失败由会话级重试处理 |
| `push_entities_batch` | O(n) | 1 | 本地数据库读取 |
| `push_messages_batch` | O(m+d) | 按 8 MiB 分块 | live 与墓碑同一 NDJSON 行 |

### 8.2 当前资源边界

- 消息处理通过 `spawn_blocking` 隔离 fingerprint、压缩和可选预渲染。
- 禁用同步预渲染时不写新 `render_cache`，消息加载路径按需生成缓存。
- Push 直接投影统一 `MessageSyncDTO`，附件关系查询按页批处理。
- Pull 的传输 chunk、NDJSON 单帧与残帧上限为 32 MiB，attempt 累计响应上限为 256 MiB。

## 9. 安全考量

### 9.1 认证与授权

所有执行器的 HTTP 请求只携带标准 Bearer 认证：

| 请求头 | 用途 | 来源 |
|--------|------|------|
| `Authorization: Bearer {token}` | 同步令牌 | 同步设置快照 |

WebSocket 仍在连接 query 中携带同一令牌；HTTP 不接受 query token。

### 9.2 路径遍历防护

同步消息只携带附件元数据，不接受跨端物理路径。附件可打开路径由各端本机 CAS 解析。

### 9.3 内存安全

`process_topic_messages` 中使用了 `std::panic::catch_unwind` 包裹 `MessageRenderCompiler::compile`。这是 Rust 中处理不可信输入的 C-FFI（Foreign Function Interface，外部函数接口）边界时的标准做法。如果渲染编译器遇到恶意构造的内容字符串而 panic，`catch_unwind` 可防止整个同步任务崩溃，将错误隔离到单条消息。

## 附录 D：错误码与处理矩阵

| 错误场景 | HTTP 状态码 | 执行器行为 | 调用方应对 |
|----------|------------|-----------|-----------|
| 实体不存在 | 404 | 返回 `Err` | 当前 attempt 失败 |
| 认证失效 | 401 | 返回 `Err` | 触发重新登录或同步令牌刷新 |
| 服务端流错误 | 200 + `kind:streamError` | 保留结构化根因并立即返回 `Err` | 按 `retry` 处理 |
| 单 Topic 错误 | 200 + `kind:topic,ok:false,error` | 记录 Topic 失败 | 终止 attempt |
| 消息解析失败 | N/A（本地错误） | `TopicNDJSONFrame` 强类型反序列化后不再发生；HTTP/JSON 层错误在更早阶段返回 `Err` | 分析日志，排查网络或序列化问题 |
| 附件读取失败 | N/A（本地 IO 错误） | 返回 `Err` | 检查文件系统完整性 |
| HTTP 传输中断/超时 | N/A | 编码为 `HTTP_TRANSPORT_FAILED`，完成失败收尾后重跑整个 attempt | 共用会话的 3 个退避重试槽 |
| Manifest/Diff 后来源发生变化 | 200 + `ok:false` 或 `SYNC_ERROR` | 保留 `SYNC_SNAPSHOT_STALE`，完成失败收尾后重新比对 | 共用会话的 3 个退避重试槽 |
| HTTP/NDJSON 响应畸形 | 2xx/非 2xx | 编码为协议错误并立即终止 attempt | 不自动重试 |
| 数据库锁超时 | N/A | `map_err` 后返回 `Err` | 减小并发度，延长超时 |

---

*当前执行器基线：VCPMobile `1.1.5` / Wire `1.4`；仅 HTTP 传输中断与快照过期自动重跑完整 attempt，DB、预算、数据和协议错误均直接失败当前 attempt。*


## 11. 常见问题排查指南

### 11.1 PullExecutor 相关

#### 现象：NDJSON 消息帧解析失败

**诊断步骤**：

1. 检查日志中是否有 `[PullExecutor] Failed to parse NDJSON frame` 或网络层错误。
2. 确认 HTTP 响应的 Content-Type 是否为 `application/x-ndjson`。
3. 对比桌面端返回的 NDJSON 帧与 `TopicNDJSONFrame` 结构体，定位字段不匹配。

**常见根因**：

| 根因 | 症状 | 修复方式 |
|------|------|----------|
| 桌面端新增必填字段 | `TopicNDJSONFrame` 反序列化报错 "missing field" | 在 `ChatMessage` 中添加 `#[serde(default)]` |
| HTTP 响应被代理篡改 | NDJSON 帧格式损坏 | 检查中间层（CDN、网关）是否修改响应体 |
| 网络中断导致流截断 | 最后一条 NDJSON 帧不完整 | 属于流级错误，由 `pull_messages_batch` 统一处理 |

#### 现象：`pull_messages_batch` 返回空结果但服务端有数据

**诊断步骤**：

1. 检查 `topics[].messageIds` 是否为空数组；空数组表示拉取全部 live 消息。
2. 检查 NDJSON 流的换行符格式。服务端必须严格使用 `\n` 而非 `\r\n`。
3. 检查 `buffer` 中是否存在残留的未闭合 JSON（流被提前中断）。

### 11.2 PushExecutor 相关

#### 现象：桌面端未收到移动端发送的消息

**诊断步骤**：

1. 检查 `push_messages_batch` 的日志，确认 HTTP 状态码是否为 200。
2. 检查响应中对应 Topic 的 `ok` 字段是否为 `true`。
3. 若 `ok=false`，按 Wire 错误码定位。

### 11.3 DeleteExecutor 相关

#### 现象：已删除的 Agent 在同步后重新出现

**诊断步骤**：

1. 确认 `soft_delete_agent` 是否被正确调用。仅删除 UI 而未调用执行器会导致本地数据库未标记删除。
2. 检查 `HashAggregator::bubble_agent_hash` 是否在事务内成功执行。若事务回滚，桌面端不会感知到删除。
3. 检查桌面端是否正确处理了带有 `deleted_at` 字段的 `AgentSyncDTO`。

#### 现象：数据库体积持续增长

**诊断步骤**：

1. 查询各表的 `deleted_at IS NOT NULL` 记录数：
   ```sql
   SELECT 'agents' as table_name, COUNT(*) as deleted_count FROM agents WHERE deleted_at IS NOT NULL
   UNION ALL
   SELECT 'groups', COUNT(*) FROM groups WHERE deleted_at IS NOT NULL
   UNION ALL
   SELECT 'topics', COUNT(*) FROM topics WHERE deleted_at IS NOT NULL
   UNION ALL
   SELECT 'messages', COUNT(*) FROM messages WHERE deleted_at IS NOT NULL;
   ```
2. 墓碑数量增长本身是预期行为。生命周期管理器每日运行的安全期清理只减少正文与渲染缓存空间，不会减少墓碑行数。

## 附录 E：`TopicNDJSONFrame` 强类型结构

（替换已删除的 `normalize_desktop_message` 速查表）

```rust
#[derive(serde::Deserialize)]
struct TopicNDJSONFrame {
    topic_id: String,
    owner_type: String,
    owner_id: String,
    messages: Vec<crate::vcp_modules::chat_manager::ChatMessage>,
    error: Option<WireSyncError>,
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `topic_id` | `String` | Topic 唯一标识符，对应请求中的 `topicId` |
| `messages` | `Vec<ChatMessage>` | 该 Topic 下的消息列表，由 `serde` 直接反序列化为强类型结构 |
| `error` | `Option<WireSyncError>` | Topic `ok:false` 时携带完整 Wire 1.4 错误对象 |

**优势**：
- 编译期类型安全：`ChatMessage` 的所有字段类型在编译时确定，无需运行时手动转换。
- 零解析失败：强类型反序列化要么成功（全部消息可用），要么在 `serde` 层失败（整个 Topic 标记为失败），不会出现部分消息解析成功、部分失败的中间态。
- `avatarUrl` 和 `avatarColor` 等桌面端专属字段已不在 `ChatMessage` 中定义，自然被 `serde` 忽略，无需手动 `remove`。

## 附录 F：并发安全分析

### F.1 `DbWriteQueue` 的线程安全

`DbWriteQueue` 通过 `tokio::sync::mpsc` 通道实现单消费者模型：

```
[多个生产者: PullExecutor / 前端逻辑]
              |
              v
       mpsc::channel / unbounded_channel
              |
              v
    [单消费者: DbWriteQueue 处理循环]
              |
              v
         SQLite WAL 写入
```

由于 SQLite 在同一时刻仅支持一个写入事务，`DbWriteQueue` 的单消费者设计天然符合 SQLite 的并发模型，无需额外的锁机制。

## 附录 H：`BatchPullResult` 与 `PushBatchResult` 结构详解

这两个结果是批量操作的部分失败隔离机制的核心数据结构。

### H.1 `BatchPullResult`

```rust
pub struct BatchPullResult {
    pub topic: TopicKey,     // 完整 Topic 身份
    pub success: bool,       // 该 Topic 是否整体处理成功
    pub legacy_attachment_warnings: usize,
    pub error: Option<String>, // 内部保留已编码的 Wire 1.4 根因或本地诊断
}
```

**使用场景**：调用方核对请求集合与返回集合，累计附件元数据告警；任一失败终止 attempt。

### H.2 `PushBatchResult`

```rust
pub struct PushBatchResult {
    pub topic_id: String,    // Topic 唯一标识符
    pub success: bool,       // 该 Topic 是否上传成功
    pub error: Option<String>, // 内部保留已编码的 Wire 1.4 根因或本地诊断
}
```

**与 `BatchPullResult` 的差异**：Push 侧不区分"解析成功/失败"，因为消息在推送前已在本地验证过格式。失败仅来源于服务端拒绝（如权限、数据校验）。

## 附录 I：`DbWriteTask` 枚举与执行器的映射

`PullExecutor` 向 `DbWriteQueue` 提交的任务类型：

| 任务变体 | 提交来源 | 说明 |
|----------|----------|------|
| `DbWriteTask::Agent { id, dto }` | `pull_entities_batch` | 单 Agent 写入 |
| `DbWriteTask::Group { id, dto }` | `pull_entities_batch` | 单 Group 写入 |
| `DbWriteTask::AgentTopicBatch { topics }` | `pull_entities_batch` | 批量 Agent Topic 写入（归口优化） |
| `DbWriteTask::GroupTopicBatch { topics }` | `pull_entities_batch` | 批量 Group Topic 写入（归口优化） |
| `DbWriteTask::TopicMessages { key, messages, contents, render_bytes, content_hashes, skip_bubble }` | `process_topic_messages` | Topic 消息批量写入 |
| `DbWriteTask::Avatar { owner_type, owner_id, bytes }` | `pull_avatar` | 头像二进制写入 |

`skip_bubble = true` 的含义：在同步期间，消息的大量写入会触发频繁的哈希冒泡计算，严重影响性能。通过设置 `skip_bubble`，`DbWriteQueue` 在批量写入消息时跳过冒泡，待同步结束后再统一计算一次父级哈希。

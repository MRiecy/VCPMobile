# 25. 工具摘要与审批系统

## 1. 概述

### 1.1 领域定位

工具摘要与审批系统是 VCP Mobile v1.1.0 新增的功能模块，分为两个独立子功能：

1. **工具调用摘要（Tool Summary Block）**：AI 在每轮对话末尾生成工具调用摘要，前端以气泡形式展示每个工具的调用状态
2. **工具审批（Tool Approval）**：当 AI 计划执行敏感工具调用时，通过通知系统向用户请求审批，支持输入理由并发送响应

### 1.2 模块构成表

| 文件 | 行数 | 职责 |
|------|------|------|
| `src/features/chat/blocks/ToolSummaryBlock.vue` | 45 | 工具摘要气泡组件：状态标签色彩映射、CSS 玻璃态容器、降级展示 |
| `src-tauri/src/vcp_modules/chat/content_parser.rs` (parse_tool_call_summary) | 52 | Rust 后端自然语言状态检测，将文本解析为 `ToolCallSummaryItem[]` |
| `src-tauri/src/vcp_modules/chat/stream_block_parser.rs` (tool_call_summary) | 3 | 流式块解析器中注册 `tool_call_summary` 块类型 |
| `src/core/composables/useNotificationProcessor.ts` (tool_approval_request) | 13 | 工具审批请求的检测、格式化与 `duration=0` 设置 |
| `src/features/notification/NotificationCard.vue` (审批理由) | 20 | 审批理由 textarea、`reasonText` 绑定、1000 字限制、事件冒泡阻止 |

## 2. ToolSummaryBlock.vue：工具调用摘要气泡

> 文件位置：`src/features/chat/blocks/ToolSummaryBlock.vue`

### 2.1 组件结构

`ToolSummaryBlock` 是消息渲染管线中的一种内容 Block 组件，由 `MessageRenderer.vue` 在遇到 `block.type === "tool-call-summary"` 时渲染。

```html
<div class="vcp-tool-call-summary-bubble" data-vcp-block-type="tool-call-summary">
  <div class="vcp-tool-call-summary-header">
    <span>🧾</span>
    <span>本轮工具调用摘要</span>
  </div>
  <!-- 有 items 时：chip 列表 -->
  <div v-if="block.items && block.items.length > 0">
    <span v-for="item in block.items" class="chip" :class="`status-${item.status}`">
      <span>{{ item.tool_name }}</span>
      <span>{{ getStatusLabel(item.status) }}</span>
    </span>
  </div>
  <!-- 无 items 时：降级展示 raw_content -->
  <div v-else>{{ block.raw_content || '无摘要内容' }}</div>
</div>
```

### 2.2 状态标签颜色映射

```typescript
const statusLabelMap: Record<string, string> = {
  success:   '成功',
  failure:   '失败',
  timeout:   '超时',
  rejected:  '拒绝',
  cancelled: '取消',
  skipped:   '跳过',
  unknown:   '未知'
};
```

7 种状态对应 CSS 类 `status-{name}`，每种状态有独立的颜色语义：

| 状态 | CSS 类 | 预期颜色语义 |
|------|--------|-------------|
| `success` | `status-success` | 绿色系（执行成功） |
| `failure` | `status-failure` | 红色系（执行失败） |
| `timeout` | `status-timeout` | 橙色系（超时） |
| `rejected` | `status-rejected` | 红色/品红系（被用户拒绝） |
| `cancelled` | `status-cancelled` | 灰色系（被取消） |
| `skipped` | `status-skipped` | 黄色/灰色系（被跳过） |
| `unknown` | `status-unknown` | 默认灰色（未知状态） |

### 2.3 CSS 玻璃态容器

气泡容器使用 UnoCSS 工具类（`.vcp-tool-call-summary-bubble`），应用了玻璃态设计语言：
- 半透明背景（`bg-black/5 dark:bg-white/5` 风格）
- 圆角卡片容器
- 微妙的边框（`border-black/5` 风格）
- Chip 元素使用圆角标签样式，状态类切换颜色

### 2.4 降级展示

当 `block.items` 为空时（如 Rust 解析失败或未知格式），组件降级展示 `block.raw_content` 原始文本，保证信息不丢失。

### 2.5 与消息渲染管线的集成

在 `MessageRenderer.vue` 的 Block 分发逻辑中：

```
block.type === "tool-call-summary" → <ToolSummaryBlock :block="block" />
```

该 Block 由 Rust 后端的 `content_parser.rs` 和 `stream_block_parser.rs` 生成，数据流：

```
VCP SSE 响应 → stream_block_parser → ContentBlock::tool_call_summary(items, raw)
             → content_parser (历史消息重解析) → ContentBlock::tool_call_summary(items, raw)
             → IPC Channel / invoke 返回 → 前端 MessageRenderer → ToolSummaryBlock
```

## 3. parse_tool_call_summary：Rust 自然语言状态检测

> 文件位置：`src-tauri/src/vcp_modules/chat/content_parser.rs`（866–917 行）

### 3.1 输入格式

AI 以自然语言文本输出工具调用摘要，格式为分号/中文分号/句号分隔的条目列表。典型输入：

```
"文件搜索调用成功；代码分析调用失败；联网搜索调用超时；数据库写入被拒绝"
```

### 3.2 解析流程

```rust
pub(crate) fn parse_tool_call_summary(content: &str) -> Vec<ToolCallSummaryItem> {
    let mut items = Vec::new();
    for entry in content.split(['；', ';', '。']) {
        let entry = entry.trim();
        if entry.is_empty() { continue; }

        // 1. 中英文关键词匹配判定状态
        let status = if entry.contains("拒绝") || entry.contains("被拒")
            || entry.contains("denied") || entry.contains("rejected") || entry.contains("refused")
        { "rejected" }
        else if entry.contains("失败") || entry.contains("错误") || entry.contains("异常")
            || entry.contains("error") || entry.contains("failed")
        { "failure" }
        else if entry.contains("超时") || entry.contains("timeout")
        { "timeout" }
        else if entry.contains("成功") || entry.contains("完成")
            || entry.contains("success") || entry.contains("succeeded") || entry.contains("ok")
        { "success" }
        else if entry.contains("取消") || entry.contains("中止") || entry.contains("cancel")
        { "cancelled" }
        else if entry.contains("跳过") || entry.contains("skip")
        { "skipped" }
        else { "unknown" };

        // 2. 从条目中提取工具名（"调用"之前的文本）
        let tool_name = if let Some(idx) = entry.find("调用") {
            entry[..idx].trim().to_string()
        } else {
            entry.to_string()
        };

        items.push(ToolCallSummaryItem { tool_name, status: status.to_string() });
    }
    items
}
```

### 3.3 匹配优先级

```mermaid
graph TD
    A[entry.trim()] --> B{包含 拒绝/denied/rejected?}
    B -->|是| R["rejected"]
    B -->|否| C{包含 失败/错误/error/failed?}
    C -->|是| F["failure"]
    C -->|否| D{包含 超时/timeout?}
    D -->|是| T["timeout"]
    D -->|否| E{包含 成功/完成/success/ok?}
    E -->|是| S["success"]
    E -->|否| G{包含 取消/中止/cancel?}
    G -->|是| C2["cancelled"]
    G -->|否| H{包含 跳过/skip?}
    H -->|是| SK["skipped"]
    H -->|否| U["unknown"]
```

**关键点**：`rejected` 优先级最高（排在 `failure` 之前），因为"拒绝"语义比"失败"更精确——工具可能因用户拒绝而未被批准执行，此时不应该标记为"失败"。

### 3.4 条目分隔符

三重分隔符覆盖中英文场景：

| 分隔符 | Unicode | 场景 |
|--------|---------|------|
| `；` | U+FF1B | 中文全角分号（AI 中文回复中最常见） |
| `;` | U+003B | ASCII 分号（英文回复） |
| `。` | U+3002 | 中文句号（AI 以句号分隔条目） |

## 4. 工具审批通知

> 文件位置：`src/core/composables/useNotificationProcessor.ts`（262–273 行）

### 4.1 tool_approval_request 检测

当 `payload.type === 'tool_approval_request'` 且 `payload.data` 存在时：

```typescript
else if (payload.type === 'tool_approval_request' && payload.data) {
  const approvalData = payload.data;
  type = 'warning';
  title = `🛠️ 审核请求: ${approvalData.toolName || 'Unknown'}`;
  message = `助手: ${approvalData.maid || 'N/A'}\n命令: ${approvalData.args?.command || JSON.stringify(approvalData.args || {})}\n时间: ${approvalData.timestamp || 'Just now'}`;
  isPreformatted = true;
  duration = 0;  // ← 关键：不自动消失
  actions = [
    { label: '允许', value: true,  color: 'bg-green-500 shadow-lg shadow-green-500/20' },
    { label: '拒绝', value: false, color: 'bg-red-500 shadow-lg shadow-red-500/20' }
  ];
}
```

### 4.2 duration=0 的不自动消失机制

`duration = 0` 是通知系统的特殊信号值——当 `duration === 0` 时，通知不会在计时器到期后自动移除，而是持久显示直到用户手动操作（点击"允许"或"拒绝"按钮）。这确保审批请求不会被用户错过。

### 4.3 双按钮 Action

```typescript
actions = [
  { label: '允许', value: true,  color: 'bg-green-500 ...' },
  { label: '拒绝', value: false, color: 'bg-red-500 ...' }
];
```

两个 Action 按钮分别绑定 `true`（通过）和 `false`（拒绝）语义值，渲染时通过 `getActionButtonClass(action)` 获得各自的颜色样式类。

## 5. 审批理由输入

> 文件位置：`src/features/notification/NotificationCard.vue`（117–130 行）

### 5.1 条件渲染

理由输入框仅在满足特定条件时显示：

```html
<div v-if="props.item.type === 'warning' && props.item.rawPayload?.type === 'tool_approval_request'">
  <textarea
    v-model="reasonText"
    placeholder="可选：告诉 AI 为什么通过或拒绝"
    maxlength="1000"
    @touchstart.stop @touchmove.stop @touchend.stop @keydown.stop
  />
  <span>拒绝时建议填写可执行的修正建议，最多 1000 字。</span>
</div>
```

双重条件过滤：
1. `item.type === 'warning'`：仅 warning 级别的通知展示理由框
2. `item.rawPayload?.type === 'tool_approval_request'`：确保是审批请求类型

### 5.2 reasonText 绑定与传递

```typescript
const reasonText = ref('');
const handleAction = (action: { label: string; value: boolean; color: string }) => {
  store.executeAction(props.item.id, action, reasonText.value);
};
```

`reasonText` 是一个本地 `ref<string>`，与 textarea 双向绑定。用户点击"允许"或"拒绝"时，`handleAction` 将用户输入的理由文本一并传递给 `store.executeAction`。

### 5.3 事件冒泡阻止

textarea 上绑定了 4 个事件拦截器：

| 事件 | 用途 |
|------|------|
| `@touchstart.stop` | 防止触摸开始事件冒泡触发通知卡的滑动手势 |
| `@touchmove.stop` | 防止触摸移动事件冒泡导致通知卡意外滑动 |
| `@touchend.stop` | 防止触摸结束事件冒泡 |
| `@keydown.stop` | 防止键盘事件冒泡（如 Android 物理返回键） |

这些拦截确保用户在 textarea 中正常输入时，不会触发通知卡的 swipe-to-dismiss 手势。

### 5.4 字符限制

- **maxlength="1000"**：HTML 原生属性，阻止输入超过 1000 个字符
- 提示文案："拒绝时建议填写可执行的修正建议，最多 1000 字"
- 无实时字符计数器（简洁设计）

## 6. 审批响应发送

### 6.1 executeAction 流程

当用户点击"允许"或"拒绝"后，`notificationStore.executeAction` 被调用：

```
notificationStore.executeAction(id, action, reasonText)
    │
    ├── 1. 根据 id 找到通知项
    ├── 2. 从 rawPayload 中提取上下文信息（toolName, maid, requestId）
    │
    ├── 3. 调用 invoke('send_vcp_log_message', {
    │       type: 'tool_approval_response',
    │       data: {
    │         approved: action.value,     // true 或 false
    │         reason: reasonText,         // 用户输入的理由
    │         toolName: ...,
    │         maid: ...
    │       }
    │     })
    │     → 通过 VCPLog WebSocket 发送给桌面 VCP 服务端
    │
    └── 4. 从通知列表中移除该通知项
```

### 6.2 通信路径

审批响应不直接操作工具执行，而是通过 VCPLog WebSocket 通道回传给桌面 VCP 服务端，由服务端决定批准或拒绝工具的执行：

```
移动端 NotificationCard
    │ [允许/拒绝 + 理由]
    ▼
notificationStore.executeAction
    │ invoke('send_vcp_log_message')
    ▼
Rust: vcp_log_service → WebSocket → 桌面 VCP 服务端
    │
    ▼
桌面 DistPluginManager / Agent 执行引擎
    │ 批准 → 执行工具
    │ 拒绝 → 跳过工具 + 通知 Agent 拒绝原因
```

## 8. 设计决策

### 8.1 为何工具摘要使用自然语言解析而非结构化 JSON？

Rust 的 `parse_tool_call_summary` 解析的是 AI 的自由文本输出（由 VCP 服务端的 prompt 指引 AI 生成特定格式的摘要），而非结构化 JSON。原因：

1. **容错性**：自然语言解析对 AI 输出格式的微小偏差更宽容（如多余的空格、缺少引号等）
2. **渐进增强**：即使解析失败，`raw_content` 降级展示仍保证用户看到原始文本
3. **无需服务端改造**：服务端只需在 prompt 中指引 AI 输出分号分隔的摘要即可

### 8.2 为何审批理由限制 1000 字？

1000 字（约 2000-3000 字节）是移动端 textarea 输入的合理上限：
- 提供足够的空间让用户写出有意义的修正建议
- 避免极长文本导致的布局问题
- 审批响应通过 WebSocket 文本帧传输（不经过 zstd 压缩），控制单帧大小

### 8.3 为何审批通知 duration=0 而不是很大的值？

`duration=0` 在通知系统中具有特殊语义——"永不自动消失"。这比设置一个极大的 duration 值（如 `86400000`）更明确：
- 代码意图清晰：`duration === 0` 在所有消费者中都能被正确理解为"永久显示"
- 避免边界情况：极大的 duration 可能在应用重启后面临计时器状态丢失的问题

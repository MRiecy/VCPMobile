## 1. 概述

### 1.1 领域定位

core/stores/ 中围绕聊天的四个 Pinia Store 构成了 VCP Mobile 前端**对话引擎的状态底座**。它们负责管理：

- `chatSessionStore` 提交导航意图，投影 Rust 接纳的焦点和窗口身份。
- `chatHistoryStore` 集成 `useChatWindow`，呈现窗口内的消息并提交发送、编辑和删除操作。
- `chatStreamStore` 消费 Rust 的请求、群轮及消息事件，更新气泡渲染与按钮状态。
- `attachmentStore` 管理待发送的附件与资源解析。

这四个 Store 通过 Tauri IPC 与 Rust 后端交互，并通过 Vue 3 的响应式系统驱动 ChatView.vue 及其子组件的渲染。

### 1.4 核心设计原则

| 原则 | 说明 |
|------|------|
| **Backend-Driven Streaming** | 后端先以单一事务创建 pending 消息、render cache、FTS 与 `active_generations`，提交成功后才发 `thinking`。前端只创建响应式 UI 对象，不再落盘 skeleton。 |
| **活动气泡** | `activeStreamMessages` 以完整会话与消息 ID 定位响应式气泡。Rust 持有生成任务，SQLite 持有已提交消息。 |
| **窗口读取** | `read_chat_window` 返回有界窗口，`reconcile_chat_window` 校对相同窗口。Vue 使用后端返回的成员顺序与边界。 |
| **异步身份** | 完整话题键由 `ownerType`、`ownerId` 和 `topicId` 组成。焦点、窗口和通话分别有自己的版本。 |

## 2. 会话状态（chatSessionStore）

### 2.1 焦点与本机偏好

`currentSelectedItem` 和 `currentTopicId` 显示 Rust 接纳的欢迎页、仅选中 owner 或具体话题。`acceptedWindow` 保存文档、焦点和窗口版本以及可选的消息锚点。`sessionEpoch` 是 Vue 的会话代次，供在途操作判断原会话是否仍可更新。名称和头像从 `assistantStore` 补全。

Pinia 保存最近选中的 owner、话题及按 `ownerType:ownerId` 区分的上次话题。首次启动进程时，`restore_chat_view` 校验这些偏好。同一 Rust 进程中重建 WebView 时，已有焦点、窗口与活跃通话仍归原所有者。[会话投影](../../../src/core/stores/chatSessionStore.ts) · [恢复逻辑](../../../src-tauri/src/vcp_modules/chat/chat_navigation.rs)

### 2.2 话题切换与通话

1. 点击话题、通知或搜索结果时，`beginNavigation()` 登记当前文档的意图序号。`request_chat_navigation` 校验目标 owner、话题及可选锚点，在提交焦点前再次核对序号。
2. `selectItem` 可以提交最近话题候选与排序方式，由 Rust 选择有效目标。`selectTopicById` 指定完整话题，可附 `anchorId`。跨话题请求与拨号共用 Rust 的准入判定。正在通话时跨话题返回 `call_in_progress`，同一话题内仍可定位消息。
3. 成功回执或 `vcp-chat-focus` 快照经 `applyFocus` 投影。换话题更新焦点版本，重新定位同一话题更新窗口版本。`setConversation` 用于应用投影和测试构造。通话界面消费带真实 `callId` 和目标的快照，显式挂断按该 `callId` 执行。[Rust 准入](../../../src-tauri/src/vcp_modules/chat/chat_focus.rs) · [通话所有者](../../../src-tauri/src/vcp_modules/chat/voice_service/call.rs)

## 3. 消息历史（chatHistoryStore）

### 3.1 消息列表状态设计

`currentChatHistory` 是当前窗口的消息投影。`loadedConversationKey`、`loadedWindowRevision` 用来核对话题和窗口代次。`hasMoreHistory`、`hasEvictedNewer` 与 `pinned` 表示读取边界；`anchorRemoved` 及 `replacementAnchorId` 用于锚点被删除后的定位。`chatHistoryStore` 单独维护编辑意图和发送等待态。[窗口投影](../../../src/core/stores/chatWindow.ts)

`ChatMessage` 类型定义位于 `src/core/types/chat.ts`：

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | `string` | 消息唯一标识。用户消息格式 `msg_{timestamp}_user_{rand}`；Assistant 消息由后端生成 |
| `role` | `string` | `"user"` / `"assistant"` / `"system"` |
| `name` | `string?` | 显示名称 |
| `content` | `string?` | 原始文本内容，**按需懒加载**（流式期间在 `chatStreamStore` 中维护） |
| `blocks` | `ContentBlock[]?` | 后端预渲染的结构化块，前端直接渲染 |
| `shell` | `MessageShell?` | 预计算的外壳属性（头像色、气泡边框、显示名等） |
| `timestamp` | `number` | 毫秒级 Unix 时间戳 |
| `attachments` | `Attachment[]?` | 附件列表 |
| `isThinking` | `boolean?` | 是否处于 thinking 状态（仅 Assistant 消息） |
| `finishReason` | `string?` | 已结算回复的原因，包括模型结束原因、`completed`、`error` 和 `cancelled_by_user` |
| `tailContent` | `string?` | **纯前端运行时字段**：Aurora 尾随区 Markdown（高频变动，不持久化） |
| `tailBlock` | `ContentBlock?` | **纯前端运行时字段**：Aurora 尾随 Block |

### 3.2 加载与分页机制

`ChatView` 观察已接纳的会话与 `windowRevision`，通过 `ensureWindow()` 读取该窗口。首次打开尾端默认取最近 5 条，指定锚点时取其前最多 12 条及后最多 8 条，上翻默认再取 10 条。Rust 以 `(timestamp, msg_id)` 稳定排序，将窗口限制在 500 条。应用重新进入前台时可按已有成员校对同一窗口。[窗口查询与边界](../../../src-tauri/src/vcp_modules/chat/chat_window.rs)

尾端可跟随新回复。锚窗或固定阅读位置的窗口只修正已有成员，窗外的新回复通过“回到最新”提示。原锚点已删除时优先定位到窗口内仍存在的相邻消息。`ChatView` 负责高亮、滚动与像素补偿。[聊天视图](../../../src/features/chat/ChatView.vue)

#### triggerGeneration

> 函数位置：`src/core/stores/chatHistoryStore.ts` 第 271–341 行

这是用户消息发送后衔接 AI 响应的**核心枢纽**：

1. **先持久化并编译用户消息**：调用 `append_single_message` 将用户消息写入 SQLite，返回 `{ blocks, topicUpdatedAt }`；随后回填本地 `userMsg.blocks`，并用数据库事务返回的活动时间直接覆盖 Topic 排序字段。
2. **创建流式 Channel**：`new Channel<any>()`，其 `onmessage` 委托给 `streamStore.processStreamEvent`。
3. **分发到 Agent/Group**：
   - Agent 聊天 → `handle_agent_chat_message`
   - Group 聊天 → `handle_group_chat_message`
   - 两者 payload 均携带 `vcpUrl` / `vcpApiKey`。

回调核对完整会话身份后，使用 `projectLiveMessage` 更新允许显示的气泡。实时完成时，当前会话可以按原条件请求话题总结。数据库补投只更新窗口投影。[消息发送与回调](../../../src/core/stores/chatHistoryStore.ts)

## 4. 流式状态（chatStreamStore）

### 4.1 Backend-Driven Streaming 架构

VCP Mobile 在 `8888d85` 架构变更后，全面转向 **Backend-Driven Streaming**：

| 旧架构 | 新架构 |
|--------|--------|
| 前端预创建 thinking 消息（带临时 ID） | 前端**不预创建** thinking 消息 |
| 前端分配 `thinking_message_id` | 后端自主生成 Assistant 消息 ID |
| `StreamEvent::content` 直接更新历史列表 | `StreamEvent::thinking` 触发 `chatStreamStore` 初始化气泡 |
| 流式期间状态分散在多处 | 流式期间状态统一由 `activeStreamMessages` 管理 |

`chatHistoryStore` 按当前窗口呈现已接纳的消息成员。`chatStreamStore` 处理实时事件，Rust 的请求和写入事务继续独立执行。


### 4.2 流式消息生命周期

#### 核心状态字段

`sessionActiveStreams` 以 `(ownerType, ownerId, topicId)` 区分话题。`activeStreamMessages` 与 `streamingMessageKey` 在话题身份之外包含 `messageId`。这些前端对象供渲染和连接控制使用。[消息流投影](../../../src/core/stores/chatStreamStore.ts)

#### 事件处理流水线（processStreamEvent）

> 函数位置：`src/core/stores/chatStreamStore.ts` 第 289–503 行

```
Rust Channel 推送 StreamEvent
       │
       ▼
┌─────────────────────────────────────────┐
│ 提取 actualMessageId, type, context     │──> 从 event 中解构

      ┌─────────┬─────────┬─────────┐
      ▼         ▼         ▼         ▼
   thinking   aurora    end      error
```

**各事件分支详解**：

| 事件类型 | 行为 | 状态变更 |
|----------|------|----------|
| `thinking` | 后端开始生成 thinking 内容 | `msg.isThinking = true`；加入 `sessionActiveStreams`；设置 `streamingMessageId` |
| `aurora` | Aurora 语义沉淀更新（含稳定区 `content`/`stableBlocks`、尾随区 `tail`/`tailBlock`/`tailFrame` 增量） | 写入 `rAFPendingUpdates` 暂存池，等待下一绘制帧统一刷入 `msg.content` / `msg.blocks` / `msg.tailContent` 等 |
| `end` | Rust 已提交终态，含模型结束原因、主动取消或真实错误 | 合入正文、原因与最终渲染块，释放活动投影。实时结束才触发完成回调。 |
| `error` | 接续或终态写入仍需重试 | 保留部分正文和活动身份，等待后续恢复。 |

#### rAF 响应式状态原子提交

> 代码位置：`src/core/stores/chatStreamStore.ts` 第 67–148 行

为消灭高频 `data` / `aurora` 事件导致的定时器空转与渲染抖动，`chatStreamStore` 引入 `rAFPendingUpdates` 暂存池：

- 每个 `messageId` 拥有独立的待渲染快照（`content` / `blocks` / `tailContent` / `tailBlock` / `tailFrame` / `tailSnapshot`）；
- `scheduleRAFUpdate(messageId)` 只合并下一次绘制前到达的更新并原子写入 Vue reactive 对象；Rust `vcp_client` 的 33ms Aurora 门禁是唯一的传输频率上限，前端不再叠加第二个时间门禁；
- `clearRAFUpdate(messageId, forceFlush = true)` 在 `end` / `error` / 手动中止时强制刷入，防止 tail 内容闪烁或丢失。

`mergeTailFrame`（第 44–63 行）负责合并连续的 `tailFrame` 增量，支持 epoch / reset 语义与 mutation 拼接。

可选的平滑流式设置不延迟这里的权威响应式状态。`MessageRenderer` 只让已经完整进入 AST DOM 的普通 Markdown 新增文本与合格块播放一次固定 250ms 的斜向柔边揭露；结构帧、恢复快照、Thought/HTML/代码等外壳和 durable `end` 仍立即抢占并收敛。

#### 生成占位与持久化

Rust 提交助手占位与 `active_generations` 后发 `thinking`。Vue 从窗口读取待处理行时可复用同一条活跃气泡；读取到已结算行时使用持久化结果并清退已确认的旧占位。
> **完成触感**：正常活动回复的 durable end 完成渲染接管后，按消息震动偏好提交 `triggerMessageHaptic('complete')`；Android 使用 CLICK，iOS 使用 light 默认强度。取消、错误和标记为重放/恢复的终态不触发。

### 4.3 与 chatHistoryStore 的协作边界

Rust 持有消息与请求生命周期。`chatHistoryStore.makeStreamChannel` 将事件交给 `chatStreamStore.processStreamEvent`，气泡创建后由窗口决定是否展示。提交后的 `end` 合入原气泡，即使已收到的正文只是发生断流前的部分回复。正常在线完成可触发标题总结及按偏好设置的触感。

### 4.4 流接续与异常恢复

1. `reconnect_chat_streams` 首次接入时登记 Channel，同一 WebView 后续凭 `connectionId` 复用它。Rust 接管现有请求、待处理生成和群轮。活动清单用于更新运行状态。
2. 接通后按当前窗口校对 SQLite。即使后台群轮在断线期间开始并全部结束，尾窗也能发现此前没有见过的消息。读取期间到达的新增、终态或删除按 ID 记录，重读发生冲突的窗口内容。窗口一旦换代，迟到的回执失效。
3. `resolve_chat_placeholders` 分批核实剩余旧占位。只有数据库确认已结算或不存在时才清退，待处理、未决或读取失败的占位留待下次核对。补投采用后端话题统计，不触发额外发送、朗读、触感、未读累加或标题总结。[输出接管](../../../src/core/stores/chatStreamStore.ts) · [窗口读取](../../../src/core/stores/chatWindow.ts)

## 5. 附件暂存（attachmentStore）

## 8. 设计决策与注意事项

### 8.1 为何采用 Backend-Driven Streaming？

旧架构中，前端需要在 `sendMessage` 时预分配一个 `thinking_message_id`，构造占位消息推入列表，然后等待后端响应。这导致：

1. **ID 冲突风险**：前后端 ID 生成策略不一致时，可能出现重复或覆盖
2. **状态同步复杂**：前端 thinking 消息与后端实际消息在 `content`、`blocks`、`finishReason` 上需要双向同步
3. **重生成场景混乱**：重新生成时，前端需要手动替换旧消息，容易出错

新架构将 thinking ID 的生成权完全交予后端（`agent_chat_application_service.rs` 第 6 步），前端仅作为事件的**被动消费者**。`chatHistoryStore` 从 400+ 行简化为只管"追加/删除/编辑"，流式复杂度全部收敛到 `chatStreamStore`。

### 8.2 全局流消息池的 OOM 防御

`activeStreamMessages` 是 `reactive<Map>`，理论上可以无限增长（用户快速切换多个话题，每个话题都在后台生成）。防御措施：

- **上限**：`MAX_STREAM_MESSAGES = 100`
- **清理策略**：按插入顺序（Map 保持插入顺序），删除最旧的**非活跃**消息（不在当前 `activeStreamingIds` 中）
- **延迟清理**：流结束后延迟 1 秒才从池中删除，确保 `finalizeStream` 和 UI 收尾能拿到对象

### 8.3 活跃气泡与持久终态

窗口读到仍在生成的消息时，`acceptPersistedMessage` 会复用相同复合键的活跃气泡，保留 Aurora 已显示的正文及尾帧。数据库返回已保存的助手终态时，使用该行并隔离旧流的迟到交付。

### 8.4 会话与窗口的一致性

Rust 用文档、完整话题、`focusRevision` 与 `windowRevision` 核对窗口读取。Vue 只应用仍属于当前窗口的结果。同一话题连续定位两条消息时，旧查询和旧滚动回调都不能覆盖后一次定位。

### 8.5 附件路径解析的安全策略

`attachmentStore.resolveMessageAssets` 负责将 Rust 返回的本地物理路径转换为 WebView 可访问的 URL：

- 仅对 `type.startsWith("image/")` 的图片执行转换
- 排除 `http://` / `https://` / `data:` 开头的已有 URL
- 使用 Tauri 的 `convertFileSrc(sourcePath)` 生成 `asset://` 或 `http://asset.localhost/` 协议 URL
- `resolvedSrc` 为**纯运行时字段**，不持久化到 DB，避免跨端同步时路径失效

### 8.6 编辑重发的乐观更新与持久化一致性

当用户长按某条用户消息选择"编辑重发"时：

1. `editingMessage` 保存完整会话键和消息 ID，输入框回填内容
2. 用户修改内容后点击发送，`sendMessage` 读取该编辑意图
3. 调用 `truncate_history_after_message` 从后端删除稳定消息锚点之后的全部消息
4. 前端乐观截断 `currentChatHistory`：`slice(0, targetIndex + 1)`
5. 调用 `triggerGeneration(targetMsg)` 以修改后的消息重新启动生成

后端截断成功后返回权威 `msg_count`，前端再更新本地历史和计数。

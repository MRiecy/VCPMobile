# 03. 会话状态与消息流

## 1. 概述

### 1.1 领域定位

core/stores/ 中围绕聊天的四个 Pinia Store 构成了 VCP Mobile 前端**对话引擎的状态底座**。它们负责管理：

- **谁在对谈**：当前选中的 Agent/Group 与话题（chatSessionStore）
- **谈了什么**：消息列表的加载、分页、追加与修改（chatHistoryStore）
- **正在说什么**：Backend-Driven Streaming 架构下的流式消息生命周期（chatStreamStore）
- **要带什么**：用户待发送的附件暂存与预处理（ttachmentStore）

这四个 Store 通过 Tauri IPC 与 Rust 后端交互，并通过 Vue 3 的响应式系统驱动 ChatView.vue 及其子组件的渲染。

### 1.4 核心设计原则

| 原则 | 说明 |
|------|------|
| **Backend-Driven Streaming** | 后端先以单一事务创建 pending 消息、render cache、FTS 与 `active_generations`，提交成功后才发 `thinking`。前端只创建响应式 UI 对象，不再落盘 skeleton。 |
| **双 Store 边界** | `chatStreamStore` 管理流式期间的响应式状态；流结束后内容移交 `chatHistoryStore`。两者职责严格分离。 |
| **全局流消息池** | `activeStreamMessages`（`Map<string, ChatMessage>`）存储所有正在生成的消息，保证前台/后台切换时流式链路不断裂。 |
| **Object Hydration** | 从 DB 加载历史时，若发现某消息正处于活跃流式中，则用全局池中"活的"响应式对象替换骨架，实现无缝接续。 |
| **小页批量加载** | 首屏 5 条、向上分页 10 条，统一由 `load_chat_history` 的 request-response 返回。小页不再额外维护 Channel completion Promise。 |
| **会话纪元校验** | 身份由不可变 `ConversationKey { ownerId, ownerType, topicId, epoch }` 表示。所有异步提交同时校验 key、epoch 与 loadId，A→B→A 也不会接纳 A 的旧回调。 |

## 2. 会话状态（chatSessionStore）

### 2.1 核心状态字段

> 文件位置：`src/core/stores/chatSessionStore.ts`

```typescript
const currentSelectedItem = ref<any>(null);      // 当前选中的 Agent 或 Group 对象
const currentTopicId = ref<string | null>(null); // 当前活跃话题 ID
const sessionEpoch = ref(0);                     // 每次身份转换单调递增
const lastActiveTopicMap = ref<Record<string, string>>({}); // ownerId -> topicId 映射

const currentConversationKey = computed(() =>
  currentSelectedItem.value && currentTopicId.value
    ? { ownerId, ownerType, topicId, epoch: sessionEpoch.value }
    : null,
);
```

| 字段 | 类型 | 持久化 | 说明 |
|------|------|--------|------|
| `currentSelectedItem` | `any` | ✅ Pinia persist | 包含 `id`, `name`, `type` (`"agent"` / `"group"`), `avatarCalculatedColor` 等 |
| `currentTopicId` | `string \| null` | ✅ Pinia persist | 当前显示的话题 ID，话题列表高亮与此绑定 |
| `sessionEpoch` | `number` | ❌ 仅运行时 | 会话身份版本。即使 A→B→A 回到相同 ID，旧 A 的异步结果也会因 epoch 不同被丢弃 |
| `currentConversationKey` | `ConversationKey \| null` | 计算值 | 用户动作与异步加载的不可变所有权快照 |
| `lastActiveTopicMap` | `Record<string, string>` | ✅ Pinia persist | 每个 `ownerId` 最后一次打开的话题 ID，下次进入时自动恢复 |

`currentSelectedItem` 与 `currentTopicId` 只能经 `setConversation` / `clearConversation` / `selectTopicById` 原子变更；组件不再直接写两个 ref。`selectItem` 在等待 `get_topics` 时会冻结选择 epoch，若期间用户已选择其他 owner，迟到结果直接丢弃。

### 2.3 与 Agent/Group 的关系

`chatSessionStore` 不直接存储 Agent/Group 的完整列表，而是消费 `useAssistantStore`（`assistant.ts`）中的 `agents` 和 `groups` 数组：

- 判定 `ownerType` 时扫描 `assistantStore.agents.some(a => a.id === itemId)`
- 构造 `currentSelectedItem` 时从 `assistantStore` 中查找对应对象并注入 `type` 字段

这意味着 Agent/Group 的增删改由 `assistantStore` 统一管理，`chatSessionStore` 只持有**选中态**的副本。

### 3.2 加载与分页机制

#### 启动预加载（preloadHistory）

> 函数位置：`src/core/stores/chatHistoryStore.ts` 第 46–62 行

在应用启动 `PRELOADING` 阶段，若 Pinia 恢复了一个活跃会话（`currentSelectedItem` + `currentTopicId`），`appLifecycle.ts` 会调用 `preloadHistory()` 提前拉取首屏历史：

```typescript
const preloadHistory = async (ownerId, ownerType, topicId, limit = 5) => {
  const messages = await invoke<ChatMessage[]>('load_chat_history', {
    ownerId, ownerType, topicId, limit, offset: 0,
    beforeTimestamp: null, beforeMessageId: null,
  });
  preloadedHistory.value = { topicId, messages };
};
```

这样 `ChatView` 挂载时可直接消费缓存，实现首屏零延迟。

#### 初始加载（loadHistoryPaginated）

> 函数位置：`src/core/stores/chatHistoryStore.ts` 第 245–254 行

切换话题时调用，强制重置分页状态并加载最新的 5 条消息：

```typescript

hasMoreHistory.value = true;
// 注意：preloadConsumed 不在此处重置，预加载缓存仅在应用启动后的首次首屏加载命中一次
await loadHistory(ownerId, ownerType, topicId, 5, 0);
```

#### 分页加载（loadMoreHistory）


#### 核心加载逻辑（loadHistory）

> 函数位置：`src/core/stores/chatHistoryStore.ts` 第 112–243 行

`loadHistory` 的首屏与分页统一使用小页批量 request-response：

- 首屏优先消费与完整 `ConversationKey` 匹配的启动预加载缓存，否则调用 `load_chat_history`；
- 向上分页冻结当前最老消息的 `(timestamp, msgId)`，以后端 BINARY 次序执行 keyset 查询；`historyOffset` 只保留为本地计数，不进入 SQL；
- 每次加载分配单调 `loadId` 并持有 AbortController。只有 `ConversationKey + epoch + loadId` 全部仍匹配，才能提交 messages、offset、loading 与 controller；
- 话题切换立即 `resetHistoryForConversation()`：取消旧加载、清空旧列表与 loaded key，旧列表不能在新标题下继续操作；
- 分页结果按 message ID 去重后 prepend，并以显式 `HistoryPageResult` 完成 `useChatScroll` 的 `loading-top` 状态。
- 活跃列表最多保留 500 条：深翻时可暂时保留最老窗口并标记 `hasEvictedNewer`；置底、非编辑发送或输入聚焦会先重载最新页再置底。这是有限内存策略，不是无限 DOM 虚拟化。

```
loadHistory(ownerId, ownerType, topicId, limit, localOffset)
       │
       ├── 冻结 ConversationKey + 分配 loadId
       ├── 首屏且缓存 key 匹配? ──► 使用预加载缓存
       └── 否则 invoke("load_chat_history")
               ├── 首屏: cursor = null
               ├── 旧页: cursor = oldest(timestamp, msgId)
               ├── key/epoch/loadId 校验
               ├── Object Hydration + ID 去重 + 500 条窗口
               └── 返回 HistoryPageResult
```

**Object Hydration 机制**：

当用户切换到一个正在进行流式生成的话题时，从 DB 拉回来的消息是"死"的 Plain Object。`loadHistory` 在收到每条消息时，检查 `streamStore.activeStreamMessages.get(msg.id)`：

- 若命中 → 使用全局池中**已 reactive** 的对象替换骨架，UI 自动接续流式动画
- 若未命中 → 使用 chunk / batch 中的原始消息对象

这保证了"后台生成 → 切换话题 → 前台展示"的链路中，消息的响应式引用不丢失。

#### triggerGeneration

> 函数位置：`src/core/stores/chatHistoryStore.ts` 第 271–341 行

这是用户消息发送后衔接 AI 响应的**核心枢纽**：

1. **先持久化并编译用户消息**：调用 `append_single_message` 将用户消息写入 SQLite，并返回编译后的 `ContentBlock[]`；随后用编译结果回填本地 `userMsg.blocks`。

```typescript
streamChannel.onmessage = (event) => streamStore.processStreamEvent(event, {
  onMessageCreated: (msg, tid) => {
    if (tid === sessionStore.currentTopicId && !currentChatHistory.value.some(m => m.id === msg.id)) {
      currentChatHistory.value.push(msg);
      currentChatHistory.value.sort((a, b) => a.timestamp - b.timestamp);

  onStreamFinished: (_mid, tid) => {
    if (tid === sessionStore.currentTopicId) {
      summarizeTopic();  // 触发 AI 总结标题

  }
});
```

## 4. 流式状态（chatStreamStore）

### 4.1 Backend-Driven Streaming 架构

VCP Mobile 在 `8888d85` 架构变更后，全面转向 **Backend-Driven Streaming**：

| 旧架构 | 新架构 |
|--------|--------|
| 前端预创建 thinking 消息（带临时 ID） | 前端**不预创建** thinking 消息 |
| 前端分配 `thinking_message_id` | 后端自主生成 Assistant 消息 ID |
| `StreamEvent::content` 直接更新历史列表 | `StreamEvent::thinking` 触发 `chatStreamStore` 初始化气泡 |
| 流式期间状态分散在多处 | 流式期间状态统一由 `activeStreamMessages` 管理 |

这一变更大幅简化了 `chatHistoryStore`：它只需关心"何时将完成的消息追加到列表"，而不再参与 thinking 状态的维护。

### 4.2 流式消息生命周期

#### 核心状态字段

> 文件位置：`src/core/stores/chatStreamStore.ts`


#### 事件处理流水线（processStreamEvent）

> 函数位置：`src/core/stores/chatStreamStore.ts` 第 289–503 行


**各事件分支详解**：

| 事件类型 | 行为 | 状态变更 |
|----------|------|----------|
| `thinking` | 后端开始生成 thinking 内容 | `msg.isThinking = true`；加入 `sessionActiveStreams`；设置 `streamingMessageId` |
| `aurora` | Aurora 语义沉淀更新（含稳定区 `content`/`stableBlocks`、尾随区 `tail`/`tailBlock`/`tailFrame` 增量） | 写入 `rAFPendingUpdates` 暂存池，等待 rAF 30Hz 统一刷入 `msg.content` / `msg.blocks` / `msg.tailContent` 等 |
| `end` | 流式正常结束 | `clearRAFUpdate(id, true)` 强制刷入尾帧；`msg.tailContent = ""`；`removeSessionStream()`；调用 `process_message_content` 编译 blocks；触发 `onStreamFinished` |
| `error` | 流式异常结束 | 同 `end`，但追加错误文本到 content；`finishReason = "error"` |

#### rAF 30Hz 合并渲染

> 代码位置：`src/core/stores/chatStreamStore.ts` 第 67–148 行

为消灭高频 `data` / `aurora` 事件导致的定时器空转与渲染抖动，`chatStreamStore` 引入 `rAFPendingUpdates` 暂存池：

- 每个 `messageId` 拥有独立的待渲染快照（`content` / `blocks` / `tailContent` / `tailBlock` / `tailFrame` / `tailSnapshot`）；
- `scheduleRAFUpdate(messageId)` 通过 `requestAnimationFrame` 以最小 33.3ms 间隔将快照原子写入 Vue reactive 对象；
- `clearRAFUpdate(messageId, forceFlush = true)` 在 `end` / `error` / 手动中止时强制刷入，防止 tail 内容闪烁或丢失。

`mergeTailFrame`（第 44–63 行）负责合并连续的 `tailFrame` 增量，支持 epoch / reset 语义与 mutation 拼接。

### 4.4 流接续与异常恢复

> 函数位置：`src/core/stores/chatStreamStore.ts` 第 585–758 行（`checkAndRecoverInterruptedStreams`）

v1.1.3 新增**活跃生成自对齐**机制：当应用从后台回到前台、网络恢复或首屏历史加载完成后，前端调用 `checkAndRecoverInterruptedStreams()`：

1. **本地扫表**：调用 `get_active_generations` 获取 Rust 后端记录的活跃生成列表；
2. **UI 预处理**：为每个活跃生成在 `activeStreamMessages` 中创建/复用消息对象，标记 `isReconnecting = true`；若消息不在当前历史列表中且属于当前话题，则推入 `currentChatHistory`；
3. **网络门控**：若设备离线，仅保留本地状态，暂停云端同步；
4. **单命令恢复**：每个 msgId 只调用一次 `recover_active_generation({msgId, streamChannel, isWarm})`。后端从查询 helper/cache、接续到 terminal DB commit 始终持有同一 attempt lease，不再存在 `recover -> resume` 两次 IPC 之间的抢占窗口；
5. **冷/温判断**：在注入占位对象之前冻结原始 warm 集合。温接续保留已有 AST，冷接续清空 `content` / `blocks` 并从事件 0 回放；
6. **双层 singleflight**：扫描入口同步设置 `isRecovering`，每个 msgId 另由 `recoveryMessageIds` 覆盖完整长命令生命周期。一条恢复失败不会中止其他消息。

**级联中止**：`stopGroupTurn(topicId)` 现在会先将后端 `interruptGroupTurn` 调用，再对当前话题所有活跃流调用 `stopMessage()`，确保群聊接力赛回合被完整终止。

## 8. 设计决策与注意事项

### 8.1 为何采用 Backend-Driven Streaming？

旧架构中，前端需要在 `sendMessage` 时预分配一个 `thinking_message_id`，构造占位消息推入列表，然后等待后端响应。这导致：

1. **ID 冲突风险**：前后端 ID 生成策略不一致时，可能出现重复或覆盖
2. **状态同步复杂**：前端 thinking 消息与后端实际消息在 `content`、`blocks`、`finishReason` 上需要双向同步
3. **重生成场景混乱**：重新生成时，前端需要手动替换旧消息，容易出错

新架构将 thinking ID 的生成权完全交予后端（`agent_chat_application_service.rs` 第 6 步），前端仅作为事件的**被动消费者**。`chatHistoryStore` 从 400+ 行简化为只管"追加/删除/编辑"，流式复杂度全部收敛到 `chatStreamStore`。

### 8.2 全局流消息池的 OOM 防御

`activeStreamMessages` 是 `reactive<Map>`，理论上可以无限增长（用户快速切换多个话题，每个话题都在后台生成）。防御措施：

- **上限**：`MAX_STREAM_MESSAGES = 100`
- **清理策略**：按插入顺序（Map 保持插入顺序），删除最旧的**非活跃**消息（不在当前 `activeStreamingIds` 中）
- **延迟清理**：流结束后延迟 1 秒才从池中删除，确保 `finalizeStream` 和 UI 收尾能拿到对象

### 8.3 Object Hydration 的必要性

没有 Hydration 时，话题切换的时序问题如下：

```
T0: 用户发送消息，AI 开始流式生成 (msg_001)
T1: 用户切换到话题 B
T2: AI 继续推送 msg_001 的 data 事件 (msg_001 在 activeStreamMessages 中)
T3: 用户切回话题 A，loadHistory 从 DB 读取 msg_001 (死的 Plain Object)
T4: AI 继续推送 msg_001 的 data 事件
    → 若使用 DB 骨架：UI 不会更新（非响应式）
    → 若使用 Hydration：用 activeStreamMessages 中的 reactive 对象替换，UI 自动更新
```

Hydration 是 Backend-Driven Streaming 能在多话题场景下正常工作的**关键补丁**。

### 8.4 会话一致性提交门禁

历史分页已改为普通 request-response，不再依赖可能丢失尾帧的 Channel completion。每次请求冻结完整 `ConversationKey(ownerId, ownerType, topicId, epoch)` 并分配 `loadId`；返回、异常与 `finally` 都只有在 key/epoch/loadId 仍是当前 owner 时才能提交列表、loading 与 controller。流式回调同样使用冻结 key，而非只比较 topicId，因此 A→B→A 也不会接纳旧 epoch 的回调。

### 8.5 附件路径解析的安全策略

`attachmentStore.resolveMessageAssets` 负责将 Rust 返回的本地物理路径转换为 WebView 可访问的 URL：

- 仅对 `type.startsWith("image/")` 的图片执行转换
- 排除 `http://` / `https://` / `data:` 开头的已有 URL
- 使用 Tauri 的 `convertFileSrc(sourcePath)` 生成 `asset://` 或 `http://asset.localhost/` 协议 URL
- `resolvedSrc` 为**纯运行时字段**，不持久化到 DB，避免跨端同步时路径失效

### 8.6 编辑重发的乐观更新与持久化一致性

当用户长按某条用户消息选择"编辑重发"时：

1. `editingOriginalMessageId` 被设为该消息 ID，输入框回填内容
2. 用户修改内容后点击发送，`sendMessage` 检测到 `editingOriginalMessageId` 存在
3. 调用 `truncate_history_after_timestamp` 从后端删除该时间戳之后的全部消息
4. 前端乐观截断 `currentChatHistory`：`slice(0, targetIndex + 1)`
5. 调用 `triggerGeneration(targetMsg)` 以修改后的消息重新启动生成

这一流程确保了**前端状态与后端数据库在截断操作上的原子一致性**：前端在调用后端截断成功后，才更新本地数组。

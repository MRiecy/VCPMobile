# 01. 应用架构与生命周期

## 1. 概述

### 1.1 领域定位

本文档覆盖 VCP Mobile 前端层的**应用级骨架**——从浏览器（WebView）加载到用户可见界面的完整链路。该领域不负责具体业务功能（如聊天、Agent 设置），而是承载以下横切关注点：

本应用的产品运行范围仅为 Android `arm64-v8a` 触控手机、平板与按当前窗口宽度响应的折叠屏。文中的“大宽度”“常驻侧栏”均指 Android WebView 窗口模式，不表示 Windows/macOS/Linux 桌面端支持；桌面用户使用 VCPChat。完整边界见 [`docs/ANDROID_UI_COMPATIBILITY.md`](../../ANDROID_UI_COMPATIBILITY.md)。

- **应用入口编排**：Vue 实例创建、Pinia / Router / 指令注册、样式系统挂载
- **启动引导状态机**：权限检查 → 后端核心就绪等待 → 业务数据预加载 → READY
- **全局 DOM 层级秩序**：背景层、主内容、抽屉、覆盖层、启动屏的 Z-Index 语义化堆叠
- **物理按键拦截**：Android 返回键的三层消费模型与 Modal History Stack（Operation Aegis）
- **生命周期桥接**：WebView 的 \visibilitychange 与 Android pause/resume/stop 事件的跨层映射

该领域是前端所有业务模块的**物理底座**。任何覆盖层、抽屉、页面栈的层级冲突，或启动时序的竞态条件，都应首先回归此处诊断。

### 1.4 核心设计原则

| 原则 | 说明 |
|------|------|
| **物理按键优先挂载** | 所有 \vcp-exit-requested、\vcp-hardware-back 监听器在 \bootstrapApp() 之前同步注册，防止启动阻塞期间返回键失效 |
| **状态机单线程推进** | ppLifecycle.ts 使用 \bootstrapPromise 单例保证并发调用被合并为同一 Promise，杜绝重复初始化 |
| **DOM 顺位即层级** | App.vue 中除语义化 z-* 类外，大量依赖 DOM 后声明者自然覆盖前声明者的策略，减少魔法数字 |
| **Z-Index 语义化** | 禁止裸写 z-50、z-[999]，所有覆盖层必须取自 layers.ts 的 12 级语义命名；editor=70、viewer=80 |
| **窗口宽度驱动** | 手机、平板、折叠屏复用同一 DOM/Store；布局按当前 viewport 推导 overlay/single-pane/dual-pane，不按机型或方向分叉 |
| **Backend-Driven 就绪检测** | 前端不猜测后端状态，而是通过 get_system_snapshot 快照 + \vcp-system-event 事件双通道确认核心引擎就绪 |
| **应用生命周期统一托管** | `useAppLifecycle()` 组合式函数集中订阅 `vcp-lifecycle-changed` 与 `visibilitychange`，统一更新 `isBackground` 并触发流恢复 |
| **流式会话后台恢复** | 应用回到前台或网络恢复时，`chatStreamStore.checkAndRecoverInterruptedStreams()` 接续异常中断的生成 |

### 2.2 插件注册顺序与理由

| 顺序 | 插件/模块 | 理由 |
|------|----------|------|
| 1 | `pinia` | 状态管理必须在所有使用 Store 的组件/逻辑之前就绪。App.vue 的模板直接依赖 `lifecycleStore.state`，若 Router 先于 Pinia 注册，则路由守卫中访问 Store 会触发未初始化错误 |
| 2 | `router` | 路由系统需在挂载前就绪，但可晚于 Pinia，因为路由配置本身不依赖 Store；`router.isReady()` 的 await 在 App.vue `onMounted` 中执行 |
| 3 | 指令 (`v-intersection-observer`, `v-longpress`) | 全局指令属于纯模板增强能力，无运行时依赖，最后注册不影响任何初始化时序 |
| 4 | 样式 (`uno.css`, `themes.css` 等) | 样式导入为副作用导入，不改变 JS 运行时状态，在 `mount` 前完成即可保证首屏渲染时 CSS 已生效 |

> **关键约束**：`main.ts` 本身**不**调用任何 Tauri Command 或执行异步初始化。所有重度异步逻辑（权限检查、主题加载、数据预加载）被下放到 `App.vue` 的 `onMounted` → `bootstrapApp()` 中，确保 Vue 应用已挂载到 DOM，监听器和响应式系统可用。前端资源只从 APK 内嵌 assets 加载，不再存在运行时前端 OTA 启动标记。

**层级设计细节**：

- **PermissionGate 与 BootScreen 的互斥**：`v-if` / `v-else` 保证两者永不同时渲染。PermissionGate 在 `PERMISSIONS` 态独占屏幕；BootScreen 在其余非 `READY` 态（含 `BOOTING/CONNECTING/PRELOADING/OPTIMIZING/ERROR`）渲染。
- **Background Layer 的 Transition 策略**：使用 `:key="backgroundStyle.backgroundImage"` 强制 Vue 在壁纸变更时重新创建 DOM 节点，配合 `bg-fade` CSS Transition 实现跨壁纸的淡入淡出。
- **Drawer Overlay 跟随呈现模式**：仅当对应侧栏以 overlay drawer 呈现且处于 open 状态时显示遮罩；不能用“`md` 等于桌面”的假设直接隐藏。分屏或折叠后窗口变窄时必须重新进入 overlay 行为。
- **DOM 顺位 + 显式 z-index 混合策略**：覆盖式 AgentSidebar / RightSidebar 与遮罩使用 `z-drawer`（20）；常驻 pane 回到局部工作区层级。更高层的 FeatureOverlays、ShareAgentSelector、UpdatePrompt 与 GlobalOverlayManager 使用 `layers.ts` 语义类，避免依赖更大魔法数字。

### 3.2 Android 窗口响应式工作区

根 shell 在 `READY` 后承载同一份 AgentSidebar、主 Chat 与 RightSidebar，并按当前 WebView 可用宽度推导三种只读表现模式：

- `overlay`（`<1024px`）：左右均为覆盖抽屉，主区占满窗口；
- `single-pane`（`1024–1279px`）：左栏 280px 常驻，右栏保持抽屉与遮罩；
- `dual-pane`（`>=1280px`）：左栏 280px、右栏 300px 常驻，但必须保留主聊天区最小可读宽度。

响应式模式只改变 CSS 几何，不接管 `layoutStore.leftDrawerOpen/rightDrawerOpen`，也不复制组件树。旋转、分屏与折叠/展开根据新 viewport 自动重排。工作区横向子项必须 `min-width: 0`，纵向滚动链必须 `min-height: 0`，避免长代码、表格或 Mermaid 撑破主区。

这里没有“桌面模式”。host 浏览器预览可用于快速检查，但不能作为 Android WebView 的布局、触控或安全区证据。

### 3.3 背景壁纸系统

> 逻辑位置：`src/App.vue` 第 240–270 行

壁纸解析采用**双模式回退链**：

```
当前主题变量 ──> 取 light/dark 对应模式壁纸
       │
       ▼
┌─────────────────────┐
│ 当前模式有壁纸?      │──> 有则直接使用
│ (非 "none")         │
└──────────┬──────────┘
      No   │
       ┌───┘
       ▼
┌─────────────────────┐
│ 尝试另一模式壁纸     │──> 例如暗色模式缺壁纸时回退到亮色壁纸
│ (跨模式回退)         │    保证任何主题下都不出现空背景
└──────────┬──────────┘
       No   │
       ┌───┘
       ▼
   返回 {} (透明背景，由 CSS 变量兜底)
```

**文件名净化逻辑**：

1. 用正则 `url\(['"]?(.*?)['"]?\)` 提取 CSS `url()` 中的路径
2. `replace(/^.*[\\\/]/, "")` 去除路径前缀
3. `split(".")[0] + ".webp"` 强制替换为 `.webp` 扩展名，匹配 `public/wallpaper/` 目录下的优化后资源

### 3.4 抽屉与遮罩交互

左右抽屉的开关状态由 `layoutStore`（`useLayoutStore`）集中管理：

| 抽屉 | Store 状态 | 关闭触发方式 |
|------|-----------|-------------|
| 左侧 AgentSidebar | `layoutStore.leftDrawerOpen` | 遮罩点击、侧边栏内关闭按钮、全局 Swipe 手势 |
| 右侧 RightSidebar | `layoutStore.rightDrawerOpen` | 遮罩点击、`@close` 事件、全局 Swipe 手势 |

全局 Swipe 手势通过 `useSidebarSwipe(appRootRef, { type: "global" })` 注册在根容器上，与抽屉组件内部的局部 Swipe 形成嵌套手势系统。

常驻 pane 不显示抽屉遮罩；overlay 模式继续由遮罩点击、边缘 Swipe 与 Android 返回键关闭。窗口模式变化不得产生“store 显示已打开、组件却不可达”的分离状态。

## 4. 启动引导流程

### 4.3 生命周期 Store 的职责

> 文件位置：`src/core/stores/appLifecycle.ts`

`useAppLifecycleStore` 采用 Pinia Composition API 风格（`defineStore('appLifecycle', () => { ... })`），对外暴露以下核心能力：

**状态与计算属性**：

| 属性 | 类型 | 说明 |
|------|------|------|
| `state` | `Ref<AppState>` | 当前七态值，驱动 App.vue 的渲染分支 |
| `statusText` | `Computed<string>` | 人类可读的状态描述，BootScreen 主标题来源 |
| `currentPhaseLabel` | `Ref<string>` | 当前阶段细标签，PRELOADING 态动态更新 |
| `errorMsg` | `Ref<string \| null>` | ERROR 态的详细错误信息 |
| `isBootstrapping` | `Ref<boolean>` | 是否正在执行 bootstrap（防并发重入） |
| `hasBootstrapped` | `Ref<boolean>` | 是否至少完成过一次成功引导 |
| `coreStatus` | `Computed<VcpStatus>` | 委托自 `notificationStore.vcpCoreStatus` 的代理；运行时还包含数据库物理优化使用的 `optimizing` 状态 |

**核心方法**：

| 方法 | 说明 |
|------|------|
| `bootstrap(force?)` | 完整的七态引导流程入口。使用单例 Promise 合并并发调用；`force=true` 用于 PermissionGate 中用户点击"进入应用"后的强制重试 |
| `hydrateSystemStatus()` | 主动拉取后端系统快照（core / log / sync / distributed + databaseRecovery），校准前端通知 Store、分布式状态与数据库恢复告警 |
| `setState(nextState, reason)` | 内部状态切换，自动记录时间戳与日志 |
| `fail(message)` | 统一的错误收敛点：清理等待器、设置 errorMsg、切换到 ERROR 态、通知核心状态看板 |

**预加载任务调度**：

`startPreloading()` 采用**全并发**策略：配置、Agent/Group、Avatar 预加载同时执行，若 Pinia 已恢复活跃会话，还把首屏聊天历史也加入同一 `Promise.all`，让 DB + IPC 开销与 Vue 组件挂载并行，首屏 ChatView mount 后可直接命中缓存：

```
startPreloading()
    │
    ▼
┌─────────────────────────────────────────────┐
│ 并发预加载                                   │
│ Promise.all([                                │
│   settingsStore.fetchSettings(),             │
│   assistantStore.fetchAgentsAndGroups(),     │
│   avatarStore.preloadMetadata()              │
│   ...(session 恢复时) historyStore.preloadHistory(...5 条) │
│ ])                                           │
│                                              │
│ 完成 -> READY                                │
│ 随后异步加载话题列表（不阻塞首屏渲染）        │
└─────────────────────────────────────────────┘
```

Avatar 预加载只读取 owner/hash/颜色/更新时间，不再把全部头像二进制送入启动 IPC；`VcpAvatar` 在进入视口前 300px 时按需读取。v1.1.3 已移除旧版的 150 ms 视觉防抖，预加载完成后立即切到 `READY`，避免人为延迟。

**核心就绪等待（`waitForCoreReady`）**：

采用**快照直读 + 响应式监听**的双保险：

1. **快照直读**：`hydrateSystemStatus()` 已把 `core` 状态写入 `notificationStore.vcpCoreStatus`，`waitForCoreReady` 直接读取该真相源，避免重复 IPC。
2. **响应式监听**：若状态为 `initializing`，则通过 `watch` 监听 `vcpCoreStatus.status`，等待其变为 `ready` 或 `error`。
3. **物理优化状态**：若后端进入 `optimizing`，切换到 `OPTIMIZING` 并取消 15 秒超时；后端变为 `ready` 后继续预加载。
4. **兜底超时**：`CONNECT_TIMEOUT_MS = 15000`，防止后端挂死时前端无限等待。

### 5.2 Modal History Stack（Operation Aegis）

> 文件位置：`src/core/composables/useModalHistory.ts`

Operation Aegis 是 VCP Mobile 的**统一返回手势拦截系统**，解决混合应用（Hybrid App）中物理返回键与 WebView History 的天然冲突。

**核心机制**：

1. **Dummy State 注入**：`initRootHistory()` 在 `window.history` 中压入一个带有 `vcpMain: true` 标记的 dummy state。这是"防护盾"——只要 dummy state 在栈底，任何 `popstate` 都不会导致 WebView 直接退出。

2. **Modal 注册**：当 Sidebar、SlidePage、Dialog 等覆盖层打开时，调用 `registerModal(id, closeHandler)`：
   - 向 history 压入一个带 `vcpModalId` 的 state
   - 将 `{ id, close }` 推入 LIFO 栈 `modalStack`

3. **PopState 拦截**：全局 `popstate` 监听器按以下优先级处理：
   - 若在 `INTERNAL_BACK` 状态（由 `unregisterModal` 触发），忽略
   - 若当前路由不是 `/chat` 或 `/`，交给 vue-router 处理真实路由后退
   - 若 `modalStack` 非空，关闭栈顶 Modal 并从栈中移除
   - 若弹到了 dummy state 之外，触发 `vcp-exit-requested` CustomEvent，然后重新注入 dummy state（THE BOUNCE）

**状态机**：

```
        ┌─────────────┐
        │    IDLE     │◄────────────────────────────┐
        └──────┬──────┘                             │
               │ registerModal                      │
               │ (UI 打开覆盖层)                     │
               ▼                                    │
        ┌─────────────┐     popstate 触发关闭      │
        │POPSTATE_    │────────────────────────────┘
        │HANDLING     │     执行 close() → 移除栈顶
        └─────────────┘     回到 IDLE
               ▲
               │ unregisterModal (UI 主动关闭)
               │ state = INTERNAL_BACK
               │ history.back()
        ┌──────┴──────┐
        │ INTERNAL_   │───► popstate 触发，识别为内部回退
        │   BACK      │     直接回到 IDLE，不执行关闭逻辑
        └─────────────┘
```

**路由避让原则**：

```typescript
// useModalHistory.ts 第 51–54 行
const currentPath = window.location.hash.replace(/^#/, '') || '/';
if (currentPath !== '/chat' && currentPath !== '/') {
  return; // 交给 vue-router
}
```

对于 `/settings`、SlidePage 路由等真实页面，返回手势应执行路由后退而非关闭 Modal。此判断确保 Aegis 仅在主界面（无真实路由可退时）生效。

### 5.3 Android 生命周期事件（pause/resume/stop）

> 监听逻辑：`src/core/composables/useAppLifecycle.ts`

v1.1.3 将生命周期监听从 `App.vue` 的 `window.addEventListener("vcp-lifecycle")` 重构为独立的 `useAppLifecycle()` 组合式函数。Rust 侧 `lifecycle_controller.rs` 通过标准 Tauri Event 通道广播 `vcp-lifecycle-changed`，前端使用 `listen()` 订阅：

```typescript
// src/core/composables/useAppLifecycle.ts 第 52–64 行
unlisten = await listen<{ state: string }>("vcp-lifecycle-changed", (event) => {
  const state = event.payload.state;
  if (state === 'pause' || state === 'stop') {
    lifecycleStore.isBackground = true;
  } else if (state === 'resume') {
    lifecycleStore.isBackground = false;
    streamStore.checkAndRecoverInterruptedStreams().catch(err => { ... });
  }
});
```

| 原生事件 | 事件 state | 前端行为 |
|---------|-----------|---------|
| `onPause` / `onStop` | `"pause"` / `"stop"` | `lifecycleStore.isBackground = true`；`useAppLifecycle` 中的 `watch` 为 `<html>` 添加 `vcp-paused-animations` 类，全局暂停 CSS 动画 |
| `onResume` | `"resume"` | `lifecycleStore.isBackground = false`；移除动画暂停类；调用 `hydrateSystemStatus()` 校准系统快照；触发 `chatStreamStore.checkAndRecoverInterruptedStreams()` 恢复被中断的流 |

**页面可见性兜底**：`document.visibilitychange` 与 `window.online` 提供额外防线。切到后台或断网时同样设置 `isBackground` 并暂停动画；回到前台或网络恢复时尝试流恢复。

> **注意**：v1.1.3 前端不再在生命周期切换时调用 `set_vcp_log_heartbeat` 调整心跳间隔，该逻辑已从 `App.vue` / `useAppLifecycle` 中移除。

### 5.4 VCP System Event 监听

> 监听逻辑：`src/App.vue` 第 394–401 行

```typescript
unlistenLog = await listen("vcp-system-event", (event: any) => {
  const payload = event.payload;
  const processed = processPayload(payload);
  if (processed && !processed.silent) {
    notificationStore.addNotification(processed);
  }
});
```

`vcp-system-event` 是 Rust 后端向前端推送系统级通知的核心通道。`useNotificationProcessor` 将原始 payload 解析为结构化的通知对象，再由 `notificationStore` 决定是显示 Toast、更新状态栏，还是静默处理。

**挂载时机约束**：此监听器必须在 `bootstrapApp()` 之前注册。因为 `bootstrap()` 中的 `waitForCoreReady()` 依赖 `vcpCoreStatus` 的变更，而该变更可能由 `vcp-system-event` 事件驱动。若监听器晚于 bootstrap 注册，则 bootstrap 期间的 `ready` 事件会丢失，导致 15 秒超时。

## 7. 设计决策与注意事项

### 7.1 为什么物理按键监听在 bootstrap 之前挂载？

`src/App.vue` 的 `onMounted` 中，第 382–387 行的 `addEventListener` 调用位于第 404 行 `await bootstrapApp()` 之前。这是**混合应用黄金铁律**：

- `bootstrapApp()` 内部包含多个可能阻塞的异步操作（权限检查、核心就绪等待、预加载），总耗时可达数秒。
- 若用户在此期间按下物理返回键，而监听器尚未注册，WebView 将执行默认行为（直接退出或返回上一页）。
- 更严重的是，Android 的 `onBackPressed` 若未在前端被消费，可能导致 Activity 直接销毁而非 `moveTaskToBack`。

因此，所有与物理交互相关的监听器必须以**同步、零依赖**的方式在 bootstrap 前完成注册。

### 7.2 生命周期事件为何改用 Tauri Event 通道？

v1.1.3 之前，`vcp-lifecycle` 曾通过 Kotlin `LifecycleBridge.kt` 的 `evaluateJavascript` 以 `window.CustomEvent` 方式注入前端。v1.1.3 起，生命周期事件改为 Rust `lifecycle_controller.rs` 统一广播的 Tauri Event `vcp-lifecycle-changed`，并由 `useAppLifecycle()` 组合式函数通过 `listen()` 订阅。这一变化基于以下权衡：

| 维度 | 旧 CustomEvent (`evaluateJavascript`) | 新 Tauri Event (`listen()`) |
|------|--------------------------------------|----------------------------|
| **注册成本** | 零，前端直接 `window.addEventListener` | 需要 Tauri Runtime 初始化完成 |
| **时序确定性** | WebView 加载完成即可接收 | Rust 核心就绪后即可接收 |
| **与后端状态联动** | 仅前端感知，需自行推断核心状态 | Rust 可同步核心状态后再广播，避免竞态 |
| **类型安全** | 弱，需手动 `as CustomEvent` 断言 | 强，通过 Rust 类型生成 |
| **生命周期恢复** | 需前端自行触发恢复逻辑 | Rust 可在 resume 时统一调配 Linger 任务与流恢复 |

`vcp-hardware-back`、`vcp-permission-change` 等仍需在 WebView 层**尽早可达**的事件仍保留 `window.CustomEvent` 方案；而应用前后台切换这类与后端状态强相关的事件，统一走 Tauri Event 可减少前端与 Rust 之间的状态窗口期。

### 7.3 为什么 Bootstrap 使用单例 Promise？

`appLifecycle.ts` 第 36 行的 `bootstrapPromise` 用于合并并发调用：

```typescript
if (bootstrapPromise && !force) {
  console.log('[Lifecycle] Reusing existing bootstrap promise');
  return bootstrapPromise;
}
```

场景：用户在 PermissionGate 点击"进入应用"后快速切换应用到后台再返回，可能触发二次 `bootstrap()` 调用。单例 Promise 保证：

1. 同一时刻仅存在一个引导流程在执行
2. 多个调用方（如 App.vue 自动触发 + PermissionGate 手动触发）共享同一结果
3. `force=true` 作为逃生舱，供用户主动点击"重试"时绕过复用逻辑

### 7.4 为什么 `initRootHistory` 在 router ready 后执行？

`initRootHistory()` 的第一次调用在 `router.isReady()` 之后（`src/App.vue` 第 407–408 行），而非 `onMounted` 开头。原因是：

- `createWebHashHistory()` 在初始化时会自动替换当前 history state
- 若在 router 就绪前注入 dummy state，router 的初始化操作可能覆盖或打乱 state 栈
- 等待 `router.isReady()` 确保 Hash 路由的初始导航已完成，此时注入 dummy state 可稳定处于栈底

此外，`router.afterEach(() => initRootHistory())` 作为后置守护，在任何路由切换后自动校准防护盾，防止第三方代码或深层导航意外弹出 dummy state。

### 7.5 视觉防抖机制的移除

v1.1.3 已移除 `startPreloading()` 中的 150 ms 视觉防抖逻辑。原因如下：

- 现代机型上本地 SQLite + 内存缓存命中可在 20 ms 内完成，人为延迟反而让首屏显得"卡顿"。
- 全并发预加载把配置、Agent/Group、Avatar、首屏历史并行化，实际耗时已足够让用户感知到加载过程。
- 若后端正在进行数据库物理优化，`waitForCoreReady` 会进入 `OPTIMIZING` 态并展示进度文案。

因此当前 BootScreen 的显示时长完全由真实任务耗时决定，不再强制补白。

# Android 与 iOS 跨平台开发规范

Vue 跨平台差异默认使用运行时分支；Rust、Kotlin、Swift 保留必要的原生编译隔离。Android 与 iOS 共享页面、Store 和业务流程，差异留在实际需要它的功能内。

功能目标以用户最新决定为准，当前实现以生产代码为准。[功能审批](../plan/vcpmobile-ios-compatibility-research/phase-2/09-功能权限与提示审议表.md) 管理功能范围；[移动端 UI 兼容性规范](./MOBILE_UI_COMPATIBILITY.md) 管理布局、CSS、Insets 与触控；[Android 插件管理规范](./ANDROID_PLUGIN_MANAGEMENT.md) 管理 Android 原生接入。本文件不记录阶段进度，也不把现有能力模型固定为后续架构。

## 1. 前端统一使用运行时平台信息

前端从 [统一平台入口](../src/core/utils/platform.ts) 取得身份，简单差异直接使用 `isIOS`、`isAndroid`。入口使用官方 [OS 插件](https://v2.tauri.app/plugin/os-info/) 的同步平台信息；组件不自行读取 UA、环境变量或调用另一种识别方式。普通 Vite 预览不冒充手机平台，布局仍只响应当前窗口宽度。

平台身份不依赖功能能力查询、权限请求或原生监听是否就绪。平台信息入口只提供身份，不附带功能审批表、权限状态机或加载重试流程。

- 文案差异使用计算属性或局部配置。
- 显示差异使用明确的条件渲染。
- 不可执行但保留入口的操作，点击说明并返回。
- 实际操作进入现有业务所有者，按本次调用需要处理系统权限与运行条件。
- 多处入口需要同一规则时，在所属功能内提取共用逻辑。

不要求每个按钮建立适配器，也不为形式统一增加转发层、平台页面副本或全局策略框架。已批准、已实现和已授权是不同事实；按实际消费者表达这些区别，不要求每项功能填写统一状态表。

## 2. 原生编译与资源归属

### 2.1 Rust 与 Cargo

平台专用的 import、类型、实现和依赖必须落在相同的目标边界。使用准确的 `target_os`，明确区分 Android、iOS 与 host 开发分支：

```rust
#[cfg(target_os = "android")]
mod android;

#[cfg(target_os = "ios")]
mod ios;

#[cfg(not(any(target_os = "android", target_os = "ios")))]
mod host;
```

这是模块隔离形式的示例，不要求把所有现有小分支拆成三个文件。少量差异可以留在函数内部；当平台资源、清理流程或类型体系已经独立时，再按领域拆分适配模块。共享请求解析、持久化和业务终态留在原领域 owner，不复制成两份业务实现。

- `#[cfg(not(target_os = "android"))]` 包含 iOS，不能用它承载 host 假实现。只有各目标语义确实相同的共享代码才使用宽条件。
- `cfg!(...)` 只生成布尔值，不移除分支；平台上不存在的类型或 API 需要 `#[cfg]` 隔离，不能依靠 `if cfg!(...)` 绕过编译。见 [Rust cfg 文档](https://doc.rust-lang.org/stable/core/macro.cfg.html)。
- 原生依赖放入对应的 `[target.'cfg(target_os = "android")'.dependencies]` 或 iOS 段；Cargo feature 用于可选能力，不另建能与目标 OS 冲突的 `ios=true` 产品开关。见 [Cargo 平台依赖](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html#platform-specific-dependencies)。
- `build.rs` 自身运行于构建主机；需要选择产品目标时读取 Cargo 提供的目标环境信息，不能以构建脚本自身的 `cfg!(target_os)` 判断正在构建的手机平台。
- host scaffold 和 fixture 不建立桌面产品能力。iOS 未实现返回真实不可用结果，不返回模拟电量、空成功文件路径或无副作用的 `Ok(())`。

### 2.2 Kotlin 与 Swift

Kotlin、JNI 与 Android 组件留在 Android target；Swift、Apple framework 与 Apple 工程声明留在 iOS target。Swift 的条件编译和运行时 `#available` 分工不同：SDK 能编译某符号，不代表 minimum system version 覆盖的全部设备都能调用。Android 新 API 同样要按实际版本条件处理。

系统对象的生命周期归原生适配层，Chat/Sync/SQLite/CAS 等业务生命周期归 Rust。原生 UI 必须在对应 UI 线程操作。请求成功、取消、失败、调用者消失及迟到回调都要有确定的资源释放路径；不能因为两个平台回调机制不同而建立第二份业务完成状态。

工程变更写入实际维护的配置、Manifest、Info.plist 或可重放生成输入，不只修改下一次生成就会丢失的工程文件。平台专用用途描述、组件、entitlement 与权限只随实际接入的能力增加。

## 3. 沿完整功能链处理执行与反馈

检查一条完整路径：入口如何呈现 → 点击执行或说明 → 自动启动、监听与恢复是否发生 → 本次结果如何反馈。隐藏界面不会自动停止初始化；保留说明入口也不表示应启动原生操作。定时任务、导入配置和 AI 调用按各自真实入口处理，多处共用的执行条件归所属功能所有者。

本项目不以防范调用方绕过界面的假想安全风险设计跨平台功能。Vue 已能确定的入口差异由 Vue 处理，不要求 Rust 再复制一套功能门禁。后端保留处理实际输入、文件、连接、任务和系统资源所需的检查；系统授权由真正使用该 API 的原生操作查询和请求。不要把统一门禁改名后逐命令复制。

共同权限引导共享外壳，只列出该平台真实存在且已接入的权限项目。未实现不等于未授权，不请求不存在的权限，也不用假定已授权来凑齐流程；从系统设置返回后刷新相关状态，可选权限不阻断无关功能。

说明入口应能正常点击，不能只给 HTML `disabled` 按钮绑定提示。预期不可用由该入口解释；执行后的成功、取消、拒绝和失败由现有结果所有者反馈，调用链各层不重复 Toast。取消后清理资源并返回，成功文案依据真实结果；超时按该任务实际语义处理，不自动视为取消或失败。

按真实消费者需要调整结果类型，不建立无人使用的通用错误系统。部分数据缺失时保留其余有效结果，不伪造零值或把缺失扩大成整个功能失败。AI 工具描述与实际执行范围保持一致。

命令注册和 Tauri 所需授权沿现有调用方式配置，见 [插件局部规范](../src-tauri/plugins/vcp-mobile/AGENTS.md)。内部 Rust 接口不为形式对称而向 Vue 公开；框架接入配置不承担产品功能审批。

## 4. 完整示例

以下说明写法，具体功能范围仍以审批为准，不表示原生适配已经完成。

| 功能 | 入口与操作 | 初始化和反馈 |
|---|---|---|
| 更新说明 | 共享设置页保留入口。Android 进入现有更新流程；iOS 点击说明“iOS 版本需在应用外自行签名安装更新”，然后返回 | 版本展示可共享；iOS 不初始化 APK 检查、下载和安装监听 |
| 共同权限引导 | 两平台共享引导外壳，按实际权限列项；iOS 不出现 OEM 自启动、通知监听或电池豁免 | 检查、请求和继续条件按真实项目定义；请求结束或返回设置后显示本次结果，不复用整套 Android 命令 |
| 缓存差异 | 共享维护页用计算文案说明本平台清理范围；实现后进入对应原生操作，尚未实现时说明并返回 | 完成提示只描述实际清理的内容，不把 WebView 缓存扩大为业务数据库或用户数据；无需前端编译裁剪 |

## 5. 何时研究前端编译裁剪

Vue 条件渲染不保证相关代码从产物中删除。只有出现大型平台专属依赖、不可接受的模块加载副作用或明确包体收益时，再研究构建裁剪；引入时同时解决目标来源、模块解析、类型检查与实际产物验证。

现阶段不要求平台别名体系、成套平台文件、额外构建入口或独立前端产物。

## 6. 实施与验证

沿当前生产调用链确定入口、状态和资源所有者，完成所涉及的显示、执行、初始化与反馈。简单差异直接处理；分享、后台执行或复杂资源生命周期等需要专题方案时再展开。批准某项功能不等于已实现，也不自动要求所有后续适配同时完成。

跨层或核心改动运行 `pnpm check`；插件 Rust 改动按局部规范检查，Kotlin/Manifest 改动编译对应 Android 目标。行为验证针对本次不确定性，例如说明入口误启动下载、通话切换丢失草稿、取消被报成失败；不把静态能力表复制成测试再相互印证。

iOS 日常进行源码审计和工程输入检查，Apple 编译与链接通过手动归档工作流验证。项目不建设 iOS 实机测试体系。源码判断、host 检查、归档与实际运行观察分别报告。见 [iOS 构建说明](IOS_BUILD.md)。

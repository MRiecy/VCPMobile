# 05 · Magi 三贤者审查与开放问题

> 按项目 §9.2 Magi 协议，对 01/02/04 篇方案做三方思辨，并汇总需要与用户讨论的决策点。

---

## 1. Melchior（逻辑与系统）

**关注点：内存安全、IPC 开销、类型完整性、OOM 防御。**

- ✅ 两个功能均为「Rust 代理 + 前端状态机」，无跨层共享可变状态，
  无 Rust 侧长生命周期对象，无生命周期风险。
- ✅ 日志全量快照上限 2MB（后端截断）+ Rust 侧 4MB JSON 上限 + 前端行数裁剪，
  三重防护下 OOM 风险可控。增量响应体通常 KB 级。
- ⚠️ **增量 offset 的字节语义**：后端按字节偏移切 UTF-8 文本，
  offset 落在多字节字符中间时会产生替换字符（U+FFFD）。
  AdminPanel-Vue 版未处理此问题（概率低但存在）。
  裁决：Rust 侧解析 JSON 后检查 content 首尾是否含 U+FFFD 并剥除半字符，低成本兜底。
- ⚠️ **trigger 的 180s 同步等待**：Tauri command 挂起 3 分钟期间，
  前端若反复点击会产生并发 trigger。裁决：store 层按 taskId 做 in-flight 去重 +
  pending 态禁用按钮；Rust 侧无需全局锁（后端自己有 running 标志与 already-running 跳过）。
- ✅ 前端轮询全部页面级（SlidePage 关闭即销），不存在泄漏定时器的长驻对象。

## 2. Balthasar（直觉与美学）

**关注点：移动端原生直觉、UI 宪法、微动画、交互心理学。**

- ✅ 日志级别用 2px accent bar + 单色文本的方案与 UI 宪法完全同构
  （AdminPanel-Vue 的 3px accent bar 语言天然契合，收敛为 2px）。
- ⚠️ **日志行不换行 + 横向滚动**在长 JSON 行上阅读体验差；
  但换行会破坏固定行高虚拟滚动。裁决：默认不换行横滚（与桌面一致、保性能），
  溢出菜单提供「自动换行」开关——开启时切换为动态测高列表（仅建议 ≤500 行时使用，
  UI 上给出性能提示）。
- ⚠️ 任务编辑器的「占位符 chips 点击插入」是本次最有价值的移动端原生设计，
  建议在 chips 行加横向滑动 + 插入时轻微高亮反馈（透明度变化，不用缩放）。
- ✅ 「更多」popover 从 3 → 5 项后改三列网格，保持圆角胶囊按钮语言一致；
  新增两入口图标语义清晰（ScrollText / CalendarClock）。
- ⚠️ 全局开关「拨动即生效」与 03 篇灵感 7（三段式防护）表面冲突。
  裁决：任务全局调度开关语义简单、无副作用扩散，拨动即生效 + Toast 可撤销感知即可；
  三段式防护留给真正高危的运行时开关（如分布式连接）。

## 3. Casper（务实与交付）

**关注点：工程复杂度、维护成本、实现周期，拒绝过度设计。**

- ✅ 复用度极高：admin_api 认证模式（diary）、useVirtualList（diary/topic）、
  SlidePage/overlay 页面栈、BottomSheet/Toast、`vcp-lifecycle-changed` 事件，全部现成。
- ⚠️ **是否抽 `admin_api_client.rs` 共享层？** 裁决：抽，但只做最小面
  （构造 client + URL 拼接 + basic_auth + 大小上限四件事），
  不做泛化封装； Diary 模块暂不重构迁入，仅新模块使用，避免无收益回归风险。
  （推翻 04 篇「三模块共用」的激进表述，降级为「新模块共用，日记不动」。）
- ⚠️ **02 篇范围仍然偏大**（10 端点 + 编辑器 + 历史 + 委托）。裁决：
  S2 内部再切两个交付批次——S2a：任务列表 + 启停 + 触发 + 历史 + 全局开关（只读为主，可快速上线）；
  S2b：任务编辑器（新建/编辑/删除）+ 委托追踪。每批独立可用。
- ✅ 不需要动 Android 插件、不需要新权限、不需要数据库——CI 影响面小。
- ❌ 否决项：不在本期做归档日志浏览（后端无 API）、不做 AA Agent 管理、
  不做 cron 表达式前端解析器（回显后端 nextRunTime 即可）。

## 4. 综合裁决摘要

1. 总体方案可行，架构与项目既有范式完全同构；
2. S1 日志中心先行，S2 任务中心拆 a/b 两批，S3 插件灵感后续评估；
3. 共享层最小化：只抽 admin_api_client 给新模块用，日记模块不动；
4. 三个需要在施工前钉死的技术点：UTF-8 半字符兜底、trigger in-flight 去重、
   日志换行模式的测高方案。

## 5. 开放问题（与用户讨论）

1. **入口位置**：两个新功能放「更多」popover（当前方案），还是直接把
   「日志中心」提升为托盘主按钮（与插件中心/灵视中心/日记中心平级，变 2×2 四主按钮 + 更多）？
2. **日志中心默认行数**：移动端建议默认 500（桌面 AdminPanel 版 5000）。是否接受？
3. **任务中心 MVP 边界**：S2a（只读 + 启停 + 触发）先行、S2b（编辑器）随后，
   还是希望一次性完整交付？
4. **Agent 列表数据源**（02 篇 O-2）：目标 Agent 选择器依赖
   `/admin_api/agent-assistant/config` 的响应结构，施工前需要一次真实环境验证；
   若你的服务器可访问，我们可以先写个只读探测脚本确认字段。
5. **异步委托追踪**：只读展示 + 取消按钮是否够？是否需要「从委托跳到对应 Agent 对话」的深链？
6. **插件中心灵感**（03 篇）：10 条灵感中你希望哪几条优先进入后续迭代 backlog？

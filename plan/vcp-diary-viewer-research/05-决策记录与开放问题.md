# 05｜决策记录与开放问题

> 用途：区分“已经由源码证据冻结的决定”和“必须由实际部署/产品选择回答的问题”。  
> 状态词：`ACCEPTED` 可直接施工；`CONDITIONAL` 满足条件后施工；`DEFERRED` 当前不进入范围；`OPEN` 尚未裁决。

## 1. 已冻结 ADR

### ADR-001｜领域对象是整文件

- **状态**：`ACCEPTED`
- **决定**：以 `{folder, file}` 作为 `DiaryNoteKey`，正文是一个不透明字符串。
- **依据**：管理 API 的 list/get/save 粒度均为文件；结构化时间来自可选文件名解析。
- **后果**：不建立 `DiaryEntry`、entry ID、entry count 或条目级写入；未来出现可靠正文 schema 时另立 ADR。

### ADR-002｜一个全局 Diary 页面，内部切换状态

- **状态**：`ACCEPTED`
- **决定**：overlayStore 只新增 `diaryCenter`；list/reader/editor/preview 是 feature 内部状态。
- **依据**：项目主要以 Overlay/SlidePage 导航；Diary 状态共享强、路径短。
- **后果**：不新增 Router，不把 reader/editor 各注册成永久全局页面；内部返回由 ModalHistory 接管。

### ADR-003｜Rust 是远端访问与安全边界

- **状态**：`ACCEPTED`
- **决定**：URL、Basic Auth、reqwest、超时、response budget、schema、hash 与错误归一化全部留在 Rust。
- **依据**：VCPMobile 已有 SettingsState、Basic Auth 和有界网络模式；Vue 不应接触管理员密码。
- **后果**：Vue 只 invoke typed command；错误消息和日志不得包含凭据或完整远端 body。

### ADR-004｜一个 Composition Pinia Store

- **状态**：`ACCEPTED`
- **决定**：folder/list/search/document/editor 使用一个 `useDiaryStore`。
- **依据**：同一交互旅程中的 target、generation、baseline 和 dirty 状态需要原子协调。
- **后果**：不建立 shelf/reader/editor 平行 Store，不复制 overlayStore 或 ModalHistory。

### ADR-005｜管理 API 与 Human Tool 分离

- **状态**：`ACCEPTED`
- **决定**：浏览/搜索/整文件保存使用 admin Basic；DailyNote/LightMemo 使用 Bearer API Key。
- **依据**：VCPChat 真实调用链和官方接口是两套鉴权。
- **后果**：配置态、错误态、可用性探测与 UI 文案分开；不能用“API Key 已配置”代表管理能力可用。

### ADR-006｜所有响应必须有 Mobile 预算

- **状态**：`ACCEPTED`
- **决定**：采用流式累计、checked-add、解码后数量/长度二次校验；超限 fail closed。
- **依据**：服务端单文件 GET 当前没有大小上限；实际正文平均数 KiB、数百字节至数十 KiB，单目录数百至数千文件。
- **后果**：正文/提交 2 MiB、列表 8 MiB/10000 项作为高余量客户端边界；不静默截断后允许编辑。

### ADR-007｜所有读请求有 generation 与 target 提交门

- **状态**：`ACCEPTED`
- **决定**：folders/list/search/document 独立 generation；success、error、finally 都核对 owner 和完整 target。
- **依据**：桌面 list/read 没有 owner，存在迟到响应覆盖；VCPMobile 已有同类并发治理模式。
- **后果**：刷新保留旧内容，旧请求只可丢弃；搜索还在 Rust 侧取消旧 owner。

### ADR-008｜保存采用 best-effort 冲突预检

- **状态**：`ACCEPTED`
- **决定**：保存前 GET + baseline hash，匹配后 POST，再 GET read-back；force 必须由用户二次确认。
- **依据**：最新上游确认没有 ETag/revision/If-Match；管理 mutation 已进入 KnowledgeBaseManager 队列并异步调度索引。
- **后果**：明确承认 GET→POST 的 TOCTOU，不能称为 CAS，超时不能自动重试；HTTP 文件成功与索引异步追平分开表达。

### ADR-009｜日记正文按可信 HTML 处理

- **状态**：`ACCEPTED`
- **决定**：允许 raw HTML，采用 `marked.parse → v-html/innerHTML`；最多复用现有轻量 trusted-content 过滤，不新增严格 Diary 白名单。
- **依据**：日记来自用户自有 VCP 服务，保留 HTML 是产品能力；用户已明确接受该信任边界。
- **后果**：信任只覆盖 `DiaryDocument.content`；文件名、摘要、LightMemo 元信息和错误仍使用文本节点。编辑器始终保存原始正文，不回写浏览器规范化后的 DOM。

### ADR-010｜首版不做离线数据库或写队列

- **状态**：`ACCEPTED`
- **决定**：VCP 服务是唯一正文真相；只在内存保留当前正文、baseline 和草稿。
- **依据**：首版没有多端合并协议、revision 或离线冲突模型。
- **后果**：无网时已加载正文可读，但不排队 save/delete/move；Android 杀进程后的草稿恢复不作承诺。

### ADR-011｜首版复用现有列表窗口化

- **状态**：`ACCEPTED`
- **决定**：文件列表从首版起使用 `@vueuse/core/useVirtualList`，固定 84px 行高；正文不窗口化。
- **依据**：用户确认单目录数百至数千文件；项目已经依赖并使用 `useVirtualList`，无需新增依赖。
- **后果**：必须覆盖稳定 key、overscan、刷新/返回后的滚动恢复；KaTeX/Mermaid/高亮仍按需加载。

### ADR-012｜移动表达是高密度线性工具，不是桌面玻璃工作台

- **状态**：`ACCEPTED`
- **决定**：实色表面、细分隔、2px Accent Bar、连续滚动、显式编辑。
- **依据**：项目 UI 宪法与手机信息密度；桌面组件没有响应式布局且重度 blur/Canvas。
- **后果**：内容区无 backdrop blur、大卡片、厚阴影、hover-scale、人为等待或持续力导图动画。

### ADR-013｜当前版本复原文件名重命名

- **状态**：`ACCEPTED`
- **决定**：阅读页提供显式“重命名文件”；正文标题和文件名保持两个概念。
- **依据**：用户已在桌面运行态验证重命名可用；此前由单个保存 handler 推出“产品没有该能力”属于错误结论。
- **后果**：先采集运行态请求。最新 VCPToolBox 无原子 rename endpoint 时，使用“写新文件 → 校验 → 删除旧文件”的可恢复 transaction；已知重名先拒绝，源删除失败返回新旧并存，成功后迁移 baseline 与 Store key。由于目标探测与 POST 仍有跨客户端 TOCTOU，不得把兼容路径称为强原子或零覆盖窗口。

### ADR-014｜当前发布包含管理与语义核心

- **状态**：`ACCEPTED`
- **决定**：P1 浏览，P2 普通搜索/编辑/重命名，P3 创建/移动/删除/批量/本机隐藏文件夹/LightMemo 语义搜索共同组成当前发布。
- **依据**：用户确认管理和语义是日记中心核心，而非增强项。
- **后果**：只有工作台、联想发现和图谱后置；不得以只读或仅编辑纵切宣称当前里程碑完成。

### ADR-015｜语义层名称服从当前源码

- **状态**：`ACCEPTED`
- **决定**：Diary 只使用 `z-page`、`z-sheet`、`z-dialog` 等语义名，不复制数值。
- **依据**：当前源码、Uno 配置、主题和 tracked docs 一致为 `editor=70, viewer=80`，与所附指令表存在漂移。
- **后果**：实现评审以 current source 为准；不为 Diary 修改全局层级数字。

### ADR-016｜文件夹独立于 Agent

- **状态**：`ACCEPTED`
- **决定**：日记中心以 folder 为第一等筛选，不从 Agent 名称推导 folder。
- **依据**：Agent 与日记本相互独立；“公共”等 folder 可由多个 Agent 与用户共同写入。
- **后果**：当前 `DiaryBlock.file_name` 只是请求后缀，故不生成深链；未来只有工具结果可可靠关联并显式给出最终 `folder + fileName` 时才能深链。Agent 页面不提供猜测式“我的日记本”。

### ADR-017｜稳定分类、服务端排除与本机隐藏

- **状态**：`ACCEPTED`
- **决定**：名称以“簇”结尾的 folder 归入“思维簇”，其他进入“日记 / 知识库”；LightMemo 语义排除以服务端为准。本机 `hiddenFolders` 作为独立、可逆的发现性偏好保留，但默认空且不硬编码 `MusicDiary`。
- **依据**：用户确认分类长期稳定，并校正此前把消费端“隐藏文件夹”功能与服务端排除目录混为一谈。最新 VCPToolBox 中，管理 `/folders` 枚举非符号链接目录；LightMemo 的 `EXCLUDED_FOLDERS` 则仅约束语义候选。
- **后果**：普通浏览/普通搜索应用本机隐藏偏好；LightMemo 结果先服从服务端排除，再应用本机隐藏的附加过滤。UI 不把两者合并成同一开关，不从服务端排除项初始化 `hiddenFolders`；本机恢复只能撤销附加过滤，不能扩大服务端范围。

### ADR-018｜Human Tool 使用官方 ESCAPE 协议

- **状态**：`ACCEPTED`
- **决定**：DailyNote 创建与 LightMemo 请求统一由 Rust serializer 生成 `「始ESCAPE」...「末ESCAPE」` 字段，并转义工具块字面量。
- **依据**：最新 VCPToolBox `ToolCallParser` 已正式实现 ESCAPE 字段与 literal map。
- **后果**：不复制桌面字符串插值；服务端可识别的大小写、`「」`/`{}` 混合括号与兼容 `EXP` 保留标记全部拒绝，以换行、引号、反斜杠、emoji、普通字段标记和工具块标记做契约测试。

### ADR-019｜DailyNote 不确定创建禁止直接重试

- **状态**：`ACCEPTED`
- **决定**：传输/超时导致创建响应丢失，或 2xx 回执畸形、超限、缺少最终 key 时，统一返回 `DIARY_CREATE_UNCERTAIN`；插件明确返回结构化失败时使用脱敏 `DIARY_TOOL_ERROR`。
- **依据**：DailyNote 最终文件名由服务端生成，客户端无法在提交前构造幂等 key；盲目重试可能产生重复日记。
- **后果**：Composer 保留输入但禁用原地重试，要求用户先返回目标文件夹刷新核对；该状态不伪装成普通网络失败。

## 3. 当前产品默认值

以下默认值已经纳入当前施工基线；若真机使用反馈要求改变，应新增或修订 ADR，而不是在组件里形成隐式分叉。

### 3.1 冲突时是否允许强制覆盖

默认允许，但只在展示“远端已变化”的冲突层中提供二级动作，并再次确认。主按钮是“保留草稿并返回比较”，不是覆盖。

若未来完全禁止 force，则保留草稿并允许复制/分享，等待服务端提供条件写或合并能力。

### 3.2 阅读页是否需要字号偏好

当前版本遵循系统字体缩放并采用 16px、1.65 的稳定基线。只有用户测试证明系统缩放不足时，再加 feature-local 字号偏好；它不进入 Delta Sync。

### 3.3 搜索默认范围

默认当前文件夹，范围标签始终可见；这与桌面 `searchScope='folder'` 默认一致。用户切换到“全部文件夹”后只在本次 Diary 会话内记忆，避免每个字符都触发更重的全局搜索。

### 3.4 外链和外部图片

已冻结：可信正文中的图片、音频与 HTML URL 按桌面语义直接渲染，不增加默认拦截层。用户主动点击的外链交给应用既有受控 opener；文件名、摘要、搜索元信息和服务端错误不进入 HTML 渲染槽。

### 3.5 草稿恢复承诺

当前版本只承诺页面生命周期内保留。若要承诺进程被杀后的恢复，需要单独 ADR：加密/过期/容量/多草稿 key/远端基线失效都必须同时解决，不能顺手塞入 localStorage。

## 4. P0 证据包规范

建议未来在测试目录中维护脱敏、最小、可复现的契约证据，而不是把生产响应粘进计划文档。

规则：

- 记录状态码、相关 header、内容类型、schema 和 byte size；
- 记录采集日期与服务端版本，但不记录内网地址；
- fixture 使用相对路径，通过 `include_str!`/`include_bytes!` 加载；
- 任何真实正文只用于本地人工验证，不进入 Git。

## 6. 变更控制

以下变化必须更新 01、03、04、05 中至少对应一份，而不能只改实现：

- 服务端新增 revision/ETag/条件写；
- list/search DTO 新增稳定 ID、size、tags 或 match offset；
- 正文获得正式条目 schema；
- 管理 API 改鉴权或 base path；
- raw-save 与索引的协调语义变化；
- 产品加入离线、跨设备偏好、多文档工作台、联想发现或图谱；
- VCPMobile 的 overlay/layer/settings 所有权发生变化。

文档的责任是标明“事实变化导致哪个决定失效”，而不是永久冻结今天的实现细节。

# VCPMobile 全局消息搜索 — 技术基础调研与实施方案

> 调研日期：2026-08-19 · 决策定稿：2026-08-19 · 状态：**决策已定稿，待施工** · 目标读者：项目维护者
>
> 目标：在移动端新增**全局消息（msg）多条件检索**，区别于现有 topic/agent 的"名称过滤式"小搜索。
> 本文盘点当前技术基础、识别差距、给出分层方案；§5 开放问题已全部拍板（见 §5 决策记录）。

## 0. 一句话结论

**后端地基已经打好且已上线运行，前端零接入。** `messages_fts` FTS5 全文索引表（migration 0003/0004）+ 多条件搜索命令 `search_messages_fts`（topic/agent/role/时间窗/limit）均已存在并注册，但**前端全仓库没有任何调用方**。真正的工作量在四处：分词质量升级、存量索引回填、结果跳转定位、以及整套搜索 UI。

## 1. 技术基础盘点

### 1.1 后端：已存在的 FTS 基础设施（最重要的发现）

| 资产 | 位置 | 状态 |
|---|---|---|
| FTS5 虚表 `messages_fts(msg_id, topic_id, content)`，`tokenize='unicode61'` | `src-tauri/migrations/0003_create_messages_fts.sql` | ✅ 已上线 |
| 物理删除 + 逻辑删除同步触发器（复合键 `(topic_id, msg_id)` 防跨话题误删） | `migrations/0003` + `0004_fix_fts_triggers.sql` | ✅ 已上线 |
| CJK 预处理 `preprocess_fts_text()`：逐汉字插空格适配 unicode61 | `persistence/db_manager.rs:598-623` | ✅ 已上线（方案粗糙，见 §2.1） |
| **多条件搜索命令 `search_messages_fts`**：query + topicId + agentId + role + startTime/endTime + limit | `persistence/db_manager.rs:637-737`，注册于 `lib.rs:33,269` | ✅ 已注册，**前端零调用** |
| 写入路径同步维护索引（新消息插入 `message_service.rs:870,1559`、编辑 `1553-1559`、同步批量写 `db_write_queue.rs:1191-1208`、删除联动） | 多处 | ✅ 已上线 |
| sqlx 0.8.6（bundled SQLite 3.46，**trigram tokenizer 可用**）+ WAL + 串行写队列 | `Cargo.toml:54-55`，`db_write_queue.rs` | ✅ 搜索读天然并发安全 |

搜索结果 DTO `FtsSearchResult`（`db_manager.rs:587-596`）：`msgId / topicId / role / content / timestamp / topicTitle`。

**DB 运行参数**（`db_manager.rs:28-68`）：路径 `/data/user/0/com.vcp.avatar/files/vcp_avatar.db`；sqlx 连接池 max=5（读侧）+ rusqlite 单连接串行写队列；WAL + synchronous=NORMAL + busy_timeout 30s + foreign_keys + mmap 256MB + 16KB page。

**messages 表 schema**（`migrations/0001:76-91`）：复合主键 `(topic_id, msg_id)`，列含 `role / name / agent_id / content(明文) / timestamp / is_group_message / group_id / content_hash / deleted_at`；现有索引仅 `topic_time` 与 `updated_at`，**`agent_id`、`role` 上无索引**。

**写入模型**：`DbWriteQueue` 单 worker 串行攒批（≤32 任务 / 500 消息 / 10ms 窗口），独立 rusqlite 持久连接；WAL 下搜索读与写入天然并发安全，无需应用层读写锁。

**体量约束**：单 topic ≤10k 消息（`push_executor.rs:26`）、写事务 ≤500 条、单条解压上限 16MB、单条 content 无长度上限。

**迁移机制**：sqlx `migrate!`（0001-0007）+ `_sqlx_migrations` checksum 追踪 + 1.1.2 老库 bootstrap 桥接（`db_manager.rs:446-585`）——**新增 migration 0008 时必须同步维护 `already_applied` 匹配表**，否则老库桥接会漏判。

### 1.2 数据基础：纯本地搜索是成立的

- 本地 SQLite 经哈希增量同步持有**全量消息历史**（三级 SHA-256：消息指纹 → Topic content_hash Merkle Root → Agent/Group 聚合哈希），存活消息永不裁剪；同步期唯一上限是内存预算（单 Topic 1 万条 / 单轮 10 万条 / 64 MiB，超限 fail-closed 报错而非截断，`phase3_message.rs:7-9`）。
- 编辑与删除均能正确收敛到 FTS：编辑 → 哈希不匹配 → 重拉 → upsert 时 DELETE+INSERT FTS 行；删除 → 墓碑 + 逻辑删除触发器清索引，搜索 SQL 另有 `m.deleted_at IS NULL` 兜底。已知边界（同步层而非搜索层问题）：桌面端在移动端离线期间删消息存在协议级复活风险（`docs/sync/11_冲突解决与边界情况.md:625`）。
- ⚠️ **搜索相关边界**：软删除满 30 天的消息正文会被置为 `'[已清空]'` 占位符但保留主键墓碑（`delete_executor.rs:259-290`）——搜索结果若命中这类消息，UI 需对占位内容做降级展示。
- 服务端（VCPToolBox 及 VCPChat 内的 VCPMobileSync 插件）**没有任何现成消息搜索 API**（端点清单已逐一核实），无需也不应做远程 fallback。
- 结论：全局搜索应做成**纯本地功能**，离线完全可用——这是对日记搜索（text/semantic 均依赖远程 HTTP、离线不可用）的架构优势。

### 1.3 前端现状：全是"小打小闹"

- `SidebarSearch.vue`（助手/话题搜索）：纯受控输入框，过滤逻辑在 `AgentList.vue:278-284`（仅名称）与 `topicListManager.ts:68-91`（标题+日期字符串），**纯内存过滤，无后端调用**。
- Forum/Mail/LogCenter/Distributed/Diary 各有局部搜索，模式各异；其中**日记搜索（DiaryCenterView）是最完整的参考模式**（见 §1.4）。
- **会话内搜索完全不存在**；消息内容搜索不存在。
- 消息加载链路：`chatHistoryStore.ts` → `load_chat_history`，keyset 游标 `(timestamp, msg_id)`（后端明确拒绝 offset），首屏 5 条、翻页 10 条、内存窗口上限 500。`ChatMessage.content` 为懒加载可选字段，渲染走预编译 `blocks` AST。

### 1.4 可复用的参考模式

**日记搜索（`src/features/diary/`）**——工程模式可直接搬运，数据通道不可搬：

- ✅ 可搬：搜索面板 UI + chips（方式/范围双 chip 组）、275ms 防抖、store 内 requestId + generation 双重竞态防护、Rust 侧 SearchOwner/CancellationToken 取消上一任搜索、`searchLimited` 上限提示、错误码协议、TreeWalker + `<mark>` 高亮工具（`diaryMarkdown.ts`）。
- ❌ 不可搬：text 搜索走远程 `GET /admin_api/dailynotes/search`、semantic 走远程 LightMemo 插件，**离线均不可用**；消息搜索应走本地 FTS。

**VCPChat 桌面端全局搜索（`VCPChat/modules/searchManager.js` + `main.html:1776-1796`）**——交互形态参考（精确行号）：Ctrl+F 入口（:59-63）、范围下拉「当前会话/所有助手和群组/单 agent/单 group」（:127-165）、**最少 2 字符才触发搜索**（:226）、TreeWalker 高亮 `<strong class="search-highlight">`（:459-511）、20 条/页分页（:513-546）、跳转链路 `navigateToMessage`（:548-582：切 agent → 切 topic → 滚动定位 + **高亮闪烁 2.5s**）。关键词**支持多行精确匹配**；**无时间范围过滤**。其实现（渲染进程 Promise.all 并发 IPC 全量读 history.json 内存 `includes` 暴力匹配，`chatHandlers.js:480-495`）不适用于本端数据量，但交互范式值得对齐；我们的 `FtsSearchFilter` 已支持时间范围，可作为对桌面端的差异化能力。另有中间形态：单 agent 内跨 topic 的**话题级**内容搜索 `search-topics-by-content`（`chatHandlers.js:408-451`），返回匹配 topicId 列表——可作搜索页"按话题聚合"视图的参考。

**VCPToolBox 日记搜索 API**（`dailyNotesRoutes.js:566`）——仅作为"多条件搜索 API 设计"参考：多关键词 AND 语义、folder 过滤、限流、可取消；与消息搜索不同域。

## 2. 差距与风险清单（按严重度排序）

### 2.1 P0 — 中文分词质量（决定搜索"能不能用"）

现状 `unicode61 + preprocess_fts_text` 逐 CJK 字插空格，等价于**单字索引**：
- **不保字序**：搜"机器学习"实际是 `机 AND 器 AND 学 AND 习` 四字各自命中，"学习机器"也命中 → 假阳性多、长查询几乎无相关性可言；
- 索引体积约为文本 2 倍（每字一个 token）。

**✅ 决策 A 已定：trigram tokenizer。** 依赖验证证据链（2026-08-19 实测）：

- `sqlx` 的 `sqlite` feature → `sqlx-sqlite/bundled` → `libsqlite3-sys 0.30.1/bundled`；`cargo tree -f "{p} {f}"` 确认 bundled feature 实际生效（sqlx 与 rusqlite 共享同一编译产物）；
- 内嵌 SQLite 版本 **3.46.0**（`libsqlite3-sys-0.30.1/sqlite3/sqlite3.h` 的 `SQLITE_VERSION` 宏）；bundled 构建带 `-DSQLITE_ENABLE_FTS5`（build.rs:129）；`sqlite3.c` 内含 trigram 分词器实现（FTS5 内置，SQLite ≥3.34 起无需额外编译开关）；
- **零新依赖、零 APK 增重**；生产环境 FTS5 已在运行（migration 0003），路径风险为零。

落地要点：
- migration 0008 `DROP + CREATE messages_fts USING fts5(..., tokenize='trigram')`；写入路径从此**存原文**，`preprocess_fts_text` 随 0008 退役（trigram 不需要任何预处理）；
- 查询构造：多关键词用短语 AND（`"机器学习" AND "部署"`）；**短查询边界**：trigram 对 <3 字的 MATCH 退化为全索引扫描——中文双字词（如"微信"）高频且合法，策略为最小 2 字符触发（对齐 VCPChat），2 字查询接受扫描成本并收紧 LIMIT，实测后再优化；
- 索引体积约为正文 2-4 倍（trigram 3 字滑窗），需在真机验收时实测；
- 回填模式直接复用 `decompress_database_migration` 的分批+事务+进度事件（`db_manager.rs:739-948`），但**触发时机改为首次打开搜索页**（决策 G，见 §3 Phase 0）。

### 2.2 P0 — 存量消息无通用回填机制

FTS 写入只发生在：新消息插入、消息编辑、同步批量写、**zstd 解压迁移**（`db_manager.rs:854-872`）。**历史明文存量消息（0003 之前入库且未走过解压迁移的）不在索引中** → 老用户搜索结果静默缺失。0008 重建为 trigram 后整张 FTS 表本身也要重建，回填成为必做项。

**✅ 决策 G 已定：首次打开搜索页时触发回填**（不做启动静默初始化——启动路径不加任何新负担）。搜索页打开时检测索引覆盖率（`messages_fts` 行数 vs `messages` 未删行数），不足则页内展示"索引构建中"进度（分批 + `vcp-system-event` 进度事件 + 断点续跑），构建期间允许对已有索引部分即时搜索。

### 2.3 P1 — 结果跳转定位链路缺失（决定搜索"用完了能不能到") 

- ❌ 聊天视图无 `scrollToMessage` / 命中高亮机制（`useMessageEvents.ts:71` 留有 TODO）；好消息是消息 DOM 已有 `data-message-id` 可定位。
- ⚠️ 后端游标只有"向前取更早"，**无 `afterTimestamp` 向后窗口**——点击一条旧消息的搜索结果后，无法加载"该消息附近"的上下文窗口，需新增锚点加载 API（按 msg_id/timestamp 取前后 N 条）。
- ⚠️ `FtsSearchResult` 缺 `ownerId/ownerType`，跳转前需反查话题归属（agent 还是 group）。

### 2.4 P1 — 搜索质量与表达能力缺口

- 无分页：固定 `LIMIT 100`，无 cursor；`load_chat_history` 的 keyset 范式可直接复用到搜索结果。
- 无高亮/摘要：未用 FTS5 `snippet()`；无相关性排序：未用 `bm25()`（当前按时间倒序）。
- 缺过滤索引：`messages.agent_id`、`messages.role` 上无索引，大库下过滤条件会拖慢 JOIN。
- ~~⚠️ 语义陷阱~~ **✅ 决策 B 已定**：现有 `agentId` 过滤的是 `messages.agent_id`（消息发送者）；定稿为**会话归属语义**——"某助手/群组名下所有话题的消息"，经 `topics.owner_id/owner_type` JOIN 过滤；如未来需要"发送者"语义，另立独立过滤字段。
- content 为原始文本（含 Markdown/代码/工具块标记），搜索词命中语法符号的体验需要 snippet 策略配合。

### 2.5 P2 — 其他

- ~~附件是否入索引~~ **✅ 决策 D 已定：附件（文件名/提取文本）不参与索引**，仅索引消息正文。
- 群组消息、系统消息（role 枚举）过滤语义待确认。
- 大库（10w+ 消息）FTS5 查询与回填耗时无实测数据，需要性能采样。

## 3. 方案草案（分层施工）

### Phase 0 — 后端加固（搜索质量地基）

1. **migration 0008**：`DROP + CREATE messages_fts USING fts5(msg_id UNINDEXED, topic_id UNINDEXED, content, tokenize='trigram')` + 重建删除触发器（0004 版本语义保持不变）+ 补 `messages(agent_id)`、`messages(role)` 索引；**同步维护 `bootstrap_legacy_if_needed` 推断表第 8 臂**，探针须能区分新旧 FTS 结构（查 `sqlite_master` 建表 SQL 是否含 `trigram`）。
2. **写入路径切换**：0008 后所有 FTS 写入点（`message_service.rs:870,1559`、`db_write_queue.rs:1208`、`message_repository.rs:627`）改为存**原文**，`preprocess_fts_text` 退役。
3. **回填命令 `rebuild_messages_fts`**：分批（500 条/批，批间 checkpoint 控制 WAL 膨胀）+ `vcp-system-event` 进度事件 + 幂等断点续跑；**触发时机为首次打开搜索页**（决策 G），不在启动路径做。搜索页打开时检测覆盖率，不足则页内显示构建进度，已有索引部分立即可搜。
4. **升级 `search_messages_fts`**：`snippet()` 命中摘要 + 默认时间倒序（bm25 相关度作为可切换选项，决策 F）+ keyset 分页 cursor + agentId 改为会话归属语义（决策 B，经 `topics.owner_id/owner_type` JOIN）+ 返回 `ownerId/ownerType`。
5. **新增锚点加载 API**：`load_chat_history_around(msg_id, before_n, after_n)`，为跳转服务。

### Phase 0 附 — Baseline 迁移机制（新决策，独立于搜索的长期基建）

**背景与动机**：项目用户群体中"删了重装 / 出 bug 就重装"是高频路径。对全新安装而言，依次跑 0001→0008 增量链意味着反复建表-改表-重建 FTS（0003 建 unicode61 FTS → 0008 又 DROP 重建），全是浪费。借鉴 Flyway baseline / Django squashmigrations 思路：**为全新安装设置新起点，全新安装永远一步到位得到最新完善 schema**。

**设计**：

1. **新增 `migrations/0100_baseline_v2.sql`**：完整最新 schema 的快照（全部表含 **trigram 版** `messages_fts`、全部索引、全部触发器），纯 `CREATE ... IF NOT EXISTS`。全新安装直接得到终态，永不经过 unicode61 FTS。
2. **全新安装快速路径**（`db_manager.rs` 新增 `bootstrap_fresh_if_needed`）：检测到无业务表且无 `_sqlx_migrations` 记录 → 直接执行 baseline 文件 → 将全部 ≤ baseline 版本号的迁移记录 seed 为已应用（checksum 同源，复用现有桥接写法）→ `migrator.run()` 时无事可做。启动路径零增量迁移。
3. **存量安装完全不受影响**：`bootstrap_legacy_if_needed` 对"有业务表"的库将 baseline 版本 seed 为已应用（baseline 只在空库上真正执行）；存量库继续走 0001→0008 增量链正常升级。
4. **未来迁移**继续使用 >0100 的版本号（0101、0102…）；链再次变长时可做下一次 re-baseline（0200），规则相同。
5. **漂移防护（必须配套）**：baseline 与增量链会随时间漂移，配套 CI/测试——分别用"baseline 快速路径"和"0001→最新增量链"各建一个库，规范化比对 `sqlite_master` 全量定义，不一致即失败。这是该机制能长期成立的前提。

**时序独立性澄清（2026-08-19 讨论修正）**：baseline 是创建时刻的 schema 快照，之后新增量照常叠加。因此 baseline **与 0008 无先后耦合**——只要创建时机在 0008 之后，快照天然含 trigram 终态；同批发或拆开发对全新安装结果等价。拆开甚至可让 baseline 快照经过生产验证的 schema。**Fast path 的 seed 规则陷阱（实现时钉死）**：只能 seed "baseline 创建时已存在"的迁移为已应用；baseline 之后新增的迁移（无论版本号大小）必须照常排队执行——若规则误写成"seed 所有版本号 ≤ baseline 的迁移"，则未来任何版本号 < baseline 的新迁移都会被全新安装静默跳过。另外空库上 DROP/CREATE 空 FTS 表是毫秒级，"全新安装经过中间态"本身也无成本顾虑。

**与搜索的交点**：baseline 里的 `messages_fts` 直接是 trigram 终态；全新安装无存量消息，无需回填，首次打开搜索页时覆盖率检测天然通过。

### Phase 1 — 全局搜索页（核心交付）

1. 新 `OverlayPageType` 成员（当前 14 种，`overlay.ts:9-24`）挂入 overlayStore 的 SlidePage 页面栈，`FeatureOverlays.vue` 懒加载注册（`defineAsyncComponent` + `createFirstOpenLatch` 首开常驻），照抄 `LogCenterView` 模式；每个页面需注册进 `useModalHistory` 支持系统返回键关闭。入口放 `AgentSidebar.vue:67-73` 顶部 header（放大镜图标，注意 SidebarSearch 输入框状态是 AgentSidebar 本地 ref 且切 Tab 清空，两者无冲突）。**注意层级差**：抽屉在 `LAYER_DRAWER(20)` 低于 page(40+)，打开搜索页需同时 `layoutStore.setLeftDrawer(false)`（参照 `TopicList.vue:193`）。传初始过滤条件可参考 diary 的 `diaryOpenTarget` 传参模式（如从话题菜单"搜索此话题"进入时预填 topicId）。
2. UI 契约：密排线性列表（禁止大圆角/厚投影/毛玻璃），Monospace 显示 msgId/时间戳，2px accent bar 标记选中态；层级走 `LAYER_PAGE_BASE` 动态计算。
3. 多条件过滤器：关键词输入 + chips 组（范围：全部/当前话题/指定助手或群组；role：用户/助手/系统；时间范围：快捷段选 + 自定义）——chip 交互参考 `DiaryCenterView`。
4. Store：新建 `useGlobalSearchStore`，搬日记的 requestId + generation 竞态防护、275ms 防抖、加载/错误/上限三态。**本地 SQLite 查询可省略 cancel command**——generation 本地作废即可（日记的 cancel command 是为中断远程 HTTP 请求存在的，本地查询毫秒级返回无此需求），同时可砍掉 reqwest 超时/双凭据/ESCAPE 协议那一整套远程代理包袱。
5. 结果列表用 `@vueuse/core` 的 `useVirtualList` 虚拟滚动（`DiaryNoteList.vue:40-43` 有现成范式，itemHeight 96 参考值），应对百级结果行。
6. 结果项：topicTitle + 发送者 + 时间 + `snippet` 高亮摘要。高亮工具注意适配差异：`highlightDiarySearchText`（`diaryMarkdown.ts:47-84`）针对渲染后 HTML 做 TreeWalker，而消息在列表中显示的是 FTS `snippet()` 纯文本摘要——可直接按命中 index 切片包 `<mark>`，更简单；进入聊天视图后的正文高亮才需要 TreeWalker 方案（且需排除代码块）。
7. 错误协议沿用 `CODE: message` 字符串 + 前端正则解析模式（`diary_types.rs:4-47` 17 个稳定错误码 + `types.ts:110-126 parseDiaryError` 是现成范本）。

# SSE 全生命周期维度二专项审查

审查日期：2026-10-31（Asia/Shanghai）。生产源码基线：`a771315ec4b5e71652621cf7343bce2344031479`。工作区：`E:\VCPMobile`，开始审查时 Git 工作树干净。

审查对象是用户附件“AST 流式渲染引擎与 SSE 全生命周期”报告的**维度二七项指控**。对维度一、三、四仅核查与这七项直接相关的复杂度旁证、严重性与修复建议。本次使用 7 位专项子代理和 1 位独立反证子代理；主审复核源码、合并裁决并执行引号性能探针。没有修改生产实现、已有测试或发布配置，没有提交、推送或操作设备。

## 核心结论

**原报告识别了若干真实的重复工作，但不足以支持“七处严重性能黑洞”的整体定性。** 它混淆了 token、网络事件、渲染窗口与屏幕帧，漏读了前端 DOM 复用、动画默认值、定时任务移除策略，也把未测量的设备结果写成了确定事实。

本次建议近期优先处理两件事：

1. **P1：多个未闭合中文左引号导致单帧平方扫描。** 这是与第 1 项相关的更强算法问题，原附件的线性复杂度纠偏反而遗漏了它。真实生产函数的 host 探针已复现随输入翻倍约四倍增长；65,535 字节输入的局部处理约 544ms。它不受递归深度限制消除，普通 tail 的 64KiB 门槛也不能保护终态/稳定化解析。
2. **P1：EOS 时普通稳定块的身份交接不一致。** 第 7 项所称 memo 失效存在，但更直接的原因是流式与终态 hash/key 不一致以及投影替换。生产 Store/Renderer 的 DOM 探针观察到表格节点重建、`scrollLeft` 从 73 变为 0；只翻转流状态或换新对象但保留同 key 的对照均保留节点。这是交互状态连续性问题，不必等到证明 GPU 或整屏卡顿才处理。

这里的 P1 是**近期优先治理**，不是已经证实的发布阻断。尚无 P0 证据；所有 Android 掉帧、GC 停顿、GPU 饱和与端到端延迟结论仍缺具名设备测量。host 探针的毫秒数不能作为 Android 性能指标。

## 影响严重性判断的共同边界

### 调度窗口不是每 token 解析，也不是每帧计算预算

正常路径将数据积累到 `pending_chunk`，以 33ms 时钟刷新，错过 tick 使用 Skip。订阅变化、恢复快照结束、断连收口和 EOS 另有立即 flush。`process_queue()` 同步执行在 Rust async 请求任务中，定时器不能抢占一次昂贵解析；最多 8 路传输各有窗口。因此既不能引用“60 token/s”推出“60 次 AST 解析/s”，也不能用“已有 33ms”证明任意输入都不会阻塞。

证据：[vcp_client.rs:2087](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2087)、[2200](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2200)、[2243](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2243)、[2337](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2337)、[2423](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2423)。

### 稳定块隔离与 64KiB 保护不能泛化为全局上限

通用 Markdown diff 只比较活动尾部的新旧 AST；已经沉淀的历史块不会在每次 tail 更新时重新进入该 diff。普通推测 tail 超过 65,536 字节会转 Plain。这限制了原报告部分“全消息每帧扫描”的推断，但并不限制总消息长度、代码围栏、JVM 正文、AST JSON 或 DOM 的大小。

段落沉淀、特殊块前文本收口和 EOS 仍会解析完整片段，不能以推测 tail 门槛排除这些阶段的大输入风险。证据：[aurora_pipeline.rs:29](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L29)、[778](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L778)、[895](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L895)、[964](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L964)、[stream_block_parser.rs:438](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L438)、[551](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L551)、[966](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L966)。

### 三种更新阶段必须分开

1. **tail 内连续变化**：表格 morphdom、InlineMath 原位更新等保护适用。
2. **tail 沉淀为 stable**：会发生渲染区域/组件所有权交接，不能用 tail 内身份保持证明此时也无重建。
3. **durable EOS 覆盖终态投影**：普通块 hash/key 变化可以再次重挂载，和前两个阶段是不同事件。

因此，“第 4 项整表每帧销毁是误判”和“第 7 项 EOS 表格确会重挂载”可以同时成立。本次探针专门分开验证了它们。

## 两个 P1 事项的依据与修复边界

### A. 未闭合中文左引号重复扫描

`split_text_by_quotes` 将每个 `“` 拆成独立 Text；`merge_quote_nodes_at_depth` 遇到每个开引号都会扫描后缀寻找 `”`。找不到时仅推进一个节点，后面的开引号再次扫描。对 q 个 `“`，内层访问次数为 `q(q+1)/2`。这是平级扫描，不由 128 层递归门槛截断。

证据：[markdown_parser.rs:1500](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1500)、[1564](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1564)、[1581](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1581)、[1675](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1675)。

生产函数 host 探针的五次中位数：4,000 个约 17.5ms，8,000 个约 73.5ms，16,000 个约 290.3ms，21,845 个约 544.1ms。最后一档仅 65,535 字节，仍能进入普通推测 AST。此计时仅覆盖 split/merge，未计入 Markdown parser、入口 children.clone、哈希、IPC 或 DOM。详细环境、源文件指纹与结果见 [验证记录](08-验证记录与复现.md)。

建议消除无闭合后缀的重复搜索，并保留当前中文/ASCII 引号的配对顺序和嵌套输出。仅新增“没有引号就跳过”的门禁不能解决本问题，因为病理输入全部是引号；也不应未经讨论以截断正文、限制新语法或容错降级代替算法修复。无引号复制优化可以同批处理，但应独立说明收益。

### B. EOS 普通稳定块身份交接

流式 `StreamBlock` 的 hash 来自原始片段的文本散列字符串，终态 `ContentBlock` 使用结构散列数值。前端普通块 key 使用 `String(block.hash)`，终态 Store 又整体替换渲染投影；tool/guidance 已有专门身份处理，普通 Markdown 并不自动获得同等保护。

证据：[stream_block_parser.rs:966](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L966)、[MessageRenderer.vue:494](../../src/features/chat/MessageRenderer.vue#L494)、[chatStreamStore.ts:1446](../../src/core/stores/chatStreamStore.ts#L1446)；完整生产类型与散列证据见 [07 专项](07-EOS编译与渲染审查.md)。

生产 Store/Renderer 的 happy-dom 探针使用相同表格内容和节点结构进行三组对照：只结束流状态，节点保留；终态换新 blocks 但保持 key，节点保留；终态切换 hash/key，旧 table 断开，新节点 scrollLeft 为 0。探针核对了实际承载横向滚动的 table 元素。输入协议样本按源码构造，没有运行 Rust parser，也没有真实触摸/布局证据；结果足以证明这条 key 交接能够丢失节点内部状态。

建议先处理同一已呈现内容在终态的稳定身份与分组对应关系。不能直接删除 `isStreaming` 的 memo 依赖来掩盖问题，也不能保证仅统一 hash 算法就足够：流式/终态的块拆分、内容规范化及组件行为可能不同。必须保留终态权威内容和恢复语义，不为减少 DOM 更新而跳过必要的终态提交。

## 对原修复建议的裁定

| 原建议 | 审查后的处理意见 |
| --- | --- |
| 引号前置字符检查 | 可作为 P2 分配优化的一部分；需递归覆盖实际参与处理的文本，且不解决上述 P1 平方扫描 |
| 延后两处 node_id 格式化 | 合理的 P3 局部优化，保留 None hash 节点的正常比较；不承诺整个 diff 零分配 |
| 直接 serialize Aurora stable_blocks | 不可直接照搬：输入类型、内容规范化、块划分、hash 和恢复路径不同，需要先定义可复用的终态产物契约 |
| mask 改 opacity，活动动画最多 2 个 | 证据不足，且会改变已有渐显视觉语义；先测实际瓶颈，再讨论交互取舍 |
| 稳定块移除 isStreaming memo 依赖 | 不足以解决 key 变化；还可能漏掉组件收口行为，需基于消费者细分依赖 |
| 表格行级增量协议 | 有优化价值，但应先量测当前整表 AST/离线 DOM/morph 的占比，再评估新增协议和 registry 维护成本 |
| 每帧 watchdog 改 Socket 空闲超时 | 不等价；当前约束在途 write/flush，普通 Socket SO_TIMEOUT 约束读取。不得直接替换 |

这些是后续实现方向，不是本次已经实施的修改。涉及新增兼容、自动纠错或容错行为时，仍需按仓库规则先讨论目标语义。

## 建议执行顺序

1. **先做两个 P1 的具体修复设计**：引号扫描去重；EOS 普通块身份/交互状态连续性。分别验证当前输出语义和真实交接，不把它们合并成全面重写渲染器。
2. **再测 P2 的主要成本**：长代码闭合/终态编译、长表格活动 tail、长回复及完成落盘失败时 helper 保留容量。记录真实事件载荷与阶段耗时；现有 fence-close bench 不足以衡量稳定块 IPC。
3. **对主动开启的渐显进行 A/B 测量**：固定设备、WebView、输入、刷新率与滚动动作，区分 JS、Paint/Raster、Composite；保留默认与用户偏好。
4. **P3 随相关维护收束**：ID 构造位置可以低成本调整；watchdog 应先证明收益，避免用更复杂的共享定时状态机替代正确的写截止语义。

Magi 视角的综合意见：逻辑上先修可证的超线性扫描和身份断裂；交互上保留选择、滚动及视觉意图；交付上按真实根因拆分，避免为没有实证的“GPU 黑洞”改造整条管线。这是审查建议，并未开启核心重构。

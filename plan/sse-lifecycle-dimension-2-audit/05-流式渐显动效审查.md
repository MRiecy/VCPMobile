# 05 — 流式渐显动效审查

审查日期：2026-10-31。代码基线：`a771315ec4b5e71652621cf7343bce2344031479`。范围：原报告维度二第 5 项，沿配置、渲染帧、AST 执行、动画清理追踪；不修改生产实现。

## 结论与紧迫性

**250ms 渐变蒙版动画及临时行内 `span` 确实存在；“默认开启”“每个 token/chunk 都生成一个动画”“10–15 个并发动画必然引起 GPU Fillrate 过载”的结论不成立或证据不足。** 当前默认关闭，显式开启时才进入此路径。动画已有合并、结构帧屏障、完成归并和生命周期清理，没有发现随完整消息长度永久累积动画节点的常态路径。

本项定为 **P2：常规性能验证与优化候选**。当前不足以作为紧急修复或发布阻断依据。若在具名 Android 设备上取得开关对照的帧耗时、Paint/Raster 或 GPU 证据，且开启时持续影响阅读/滚动，再提升为 P1。无需根据原报告立即替换视觉效果或硬设“最多 2 个动画”。

| 原报告断言 | 核实结果 | 证据级别 |
|---|---|---|
| 平滑流式默认开启 | **错误**；当前默认 `false`，已有本地偏好可恢复为 `true` | 源码事实 |
| 每个文本 chunk 都插入 span | **过度概括**；仅符合门禁的全 `append` 渲染帧进入，同一帧同一文本目标合并；已有块级揭露祖先时直接写文本 | 源码事实 |
| 动画持续 250ms、使用渐变 mask | **成立** | 源码事实 |
| 40–60 token/s 导致 10–15 个并发动画 | **不能这样推导**；模型 token、SSE chunk、Aurora 帧、DOM mutation 不是同一单位 | 调度源码反证；真实并发数未采集 |
| 多蒙版必然造成合成层暴增、GPU Fillrate 过载 | **未证实**；没有设备、WebView、Layer/Paint/Raster/GPU 记录 | 性能假设 |
| 历史片段不断积累 | 原报告虽未明确称泄漏，但其风险描述遗漏完成归并和清理；当前常态路径不支持此解释 | 源码事实 |

## 1. 配置与实际可达条件

[`preferences/model.ts:24–29`](../../src/features/chat/preferences/model.ts#L24) 明确写出 `smoothStreamingEnabled: false`。[`preferences/storage.ts:35–40`](../../src/features/chat/preferences/storage.ts#L35) 从本地偏好恢复，缺失时使用该默认值。因此默认关闭不意味着所有现有用户都关闭，也不能根据默认值忽略主动开启后的性能。

[`MessageRenderer.vue:100–115`](../../src/features/chat/MessageRenderer.vue#L100) 要求：用户开启平滑动效、消息正在流式、当前 Tail 使用 AST、组件非后台、文档可见、系统未要求减少动态效果；Tail 还须为 Markdown，且当前帧不是 reset/snapshot。[`useMessageTailRenderer.ts:224–250`](../../src/features/chat/composables/useMessageTailRenderer.ts#L224) 在恢复快照或跨流接管时另行控制动画，避免把历史恢复当成新文字。

特性检测也不是空白：[`streamTextFade.ts:11–47`](../../src/core/utils/streamTextFade.ts#L11) 检查 `Element.animate`、CSS mask 支持以及 typed custom property 注册。注册属性 `inherits: false`。能力不可用或 `animate()` 抛错时，当前生产实现将文字直接写入权威 Text 节点（163–192 行）。本审查只确认已有行为，不建议增设新的兼容分支。

## 2. 一个 token 并不等于一个动画

完整链路如下：

1. Rust 网络读取得到内容后进入 `pending_chunk`；正常渲染时钟为 33ms，MissedTickBehavior 为 `Skip`，到时才处理当前内容窗口。见 [`vcp_client.rs:339`](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L339)、[2200–2204](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2200)、[2251–2267](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2251)。连接状态变化等还存在立即 flush 的特殊路径，不能把 33ms 说成所有路径的绝对速率保证。
2. 前端 [`chatStreamStore.ts:408–424`](../../src/core/stores/chatStreamStore.ts#L408) 把下一次 rAF 前到达的更新暂存后原子提交；这不是每个网络 chunk 都立即调用 DOM 动画。
3. [`astExecutor.ts:1149–1159`](../../src/core/utils/astExecutor.ts#L1149) 只有 `smoothStreaming === true`、mutations 非空且**整帧全部为 append** 时才生成 `inlineRevealToken`。出现结构变更即先 flush 所有行内片段并清除块级揭露样式。
4. [`streamTextFade.ts:151–160`](../../src/core/utils/streamTextFade.ts#L151) 将同一 `applyFrame`、同一 Text target 的连续 append 合并到最后一个片段，而不是新增动画；若祖先已是块级揭露 surface，则直接追加文字（118–120 行）。
5. 只有走到 [`streamTextFade.ts:169–209`](../../src/core/utils/streamTextFade.ts#L169) 才创建新的 span 和 250ms Web Animation。

**可推导的量级而非实测：** 假设只有一个 Text target、每个正常 33ms 窗口都生成一次纯 append、没有特殊刷新/结构屏障且结束回调及时执行，250ms 内约为 `ceil(250/33) = 8` 个仍在进行的行内动画。此数字不是全局硬上限：多个文本目标、多条活跃消息、特殊刷新，以及结束回调延迟都会改变驻留片段数。相反，rAF 合并、网络间隙和结构帧又可能减少它。

因此原报告的 `40–60 token/s × 0.25s = 10–15` 只是建立在“每 token 恰好独立生成一个动画”假设上的算式，当前生产链路没有提供该假设。系统也没有显式动画并发预算，开启情况下仍有测量价值。

## 3. 作用范围与清理闭环

| 场景 | 当前行为与定位 |
|---|---|
| 纯文本增量 | `append` 修改注册 Text 节点；纯 append 帧才进入行内动画。[astExecutor.ts:655–669](../../src/core/utils/astExecutor.ts#L655) |
| 普通块追加 | 新 paragraph、heading、blockquote、list、table 可做一次块级 CSS 揭露；祖先正在揭露时避免嵌套揭露。[astExecutor.ts:109–143](../../src/core/utils/astExecutor.ts#L109)、[789–803](../../src/core/utils/astExecutor.ts#L789) |
| 代码围栏、Raw HTML、分隔线 | `shouldRevealAddedMarkdownNode` 排除；代码增量走 `patch_code`，不是文本 append 动画。[astExecutor.ts:127–143](../../src/core/utils/astExecutor.ts#L127)、[688–700](../../src/core/utils/astExecutor.ts#L688) |
| 行内代码/公式 | 不应计为逐 token 行内文字动画；行内代码变化生成 ReplaceInline，其他无法专用差分的内联节点也走 ReplaceInline。它们可能位于首次揭露的 paragraph/其他祖先块内，从而随父块一次揭露。[ast_diff.rs:698–714](../../src-tauri/src/vcp_modules/chat/ast_diff.rs#L698)、[astExecutor.ts:481](../../src/core/utils/astExecutor.ts#L481) |
| 动画结束/取消 | 标记完成，按原顺序将 chunk 合并回规范 Text 节点，移除 span，并在目标为空时清理 Map。[streamTextFade.ts:68–108](../../src/core/utils/streamTextFade.ts#L68)、[195–209](../../src/core/utils/streamTextFade.ts#L195) |
| 结构帧接管 | 先 flush 行内片段，避免临时 fragment 与 AST 修改分叉。[astExecutor.ts:1150–1155](../../src/core/utils/astExecutor.ts#L1150) |
| 稳定块接管旧 Tail | discard 旧 fragment，防止回写旧 Text 节点；已经可见的 Tail 对应首个新增稳定块不会重播揭露。[MessageRenderer.vue:701–714](../../src/features/chat/MessageRenderer.vue#L701) |
| 流结束、关闭设置、重连、组件转后台 | 收束已有动画。[MessageRenderer.vue:728–757](../../src/features/chat/MessageRenderer.vue#L728) |
| 文档隐藏/减少动态效果 | 提交已有片段并清除块揭露；CSS reduced-motion 同时移除 mask。[streamTextFade.ts:230–252](../../src/core/utils/streamTextFade.ts#L230)、[message-blocks.css:886–892](../../src/assets/message-blocks.css#L886) |
| 组件/注册表释放 | `cleanupRegistry` 先 discard，释放片段引用。[astExecutor.ts:151–157](../../src/core/utils/astExecutor.ts#L151) |

清理证据意味着“动画随全文长度无界保留”不能作为当前结论；它不证明任意主线程繁忙、后台异常调度或所有设备上的清理延迟为零。

## 4. 真正值得测量的成本

[`message-blocks.css:854–883`](../../src/assets/message-blocks.css#L854) 的确用变化的 custom property 驱动 `linear-gradient` mask。新增片段还产生 DOM 节点、动画对象、插入与最终 Text 合并工作。随着活跃 surface 的数量和面积增长，样式、绘制、栅格与合成工作可能增加；源码足以提出这一性能风险。

但调用 Web Animations API **不自动证明整个动画仅在 GPU 合成线程上运行**；同样，存在 CSS mask 也不自动证明每个 span 都成为独立合成层。Google 的[动画性能指南](https://web.dev/articles/animations-guide?hl=en)要求对非 transform/opacity 动画检查实际渲染阶段；Chrome 的[非合成动画诊断说明](https://developer.chrome.com/docs/lighthouse/performance/non-composited-animations/)明确指出实际失败原因记录在 DevTools trace 中。以上材料支持“需要 trace 定位阶段”，不能替本应用提供 GPU 饱和证据。

原报告没有设备型号、SoC、WebView 版本、屏幕分辨率、刷新率、Surface 面积、Layer 数、Paint/Raster 耗时或帧统计。由此无法判定瓶颈究竟是 JS/Style/Paint、栅格化、合成，还是上游解析、IPC 或同帧结构修改，更无法直接指向 Mali/Adreno 的 Fillrate。

## 6. 建议与升级条件

先做开启/关闭平滑动效的同输入对照，保留现有视觉意图。选择具名 Android 手机与 WebView 版本，固定屏幕宽度、刷新率、消息输入和滚动动作；至少覆盖纯长段落、频繁格式变更、多目标列表、单次大 chunk 与持续小 chunk。记录实际 Aurora/applyFrame 速率、动画 surface 峰值/面积、结束后残留、帧间隔及 Style/Layout/Paint/Raster/Composite 时间。桌面 Vite 仅能协助定位，不替代移动证据。

如果证据显示多个小 surface 的管理成本占主导，再研究跨相邻帧合并或有限活动 surface 预算；必须确认不会重启旧内容揭露、延迟新文字、破坏选择/换行或造成内容跳变。如果证据显示 mask 的绘制成本占主导，再提出视觉等价的实现或产品可接受的效果调整，并比较实际收益。

原报告的“改 opacity、最多 2 个动画”改变了从左向右柔边揭露的语义，数值也无设备测量依据。它可以成为经评估的设计备选，不能作为本次审查已经证明必要的修复。当前建议继续保留默认关闭、用户开关与现有清理逻辑，按 P2 进行有针对性的测量；若出现可复现持续掉帧或明显清理积压，再按实际证据提级。

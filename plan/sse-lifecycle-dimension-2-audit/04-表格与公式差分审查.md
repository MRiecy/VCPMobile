# 04 — 表格与公式差分审查

审查日期：2026-10-31。基线：`a771315ec4b5e71652621cf7343bce2344031479`。范围：附件“维度二”第 4 项，追踪 Rust Markdown AST、Aurora 活动尾部、IPC mutation 与前端 DOM 执行器。未修改生产代码。

## 裁决

**原报告部分属实，但主要故障叙述不成立。** 变化的表格确实缺少行/单元格级 AST diff，会发送整表 `Replace`；前端已经专门拦截该操作，使用 `morphdom` 更新现有表格，并非每次将已挂载的整表摘除重建。公式的描述存在类型错误：当前 `MarkdownNode` 没有 `MathBlock`，块公式同样使用 `InlineMath { display_mode: true }`；公式内容变更走 `ReplaceInline`，前端有原地更新分支。

实际保留的问题是：**大表格尚在活动 tail 中且内容发生变化时，后端整表解析、哈希、克隆和发送 AST，前端创建整表临时 DOM，再做 morph 比较，成本随当前表格规模增长。** 这是可优化的全量处理成本，不是已经证明的“DOM 整树销毁”或“剧烈闪烁”。

建议优先级：**表格 P2（常规性能优化）；原报告所述公式缺陷不立项。** 若具名 Android 设备证明大表格更新持续超出帧预算、干扰触控或滚动，再将表格事项提升 P1。现有证据不足以列为 P0 或发布阻断项。

## 原断言逐项核实

| 原断言 | 当前证据 | 裁决 |

## 生产调用链与边界

### 1. 表格何时生成、比较和退出热路径

1. `parse_markdown_to_ast_streaming` 进入与普通解析共用的实现，启用 `ENABLE_TABLES` 和 `ENABLE_MATH`；表格解析事件构建 `header/rows`。见 [markdown_parser.rs:925](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L925)、[markdown_parser.rs:954](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L954)、[markdown_parser.rs:1029](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1029)、[markdown_parser.rs:1411](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1411)。
2. 解析结束后计算递归 hash，Table 和 InlineMath 都保存并返回 hash。相同 hash 的公共节点在调用专职 diff 前直接 `continue`。见 [markdown_parser.rs:1149](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1149)、[markdown_ast.rs:150](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_ast.rs#L150)、[markdown_ast.rs:266](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_ast.rs#L266)、[ast_diff.rs:170](../../src-tauri/src/vcp_modules/chat/ast_diff.rs#L170)。
3. hash 改变后，Table 落入通用 `Replace`。启用高亮器时 `prepare_stream_node` 首先 clone 新节点；Table 没有可复用的行/单元格 patch。见 [ast_diff.rs:387](../../src-tauri/src/vcp_modules/chat/ast_diff.rs#L387)、[ast_diff.rs:401](../../src-tauri/src/vcp_modules/chat/ast_diff.rs#L401)。
4. Aurora 只拿 `prev_tail_ast` 与当前尾部 `new_nodes` 比较，并非每次重访整条消息的所有 stable blocks。普通 Markdown 通过空行 `\n\n` 沉淀，特种块出现前的文本也会沉淀；流结束时 finalize 收尾。见 [aurora_pipeline.rs:943](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L943)、[aurora_pipeline.rs:964](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L964)、[stream_block_parser.rs:427](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L427)、[stream_block_parser.rs:550](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L550)、[stream_block_parser.rs:943](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L943)。
5. 表格通常以单换行分隔行，因此整张正在增长的表格可以一直处于一个未沉淀 tail 内。这使逐次发送当前整表的问题在普通 Markdown 表格输入中可达，不需要假设绕过入口。
6. 普通 Markdown tail 超过 **65,536 字节**后改走纯文本投影；Table 不在代码/协议增量路径的豁免集合内。这个限制约束源文本大小，**不等于 AST JSON、临时 DOM 或整体消息大小只有 64KiB**。含大量短单元格的表格可能在源文本较小时已产生很多节点。见 [aurora_pipeline.rs:15](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L15)、[aurora_pipeline.rs:895](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L895)、[aurora_pipeline.rs:980](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L980)。
7. SSE 普通更新由 **33ms** 时钟合并，错过 tick 采取 Skip，只在 `pending_chunk` 非空时 flush；消费者变化等路径另可主动 flush。应按“有变化的解析窗口”统计，而不能把 token 数、网络 chunk 数和 DOM 帧数视为相同。见 [vcp_client.rs:339](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L339)、[vcp_client.rs:2200](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2200)、[vcp_client.rs:2243](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2243)。

### 2. Table Replace 的真实 DOM 行为

`astExecutor` 收到 Table Replace 后：

1. 使用临时 registry 调用 `createDomFromNode`，确实重新创建完整的 **离线目标 DOM**，包括 wrapper/table/thead/tbody/各行各单元格。见 [astExecutor.ts:332](../../src/core/utils/astExecutor.ts#L332)。
2. 对现有节点调用 `morphdom(oldNode, newDom)`，相等子树通过 `isEqualNode` 跳过；随后保留根 registry 引用，清理子孙引用。该分支 `break`，不会继续进入后面的 `parent.replaceChild`。见 [astExecutor.ts:923](../../src/core/utils/astExecutor.ts#L923)、[astExecutor.ts:943](../../src/core/utils/astExecutor.ts#L943)、[astExecutor.ts:960](../../src/core/utils/astExecutor.ts#L960)。
3. 原报告引用范围内已经存在这段优化。仅看到后端 mutation 名为 Replace，就认定线上 DOM 全树重建，漏掉了执行器的专职分支。

这并不意味着所有表格结构变化都保留每一个节点。结构变化、tail epoch reset、tail 转 stable 时可以新增、移除或重新挂载节点。当前前端在显式 reset 时会清空 sandbox 并重建 snapshot，属于有条件的生命周期行为，不能推广为正常增长的每帧必然动作。见 [useMessageTailRenderer.ts:220](../../src/features/chat/composables/useMessageTailRenderer.ts#L220)。

### 3. 公式并不存在报告描述的 MathBlock 热路径

- `MarkdownNode` 完整枚举只有 Paragraph/Heading/CodeBlock/Blockquote/List/Table/ThematicBreak/RawHtml。公式定义位于 `InlineNode::InlineMath`，带 `content`、`display_mode` 和 `hash`。见 [markdown_ast.rs:6](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_ast.rs#L6)、[markdown_ast.rs:114](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_ast.rs#L114)。
- pulldown 的 `Event::DisplayMath` 被转换为 `InlineMath(..., true)`，放入父节点，或包装为 Paragraph。见 [markdown_parser.rs:1003](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1003)。
- 相同 InlineMath hash 直接跳过；内容变化时可走 `ReplaceInline`，不会因为存在块公式而进入块级 Table 兜底。见 [markdown_ast.rs:297](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_ast.rs#L297)、[ast_diff.rs:539](../../src-tauri/src/vcp_modules/chat/ast_diff.rs#L539)、[ast_diff.rs:709](../../src-tauri/src/vcp_modules/chat/ast_diff.rs#L709)。
- 前端 `inline_math` 更新有专门分支：保留原 span，只修改 `data-latex` 与 `textContent`。这是原地替换公式文本，不是公式内部 token 级 diff，但也不是重建整棵 KaTeX 树。见 [astExecutor.ts:481](../../src/core/utils/astExecutor.ts#L481)、[astExecutor.ts:1003](../../src/core/utils/astExecutor.ts#L1003)。
- `renderHeavyContent` 只在 `[data-message-render-region="stable"]` 内查询公式并调用 KaTeX；活动 AST/morphdom tail 不属于该区域。因此不能声称尾部每次更新都重跑 KaTeX。见 [MessageRenderer.vue:584](../../src/features/chat/MessageRenderer.vue#L584)、[MessageRenderer.vue:598](../../src/features/chat/MessageRenderer.vue#L598)。

公式定界符刚被识别时，文本节点可能转为公式节点；稳定化后首次 KaTeX 排版也可能改变尺寸。这些是不同的阶段，若实际存在闪烁，必须分别定位，不能用不存在的 MathBlock 分支解释。

## 紧迫性与实施边界

表格的额外工作量可表示为：若第 `i` 次有效表格更新的 AST 大小为 `S_i`，发送和临时 DOM 构造累计随 `ΣS_i` 增长。在更新粒度近似固定且表格持续增长的区间内，累计成本可能接近平方增长；这受空行沉淀、33ms 合并和 64KiB 源 tail 上限约束，不能据此宣称任意长消息都发生无界平方开销。

**P2 的理由：** 已证明有多层全量工作，长表格是正常可达输入，值得进入性能优化计划；同时前端已有 live DOM 复用、稳定区隔离与 tail 上限，未发现该事项导致数据丢失、崩溃或已复现的严重卡顿。原报告“极高”评级缺少支撑。

改进建议与风险：

1. 优先测量长表格的 AST/IPC 字节、前端临时 DOM 创建及 morph 耗时，再决定是否增加行/单元格 mutation。仅有小表格时，新增跨层协议的维护负担可能超过收益。
2. 如增加行/单元格增量协议，需同时修改 Rust mutation、TypeScript 契约及执行器 registry 管理。当前 Table Replace 后刻意清空子孙 registry，不能只在后端新增子级 mutation 就认为链路成立。
3. 需要覆盖表头分隔线刚识别、列数变化、末行尚未闭合、单元格行内样式重分类、图片与公式、空行沉淀、恢复 snapshot 与超过 cap 等情况。优化不得提前冻结仍可被 Markdown 语法重新解释的末行/单元格。
4. 如后续性能测量指向公式，单独比较“定界符成形”“tail 转 stable”“稳定区 KaTeX 首次渲染”三个阶段，不为修复不存在的 MathBlock diff 而扩展协议。

建议的升级证据：在具名 Android 手机、明确 WebView 版本和构建模式下，使用固定表格流，记录 10/100/500 行与不同列数输入，分别观察传输字节、JS 长任务、布局/绘制和滚动响应；对 64KiB cap 前后另作记录。只有获得这些证据，才能把优化优先级与用户可见紧迫性直接关联。

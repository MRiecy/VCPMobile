# 维度二问题 1：引号合并分配审查

审查日期：2026-10-31。源码基线：`a771315ec4b5e71652621cf7343bce2344031479`。本报告审查当前生产源码，并纳入主审执行的生产引号函数 host 探针结果；未改动生产代码或既有测试，未进行 Android 性能采样。

## 结论与紧迫性

**问题存在，但原报告对范围、频率和严重程度的描述需要收窄。建议按 P2 常规性能优化处理；现有证据不足以把这项普通文本分配开销定为“极高”或发布阻断问题。**

对于一个没有引号、没有嵌套格式的非空 `Text` 段落，引号后处理确实额外产生三轮文本复制：入口克隆、拆分时重新构造字符串、合并时再次克隆。它们都没有带来语义变化。这是可以直接从当前源码确认的浪费，并非误报。

但它不等于“每秒 30–60 次复制整条消息的全部 AST”：常规调度窗口为 33ms；稳定块已从活动尾部移出；普通 Markdown 活动尾部超过 65,536 字节后不再做投机 AST 解析；代码围栏等还有独立路径。“严重分配抖动”“分配器频繁加锁”“用户可见卡顿”均未在本次审查中测量。

此外，同一函数存在一个应独立定为 **P1** 的附加问题：**多个未闭合中文左引号会重复扫描后缀，单帧为 O(q²)**。生产源码证明该输入可在普通 Markdown 尾部保护上限内进入处理；直接执行生产拆分/合并函数的 host 探针也复现了平方增长，65,535 字节案例五次中位数为 544.064ms。这是对附件旁证中复杂度判断的纠正，不能和“无引号也复制”的常见负担混为一谈，也不能把 host 数值当作 Android 帧耗时。

## 三次复制的精确含义

`InlineNode` 派生 `Clone`，而 `Text.value` 是拥有所有权的 `String`，不是共享字符串引用；`InlineNode::text` 只是接收该字符串，没有第四次复制。见 [markdown_ast.rs:68](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_ast.rs#L68) 与 [markdown_ast.rs:304](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_ast.rs#L304)。

以 `Paragraph { children: [Text("普通文字")] }` 为例，以下是**源码操作计数，不是 allocator 实测结果**：

1. `children.clone()`：克隆向量及其中的 `String`，复制一次文本。
2. `split_text_by_quotes`：遍历字符串的全部字符，没有发现 `“`、`”`、`"`，仍通过 `to_string()` 复制全文到新的 `Text`。
3. `merge_quote_nodes_at_depth`：没有发现可合并的起始引号，执行 `inlines[i].clone()`，再次复制全文到结果向量。

原 AST 构造所需的字符串分配不在这三次之内；向量的分配、扩容和旧对象释放也应单独计算。对总文本字节数为 B、含 m 个非空纯文本节点且无嵌套的段落，这条后处理路径大致新增 `3B` 文本复制量和 `3m` 次字符串构造/克隆操作，另外还有容器开销。不能把它表述成“峰值内存同时维持四份完整 AST”：中间向量逐步消费，旧字符串也会逐步释放。

遇到 `Strong`、`Emphasis`、`Link`、`Strikethrough` 或带子节点的 `VcpCustom`，合并阶段先克隆整个节点，又克隆 `children` 再递归，后代内容可能被重复复制多次。因此“三次”是无嵌套纯文本案例的精确计数，不是所有输入的上限。拆分阶段递归使用 `mem::take`，这一部分已经采用所有权转移，不能统称为每层全部深拷贝。

## 真实可达范围与生命周期

正常接收路径先把 SSE 内容积累进窗口，再由 `flush_aurora_window` 交给 `AuroraBuffer::process_queue`。常规时钟使用 33ms 间隔，并设置 `MissedTickBehavior::Skip`；时钟分支只有在 `pending_chunk` 非空时才解析。订阅变化、快照收尾、终态等路径也会触发 flush，所以 33ms 不能解释成任何情况下都严格不超过 30 次/秒的硬限流。见 [vcp_client.rs:2087](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2087)、[vcp_client.rs:2200](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2200)、[vcp_client.rs:2243](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2243)。

活动尾部与稳定历史的界限直接影响本项成本：

- 普通文本以空行切分，完整段落在沉淀时解析，余下尾部保留供后续窗口解析。见 [stream_block_parser.rs:945](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L945)。后续窗口不会因本项再解析已沉淀的整条历史消息。
- 投机解析普通 Markdown 尾部时，才会再次进入 `parse_markdown_to_ast_streaming`。见 [aurora_pipeline.rs:943](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L943)。无空行的长段落、长列表、未完表格、部分未闭合特殊块内 Markdown 是更值得量测的输入。
- `MAX_SPECULATIVE_TAIL_AST_BYTES = 65536`；普通尾部**超过**此值会转为 Plain 路径。见 [aurora_pipeline.rs:29](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L29)、[aurora_pipeline.rs:895](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L895)。这是活动尾部的保护，不能推导为静态解析或终态解析也受同一上限保护。
- 正常未闭合代码围栏直接构造代码节点；HTML 容器、思维链、语音指导、部分协议块也有各自路径，不是所有 SSE 内容都经过这个引号后处理。见 [aurora_pipeline.rs:798](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L798)、[aurora_pipeline.rs:909](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L909)。

在无引号、浅层格式输入中，单次后处理对文本规模近似线性；若同一尾部以固定小增量连续增长，在进入保护上限前，累计复制量随各窗口尾部长度求和增长。这说明重复解析尾部的放大效应确实存在，但不能把所有历史消息长度当作每帧 B。

## 相关边界：多处未闭合中文左引号

附件在维度一声称“只有首个未闭合引号向后探测，后续节点不触发内层循环，因此单帧仍为 O(n)”。这只覆盖后续节点都不是起始引号的特定输入。

在当前实现中，`split_text_by_quotes` 会把每个 `“` 拆成单独 `Text`。对由 q 个 `“` 组成且不含 `”` 的内容，合并阶段每到一个节点都会再次认定为开引号，然后从该位置扫描到尾部；由于没有闭合符，无法使用 `i = e_idx + 1` 跳过已消费片段。见 [markdown_parser.rs:1507](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1507)、[markdown_parser.rs:1564](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1564)、[markdown_parser.rs:1581](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L1581)。

因此，仅计算内层访问，次数为 `q + (q - 1) + … + 1 = q(q + 1) / 2`。这是按当前循环推导的路径计数，不是基准数据。例如 21,845 个三字节 `“` 占 65,535 字节，仍未超过投机上限，对应约 2.39 亿次内层节点访问；128 层嵌套限制不能截断这种发生在同一层的重复扫描。

**附加问题定为 P1：生产可达的单层重复扫描已经有算法推导与局部运行复现，应近期修复。** 这不等于证明日常用户消息高频包含此输入，也不等于发布必须阻断。无引号门禁不会修复它，因为输入恰好含有引号。未来优化应同时保留原有引号配对语义并消除已知无闭合后缀的重复探测，而不是只给主问题添加字符检查后就宣称整个引号路径已经线性化。

## 改进方向与语义风险

最小收益明确的方向是：在无引号情况下保留现有节点，并使用所有权转移消除已经可以避免的克隆。应以当前生产 AST 输出为比较对象，不新增引号语法、自动纠错或兼容规则。

实施时需核对以下边界：

- 检查位置必须覆盖真正参与合并的文本和递归子节点。仅检查段落第一层 `Text`，会漏掉格式节点内部的引号。
- 当前普通引号集合是 `“`、`”`、`"`；不要顺手引入单引号、中文单引号或转义规则。
- 块级 `CodeBlock`、`RawHtml` 与行内 `Code`、`InlineMath`、`RawHtmlInline` 目前有不同处理边界。行内节点可以随所属集合克隆，但这些节点内部的字符串不按普通 `Text` 拆引号；不能因复用一个通用递归函数而扩大引号加工范围。
- 已经投影成 `VcpCustom(kind="quote")` 的节点、跨粗体/链接的引号对、表格单元格、嵌套容器需要检查，避免移动所有权时漏子节点、改变匹配顺序或输出节点顺序。
- 即使消除了本项三次复制，Markdown 解析、哈希和 diff 等其他扫描仍存在；不能承诺整个 Markdown tail 从 O(B) 变为 O(增量)。

## 验证建议与本次证据边界

本次执行源码审查，并纳入主审运行的局部生产函数 host 探针；没有运行本项的 cargo criterion 基准或真机采样，也没有把阅读现有测试当作测试已通过。该探针通过直接 `rustc` 编译局部函数，不能替代完整 Android 构建或生产请求链测试；其输出会记录 HEAD、解析器 SHA-256 与 Rust 工具链版本，以便重跑核对。仓库根目录复现命令为 `node plan/sse-lifecycle-dimension-2-audit/probes/quote_cost_probe.mjs`，需已有兼容的 host 依赖构建产物。文档与审查探针不改变跨层或核心生产逻辑，因此未以 `pnpm check` 代替性能证据。

后续实际实施建议分别回答三个问题：

1. **行为是否保留**：比较修改前后生产解析函数产出的 AST 和渲染结果，覆盖无引号、ASCII/中文引号、未闭合引号、跨格式引号、表格及行内代码；重点检查算法的真实边界，不添加无消费方接口。
2. **分配是否减少**：用 allocation profile 分离 `apply_quote_merging` 的字符串字节量和分配次数；覆盖 2KB、16KB、约 64KB 的无空行纯文本与嵌套格式，并测多个未闭合 `“`。整条 Markdown 基准耗时不能全部归因于此函数。
3. **用户体验是否改善**：在具名 Android 设备上测总解析窗口耗时、p95/p99 延迟和主线程帧时间；不要用 host Rust 的耗时或理论分配计数宣布真机掉帧已经解决。

优先级依据：调用频繁、无语义收益的浪费明确、局部改进空间清楚，因此值得排进常规优化；但已有尾部切分与大小保护，且本次没有实际设备退化证据，因此主问题维持 P2。多个未闭合左引号的扫描反例已有生产可达性分析及 host 平方增长复现，独立列为 P1；其发生率及 Android 端实际延迟仍未测量。

# 03 — 代码围栏闭合：全量高亮与交接成本审查

审查日期：2026-10-31（Asia/Shanghai）。源码基线：`a771315ec4b5e71652621cf7343bce2344031479`。范围为原报告维度二第 3 项；本文只记录审查结果，不修改生产行为。

## 结论与紧迫性

**问题部分成立，建议 P2（常规性能优化，优先补齐测量）；不能凭现有证据定为已发生的严重移动端卡顿。**

代码围栏闭合时，Rust 确实重新对整块代码执行 Syntect 高亮，生成完成态 HTML；前端也确实从 tail 沙箱切换至新稳定块。超长代码因此存在可解释的 CPU、分配、IPC 和 DOM 交接峰值。但原报告给出的 **“1000 行 / 40KB 对应 30–80ms、200KB+ IPC、肉眼可见 Jank”没有测量依据**，不能当作本仓库当前 Android 产品的性能事实。已有 benchmark 是测量入口，不是测量结果，且其闭合项未覆盖真实稳定块 IPC 载荷。

“彻底抛弃已经生成的完整高亮结果”也需要修正：后端增量高亮器**没有保存历史 HTML**，只保存词法状态、scope 栈和游标；过去的增量 HTML 已交给前端 DOM。完成态还使用不同的 HTML 发射形态，因此这不是把一次函数调用换成缓存读取即可解决的浪费。

若具名 Android 设备验证发现常见代码长度就造成持续可感知交接停顿，或多路流同时闭合占满运行时 worker，再提升为 **P1（近期优先治理）**。本次没有 P0 / 发布阻断证据。

## 对原断言的逐项裁定

| 原断言 | 裁定 | 当前生产代码说明 |
| --- | --- | --- |
| 闭合后整块 Syntect 从头解析 | **成立，存在例外** | 普通代码调用 `finalized_code_block_node`；`html` 转为 `HtmlPreview` 后也调用完整高亮；精确匹配的 `mermaid` 不执行 Syntect。 |
| 增量结果已经在 Rust 内完整可复用 | **不成立** | `CodeHighlightSession` 不保存历史 HTML。只复用尾部 `ParseState` 不能重新取得历史 token HTML。 |
| 流式稳态严格为 O(chunk) | **表述过强** | 词法工作主要针对新增完整行及当前活动行，但 `strip_prefix(old_code)` 仍比较旧前缀；tail 节点构造也复制完整代码。不能把整条调用链称为严格 O(chunk)。 |
| 40KB 必然花费 30–80ms | **未证实** | 未提供设备、构建模式、语言、输入、分位数、冷暖状态或原始测量。源码只能证明重高亮工作与整块内容相关。 |
| 必然下发 200KB+ HTML | **未证实** | HTML 随语言 scope 密度、转义和输入变化；代码中没有这个常数或保证。完整终态 HTML 确实随稳定块传送。 |
| Rust 高亮阻塞前端主线程 | **需拆分** | 高亮同步执行在 Rust async 请求任务中，会延迟该任务后续处理；WebView 主线程承担另一段 JSON/Store/HTML/DOM 工作，不能把 Rust 耗时直接计作前端主线程阻塞。 |
| 闭合开销每个 token 都发生 | **不成立** | 主要在每个代码块闭合或未闭合块终止定稿时发生一次；稳态通常走增量高亮。 |

## 生产调用链与证据

### 1. 未闭合阶段确实维持增量词法状态

[`code_highlighter.rs:20–36`](../../src-tauri/src/vcp_modules/chat/pre_renderer/code_highlighter.rs#L20) 的 `CodeHighlightSession` 只有 `language`、`committed_len`、`parse_state`、`scope_stack` 和 `seen_generation`。源码明确说明历史 HTML 只存在于前端 DOM，不在 Rust 中再留等长镜像。

[`append:85–127`](../../src-tauri/src/vcp_modules/chat/pre_renderer/code_highlighter.rs#L85) 先检查新代码是否严格追加，再从最后一个完整换行后的字节游标向前推进。返回 `completed_html` 与 `active_html`；[`ast_diff.rs:351–384`](../../src-tauri/src/vcp_modules/chat/ast_diff.rs#L351) 将其包装成 `PatchCode`。未完成的超长单行仍需重新解析该活动行，并不是每次只解析新增几个字符。

此外，`new_code.strip_prefix(old_code)` 包含前缀比较；[`code_fence_tail_nodes:220–261`](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L220) 仍会执行 `code.to_string()`，必要时规范化换行与缩进。本文不扩展为新的独立问题，但不能照抄原报告对稳态 O(chunk) 的绝对描述。

### 2. 闭合时普通代码与 HTML 都进行完成态高亮

[`stream_block_parser.rs:893–919`](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L893) 从完整围栏提取语言与代码：

- 非 `html` 围栏调用 [`finalized_code_block_node:141–155`](../../src-tauri/src/vcp_modules/chat/pre_renderer/markdown_parser.rs#L141)，精确 `mermaid` 除外均调用 `highlight_code_block`。
- `html` 围栏调用 [`StreamBlock::html_preview:164–177`](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L164)，同样对全文执行 `highlight_code_block(..., CodeBlockShell::Html)`。
- [`highlight_code_block:346–386`](../../src-tauri/src/vcp_modules/chat/pre_renderer/code_highlighter.rs#L346) 新建 `ClassedHTMLGenerator`，遍历 `LinesWithEndings` 的全部代码行，再 `finalize()` 生成完成态 HTML。因此“重跑整块词法高亮”有直接源码证据。

这里已经有一项针对闭合的优化：非 HTML 分支不再把已提取的围栏送回整个 Markdown 预处理管线。因此准确描述是**重新提取/完成态整块高亮与哈希**，并非无差别重跑全部 Markdown 处理步骤。

同一轮 [`AuroraBuffer::process_queue:778–786`](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L778) 把新块放进 `stable_blocks`，递增 epoch，清空旧 tail AST 与增量高亮器状态。完整高亮在 parser 生成稳定块时已经发生，不能通过简单延后 `clear()` 自动消除。

未闭合围栏在 EOS 也会定稿：[`StreamBlockParser::finalize:551–567`](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs#L551) 将剩余尾部走非流式 Markdown 解析，随后 [`AuroraBuffer::finalize:1027–1042`](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L1027) 进入稳定块并清空尾部状态。这与维度二第 7 项的持久化重编译有关，但不能把两段开销混为一个闭合帧结论。

### 3. CPU 调度：33ms 合批，不是每个 SSE chunk 直接解析

[`vcp_client.rs:339`](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L339) 定义 33ms 的 `AURORA_PARSE_INTERVAL`；[`2200–2204`](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2200) 设置漏 tick 时 `Skip`。多个 SSE delta 先累积在 `pending_chunk`，到 render tick 再执行 [`flush_aurora_window:2087–2092`](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2087)。恢复/消费者变化及终止还存在立即 flush 的路径，33ms 不是所有路径的绝对帧率上限。

[`render_clock` 分支 2251–2259](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2251) 同步执行 `buffer.process_queue()` 后才发送更新；闭合高亮未单独 offload 到 `spawn_blocking`。因此它会占用执行该 async 请求的 Rust worker、延迟该任务的读帧/取消/后续发送；是否波及其他请求取决于设备、实际耗时、运行时 worker 数量及同时活跃的任务。当前传输并发门限是 [`8 路`](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L2082)。

这不是 Kotlin UI 线程或 WebView 主线程直接运行 Syntect。前端卡顿是否发生，必须单独看消息到达后主线程的处理时长和帧表现。

### 4. IPC 实际发送什么

正常消费者已连接、没有强制快照时，[`prepare_delta_update:543–625`](../../src-tauri/src/vcp_modules/chat/aurora_pipeline.rs#L543) 仅把新增稳定块放进 `stable_append`；原有稳定块不随每次闭合重复发送。闭合且无后续 tail 的常见更新包含：

- 新稳定块：普通代码为 `Markdown.content`（含围栏原文）与 `nodes[0].code`、`nodes[0].highlighted_html`；HTML 预览为 `content` 与 `highlighted_content`。
- `tail_op = Clear` 和旧 tail 的 reset/空 snapshot；不会把刚生成的稳定块 HTML 再装进旧 tail snapshot。
- 本次新到达的原文 `chunk`（通常包括闭合围栏，也可能夹带更多内容）。

所以正常闭合更新内的**完成态高亮 HTML 通常是一份**，但普通代码还包含两种原文表示；序列化转义也增加 payload。内存 `clone()` 与 IPC 中重复出现是两个不同问题，不能因为内存复制就断言发送多份相同 HTML。

[`RequestOutput::send_aurora:570–588`](../../src-tauri/src/vcp_modules/infra/vcp_client.rs#L570) 在恢复/重连时可发送完整 snapshot；没有前端 channel 且没有朗读消费者时，会丢弃 pending delivery，不生成这次 IPC 更新。因此“任何闭合一定产生 IPC 洪峰”也不准确。

### 5. 前端确实发生尾部到稳定块的 DOM 交接

[`chatStreamStore.ts:571–577`](../../src/core/stores/chatStreamStore.ts#L571) 追加新稳定块，[`608–612`](../../src/core/stores/chatStreamStore.ts#L608) 清除尾部。普通稳定 Markdown 由 [`MessageRenderer.vue:385–390`](../../src/features/chat/MessageRenderer.vue#L385) 生成 HTML，通过 [`1063–1067`](../../src/features/chat/MessageRenderer.vue#L1063) 的 `v-html` 呈现。代码节点优先使用后端的 [`highlighted_html`](../../src/core/utils/astRenderer.ts#L243)；HTML 预览另有 [`HtmlPreviewBlock`](../../src/features/chat/MessageRenderer.vue#L1092) 接管。

旧 tail 沙箱在 [`useMessageTailRenderer.ts:186–192`](../../src/features/chat/composables/useMessageTailRenderer.ts#L186) 清理。这支持“当前实现没有把整块 tail 代码 DOM 原位转交给稳定块”的判断，也支持大块 HTML 存在解析/挂载成本。**源码无法证明肉眼可见卡顿、具体 Reflow 时长或某台设备的掉帧程度。**

## 为什么不能直接复用高亮器解决

这里同时存在状态所有权和表示差异：

1. 增量高亮器仅保留最后完整行 checkpoint，无法反向恢复已经输出到 DOM 的所有 HTML。需要复用的是前端已经呈现的内容，或后端新增保存的完整结果；后者会增加常驻内存和 snapshot/终态维护负担。
2. [`classed_line_html:223–232`](../../src-tauri/src/vcp_modules/chat/pre_renderer/code_highlighter.rs#L223) 使用逐行闭合、按最内层 scope 平铺的 span；完成态 `ClassedHTMLGenerator` 使用另一种嵌套结构。相同 CSS 类命名不等于相同 HTML 结构。
3. `html` 闭合后从流式源码转为 HTML 预览组件，这是现有产品语义，不能为了省一次高亮取消这个交接。
4. 没有已挂载 DOM 的重连快照、冷加载、未闭合 EOS 及持久化仍需自足的终态表示。只优化在线 DOM 交接不能替代这些路径。

## 现有 benchmark 的证据范围

[`Cargo.toml:107–109`](../../src-tauri/Cargo.toml#L107) 已注册 `ast_tail_bench`；[`perf profile:123–131`](../../src-tauri/Cargo.toml#L123) 采用优化构建。现有 [`bench_worst_frame_fence_close:207–235`](../../src-tauri/benches/ast_tail_bench.rs#L207) 用 `html` 围栏、4KB/16KB/40KB 三档预填充，计时区执行闭合后的 `process_queue()` 和 `take_tail_frame()` 序列化。

**关键遗漏：它序列化的是 TailFrame，而完整完成态 HTML 在 `AuroraUpdate.stable_append`。** 闭合后 TailFrame 通常是清空尾部的 reset/snapshot。该 benchmark 能测到 parser 中的完整高亮 CPU，不能代表实际 `prepare_delta_update`、完整 StreamEvent 序列化、IPC 传输及前端 DOM 交接成本，更不能据此声称“实测 200KB IPC”。

本次只读审查没有运行该 benchmark，没有读取到可归属当前基线的 benchmark 数值结果；也没有执行 Android 性能采集。未构建 APK、未更改生产或测试文件。文档中的测量需求不能写成已经完成的测试。

## 建议与后续验收

先按真实交接边界测量，再决定是否修改表示或调度。建议取仓库相对路径 fixture，覆盖常见小代码、40KB 和更长代码；至少包含 Rust、HTML、未知语言、多行字符串、超长单行、末行无换行、嵌套围栏与未闭合 EOS。

测量应分别记录：

1. `process_queue` / 完成态高亮耗时及分配；冷启动语法加载与暖态分开。
2. 真实 `AuroraUpdate` / `StreamEvent` 的序列化总字节数及分项大小，覆盖 `stable_append`，而非仅统计 TailFrame。
3. 具名 Android Debug 设备的闭合事件到达、JSON/Store 消费、稳定 HTML 挂载与帧时间；单路和多路并发分别记录。
4. 交接前后代码原文一致性、语法着色、复制/选择、滚动位置、HTML 预览可用性，以及重连和终态持久化的一致性。

若数据确认需要治理，可先评估 CPU 工作隔离或调度，使长块闭合不长时间占用 async worker，但必须保持流内顺序、取消、背压和有界任务数量。该措施不会消除高亮 CPU 或 IPC/DOM 体积，不能声称根治。只有实际峰值仍不达标时，再评估终态发射形态统一、在线 DOM 接管或可复用高亮结果的所有权设计；这属于跨层设计，不能作为局部缓存补丁直接落地。

优先级按 **P2** 入列的理由是：重复工作真实存在、代码块长度可变且围栏 tail 不受通用 64KB AST 上限约束，值得测量与优化；但它是每块一次的交接成本，当前没有用户可感知损害的设备证据，也没有支持原报告定量严重度的数据。

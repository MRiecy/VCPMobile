## 3. 围栏完整事件测量

基准现在先提交预填充 snapshot 的交付游标，再计时追加闭合串、解析、`prepare_delta_update`、完整 `StreamEvent` JSON 序列化和交付提交。计时外验证 `stableAppend` 中确实包含完成态高亮，且只发送新增闭合串，不重复发送已交付全文。

闭合串末尾的换行按生产定界规则留下新的 Markdown tail，因此实际协议是 `Replace("\n")` 和空 AST reset。首次基准的 `Clear` 假设已按生产行为纠正，未修改生产协议。

| 档位 | 实际 fixture 字节 | 完整闭合事件耗时 | 独立高亮基线耗时 | 完整 JSON 字节 |
| --- | ---: | ---: | ---: | ---: |
| 4 KiB | 4,094 | 7.6372 ms | 7.6873 ms | 67,947 |
| 16 KiB | 16,384 | 39.391 ms | 40.975 ms | 305,452 |
| 40 KiB | 40,960 | 74.857 ms | 74.083 ms | 770,229 |

耗时为 Criterion 点估计，使用现有 `perf` profile。完整事件三档区间分别为 7.3136–7.8961、36.542–42.963、68.312–82.077 ms。独立高亮直接处理原 fixture，闭合路径使用生产规范化后的代码；两列不能相减当作精确分项耗时。

完整管线在 benchmark 的 `cfg(test)` 构建下还含原有诊断输出成本；采集器只过滤展示，没有消除其运行成本。独立高亮基线不经过这些诊断路径。以上均未测量原生 IPC 传输、WebView 或 GPU。

复现命令，在 `src-tauri/` 执行：

```powershell
cargo bench --locked --profile perf --bench ast_tail_bench -- '(stream_worst_frame_fence_close/full_event|tail_syntect_highlight)/(4096|16384|40960)$'
```

本表测量的是围栏闭合时的整块高亮与完整事件序列化，不是持续生成期间的每次增量更新。流式高亮复用已提交完整行的解析状态，追加新完成行并更新当前未完成行；围栏闭合时再生成完成态高亮。整条消息落盘时仍会全量编译一次，该持久化编译已经使用受限的 blocking pool。因此正常闭合块并非整个生命周期只全量处理一次，但也不是每次流式更新都重做整块高亮。上一节约 64 KiB 的输入属于未闭合引号探针，本节代码块最大档位为 40 KiB。

16/40 KiB 高亮虽超过附件的 15 ms 条件，但不能用每帧预算直接判定这种低频收尾工作的紧迫性，也不能把后端耗时等同于界面冻结时间。用户明确接受此类收尾阶段几十至几百毫秒的开销；目前缺少真机上的明显卡顿或并发影响证据，本轮只保留测量结论，生产调度改造继续暂缓。调度隔离还涉及五处 flush 的状态所有权、失败、取消、恢复与终态衔接；线程隔离本身不会减少高亮 CPU 工作量或事件载荷。

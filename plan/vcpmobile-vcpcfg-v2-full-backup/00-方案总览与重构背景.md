# 00 - 方案总览与重构背景

## 1. 业务驱动与背景分析

VCP Mobile（代号：Project Avatar）经过百余次迭代，完成了核心对话引擎、流式渲染管线（SSE）、JEV 群聊自治系统、多端数据同步 V2、离线日记中心以及 iOS 跨平台适配等庞大功能的工程落地。

在当前生产环境中，配置文件导出与恢复功能（`.vcpcfg` / `.vcpcfg.json`）一直停留在早期设计：
- **历史设计局限**：原先导出主要用于解决在手机上频繁手动输入 Server URL、API Key、Sync Token 的繁琐输入问题。
- **配置割裂与数据孤岛**：
  - 聊天记录、话题、头像、基础群成员等数据走 **Sync V2 协议**（WebSocket + CDS 增量同步）。
  - 然而，移动端拥有大量**专有能力与深度自定义配置**（例如：Agent 移动端专用系统提示词 `mobile_system_prompt`、独立声音合成音色 `AgentVoiceConfig`、群聊 JEV 算法参数 `GroupModeSettings`、成员上下文消息窗口 `context_message_window_size`、用户本地模型收藏 `model_favorites`、本地 Tarven 规则库 `tarven_rules` 等）。
  - 这些配置无法、也不应随意塞入双端同步 DTO（Data Transfer Object）：
    1. **DTO 演进成本极高**：Sync DTO 是桌面端与移动端共享的物理契约（The Shared Truth），变更 DTO 需要同步更新桌面端 VChat/CDS 数据库、哈希计算逻辑、校验管道与迁移脚本；
    2. **平台特性不对等**：移动端专为触控屏幕与移动语音定制的参数（如针对移动端紧凑输出的 `mobile_system_prompt`、移动端原生麦克风录音编码、震动触感反馈），桌面端根本没有对应的概念和消费方。
  - **导致的严重痛点**：用户一旦重装应用或更换新手机，即使通过 Sync V2 成功同步回了全部 Agent 和群聊消息，所有在手机上精心调整的移动端专用提示词、群组发言顺序、独立音色配置、主题与日记视图排版**全部丢失**，被迫逐个手动重新设置。

## 2. 核心架构矛盾与设计决策

### 矛盾一：版本号决策（V2 还是 V3？）
- **决策结论**：**严格保持版本号为 V2 (`version: 2`)**。
- **理由**：
  - 项目当前处于高速开发阶段，版本定义契约并未冻结。
  - Rust 的强类型反序列化与前端基于 Object 键 presence 的 Patch 归一化体系（见 `src-tauri/src/vcp_modules/infra/settings_manager/backup.rs`）天生支持增量扩展字段：
    - 旧版 V2 备份缺少新字段时，`Option<T>` 自然解析为 `None` 或空集合，绝不破坏解析；
    - 新版 V2 备份在包含新增字段时，旧解析器按 schema 过滤非自身识别的键，保持向前兼容。
  - 因此无需引入破坏性的 V3 格式升级，继续在 V2 规范上做结构化扩展。

### 矛盾二：空机导入时序倒挂（The Bootstrap Paradox）
- **现象**：
  - 导出是在有数据的旧设备上发生的：包含了 `agent_id_A` 的移动端提示词，以及 `group_id_B` 的发言顺序。
  - 导入通常是在空机首次启动时发生：此时本地 SQLite 数据库中 `agents` 和 `groups` 表为空（尚未进行数据同步）。
  - 如果强行按 `agent_id` 写入，外键或逻辑存在性校验会失败；如果提前伪造假实体，会破坏后续 Sync 增量比对协议与哈希链。
- **决策结论**：**“强绑定匹配 + 墓碑/缺失静默跳过 + 两阶段恢复引导”**。
  - 导入遵循现有群组本地设置（`import_group_local_settings`）的严格原则：
    1. 若实体在本地存活（`deleted_at IS NULL`）：立即原子写入配置；
    2. 若实体已被删除（`deleted_at IS NOT NULL`，墓碑）：静默跳过；
    3. 若实体尚未同步（本地不存在该 ID）：记录为 `missingEntities`，不预造空实体，跳过本次写入；
    4. 报告结果明确告知用户：“全局连接与偏好已恢复；检测到 N 个助手与群组配置待同步后生效”；
    5. 通过新手引导与首次同步完成事件，驱动用户在同步完成后“一键应用待恢复配置”或二次导入。

### 矛盾三：配置归属权与前端 Pinia 持久化
- **现状**：前端部分设置由 Pinia 管理并持久化在 `localStorage`（如 `theme`、`chatPreferences`、`topic.sortMode`、`diaryStore`），而全局核心配置保存在 Rust SQLite `config_domains` 表中（见 `0103_config_domains.sql` 物理迁移，原 `settings` 表仅用于旧版一次性过渡）。
- **决策结论**：**三层物理分离，统一信封聚合**。
  - 备份文件采用统一 JSON 信封：
    - `domains`：Rust 数据库全局设置（原子提交至 `config_domains` 表，包含解除导出限制的 `navigation` 侧栏排序）；
    - `agentPreferences`：Agent 本地列补丁（原子提交至 `agents` 表本地专用列）；
    - `groupPreferences`：Group 本机设置补丁（原子提交至 `group_local_settings` 表）；
    - `standaloneData`：模型收藏（`model_favorites`）与 Tarven 规则库（`tarven_rules`，区分系统预置开关与自定义规则）；
    - `preferences`：前端 Pinia 持久化偏好（由各 Store 专有 normalizer 解析回填；`developerSettings` 属单机诊断黑名单，坚决排除）。
  - 导出时由前端向 Rust 获取 DB 层的不可变快照，聚合前端各 Store 当前持久偏好，生成单一 `.vcpcfg.json`。
  - 导入时先由 Rust 校验信封与大小安全，拆解并分发给各模块所有者。

## 3. 七项核心架构准则与事实基石

重构方案必须严格建立在以下 7 项经物理源码审计验证的架构事实之上：

1. **Rust 单一写事务与锁序保障**：所有持久化导入必须经由 `SettingsState` 的 `writer` 互斥排队，并通过 `DbState::write_transaction("settings.import-full-backup")` 派发写事务，在一单条 SQLite 事务中一并提交 `config_domains`、`agents`、`group_local_settings`、`model_favorites` 与 `tarven_rules`，严禁跨多事务碎片化写入，亦严禁在 `SettingsInner` 凭空假定 `pool`。
2. **Agent 本地列与同步哈希绝对隔离**：智能体本地列仅包含 `mobile_system_prompt`、`use_temperature`、`voice_config`。导入写入时**严禁变更 `config_hash` 与 `updated_at`**，确保不会向桌面端 CDS 触发反向脏同步。
3. **Group 本地配置对等匹配与墓碑免疫**：群组模式参数（`chat_mode`、`mode_settings`、上下文窗口）严格沿用 `group_local_settings` 现有的物理隔离机制；未入库实体计入缺失，墓碑实体（`deleted_at IS NOT NULL`）静默跳过，绝不复活已删群组。
4. **独立业务表完整纳入与预置规则防冲**：`model_favorites` 与用户自定义 `tarven_rules` 完全纳入 `standaloneData` 独立备份；Tarven 预置规则（`sort_order: -100` 的 `system_meta_injection`、`time_anchoring_v2`）在还原时仅恢复启用开关状态，严禁覆盖内置模板；模型收藏按时间戳递减分配复原排序优先级。
5. **Pinia 持久化四级分流边界**：确立“通用客户端偏好”、“实体弱绑定偏好（容错渲染）”、“独立离线数据”与“严禁导出的运行时易失黑名单（冷启会话、引导完成标记、权限引导、开发者模式）”的清晰边界。
6. **两阶段恢复与暂存快照免重选**：阶段一空机预配置写入全局网络与偏好，将未匹配实体偏好持久化暂存于前端 `localStorage['vcp_staged_entity_backup']`（附带 7 天 TTL）；阶段二在 CDS 数据同步完成钩子（`syncSessionStore.stopAndReload()`）唤起 `overlay.showConfirm` 提示，用户确认即可直接应用暂存 Payload，彻底免除在系统文件管理器中二次翻找文件的摩擦。
7. **契约生成与向下兼容契约**：版本号严格保留为 `2`；Rust 端通过 `ts_rs` 派生 `ConfigBackupImportResult`，通过 `pnpm config:generate` 自动保证前后端类型一致；物理上强制执行 1 MiB 读取硬限；在 `schema.rs:88` 移除对 `Navigation` 领域的排除，并同步更新既有测试断言。

# 03 - 空机导入生命周期与两阶段恢复架构

## 1. 空机导入时序倒挂（The Bootstrap Paradox）

### 1.1 核心矛盾剖析
在移动端应用生命周期中，用户导入配置备份的最典型时机，恰恰是：**全新安装、清除数据后重新打开，或更换新手机后的首次初始化**。

此时的物理状态如下：
1. **SQLite 数据库为空（初始 Baseline 状态）**：`agents`、`groups`、`topics`、`messages` 表中没有一行用户业务数据。
2. **Sync 尚未启动**：因为空机上还没有配置 `server.url` 和 `sync.token`，必须先配置或导入网络参数才能连接桌面端服务。
3. **备份文件（.vcpcfg.json）包含强绑定的实体配置**：备份文件中包含了 20 个 `agentPreferences`（针对特定 Agent UUID）和 5 个 `groupPreferences`（针对特定 Group ID）。

如果直接将这些实体偏好执行 SQL `UPDATE` 或强行 `INSERT`：
- **方案缺陷 A（伪造临时行）**：若强行在 `agents` / `groups` 插入空壳行，后续当 Sync V2 启动时，桌面端增量推送会因本地已存在未完成初始化的相同 ID 而发生哈希碰撞或主键冲突，导致同步流水线严重损坏；
- **方案缺陷 B（硬性报错阻断）**：若因本地实体不存在而直接报错终止导入，则用户连最基本的 Server URL、API Key、主题和语音参数都无法还原，备份彻底沦为废纸。

## 2. 核心架构设计：强绑定匹配与两阶段恢复

### 2.1 实体匹配三大物理铁律
当导入 `agentPreferences` 和 `groupPreferences` 时，对每个 `entity_id` 施加严格的状态机判定：

```
                              ┌──────────────────┐
                              │  读取 entity_id   │
                              └────────┬─────────┘
                                       │
                      ┌────────────────┴────────────────┐
                      ▼                                 ▼
              本地数据库存在?                      本地数据库不存在?
                      │                                 │
             ┌────────┴────────┐                        ▼
             ▼                 ▼                  【MISSING 状态】
     deleted_at IS NULL   deleted_at IS NOT NULL   跳过写入，计入 missingCount
             │                 │                   提示用户后续同步
             ▼                 ▼
      【ACTIVE 状态】    【TOMBSTONE 状态】
      执行原子字段合并   静默跳过 (已墓碑化)
      落盘持久化         防止复活已删实体
```

1. **ACTIVE（存活实体）**：实体存在且 `deleted_at IS NULL`。
   - 提取补丁中明确提供的非空字段，执行局部合并写入；
   - 绝不修改 `config_hash` 和 `updated_at`（保证不触发桌面端反向脏同步）；
2. **TOMBSTONE（墓碑实体）**：实体存在但 `deleted_at IS NOT NULL`（用户在某端已删除此实体）。
   - **绝对静默跳过**，严禁将已删除的实体复活；
3. **MISSING（缺失实体）**：本地数据库中不存在该 ID（空机状态或新增实体未同步）。
   - **不预存无主实体**；
   - 计入 `missing_agents` / `missing_groups` 计数器，作为导入收尾反馈。

## 3. 两阶段恢复流程详解

### 阶段一：空机预配置（Pre-Sync / Initial Import）
- **触发时机**：应用首屏新手向导点击「导入配置备份」或设置页手动导入。
- **执行内容**：
  1. Rust 打开 SQLite 单一写事务 `settings.import-full-backup`；
  2. 写入全局 `domains`（主服务器 URL、API Key、Sync Token、Voice 等）；
  3. 写入全局独立数据（`model_favorites`、`tarven_rules`）；
  4. 恢复前端 Pinia 全局偏好（`theme`、`chatPreferences`、`topic.sortMode` 等）；
  5. 尝试匹配 `agentPreferences` 与 `groupPreferences`：在空机上检测到所有实体均为 Missing；
  6. 事务提交。
- **向用户反馈**：
  - 成功项：`["主服务器连接", "数据同步", "主题与深浅模式", "聊天偏好", "常用模型收藏", "Tarven规则"]`；
  - 待恢复项：`"检测到配置中包含 12 个助手与 4 个群聊的专用设置。当前尚未进行数据同步，暂未应用。请先完成【数据同步】，同步后即可还原助手与群组配置。"`
- **关键机制：暂存 Token 与未竟标记 (Dual-Tier Lifecycle Staging)**：
  - 前端持久化存储 `localStorage.setItem('vcp_staged_entity_backup', JSON.stringify({ importedAt: Date.now(), agentPreferences, groupPreferences }))`；
  - 设置 `has_pending_entity_config = true`，附带 7 天 TTL；
  - 这种轻量持久化即便在用户关闭应用、冷启动或切换到桌面端时依然保持有效，同时避免了在 SQLite 中增加临时表的过度工程开销。

### 阶段二：首次同步后一键恢复（Post-Sync / Deferred Apply）
- **触发时机**：
  - 用户配置好网络后，进入同步面板运行 Sync V2；
  - CDS 服务通过 WebSocket 将桌面端的 Agents、Groups、Topics、Messages 批量拉取并原子写入 SQLite；
  - 前端 `syncSessionStore.stopAndReload()` 执行 `useDataReload().performFullReload()` 完成，数据正式在 Vue 渲染层就绪。
- **智能感知与弹窗唤起**：
  - 同步收尾钩子检测到：
    1. 本次同步成功完成（`status === 'completed'` 或 `'completed_with_warnings'`）；
    2. 存在未竟配置标记（`has_pending_entity_config === true`）；
  - 自动向用户展示通过 `overlay.showConfirm` 唤起的提示弹窗：
    > **标题**：「同步已完成 · 恢复助手专用设置」  
    > **内容**：智能体与群组数据已成功同步回本机。检测到您此前导入的配置备份中包含专属提示词与群聊模式，点击即可一键应用。
- **执行效果**：
  - 用户点击确认后，直接读取 `vcp_staged_entity_backup` 中的 payload 提交 Rust IPC 局部补丁写入；
  - 此时 `agents` 和 `groups` 表已全部就位，所有 ID 瞬间完成匹配；
  - 若暂存载荷丢失（如被用户清理应用缓存），则降级提示用户重新选择 `.vcpcfg.json` 文件补全；
  - 各 Agent 移动端提示词、音色、以及 Group JEV 参数在 50ms 内完全恢复，随后清除暂存标记！

## 4. Rust 后端单一事务与锁序保证（ACID Architecture）

所有导入动作必须严格收束于 `SettingsState` 与 `SettingsRepository` 的统一管线中，由 `DbState::write_transaction` 统一派发写锁与事务，杜绝跨事务碎片化写入导致的脏状态：

```rust
// src-tauri/src/vcp_modules/infra/settings_manager/repository.rs

// 统一导入载荷封装
pub struct BackupImportPayload {
    pub group_preferences: BTreeMap<String, GroupLocalSettingsPatch>,
    pub agent_preferences: BTreeMap<String, AgentLocalSettingsPatch>,
    pub model_favorites: Vec<String>,
    pub tarven_rules: Vec<TarvenRule>,
}

pub enum ConfigMutation {
    Update(ConfigUpdate),
    Import(ConfigUpdate, BackupImportPayload),
}

// 在 SettingsRepository::apply_owned 内部统一加锁与事务执行：
// 1. 获取 writer 锁：let guard = self.inner.writer.clone().lock_owned().await; (死锁防御第一道闸)
// 2. 开启单个 SQLite 事务：let mut transaction = db.write_transaction("settings.import-full-backup").await?;

// 3. 执行全局 config_domains 表记录写入 (0103_config_domains.sql 物理表)
let mut next_records = records;
for write in writes {
    persist_record(&mut transaction, write.domain, &write.record).await?;
    next_records.insert(write.domain, write.record);
}

// 4. 群组本地配置写入 (复用已验证并经测试覆盖的 import_group_local_settings)
// 注：该机制早已在 group_service.rs#L1595 单测中确立“同步实体前不自动还原、等同步后显式重导”原则
let missing_groups = if !payload.group_preferences.is_empty() {
    crate::vcp_modules::group::group_service::import_group_local_settings(
        &mut transaction,
        &payload.group_preferences,
    ).await?
} else { false };

// 5. 智能体本地列写入 (严格保护 config_hash 与 updated_at 不被触发)
let missing_agents = if !payload.agent_preferences.is_empty() {
    crate::vcp_modules::agent::agent_service::import_agent_local_settings(
        &mut transaction,
        &payload.agent_preferences,
    ).await?
} else { false };

// 6. 独立业务表写入 (模型收藏与 Tarven 自定义规则)
// 模型收藏按时间戳递减分配，复原用户在界面上的置顶排序优先级 (ORDER BY created_at DESC)
let base_time = crate::vcp_modules::infra::utils::now_millis();
let total_models = payload.model_favorites.len();
for (idx, model_id) in payload.model_favorites.iter().enumerate() {
    let assigned_time = base_time + ((total_models - idx) as i64) * 1000;
    sqlx::query("INSERT OR REPLACE INTO model_favorites (model_id, created_at) VALUES (?, ?)")
        .bind(model_id).bind(assigned_time)
        .execute(&mut *transaction).await?;
}

// Tarven 规则库：预置规则 (system_meta_injection, time_anchoring_v2) 仅更新 is_enabled 开关，
// 严禁覆盖内置模板定义；自定义规则执行全量 upsert
for rule in &payload.tarven_rules {
    if rule.id == "system_meta_injection" || rule.id == "time_anchoring_v2" {
        sqlx::query("UPDATE tarven_rules SET is_enabled = ? WHERE id = ?")
            .bind(rule.is_enabled)
            .bind(&rule.id)
            .execute(&mut *transaction).await?;
    } else {
        sqlx::query(r#"
            INSERT INTO tarven_rules (id, name, rule_type, is_enabled, content, scope, wrap, role, depth, position, sort_order, created_at, updated_at)
            VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
            ON CONFLICT(id) DO UPDATE SET
                name = excluded.name, rule_type = excluded.rule_type, is_enabled = excluded.is_enabled,
                content = excluded.content, scope = excluded.scope, wrap = excluded.wrap,
                role = excluded.role, depth = excluded.depth, position = excluded.position,
                sort_order = excluded.sort_order, updated_at = excluded.updated_at
        "#)
        .bind(&rule.id).bind(&rule.name).bind(&rule.rule_type).bind(rule.is_enabled)
        .bind(&rule.content).bind(&rule.scope).bind(rule.wrap).bind(&rule.role)
        .bind(rule.depth).bind(&rule.position).bind(rule.sort_order)
        .bind(rule.created_at).bind(rule.updated_at)
        .execute(&mut *transaction).await?;
    }
}
    // 预置规则仅更新 is_enabled 开关，不篡改内部定义；自定义规则全量 UPSERT
    if rule.id == "system_meta_injection" || rule.id == "time_anchoring_v2" {
        sqlx::query("UPDATE tarven_rules SET is_enabled = ? WHERE id = ?")
            .bind(rule.is_enabled).bind(&rule.id).execute(&mut *transaction).await?;
    } else {
        sqlx::query("INSERT INTO tarven_rules (id, name, rule_type, is_enabled, content, scope, wrap, role, depth, position, sort_order, created_at, updated_at)
                     VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
                     ON CONFLICT(id) DO UPDATE SET name=excluded.name, content=excluded.content, is_enabled=excluded.is_enabled, updated_at=excluded.updated_at")
            // ... binds ...
            .execute(&mut *transaction).await?;
    }
}

// 7. 提交单事务并释放锁
let next = Arc::new(project_records(&next_records)?);
transaction.commit().await?;
*self.inner.cache.write().await = Some(next.clone());
drop(guard);

// 8. 执行同步生命周期回调 on_committed：
//    - GroupManagerState.invalidate_cache() 清理群组内存缓存
//    - ActiveGroupTurns.notify_group_changed() 通知活跃轮次
//    - settings_committed() 向前端发出 'vcp-config-changed' 事件
```

### 缓存失效与运行时协调
物理提交成功后，必须同步执行全局缓存失效：
1. `group_state.invalidate_cache()`：清除已载入的群组模式内存缓存；
2. `ActiveGroupTurns.notify_group_changed(&id)`：中断或更新正在运行的轮次；
3. `app.emit("vcp-config-changed", snapshot)`：通知 Vue 前端更新 `useSettingsStore`；
4. 前端调用 `useAssistantStore().fetchAgentsAndGroups()`：刷新本地助手机制与侧栏展示。

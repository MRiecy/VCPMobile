## 1. 调研边界

本文件回答三个问题：Release 首屏目前实际经过哪些阶段，当前构建向 WebView 交付了什么，以及哪些问题已经可以由源码证明。它不宣称已经测得真机瓶颈。

本轮只读审计覆盖：

- `index.html`、`src/main.ts`、`src/App.vue` 与 `AppLifecycle` 启动链；
- Chat 路由、消息历史、头像、设置、主题和 Overlay 的加载方式；
- `MessageRenderer.vue` 的稳定块、流式尾部和重内容渲染；
- Vite 当前生产 Web build 与生成资源；
- Android 配置、性能脚本与测试边界。

没有覆盖的实测项包括：Release APK 的 Profile/Perfetto、WebView DevTools trace、真实旧手机和平板截图、热状态下长稳、GPU 合成层和 RSS 峰值。

## 2. 当前启动关键路径

源码可还原出以下顺序：

```text
Android Activity / WebView 创建
  → index.html 静态 preloader 首次绘制
  → 初始 JS/CSS 解析与执行
  → createApp(App).use(router).mount('#app')
  → App.vue onMounted
      → 注册系统事件监听
      → bootstrapApp()
          → get_system_snapshot
          → [theme.initTheme || waitForCoreReady]
          → PRELOADING Promise.all
              ├─ settings.fetchSettings
              │    ├─ read_settings
              │    └─ get_settings_recovery_status（串行）
              ├─ assistant.fetchAgentsAndGroups
              │    └─ get_assistants_snapshot
              ├─ avatar.preloadAll
              │    └─ batch_get_avatars → JS Uint8Array → Blob → ObjectURL
              └─ 已恢复会话时 preloadHistory(..., 5)
          → AppLifecycle.READY
  → main / sidebars / global overlays / feature overlays 挂载
  → 首屏 DOM、异步 Overlay chunk 与重内容后处理竞争主线程
```

对应证据：

- `src/main.ts` 在 mount 前静态导入全局主题、消息块样式和 KaTeX CSS。
- `src/App.vue:447-475` 仅在 `READY` 后创建主界面、侧栏和大部分 Overlay。
- `src/core/stores/appLifecycle.ts:129-171` 明确让四类预加载工作共同阻塞 `READY`。
- `src/core/stores/settings.ts:60-83` 的恢复状态查询位于设置读取之后，是两个串行 IPC。
- `src/core/stores/avatar.ts:244-278` 在一个 Promise 内把批量头像逐个转为 Blob URL。
- `src-tauri/src/vcp_modules/agent/avatar_service.rs:7-8,211-290` 允许单头像 20 MiB、批次 64 MiB，并把完整 `Vec<u8>` 序列化过 IPC。

这里最重要的判断是：**当前首屏时间不是单纯的 Vue render 时间。** 它至少混合了模块解析、CSS parse/style、Vue mount、Tauri IPC、SQLite/文件读取、二进制序列化、JS 内存复制、Blob 创建和 DOM/paint。任何单点归因必须由分段 mark 支持。

## 3. 当前生产 Web build 快照

2026-08-12 在当前工作区执行 `pnpm build` 成功。该构建含未提交 Diary WIP，`dist/` 又被忽略，因此只作为问题定位快照：

| 初始资源 | raw | gzip（约） | 说明 |
|---|---:|---:|---|
| main JS | 454,261 B | 134,867 B | App、静态路由、壳组件及当前业务依赖 |
| Vue vendor | 119,692 B | 46,379 B | Vue、Pinia、router |
| render vendor | 117,567 B | 37,673 B | marked、morphdom、DOMPurify 等 |
| Tauri vendor | 21,687 B | 5,101 B | 前端 Tauri API |
| main CSS | 211,215 B | 38,975 B | UnoCSS、全局样式、KaTeX CSS 等 |
| `index.html` | 1,791 B | 850 B | 含静态 preloader 与 modulepreload |
| **合计** | **约 926 KB** | **约 264 KB** | 本地 APK 资源，gzip 只作体积对照 |

对 WebView 来说，本地资源没有公网传输延迟，但仍有读取、解压或映射、JS parse/compile/execute、CSS parse/style 和内存占用。故“gzip 很小”不能证明首屏便宜。

当前还会生成：

- KaTeX JS 约 259 KB raw，并生成多份字体资源；
- Mermaid core 约 566 KB raw，另有 Cytoscape 和各图类型 chunk；
- 多个低频业务页面 chunk；
- `public/wallpaper` 总量约 6.5 MB，只有当前背景会在首屏实际解码，但都会进入安装包资源。

### 3.1 拆包为何没有等于延迟加载

`vite.config.ts` 的 `manualChunks` 把 Vue、render 和 Tauri 依赖命名分组，但首屏是否加载由 import graph 决定：

- `src/core/router/index.ts` 静态导入 `ChatView`；
- `ChatView.vue` 静态导入 `MessageRenderer`；
- `MessageRenderer.vue` 静态导入 morphdom 和各稳定块组件；
- `App.vue` 静态导入 `UpdatePrompt`，后者静态导入 marked 与 DOMPurify；
- 当前 `dist/index.html` 因而对 `render-vendor` 做了 `modulepreload`。

因此，首轮优化应先改变“哪些模块属于首屏调用链”，再讨论 chunk 名和大小阈值。仅调整 `manualChunks` 或提高 `chunkSizeWarningLimit` 不会减少解析执行工作。

## 4. 已确认问题

### C-01：现有脚本测不到应用可用时刻

`tests/perf/scripts/measure_startup_adb.cjs` 只采集 `am start -W` 的 `ThisTime`、`TotalTime`、`WaitTime`，文件自身也注明 boot-ready 尚未埋点。`index.html` 会先画静态 preloader，因此 Activity 已显示不代表 Chat 已可输入，也不代表恢复会话的富内容稳定。

结论：现有结果只能叫“Activity 启动时间”，不能叫“Vue 首屏”或“应用可交互时间”。

### C-02：`READY` 被非最小关键集阻塞

当前 `Promise.all` 中，全量头像和设置恢复通知不是显示第一个可交互聊天框的普遍必要条件。尤其 `batch_get_avatars` 的协议上限允许 64 MiB 二进制进入同一响应，随后 JS 主线程还会逐项创建 `Uint8Array`、Blob 和 ObjectURL。

这不等于当前用户数据已经达到 64 MiB，但足以证明“批量全头像”不是可忽略的固定成本，必须拆出实际字节数、IPC 时间、JS 转换时间和内存峰值。

### C-03：异步 Overlay 在 `READY` 后被立即实例化

`FeatureOverlays.vue` 使用 `defineAsyncComponent` 是正确方向，但 `onMounted` 立即把 `isMounted` 设为 true，Settings、Agent、Group、Distributed、RAG 等组件即使关闭也会实例化。异步组件在第一次实例化时就会请求 chunk，因此它们从“阻塞 READY”变成了“READY 后立即竞争首个交互帧”。

Diary 当前已经采用“首次打开后才 mounted”的更严格模式，可作为候选模板；不过设置页保留草稿和退出动画的需求必须在改造时继续满足。

### C-04：全局 KaTeX CSS 位于初始样式

KaTeX JS 已经只在发现公式占位符后动态导入，但 `src/main.ts` 全局静态导入 `katex.min.css`。这会让所有会话先解析公式样式，并让构建发射全部 KaTeX 字体，即便欢迎页或普通对话没有公式。

优化目标不是取消 KaTeX，而是让“KaTeX JS + CSS 资源准备”由同一个幂等 loader 管理，在首个公式绘制前完成，避免 FOUC。

### C-05：主题代码 eager 进入初始图

`src/core/stores/theme.ts` 对主题模块采用 `import.meta.glob(..., { eager: true })`。当前 13 个主题会随首屏代码一起解析；主题元数据虽然在 idle 阶段读取，模块本身却已加载。其影响需要 trace 验证，优先级低于全量头像和 Overlay。

### C-06：平板根布局存在结构矛盾

`App.vue` 根节点始终为 `flex flex-col`。在 `min-width: 768px` 时，左右侧栏都由 absolute drawer 改成 `position: relative`，强制 `transform: translateX(0)`，宽度分别为 280/300px；它们又是 `<main>` 后方的兄弟节点。

这意味着它们进入纵向普通流，而不是与 main 横向排布；根节点同时 `overflow-hidden`。由布局规则推导，侧栏很可能被放到主内容下方并被裁切。这是 `CONFIRMED-CODE` 的结构错误候选，仍需以受影响平板的 portrait/landscape 截图确认具体症状。

### C-07：CSS 兼容目标没有成为显式产品契约

`vite.config.ts` 没有显式 `build.target` 或 `build.cssTarget`，当前 Vite 6 安装版本内部默认 modules target 包含 Chrome 87。更重要的是，构建目标不能自动替代所有 CSS fallback：当前生成 CSS 仍保留 `color-mix()`。

当前工作树在 2026-08-12 末次复核时扫描到（包含 Diary WIP，数量会随工作区变化）：

- 20 处 `color-mix()`；
- 3 处 `content-visibility`；
- 5 处 backdrop blur/filter；
- 188 处 `transition-all`；
- 11 处 `will-change`；
- 0 处 `@supports`。

其中部分 `color-mix()` 已先写实色 fallback，但 `themes.css` 的 `.glass-panel`、`.glass-panel-active`、消息气泡边框，以及若干 inline style 没有完整 fallback。旧 WebView 丢弃未知声明时，装饰会消失；若未来把它用于结构性属性，则会升级为布局故障。

## 5. 已有正确基础

专项不能把成熟能力误判为问题：

- `index.html` 有不依赖 Vue 的静态 preloader，具备早期视觉反馈基础；
- 生命周期已由单一 `AppLifecycle` 编排，可在现有 owner 中减轻 READY 门禁；
- 首屏历史只预取 5 条，数据窗口有界；
- `MessageRenderer` 对稳定块使用 `v-memo`；
- 流式尾部优先使用 AST diff，失败时有 snapshot/morphdom 恢复；
- KaTeX/Mermaid JS 已按占位符动态加载，Mermaid 有结果缓存和进行中 Promise 去重；
- 消息项使用 `content-visibility: auto`，现代 WebView 可跳过离屏布局；旧 WebView 即使忽略该属性，内容也仍存在；
- `chatStreamStore` 已对后台 WebView 的 rAF 停摆做回压收敛；
- Rust 侧有消息、头像、文件和 OOM 边界。

性能方案应扩展这些既有所有权和门禁，而不是重写一套平行渲染器。

## 6. 待验证瓶颈排序

| 排名 | 候选 | 证据强度 | 必须采集的证据 |
|---:|---|---|---|
| 1 | `READY` 中的全量头像 IPC、复制与 Blob 创建 | 高 | 响应字节、IPC 时长、JS 转换时长、峰值 RSS |
| 2 | 初始静态依赖 parse/execute 与主 CSS style | 高 | main-thread long task、script parse/evaluate、style recalc |
| 3 | READY 后关闭 Overlay 的 chunk/setup 风暴 | 高 | chunk 请求时间线、组件 setup、首个交互帧延迟 |
| 4 | 恢复会话 5 条历史的 Rust 编译、IPC 与 DOM paint | 中 | 普通/强渲染 fixture 分段对比 |
| 5 | 每个 `MessageRenderer` 的重内容 DOM 扫描与表情后处理 | 中 | 每帧扫描次数、无公式消息耗时、长任务 |
| 6 | eager 主题模块、自动更新和全局管理组件 | 中低 | coverage/execute time、A/B 差值 |
| 7 | 壁纸解码、动画、blur、持续 `will-change` 的 GPU 成本 | 设备相关 | GPU profile、layer count、帧时间、热状态 |

排序只是实验顺序，不是最终责任判定。

## 7. 明确不能从当前证据推出的结论

- 不能说“Rust 已经亚毫秒，所以剩下全部是 Vue”。Rust benchmark 覆盖 AST 路径，不覆盖启动快照、头像 IPC、WebView parse 和 paint。
- 不能说“初始 926 KB 就是首屏慢的根因”。资源在 APK 本地，真正成本需 trace。
- 不能说“旧机一定是某个 CSS 属性导致”。必须记录实际 WebView 包/版本并对生成 CSS 和截图定位。
- 不能说“API 26 模拟器代表所有 API 26 设备”。WebView 是独立、可更新且可更换的提供程序。
- 不能把 happy-dom 的绿色测试解释为 CSS、布局、GPU 或 WebView 兼容证明。
- 不能用空欢迎页的漂亮数字代表恢复强渲染会话。

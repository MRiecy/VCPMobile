# 03. 首屏与运行时性能优化方案

## 1. 优化目标与原则

本方案优化的是“用户何时看到并能操作正确内容”，而不是单纯追求更小的 bundle 或更早隐藏 BootScreen。

目标顺序：

1. 尽早给出稳定且不闪退的可见反馈；
2. 尽早让 Chat 主路径可输入、可滚动、可恢复；
3. 在不阻塞交互的情况下完成侧栏、头像、更新、设置等暖机；
4. 保持消息强渲染完整，并降低无关消息上的扫描和主线程争用；
5. 保持现有生命周期、Store 和渲染 owner，拒绝平行状态机。

所有候选必须遵循“一次改变一个机制、基线与候选交错测量、无显著收益即回退”。下面的顺序是实验队列，不是一次性重构清单。

## 2. 首屏语义重构：扩展现有 AppLifecycle

不新增另一套启动状态机。建议在 `AppLifecycle` 内把现有工作分成两个 Promise 集合，并保留当前 `BOOTING → CONNECTING → PRELOADING → READY` 主状态：

### 2.1 阻塞 READY 的最小核心集

- `get_system_snapshot` 与核心服务 ready；
- 当前主题立即绘制所需的最小变量；
- 经 trace 证明为 Chat 输入/网络/渲染必需的 settings；
- 当前助手/群组快照；若它很轻则不为拆 DTO 而拆 DTO；
- 恢复会话时当前对象的头像和首屏 5 条历史；

`READY` 继续是生命周期数据门。当前 App 只有在 `READY` 后才创建 Chat，因此 `chat-shell-double-raf` 与首次输入响应只能是 READY 之后的独立测量点，绝不能反向加入 READY Promise；两个 rAF 只表示浏览器获得了绘制机会，也不能单独证明真实 paint 或可交互。

### 2.2 READY 后暖机集

- 所有非当前头像；
- settings recovery 通知；
- 主题目录和预览元数据；
- 话题列表（当前已经延后）；
- 未打开 Overlay 的业务 chunk 与 setup；
- 自动更新 release notes 的 Markdown/DOMPurify 依赖；
- 非当前会话和非可见附件的预取。

首轮只需把这些具名任务移到 `chat-shell-double-raf` 之后，并分别计时、限并发；继续由 `AppLifecycle` 拥有启动流程，不创建通用队列或全局“性能 Store”。只有 trace 证明存在后台抢占、重入或内存压力问题时，才为对应任务增加局部取消和 boot sequence。

重要：`READY` 不等于“所有功能数据都已下载”，它只表示当前生命周期数据门已经满足；真实可交互由后续 mark 和输入探针证明。侧栏首次打开仍需加载时，必须提供原生、克制的局部 loading/error 状态，不能静默空白。

## 3. 候选实验 A：移出全量头像

### 机制

当前 `avatarStore.preloadAll()` 可能把最多 64 MiB 图片数据送过 Tauri IPC，随后在主线程逐项复制和建 Blob URL。即便 Rust 查询很快，这条路径也可能受跨层序列化、内存分配和 GC 支配。

### 最小改法

1. 先延迟手机端关闭侧栏中的 AgentList、Sortable 和 VcpAvatar 实例化；否则移除批量预热会把一次 IPC 变成隐藏列表的 N 次请求；
2. 再让 READY 只加载 user、当前 agent/group 和平板常驻侧栏的真实可见项；若两步无法独立验证，则明确作为一个耦合实验提交；
3. 助手快照继续使用已有 dominantColor；只有去重/失效证据需要时，才新增有界的 avatar version 元数据，不携带全量二进制；
4. 可见项通过现有 `getAvatarUrl` 按需去重加载，`chat-shell-double-raf` 后再以小并发暖机剩余头像；
5. 保持原图字节和显示质量；允许现有首字母作为加载期 fallback，但不得永久降级、缩略或压缩，除非另有独立图像产品决策。

### 验收与回滚

- 当前头像不得闪成错误对象，列表快速滚动不得重复请求风暴；
- 同一 key 仍由唯一缓存 owner 管理，替换 Blob 前 revoke 旧 URL；
- 首屏 median/p95、峰值 RSS 和 GC pause 至少一项有超过噪声的改善，且其他项不退化；
- 无收益则回滚整个实验，不保留永久双路径。

## 4. 候选实验 B：Overlay 真正按首次打开挂载

### 机制

`defineAsyncComponent` 只有在组件不被实例化时才真正延迟。当前 FeatureOverlays 在 READY 后立即创建多数关闭页面，使其 chunk 和 setup 与首个交互帧竞争。

### 最小改法

- 为每个页面复用 Diary 的 `everOpened` 模式：第一次 open 才挂载，之后根据草稿/动画需求选择常驻；
- 或用统一 `openedPages` Set 由 `overlayStore.pageStack` 派生，不另建页面状态 owner；
- ToolInteractionOverlay 继续只在 distributedEnabled 时存在；
- 全局 Prompt/Toast 等轻量基础设施保留常驻，重型 viewer/editor 在首次使用时加载。

### 注意

设置页“关闭后保留未保存草稿”和 SlidePage leave 动画是现有契约。不能简单给所有组件加 `v-if=isOpen`；应先让首次打开触发挂载，再让已挂载页面按需要常驻。

### 侧栏同级实验

在进入全局依赖拆分前，还应把“关闭侧栏的运行时工作”作为 B 的同级实验：`App.vue` 在 READY 时始终挂载 `AgentSidebar`，其 `AgentList` 静态引入 Sortable、渲染当前 agent/group，并在 mounted 初始化拖拽。手机首屏侧栏不可见时，可延迟到首次打开再挂载或至少延迟 Sortable 初始化；平板常驻模式则仍应即时挂载。必须验收排序、选中态、抽屉首次打开和草稿状态，不能全局一刀切。

## 5. 候选实验 C：收紧初始 import graph

按执行覆盖率依次验证：

1. **UpdatePrompt。** App 静态导入它，组件又静态导入 marked/DOMPurify，可能使 render-vendor 首屏 preload。将更新提示和 release notes renderer 按实际打开懒加载；更新检查本身仍可后台进行。
2. **GlobalOverlayManager。** Prompt/Toast 可留在核心，AttachmentViewer/FullScreenEditor/RenderedImageViewer 等按首次打开加载。
3. **稀有消息 Block。** 只有 trace 证明静态组件模块本身显著时才异步化；普通 Markdown 和当前消息骨架必须即时。
4. **主题模块。** 把 eager 全主题改为轻量 manifest + 显式 loader map，启动只加载当前主题；切换主题前先完成目标 loader。

Chat 是唯一主路由，改成异步 route 很可能只移动同一等待位置，列为低优先级探针而非正式候选；只有 Coverage/trace 证明它能与生命周期工作有效重叠且不产生白屏时才考虑。

每一步都先看 Coverage 与 Performance trace。不要先做依赖全升级或重写 bundler 配置。`manualChunks` 只在 import graph 定型后重新评估，否则只是改文件名。

## 6. 候选实验 D：KaTeX CSS 与 JS 同步按需

建立单个幂等资源 loader：

```text
ensureKatexReady()
  → 并发 import('katex') 与 import('katex/dist/katex.min.css')
  → 同一 Promise 去重
  → CSS ready 后再对占位符 render
```

要求：

- 第一条公式不能出现长期无样式 MathML/FOUC；
- 公式字体加载期间保留合理 intrinsic size，减少布局跳动；
- 离线 APK 内资源路径仍可解析；
- loader 失败时清除失败的 in-flight Promise，保留局部错误状态，并允许下一次显式操作或重新渲染重试；
- 相同公式渲染能力、错误提示和复制行为全部保留；
- 对“无公式欢迎页/普通 5 消息/公式 5 消息”分别测量，避免优化普通场景却恶化公式场景。

## 7. 候选实验 E：拆开 settings 的关键数据与恢复通知

`fetchSettings()` 目前先 `read_settings`，再等待 `get_settings_recovery_status`。如果第一段 trace 确认第二 IPC 显著阻塞：

- settings 值写入 Store 后即可满足关键路径；
- recovery status 改为 READY 后的通知任务；
- 失败仍进入现有 Notification/错误所有权；
- 不把两个调用盲目合并进一个新的“大而全 bootstrap snapshot”，除非 IPC 次数本身被证明确为瓶颈。

优先移动非关键工作，后考虑扩张 DTO。这样变更面更小，也避免系统快照最终携带头像等大对象。

## 8. 恢复会话与消息首屏

当前恢复会话预取 5 条是合理上限，不建议首轮减少消息数量来美化结果。应分别测量：

- 无恢复会话；
- 5 条普通 Markdown；
- 5 条强渲染混合消息；
- 历史达到 500 条但首屏只取尾部 5 条；
- 一条超长代码/表格/Diagram 位于首屏。

若 Rust history 查询快而 WebView paint 慢，优化方向应是分帧提交与稳定高度占位，而不是把强内容改成纯文本。若 IPC/缓存编译慢，则优化后端读取/缓存，不在 Vue 侧重复 parser。

## 9. MessageRenderer 运行时优化

现有强项应保留：稳定块 `v-memo`、AST diff、snapshot fallback、Mermaid cache、进行中 Promise 去重、动态 KaTeX/Mermaid import。

### 9.1 当前可测热点

每个 MessageRenderer 在 blocks 引用变化时都会：

1. `nextTick()`；
2. 查询整条消息中的 KaTeX selectors；
3. 查询 Mermaid selectors；
4. 对容器执行表情后处理；
5. 流式结束时再执行一次。

普通消息也会走 DOM 查询和表情扫描。历史多、流式频繁时，这可能形成大量小任务。

### 9.2 保能力的优化顺序

1. 先在现有 blocks/节点遍历中派生 `hasMath/hasMermaid/hasEmoticonCandidate` 等只读 feature hints；本地无法可靠判定且 trace 证明有收益时，再考虑扩张 Rust DTO。hint 只跳过确定无关的扫描，不改变渲染结果。
2. 同一帧内合并同一消息的重复请求，由 rAF/微任务队列保留最后一次版本；流式终态必须强制 flush。
3. 给重内容 renderer 使用组件局部 revision token 与 element containment 校验；异步 KaTeX/Mermaid 返回时先确认节点仍属于当前消息版本。只有竞态测试证明仍不足时，再引入会话 epoch。
4. 只对新插入/变化的 block 扫描，稳定块不重复处理。
5. 大量首屏强内容可以按视口优先调度，但最终必须全部完成；用户滚到占位符前应提升优先级。

`astRenderer` 的 HTML cache 当前达到 500 项后会整表清空。只有 trace 观察到周期性重算尖峰时，才把它替换为同容量的增量 LRU；key、单消息失效与全量清理语义必须保持不变。

这些方案只能减少无效工作，不能改变 Markdown parser、HTML、公式或图表输出。

## 10. 旧 WebView 的离屏性能

现代 WebView 会从 `content-visibility: auto` 获益；旧引擎忽略后，500 条历史的 DOM 可能显著变重。不要立刻引入全面虚拟列表。分期验证：

1. 保持数据窗口 500，但确认初始 DOM 实际只有已加载页；
2. 继续以 5 条首屏和向上分页控制新增 DOM；
3. 若目标旧机长会话仍不达标，再做“消息容器窗口化”原型；
4. 窗口化只卸载离屏 Vue DOM，不删除消息数据；需保存高度、scroll anchor、展开态、选区/焦点和 Mermaid/KaTeX 恢复能力；
5. 回滚到非窗口化路径时最终 DOM 与能力必须一致。

窗口化属于 P3 候选，因为它和 `useChatScroll`、ResizeObserver、流式 owner、附件 viewer 交互复杂，不能作为首轮轻率修复。

## 11. GPU、图片与动画候选

- 用 trace 定位首屏壁纸 decode；若显著，优先提供与显示尺寸匹配的资源选择，不降低源图能力或默认画质。
- 关闭的 fixed Overlay 不应建立 blur 合成层；内容区继续禁止 backdrop blur。
- 流式/hover 结束后释放 `will-change`，避免历史消息长期占层。
- `transition-all` 只在性能热点逐一改为明确属性。
- `.theme-switching *` 当前会把多属性 transition 施加到整个消息 DOM；若主题切换 trace 证实大范围 style/paint，应收口到固定 shell 或单层淡入，消息内容不参与全树过渡。
- 所有动画优化同时检查 reduced-motion 和状态可辨识性。

## 12. 明确不做

- 不移除 Vue、Pinia 或现有 Rust AST 管线；
- 不关闭 raw HTML、KaTeX、Mermaid、代码高亮、SVG/MathML、Tool/Thought/Diary 或附件；
- 不用纯文本占位作为永久输出；
- 不把所有 IPC 合并成一个无边界超级快照；
- 不同时改启动门禁、布局、消息调度和 bundler，以免无法归因；
- 不把 Debug 或桌面浏览器结果当 Release Android 结论；
- 不在未测量前做依赖全升级、全面 polyfill、全面虚拟列表或大文件拆分。

# 05. 测量矩阵与验收门禁

## 1. 当前测量能力缺口

仓库现有 `tests/perf/scripts/measure_startup_adb.cjs`：

- 默认 10 次 `force-stop → am start -W`；
- 只记录 Activity 的 `ThisTime/TotalTime/WaitTime`；
- 文件明确注明 boot-ready 仍待应用内埋点；
- 当前简单顺序统计下，10 个样本的 p95 接近单次最大值，不能稳定承担门禁。

`tests/perf/README.md` 也明确这些脚本只供本地手工采集，不进入 CI/Release。现有 Criterion 覆盖 Rust AST/Aurora 路径，CI 只编译 benchmark；Vitest 使用 happy-dom 且 `css: false`。因此当前自动化无法回答：

- preloader、Vue mount、READY、可交互、首条消息、富内容稳定分别发生在何时；
- 时间花在 WebView parse/style、Tauri IPC、头像复制、SQLite 还是 DOM/paint；
- 旧 WebView 丢了哪些生成 CSS；
- 平板是否裁切、键盘是否重复计算 inset；
- 低端机是否因 blur、`will-change` 或壁纸出现 GPU/RSS 问题。

本轮 `adb devices -l` 为空。故下面定义的是测量方案和门禁方法，不是已经取得的性能结果。

## 2. 测量身份

每份报告必须包含：

```json
{
  "commit": "full git sha",
  "worktree_dirty": false,
  "apk_sha256": "...",
  "build_kind": "signed-release | release-like-profileable",
  "package": "com.vcp.avatar",
  "android_api": 0,
  "webview_package": "... | unavailable",
  "webview_version": "... | unavailable",
  "webview_unavailable_reason": null,
  "manufacturer": "...",
  "model": "...",
  "abi": "arm64-v8a",
  "viewport_css_px": [0, 0],
  "density": 0,
  "refresh_hz": 0,
  "memory_class_mb": 0,
  "navigation_mode": "gesture | three-button",
  "orientation": "portrait | landscape",
  "thermal_before": "...",
  "power_source": "battery | usb"
}
```

性能基线必须来自 clean、可复现的固定 commit。当前 ignored `dist` 包含 Diary WIP，只可用于诊断，不得写入正式基线。Debug 的 source map、未优化 Rust 和调试 WebView 行为与 Release 不同，不能混入同一统计。

Android 侧应在每批测试开始时通过 `WebViewCompat.getCurrentWebViewPackage()` 取得 provider/version；该 API 允许返回 `null`，报告必须记为 `unavailable` 并保留原因。实验脚本可额外记录 `dumpsys webviewupdate` 交叉核对，不能假设实验期间 provider 永远不变。项目已依赖 `androidx.webkit:webkit:1.14.0`，无需为了版本采集引入新库。

## 3. 应用内启动 marks

所有 mark 先写入前端内存中的单次 `BootTrace`，达到 `rich-settled` 或 10 秒截止线后一次性导出，避免每阶段 IPC 扰动被测对象。建议字段：

| Mark | 定义 | owner |
|---|---|---|
| `html-inline-start` | `index.html` 内联脚本开始 | HTML |
| `browser-first-paint` | buffered Paint Timing 可用时记录 `first-paint` | WebView |
| `js-entry` | `src/main.ts` 第一条可执行语句 | main |
| `vue-mounted` | `app.mount()` 返回 | main |
| `boot-double-raf` | mount 后两个 rAF，Boot UI 有绘制机会 | App |
| `system-listener-ready` | `listen('vcp-system-event')` 注册完成 | App |
| `system-snapshot-start/end` | `get_system_snapshot` invoke 边界 | AppLifecycle |
| `theme-ready` | 当前主题变量可用 | ThemeStore |
| `core-ready` | 核心服务进入 ready | AppLifecycle |
| `settings-start/end` | 设置值可用；recovery 单独计时 | SettingsStore |
| `assistants-start/end` | snapshot 返回并提交 Store | AssistantStore |
| `avatars-ipc-start/end` | 响应返回，同时记录 count/bytes | AvatarStore |
| `avatars-materialize-end` | Uint8Array/Blob/ObjectURL 完成 | AvatarStore |
| `history-start/end` | 首屏 5 条返回，记录 hit/miss 与 block 数 | HistoryStore |
| `lifecycle-ready` | READY 状态原子提交 | AppLifecycle |
| `chat-shell-double-raf` | Chat main、header、input 挂载后获得两个 frame opportunity；不单独等于真实 paint | ChatView |
| `first-message-double-raf` | 第一条可见消息挂载后获得两个 frame opportunity | MessageRenderer |
| `rich-settled` | 可见 KaTeX/Mermaid/异步 Block 全 settled | Rich renderer |
| `first-input-response` | 启动后首次真实或脚本输入；支持 Event Timing 时读取其时长，否则在 handler 两端打 mark | Chat input |

同时记录：

- 支持 Long Tasks API 时记录 >50 ms 任务；不支持时用 rAF gap 与 Perfetto 补位；
- `PerformanceResourceTiming` 只记录初始/异步 chunk 与壁纸资源读取；可控 `<img>` 实验用 `HTMLImageElement.decode()` mark，CSS 背景的实际 decode/paint 由 Perfetto/帧证据判断；
- 各阶段失败、超时、取消和最终状态；
- 启动后 5 秒/30 秒 RSS、Java/native/WebView 内存；
- `dumpsys gfxinfo framestats` 的长帧；
- 有条件时用 Perfetto 采集 WebView/Chromium、sched、gfx 和内存轨道。

Paint Timing、Long Tasks、Event Timing 与 Resource Timing 都必须先 feature-detect。真实首次输入由 adb/instrumentation 执行，并测到下一帧或真实 Event Timing；脚本派发的不可信 DOM event 只能做组件测试，不能命名为用户输入延迟。

导出通道也必须落地：建议新增一个有界的 `record_boot_trace` Tauri command，在终态只接收一次不超过 32 KiB、无消息正文/ID/路径/URL 的 trace，由 Rust 以稳定 marker 分块写入 Android logcat。采集脚本等待 marker 最多 20 秒，把完整或超时 partial trace 存入 `tests/perf/reports/<timestamp>/`；命令放在现有生命周期/诊断模块，不新建状态 owner。正式实现仍需注册 command 和补契约测试。

不能只靠散落的 `console.log(Date.now())`：它无法对应 paint、long task 和跨进程调度，Release 日志还可能改变时序。

## 4. 场景 fixture

### S0：清数据首次安装

- 无持久化 session、无头像、默认主题；
- 单独记录权限/数据库初始化；
- 它不是每次 process-cold 的代表，不与后续样本混算。

### S1：欢迎页 process-cold

- 已完成首次安装，无恢复会话；
- 用于隔离初始模块/CSS/AppLifecycle 基础成本。

### S2：普通恢复会话

- 固定 agent/topic；
- 5 条普通 Markdown，render cache hit；
- 真实规模头像集和主题；
- 用于日常首屏基线。

### S3：强渲染恢复会话

- 一组固定五消息数据集 [StrongRenderingFixtureV1](./04-消息强渲染能力保护契约.md#5-标准强渲染-fixture)；
- 分 cache hit 与 miss；
- 测 `first-message` 与 `rich-settled`，不能只看 READY。

### S4：规模与边界

- 0 头像、实际生产分布、接近 64 MiB 批次上限分别运行；
- 历史 500 条、首屏仍取 5 条，再连续上翻；
- 100+ 富消息滚动、主题切换、键盘反复开合；
- 属于压力/长稳，不与日常首屏 SLA 混算。

### S5：Overlay 与侧栏

- READY 后立即输入；
- 首次打开左右栏、设置、RAG、Distributed、Diary；
- 验证延迟挂载改善首屏后，不把首次打开变成不可接受卡顿。

## 5. 设备与 WebView 矩阵

最低集合：

| 类别 | 必测对象 | 目的 |
|---|---|---|
| 受影响旧手机 | 用户实际报告设备及原 WebView provider/version | 复现兼容与性能问题 |
| 受影响平板 | 用户实际报告设备，portrait/landscape | 复现布局不完整 |
| 现代对照机 | 当前稳定 WebView、主流中端硬件 | 排除全局回归 |
| 最低能力实验 | 可固定 WebView 约 87 代际的实验设备/镜像 | 检查当前 Vite 目标附近功能基础 |
| 增强边界实验 | WebView 111 与最新版 | 验证 `color-mix` 分界和现代增强 |

WebView 87/111/最新版是建议的实验锚点，不是已经冻结的产品支持声明。Phase 0 由产品负责人和技术负责人共同冻结一份 tracked 支持基线，至少写明最低 WebView major、允许/禁止的 provider 例外、必测实体设备和生效版本。只有落在该基线内的设备才参与 Release 阻断；87/111 等探边设备若在支持范围外，只提供决策数据。若真实受影响设备低于 87，应先验证生成 JS 是否能启动，再决定降低 build/css target、提供结构 fallback，或形成明确的支持政策。

OEM 至少覆盖 AOSP/Pixel 路径和两个实际用户较多的厂商 ROM。API 26 模拟器可以做语法筛查，不能替代实际 WebView、GPU、字体、键盘和系统栏行为。

几何至少覆盖：

- 手机 360×640、360×800、412×915；
- 平板 600×960、800×1280、834×1194；
- 平板 landscape 1280×800、1194×834；
- 分屏窄窗口、字体放大 1.5×与大显示尺寸；
- 手势/三键导航、刘海/无刘海、键盘开/关。

## 6. 采样方法

### 6.1 启动分类

- `first-install`：安装/清数据后的第一次，单列；
- `process-cold`：`am force-stop` 后启动，不能称为磁盘完全冷启动；
- `warm-resume`：进程存活，从后台恢复；
- `hot-navigation`：应用内打开页面，不与启动混算。

### 6.2 探索期与正式候选分开

Phase 1 探索只跑“3 台核心设备 × S1—S3”，每个单元格 5—10 次，用于定位最大阶段；Perfetto 只采有代表性的异常样本，不对每次启动录 trace。它不产生发布结论。

进入正式候选 A/B 后，只跑该候选实际影响的场景；每个 build、每个单元格总计 20—30 个有效样本，分布在至少三批，而不是每批再跑 20—30 次。基线 A 与候选 B 交错执行。S4/S5 和完整几何矩阵只在候选入围或 Release 前扩展，避免把探索阶段膨胀成上千次冷启。

### 6.3 每个正式单元格

1. 固定亮度、刷新率、网络、供电策略和后台应用；
2. 设备先恢复到规定热状态；
3. 3 次预热不纳入统计；
4. 每个 build 总计 20—30 次有效 process-cold，分到至少三批；
5. 基线 A 与候选 B 采用 ABBA/随机交错，不先跑完 A 再跑 B；
6. 记录每次原始值，不只保存汇总；
7. 报告 median、p90/p95、MAD/批间抖动、失败率和异常值原因；
8. 用三批间差异估计环境噪声 `J`。

## 7. 门禁定义

### 7.1 正确性与兼容性：零容忍硬门槛

- 主消息区、输入、抽屉、Overlay、关闭/返回控件全部可见可达；
- 键盘和系统栏不遮挡核心操作，安全区不重复计算；
- 强渲染 fixture 的所有能力和交互存在；
- 没有永久 skeleton、空白 Block、错误 owner 写回或异步资源失联；
- 正式门禁中，支持基线内任一必测设备失败即失败，不能用现代机平均值抵消旧机；基线外探边设备单独报告。

### 7.2 性能回归

在首轮基线前不编造绝对毫秒。先用三批相同 build 得到噪声包络 `J`：

- 候选 median/p95 不得超过基线噪声包络；
- `T_chat_shell` 提升却让 `T_rich_settled`、RSS、长帧或错误率退化，仍视为失败；
- 声称优化时，三批方向应一致，改善幅度必须显著大于 `J`；
- 先 report-only，取得至少三批稳定噪声数据后，再由产品冻结每个“设备 × 场景”的绝对 SLA；
- bundle 体积是诊断门禁，不替代运行时指标。

### 7.3 资源预算

先在 clean fixed commit 上生成 manifest，记录：

- index 初始 JS/CSS raw 与 gzip；
- modulepreload 列表；
- 首屏实际 execute coverage；
- 初次公式/图表/Overlay 的增量资源；
- APK 总资源、壁纸和字体大小。

报告期内任何初始资源增加都需要说明；基线稳定后再冻结数值阈值。不能把资源从 initial 改名为 async 却在 READY 后立即加载，然后宣称预算改善。

## 8. CI、设备实验与 Release 分工

### PR 快速门禁

- `pnpm check`、前端/Rust/插件测试；
- 明确执行一次 production `pnpm build`；
- 生成 initial-resource manifest 并与基线对比；
- 扫描生成 CSS 中无 fallback 的关键新特性；
- 强渲染语义 fixture、启动 trace schema 和响应式几何测试。

### Nightly/具名手工设备门禁

- 固定设备 Release-like APK 常规跑 S1—S3；S4/S5 仅在相关候选、周期长稳或 Release 前扩展；
- WebView provider/version、截图、Perfetto/gfxinfo、RSS 与原始样本归档；
- 低端/旧 WebView 和真实平板不可缺席。

### Release 门禁

- 使用最终签名配置的 Release APK；
- 固定 commit、APK hash 与同 commit CI 结果；
- 若设备流水线尚未可靠自动化，使用具名验收人和归档报告，不伪称 GitHub CI 已验证真机；
- 支持基线内任一设备的 L0—L2 兼容失败直接阻断发布；探边但不在支持范围内的设备不参与硬阻断。

当前 `.github/workflows/release.yml` 只在 GitHub Release 已 `published` 后构建，无法执行真正的“发布前设备门禁”。Phase 5 必须先增加 pre-publish RC 路径：通过 `workflow_dispatch` 或等效受控入口构建签名 RC，记录 commit/APK SHA，完成设备验收并由具名负责人批准后，才发布并上传**同一份已验收 artifact**。在该路径落地前，这一门禁只能作为 draft Release 前的人工流程，不能宣称 CI 会自动阻止发布。

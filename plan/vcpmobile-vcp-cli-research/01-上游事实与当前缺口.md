# 01｜上游事实与当前缺口

## 1. VChat 如何调用所谓 VCP CLI

VChat 当前没有一个独立模块名叫 `VCPCLI`。可验证实现主要是 Windows `PowerShellExecutor` 和 Linux `PTYShellExecutor`，并分成人工入口与 Agent 入口两条链。

### 1.1 人工入口：本机直调

桌面启动器收到 `open-powershell-executor-terminal` 后，直接 `require()` 本地插件并调用 `openGuiTerminal()`；不会先请求 VCPToolBox。当前官方源码见：

- [`desktopHandlers.js@8a65eb7`](https://github.com/lioensky/VCPChat/blob/8a65eb780974eed93da449167f4385d16f8aa1ab/modules/ipc/desktopHandlers.js#L1385-L1393)
- [`PowerShellExecutor.js@8a65eb7`](https://github.com/lioensky/VCPChat/blob/8a65eb780974eed93da449167f4385d16f8aa1ab/VCPDistributedServer/Plugin/PowerShellExecutor/PowerShellExecutor.js#L836-L858)

`PowerShellExecutor` 使用持久 node-pty 和 xterm GUI。`execute` 处理短命令；`startInteractive` 启动 codex/claude/vim 等 TUI 后立即返回，由人接管；`queryVisibleN` 读取当前终端画面；`endInteractive` 只释放占用标志。它是“持久会话 + 人机接管”，不是跨进程死亡可恢复的后台工作系统。

### 1.2 Agent 入口：HTTP 对话 + Distributed WebSocket

VChat 的对话请求与本机工具注册是两条独立连接：

```text
Chat messages
  → HTTP /v1/chat/completions 或 /v1/chatvcp/completions
  → VCPToolBox 解析模型输出的 VCP block

VChat local plugins
  → WS /vcp-distributed-server/VCP_Key=...
  → register_tools
  ← execute_tool
  → 本机 PluginManager.processToolCall
  → tool_result
```

VChat 在连接成功后发送完整 manifest：

```json
{
  "type": "register_tools",
  "data": {
    "serverName": "...",
    "tools": []
  }
}
```

主端随后以 `execute_tool.data.{requestId,toolName,toolArgs}` 下发；VChat 执行本机 direct 插件，再以 `tool_result` 回包。证据：

- [`VCPDistributedServer.js@8a65eb7` 注册](https://github.com/lioensky/VCPChat/blob/8a65eb780974eed93da449167f4385d16f8aa1ab/VCPDistributedServer/VCPDistributedServer.js#L320-L357)
- [`VCPDistributedServer.js@8a65eb7` 执行](https://github.com/lioensky/VCPChat/blob/8a65eb780974eed93da449167f4385d16f8aa1ab/VCPDistributedServer/VCPDistributedServer.js#L594-L667)
- [`VCPDistributedServer.js@8a65eb7` 结果](https://github.com/lioensky/VCPChat/blob/8a65eb780974eed93da449167f4385d16f8aa1ab/VCPDistributedServer/VCPDistributedServer.js#L817-L838)

这里的直接后果是：桌面 Agent 调 CLI 要经历模型请求、VCPToolBox 解析、WS 下发、VChat 本机执行、WS 回包、模型续轮。稳定桌面网络下可以接受，手机弱网和后台挂起下则成为高失败面。

### 1.3 `/chatvcp` 不是插件总开关

当前官方 VCPToolBox 的 `/v1/chat/completions` 与 `/v1/chatvcp/completions` 进入同一 handler，后者主要强制显示 VCP 结果；工具能否执行取决于提示词、插件在线状态和工具禁用指令。VCPMobile 现有 `enableVcpToolInjection` 只切 URL，不能被继续当作“真实 VCP 能力开关”。

- [`server.js@311dc42`](https://github.com/lioensky/VCPToolBox/blob/311dc42e8374afd1867bd1b5c06217baf8b0f463/server.js#L1216-L1242)
- [`chatCompletionHandler.js@311dc42`](https://github.com/lioensky/VCPToolBox/blob/311dc42e8374afd1867bd1b5c06217baf8b0f463/modules/chatCompletionHandler.js#L644-L690)
- VCPMobile 当前切换点：[vcp_client.rs](../../src-tauri/src/vcp_modules/infra/vcp_client.rs)

## 2. VCPToolBox 真正值得兼容的部分

### 2.1 模型调用协议

模型在 assistant 正文中输出纯文本工具块：

```text
<<<[TOOL_REQUEST]>>>
tool_name:「始」PowerShellExecutor「末」,
command:「始」Get-ChildItem「末」
<<<[END_TOOL_REQUEST]>>>
```

VCPToolBox 不依赖原生 function calling；字段正文可容纳多行文本和代码。解析器还会排除 `<think>/<thinking>` 中的调用，并保守处理未闭合思考块和 escape marker。移动端本地回环必须复用这些边界，不能用一个宽松正则替代。

- [`toolCallParser.js@311dc42`](https://github.com/lioensky/VCPToolBox/blob/311dc42e8374afd1867bd1b5c06217baf8b0f463/modules/vcpLoop/toolCallParser.js#L5-L67)
- [`toolCallParser.js@311dc42` 字段解析](https://github.com/lioensky/VCPToolBox/blob/311dc42e8374afd1867bd1b5c06217baf8b0f463/modules/vcpLoop/toolCallParser.js#L120-L165)

### 2.2 工具结果有模型面与展示面

VCP 工具执行完后，不只是生成一个供用户看的结果块。真正让 Agent 继续工作的内容是一个新的 `role:user` 消息：

```text
<!-- VCP_TOOL_PAYLOAD -->
[{"type":"text","text":"工具真实输出"}]
```

展示面则可以生成 `[[VCP调用结果信息汇总: ...]]`，供客户端渲染执行状态与摘要。若本地回环只伪造展示面，模型不会拿到结果，也不会继续下一步。

- [`streamHandler.js@311dc42`](https://github.com/lioensky/VCPToolBox/blob/311dc42e8374afd1867bd1b5c06217baf8b0f463/modules/handlers/streamHandler.js#L665-L700)
- [`vcpInfoHandler.js@311dc42`](https://github.com/lioensky/VCPToolBox/blob/311dc42e8374afd1867bd1b5c06217baf8b0f463/vcpInfoHandler.js#L96-L152)

### 2.3 manifest 是主要工具提示词源

VCPToolBox 从 `capabilities.invocationCommands[].description/example` 生成 `{{VCP<manifest.name>}}`，还支持 `{{VCPAllTools}}` 和 `{{VCPDynamicTools}}`。对本专项而言，manifest 就是 CLI 工具说明的规范源；VCPToolBox 负责把它插入 Agent 提示词，并允许用户在管理端手动微调指令描述。Mobile 不再另外维护 `CliPromptCatalog`，也不在聊天上下文装配层追加第二份 CLI 说明。

- [`Plugin.js@311dc42`](https://github.com/lioensky/VCPToolBox/blob/311dc42e8374afd1867bd1b5c06217baf8b0f463/Plugin.js#L1027-L1062)
- [`messageProcessor.js@311dc42`](https://github.com/lioensky/VCPToolBox/blob/311dc42e8374afd1867bd1b5c06217baf8b0f463/modules/messageProcessor.js#L783-L812)

“是否发布真实分布式插件”和“是否让 Agent 看见 manifest 说明”仍需分开：本地回环可以复用同一份 manifest 作为 VCPToolBox 侧提示词来源，而不把插件注册为远端执行器。具体占位符、DynamicTools 或用户提示词如何引用它，由用户在 VCPToolBox 侧配置；Mobile 只保证 manifest、parser 和 Runtime 合同一致。

## 3. OpenMinis 如何做本地 CLI 和长期工作

### 3.1 Android 本地执行

OpenMinis Android 当前每个会话维护一个长期 `PersistentShell`：

- 全局 PRoot/Alpine rootfs 只启动一次；
- 每会话一个 `/bin/sh` 进程和独立 bind mounts；
- 同会话命令用 Mutex 串行，不同会话可并行；
- 工作目录、环境变量、已安装软件和文件系统状态可跨命令延续；
- 人工终端另建真实 PTY，不和 Agent 的一次性工具块混为一体。

证据：

- [`ExecutionCoordinator.kt@9cf3a85`](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/src/android/app/src/main/java/com/openminis/app/sandbox/ExecutionCoordinator.kt#L11-L25)
- [`PersistentShell.kt@9cf3a85`](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/src/android/app/src/main/java/com/openminis/app/sandbox/PersistentShell.kt#L16-L24)
- [`TerminalSession.kt@9cf3a85`](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/src/android/app/src/main/java/com/openminis/app/sandbox/TerminalSession.kt#L21-L31)

### 3.2 Android 长任务不是“永久可靠”

OpenMinis 用前台服务、常驻通知和 `PARTIAL_WAKE_LOCK` 支持屏幕熄灭后的任务；用户可从通知停止活动 Agent。它也明确把 crontab/at/nohup 与 Android 原生 AlarmManager 调度区分开。

但其当前 `PersistentShell.executeCommand()` 超时只清空回调并返回 124，**不会终止仍在 shell 中运行的命令**。下一次命令可能与旧进程争用输出或状态。这是 VCPMobile 必须修正的反例：

- [`PersistentShell.kt@9cf3a85` 超时路径](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/src/android/app/src/main/java/com/openminis/app/sandbox/PersistentShell.kt#L265-L317)
- [`AgentForegroundService.kt@9cf3a85`](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/src/android/app/src/main/java/com/openminis/app/service/AgentForegroundService.kt#L148-L210)

### 3.3 原生能力 CLI 化

OpenMinis 会拦截 PRoot guest 中特定 `execve`，通过本地 abstract Unix Socket 把 argv/env/cwd 交给 Kotlin handler，再把 stdout 与退出码返回 shell。这样文件、通知、剪贴板、Shizuku 等 Android 能力都可表现成 `android-*` 命令，而无需每个能力都经过远端工具中心。

- [`NativeOffload.kt@9cf3a85`](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/src/android/app/src/main/java/com/openminis/app/sandbox/NativeOffload.kt#L15-L27)

这类桥接适合未来的 `vcp-*` 原生命令，但 [OpenMinis 明确说明其组合工程按 GPLv3 分发](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/README.md#L196-L203)，VCPMobile 不能直接复制实现后忽略许可证与发行义务。P0 必须分别审计 PRoot、rootfs、PTY/offload patch 和被打包命令的许可证。

### 3.4 Skills 采用渐进披露

OpenMinis 不把所有 `SKILL.md` 正文放进系统提示词。它最多披露 20 个启用 Skills 的名称、短描述和路径，优先 bundled、最近更新、常用项；Agent 需要时再读取完整文件。VCPMobile 只借鉴其“先索引、后正文”的渐进读取，不复制注入方式：`VCPMobileCLI` manifest 直接声明 `list_skills` 与 `read_skill` 两个 action，Agent 先查询受控索引，再按 ID 阅读正文或资源。Mobile 不额外把 Skill 摘要注入角色提示词。

- [`SkillRepository.kt@9cf3a85`](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/src/android/app/src/main/java/com/openminis/app/data/repository/SkillRepository.kt#L221-L296)

## 4. VCPMobile 已有的基础与缺口

### 4.1 已有基础

- [distributed/types.rs](../../src-tauri/src/distributed/types.rs) 已定义 `register_tools`、`execute_tool`、`tool_result` 和 VCP manifest DTO。
- [distributed/client.rs](../../src-tauri/src/distributed/client.rs) 已能连接 VCPToolBox、上报已启用 manifest、限制入站大小与并发、执行工具后回包。
- [distributed/tool_registry.rs](../../src-tauri/src/distributed/tool_registry.rs) 已有 OneShot/Interactive/Streaming 边界和默认禁用意图。
- [content_parser.rs](../../src-tauri/src/vcp_modules/chat/content_parser.rs) 与 [stream_block_parser.rs](../../src-tauri/src/vcp_modules/chat/stream_block_parser.rs) 已能识别和显示 VCP 工具块。
- [context_assembler.rs](../../src-tauri/src/vcp_modules/chat/context_assembler.rs) 继续只装配现有聊天上下文；本专项不在此新增 CLI 工具提示词。
- Android 插件已有 `ForegroundGuardian`、键盘 Insets、原生能力命令和前台通知基础设施。

### 4.2 关键缺口

1. 当前 Agent/Group 一次发送只进行一次模型请求，随后 finalizer；没有“模型 → 本地工具 → 结果回灌 → 模型续轮”的本地 coordinator。
2. 当前工具 block parser 面向渲染，不等于可安全执行的完整 VCP parser；还缺 think/escape/保留字段/重复执行保护。
3. 当前 `enableVcpToolInjection` 是松散 `extra` 布尔值和 URL 切换，不表达 local/VCP route 的互斥所有权。
4. 当前 ToolRegistry 仅持久化 disabled names，`is_enabled` 靠“不在 disabled 集合”取反。升级用户的旧配置不含新增 CLI 名，加载时整集合替换后会把新 CLI 误判为启用；目标应改为全量扫描 catalog + 默认空的 enabled allowlist。
5. 当前 ForegroundGuardian 的 `stream:{agent_name}` tag 会让同 Agent 的多话题任务共享 lease；不能充当 CLI job 身份。
6. 当前 Android 插件 acquire DTO 没有传入 `timeoutMs`，未知 tag 默认约 15 分钟释放；现有服务类型、通知取消和划卡行为都未证明适合任意 CLI。
7. 当前 Root 命令接口缺少完整 exit code、stderr、timeout 和可取消 owner，不可作为默认 CLI Runtime。

## 5. 研究结论

VCPMobile 已经具备真实 VCP transport 和聊天展示资产，缺的不是“再做一个插件中心页面”，而是三个集中 owner：

```text
VcpCliProtocol      唯一工具名、parser、schema、结果序列化
MobileCliRuntime    唯一 session/job/process/output/cancel owner
LocalVcpTurnOwner   唯一模型续轮、step ledger、幂等与 finalizer owner
```

Distributed VCP 只应成为 `MobileCliRuntime` 的一个可选适配器；本地回环则成为默认适配器。这样才能真正解决手机端对稳定连接的依赖，而不是把桌面的长链路原样缩进 WebView。

# 02｜统一协议与双路由架构

> ⚠️ **已被 08 ADR 收敛取代（S1-S3 已实施，2026-08-15）**：本文的 `localLoopback | vcpPlugin` 双路由已收敛为 vcpPlugin 单路由；`[[VCPToolUse=Forbidden]]` 注入、本地 meta owner、双 owner 分支与「10 秒 communication.timeout」均已废弃。协议核心（manifest 身份、action 语法、结果 envelope）仍有效；路由与元字段语义以 [08-本地回环收敛与保活分层ADR.md](./08-本地回环收敛与保活分层ADR.md)、[10-S1审计-localLoopback删除映射表.md](./10-S1审计-localLoopback删除映射表.md) 与本仓库当前代码为准。

## 1. 协议目标

本专项冻结一个独立、transport 中立的工具身份：

```text
产品名称：VCP CLI
manifest.name：VCPMobileCLI
invocationCommands[].commandIdentifier：VCPMobileCLI
TOOL_REQUEST.tool_name：VCPMobileCLI
```

`VCPMobileCLI` 是一个独立工具，不是任何其他执行器的移动版、别名或兼容层。manifest 只能陈述本工具自己的环境、参数和行为，禁止出现“沿用某执行器”“与桌面端相同”或要求 Agent 了解其他项目的措辞。

三个名字完全相同是本工具的单命令 manifest 约定，用来避免 `ServerPowerShellExecutor` manifest 名与示例名不一致一类歧义；这不是 VCP 对所有多命令插件的普遍要求。

### 1.1 Shell 与命令集冻结

Agent 调用的不是 Android `/system/bin/sh`，也不是 PowerShell。Android 首期 Shell 合同冻结为：

```text
CPU/系统：     Android arm64 应用沙箱内的 PRoot guest
发行版：       Alpine Linux（musl libc）
解释器：       GNU Bash，固定以 /bin/bash -lc <command> 执行
默认 cwd：     /workspace
权限：         Android host 非 Root；guest 内为 PRoot 模拟 root，仅管理隔离 rootfs
包管理器：     apk
交互：         Agent 调用无 PTY、无 stdin；交互任务转人工终端
持久状态：     /workspace、已安装包和其他 guest 文件持久；Skill 由 host action catalog 独立持有
非持久状态：   cd、export、alias、shell function 不跨 run 调用保存
```

首发 rootfs 必须随版本维护一份可机器校验的 `command-profile.json`。下面是 manifest 可以承诺的基线命令族；缺少任一项就必须在发布前修改 manifest，而不是让 Agent 猜测：

| 命令族 | 首发基线 |
|---|---|
| Bash/GNU 基础文件 | `bash`, `sh`, `pwd`, `ls`, `mkdir`, `cp`, `mv`, `rm`, `ln`, `touch`, `cat`, `head`, `tail`, `wc`, `stat` |
| GNU 文本与搜索 | `grep`, `sed`, `awk`, `sort`, `uniq`, `cut`, `tr`, `xargs`, `find`, `diff`, `patch` |
| 归档与结构化数据 | `tar`, `gzip`, `xz`, `zip`, `unzip`, `file`, `jq` |
| 网络与版本控制 | `curl`, `wget`, `git`, `ssh`, `scp` |
| 脚本与包 | `python3`, `pip`, `apk` |

rootfs 基线包至少对应 `bash coreutils findutils grep sed gawk diffutils patch tar gzip xz zip unzip file jq curl wget git openssh-client-default python3 py3-pip ca-certificates tzdata`；版本与实际二进制由 `command-profile.json` 记录。BusyBox 可以作为 Alpine 基础设施存在，但 manifest 广告的命令必须通过上述明确包提供和探测，不能让 Agent 在 GNU/BusyBox 方言间猜测。Skill 读取不是 guest 命令集的一部分，而是同一 manifest 中的独立 action。

默认没有 `sudo`、`apt`、`dnf`、`systemctl`、Docker、GUI 或 Android `adb`。guest 内的“root”只是 PRoot 对隔离 rootfs 的模拟身份，使 `apk add` 无需 `sudo`；它没有 Android root、不能越过 App UID 或读取其他 App 私有数据。Alpine 使用 musl，部分只有 glibc wheel 的 Python 包不能直接安装；优先 `apk search`/`apk add py3-*`，纯 Python 包再用 `pip`。是否额外提供 Node、编译器或原生 Android 命令桥，必须以后由 `command-profile.json` 和 manifest 同步声明。

选择 Bash 是为了让跨模型常见的 Bash 命令与脚本模式直接适用；Alpine aarch64 有正式 [`bash`](https://pkgs.alpinelinux.org/package/edge/main/aarch64/bash) 和 [`openssh-client-default`](https://pkgs.alpinelinux.org/package/v3.22/main/aarch64/openssh-client-default) 包，但实际锁定分支、版本、许可证义务与 APK 增量仍属于 P0。不会采用“默认 BusyBox `ash`，检测到 bashism 再临时安装 Bash”的双语义。若 P0 证明 APK/许可证预算无法稳定内置 Bash，则应回到本节重新裁决，不能在运行时静默降级成 `ash`。

### 1.2 OpenMinis 与常见 Agent Shell 的接口取舍

OpenMinis Android 在固定快照中不是只给模型一个“万能命令”，而是按能力拆成以下工具组：

| 分组 | 工具 | 暴露条件/用途 |
|---|---|---|
| Shell | `shell_execute` | 必有；`tool_title`, `command`, `timeout`, `delay` |
| 文件 | `file_read`, `file_write`, `file_edit` | 必有；避免让模型为普通编辑反复组装 Shell 转义 |
| 图像 | `read_image` | 仅模型支持图像输入时注册 |
| 浏览器 | `browser_use` | 独立 action 工具，不塞进 Shell |
| 记忆 | `memory_write`, `memory_get` | 仅用户开启 memory 时注册 |

其 Shell 实现是 PRoot/Alpine 中按 session 复用的 `/bin/sh`。当前 `shell_execute` description 又写“每次调用新进程”，与 `ExecutionCoordinator` 的持久 Shell 实现并不完全一致，因此本专项只借鉴其工具分组、字段命名与移动沙箱经验，不复制这段描述：

- [`AgentTools.kt@9cf3a85`](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/src/android/app/src/main/java/com/openminis/app/tools/AgentTools.kt#L23-L53)
- [`ExecutionCoordinator.kt@9cf3a85`](https://github.com/OpenMinis/OpenMinis/blob/9cf3a855fecd27bb5735b84cacbd56852a3ab8dd/src/android/app/src/main/java/com/openminis/app/sandbox/ExecutionCoordinator.kt#L11-L24)

常见 Agent Shell 的稳定交集是：

| 来源 | 模型侧核心字段 | 本专项取舍 |
|---|---|---|
| OpenMinis `shell_execute` | `command`, `timeout`, `delay`, `tool_title` | 保留 `command` 和超时；不把等待延迟做成 CLI 能力 |
| Claude Code `Bash` | `command`, `description`, `timeout`, `run_in_background` | 保留同名字段，降低模型迁移成本 |
| OpenAI Shell | `commands`, `timeout_ms`, `max_output_length`，结果含 stdout/stderr/outcome | 使用单个 `command`，结果保留 stdout/stderr/exit/timeout |
| Gemini CLI `run_shell_command` | `command`, `description`, `directory` | 采用 `cwd` 表达工作目录，语义等价但路径规则更明确 |

来源：[`Claude Code Hooks` 的 Bash 输入字段](https://code.claude.com/docs/en/hooks#pretooluse-input)、[OpenAI Shell 本地执行合同](https://developers.openai.com/api/docs/guides/tools-shell#local-shell-mode)、[Gemini CLI `run_shell_command`](https://google-gemini.github.io/gemini-cli/docs/tools/shell.html)。这些来源用于选择模型熟悉的字段，不表示 VCPMobile 要兼容其 wire protocol。

因此不照搬 OpenMinis 的完整工具集。VCPMobile 现有文件、浏览器、记忆与 Android 原生能力各有自己的 owner；它们不应被为了“看起来像 OpenMinis”强行并入 CLI manifest。CLI 首期只注册一个 `VCPMobileCLI`；普通执行采用最熟悉的 `command` 主路径，长任务仅增加最小 Job 生命周期字段。

### 1.3 规范 manifest

规范 manifest 只有一个事实源：[`manifest.rs`](../../src-tauri/src/vcp_modules/cli/manifest.rs) 构建 typed manifest，[golden fixture](../../src-tauri/src/vcp_modules/cli/fixtures/vcp_mobile_cli_manifest.golden.json) 冻结逐字序列化结果。Mobile 的复制/导出入口与 Distributed 注册必须共同使用该 serializer；本文不再内嵌 JSON 副本，避免 action、River 能力和路由边界随实现演进后漂移。

真实 VCP route 注册时，VCPToolBox 可从该 manifest 生成主要工具提示词；默认本地 route 不建立 Distributed 连接，因而不会自动把动态 manifest 送到 VCPToolBox，首次使用前由用户在 VCPToolBox 侧导入/放置这份说明并微调。Mobile 不追加另一份提示词。当前 serializer 的通信 timeout 固定为 10 秒，所以所有 action 都必须在 10 秒内返回；长命令不能让 Distributed WS 同步等待。`run` 的 8 秒 yield 为传输响应预算，`timeout_ms` 才是 Job 执行期限，两者不得混淆。

## 2. VCP 请求合同

### 2.1 一等 action

首期规范 action：

| action | 必需参数 | 语义 | 最长接口占用 |
|---|---|---|---|
| `run`（默认） | `command` | 启动独立 Bash Job；短任务直接给结果，超过 yield 自动返回 `job_id` | 8 秒 |
| `list_skills` | 无 | 返回已安装且完整性校验通过的 Skill 元数据索引 | 1 秒目标 |
| `read_skill` | `skill_id` | 读取 `SKILL.md` 或 Skill 内受控相对资源，返回有界正文和逻辑引用 | 1 秒目标 |
| `poll` | `job_id` | 查询状态并从 cursor 增量读取 stdout/stderr | `wait_ms`，最大 8 秒 |
| `cancel` | `job_id` | 取消目标 attempt 与整个进程组，返回确认后的终态 | 8 秒 |
| `list` | 无 | 返回当前 CLI session 的有界 Job 摘要 | 1 秒目标 |

不再保留 `execute` 与 `start` 两个近义 Shell 入口。执行命令时 Agent 只需学会 `run`：默认先等一小段时间，任务尚未完成时自动变成可查询 Job；明确知道会很久时加 `run_in_background=true` 立即返回。Skill 则由命名明确的 `list_skills/read_skill` 暴露，不伪装成 Bash 命令。这样既兼容 VCP 的 10 秒通信壳，也让 manifest 能用模型熟悉的动词直接表达两类能力。

候选参数：

```text
action              enum，run|list_skills|read_skill|poll|cancel|list；省略即 run
command             string，run 必需；UTF-8 最多 64 KiB，传给 /bin/bash -lc，不做二次 argv 拼接
description         string，可选；3–10 个词的用户可见目的说明
cwd                 string，可选；沙箱绝对路径，默认 /workspace
timeout_ms          integer，可选；Job 硬期限，默认 30 分钟，允许 1 秒至 12 小时
run_in_background   boolean，可选；true 时启动后立即返回，默认 false
job_id              string，poll/cancel 必需
cursor              string，poll 可选；分别编码 stdout/stderr 单调位置
max_output_bytes    integer，poll 可选；UTF-8 默认 65536，夹紧至 262144
wait_ms             integer，poll 可选；长轮询等待，范围 0–8000
skill_id            string，read_skill 必需；只能引用受控 Skill catalog 中校验通过的稳定 ID
resource_path       string，read_skill 可选；默认 SKILL.md，只允许 Skill 根内相对普通文件
max_bytes           integer，read_skill 可选；默认 65536，夹紧至 262144
```

`description` 只用于工具块/通知标题，不进入 Shell；`cwd` 由 Runtime 解析并校验，不允许靠 `cd ../../..` 越出 guest。`timeout_ms` 是执行期限，不代表系统承诺能在 Android 被强杀后继续运行。Skill 字段只允许出现在 `read_skill`，`list_skills` 不接收 Shell/Job 字段；`read_skill` 不启动进程、不执行资源内容。字段名不接受模糊同义词作为长期协议；parser 可以在开发期记录未知字段，但不得静默猜测。

例：

```text
<<<[TOOL_REQUEST]>>>
tool_name:「始」VCPMobileCLI「末」,
action:「始」run「末」,
command:「始」pwd && find . -maxdepth 2 -type f | sort「末」,
description:「始」扫描工作区文件「末」,
timeout_ms:「始」1800000「末」,
ink:「始」mark_history「末」
<<<[END_TOOL_REQUEST]>>>
```

后台启动与增量查询：

```text
<<<[TOOL_REQUEST]>>>
tool_name:「始」VCPMobileCLI「末」,
action:「始」run「末」,
command:「始」python3 train.py「末」,
description:「始」运行本地训练任务「末」,
timeout_ms:「始」21600000「末」,
run_in_background:「始」true「末」
<<<[END_TOOL_REQUEST]>>>

<<<[TOOL_REQUEST]>>>
tool_name:「始」VCPMobileCLI「末」,
action:「始」poll「末」,
job_id:「始」job_01J...「末」,
cursor:「始」c_42...「末」,
max_output_bytes:「始」65536「末」,
wait_ms:「始」8000「末」
<<<[END_TOOL_REQUEST]>>>
```

VCP parser 初始把字段解析为字符串，再由 `VcpCliProtocol` 做 typed validation。禁止直接把未知字段拼入 shell；`tool_name` 与全局保留字段必须先剥离。

### 2.2 保留字段

以下字段属于 VCP 元协议，不是 CLI argv：

```text
tool_name
archery
ink
river
vref
```

即使某阶段尚未实现其完整行为，也必须识别并从 Bash action 中剥离，绝不能把 `ink=mark_history` 等元字段当作环境变量或命令参数传给 shell。`ink` 可作用于任意 action 的历史投影；`river`、`vref` 和 `archery` 首期只允许用于 `run`，其他 action 携带这些字段返回 `invalid_request`。本地 `run` 的合法 `river/vref` 是 best-effort：无法应用时继续命令并在 ToolResult 中提示 Agent；远端引用、伪造物化字段与语法错误不适用该降级。本地实现矩阵见 [04-提示词Skills记忆与召回语义.md](./04-提示词Skills记忆与召回语义.md)。

### 2.3 人工交互不是普通 action

首期不让 Agent 通过 `startInteractive` 自动进入密码/SSH/TUI。需要人接管时，工具返回 `waiting_user` 与一个受控的终端打开动作；UI 显示“打开终端”，命令只预填、不执行。

若以后让 Agent 操作 PTY，必须另建独立工具和权限合同；不得把 `startInteractive/queryVisibleN/endInteractive` 等其他工具的名称塞进 `VCPMobileCLI`，也不能和 `run/poll/cancel/list` 的后台 Job 复用一个含糊状态。

## 3. 四层结果合同

“伪装 VCP 响应格式”必须精确区分四层，不能把它们揉成一个自创 JSON。

### 3.1 Runtime 规范结果

`MobileCliRuntime` 对本地和远端 adapter 返回同一领域 envelope。Job action 的结果形状为：

```json
{
  "status": "success",
  "result": {
    "content": [
      {
        "type": "text",
        "text": "...bounded output..."
      }
    ],
    "job": {
      "id": "job_...",
      "state": "completed",
      "stdout": "...bounded stdout...",
      "stderr": "...bounded stderr...",
      "exit_code": 0,
      "cursor": "...",
      "truncated": false,
      "artifact": null
    },
    "runtime": {
      "platform": "android",
      "shell": "/bin/bash",
      "distribution": "alpine",
      "libc": "musl",
      "source": "local_loopback"
    }
  }
}
```

Skill action 不伪造 Job。`list_skills` 返回有界 `skills[]` 索引；`read_skill` 返回如下结构，其中 `skill_root` 是不可直接传给 Shell 的逻辑引用，不能用作宿主文件授权：

```json
{
  "status": "success",
  "result": {
    "content": [
      {
        "type": "text",
        "text": "# Skill instructions..."
      }
    ],
    "skill": {
      "id": "example-skill",
      "name": "Example Skill",
      "resource_path": "SKILL.md",
      "skill_root": "vcp-skill://example-skill",
      "sha256": "...",
      "truncated": false
    },
    "runtime": {
      "platform": "android",
      "source": "local_loopback"
    }
  }
}
```

这里的顶层 `status=success` 表示 action 已被 Runtime 正常受理，不表示命令退出码一定为 0，也不表示 Skill 内容已获执行授权。非零退出、超时和取消分别由 `job.state=failed|timed_out|cancelled`、`exit_code` 与终止原因表达，并仍作为可读工具结果回灌 Agent。顶层失败合同只用于参数无效、Job/Skill 不存在、完整性失效、权限拒绝、route 不可用或 Runtime 内部错误：

```json
{
  "status": "error",
  "error": "human readable summary",
  "code": "invalid_request|unsupported_mode|job_not_found|skill_not_found|skill_integrity_failed|permission_denied|user_disabled|remote_disconnected|runtime_unavailable|...",
  "result": {
    "content": [
      { "type": "text", "text": "bounded diagnostic" }
    ]
  }
}
```

错误也应转换成可回灌的 tool content，让 Agent 有机会修正调用；只有协议破坏、owner 失效或安全门拒绝才结束整个 turn。

### 3.2 Distributed VCP wire

真实 VCP 模式在外层包已有 wire envelope：

```json
{
  "type": "tool_result",
  "data": {
    "requestId": "...",
    "status": "success",
    "result": {}
  }
}
```

错误时 `data.status=error` 且使用 `data.error`。必须绑定 `(connection_epoch, server_id, request_id)`；晚到的旧连接结果不能完成新请求。

### 3.3 模型续轮 payload

本地循环从规范结果抽取 OpenAI 多模态 `content` 数组，追加：

```text
role: user
content:
<!-- VCP_TOOL_PAYLOAD -->
[{"type":"text","text":"..."}]
```

这是 Agent 继续工作的数据面。必须同时保留上一轮 assistant 原始工具请求，保持因果链。

### 3.4 UI 展示事件

UI 通过本地事件/Channel 获取结构化状态，渲染工具名、`LOCAL`/`VCP` 来源、Job 状态、尾部输出和取消按钮。若为了兼容现有消息渲染生成 `[[VCP调用结果信息汇总:...]]`，它只是展示投影，不能反向成为 Runtime 真源。

## 4. 双路由与唯一 owner

### 4.1 typed 设置

用 typed enum 替代松散 `enableVcpToolInjection` 语义：

```text
mobileCliAgentRoute:
  localLoopback   # 默认
  vcpPlugin       # 用户显式选择
```

`vcpPlugin` route 选择只决定工具循环 owner；`VCPMobileCLI` 是否允许发布/执行，由 Distributed 工具清单中的独立 allowlist 开关决定，不再设置另一个 CLI 专用布尔值。切换 route 时只做校验和引导，不静默打开 Distributed、填写凭据或授权任何工具。

### 4.2 localLoopback

```text
VCPToolBox 提示词配置
  ├─ 用户导入/放置 Mobile 导出的规范 manifest description/example
  ├─ 用户在 VCPToolBox 侧微调或通过 DynamicTools 选择
  └─ Mobile 不复制或改写上述工具说明
          ↓
typed local transport 在首个 system 网络投影加入 [[VCPToolUse=Forbidden]]
          ↓ VCPToolBox 读取并剥离控制标记，中央 parser/executor 禁止执行
普通 /v1/chat/completions → 上游模型
          ↓
Mobile 收集完整 assistant VCP block
          ↓
LocalVcpTurnOwner → LocalVcpMetaProcessor → MobileCliRuntime
          ↓
VCP_TOOL_PAYLOAD user message
          ↓
下一步模型请求，直到自然回复或 step budget
```

用户实际部署已证明：只要不发送 `[[VCPToolUse=Forbidden]]`，普通 `/v1/chat/completions` 仍会先执行同一个工具块，再把结果续给模型，随后 Mobile 还会再次执行；发送标记后中央调用摘要消失，Mobile 成为唯一 owner。故该标记由 typed `localLoopback` transport 每个 step 自动加入临时首个 system 消息，并由 VCPToolBox 在上游模型前剥离。它不是 Mobile 的 CLI 工具提示词，不写入 `mobile_system_prompt`、`context_assembler.rs`、消息历史或 manifest；用户仍只在 VCPToolBox 管理真正面向 Agent 的工具说明。`vcpPlugin` 不发送该标记，由 VCPToolBox 保持工具循环 owner。

这也冻结了支持下限：本地回环要求 VCPToolBox 实现该请求级禁执行合同。旧部署若不认识标记，就不能证明唯一执行 owner，不能宣称兼容；Mobile 不以“过滤调用摘要”掩盖已经发生的远端副作用。

本地 route 下不得注册 `VCPMobileCLI` 到 VCPToolBox，也不得为回环启动 WS、localhost HTTP 或本地 SSE 服务。

因此 local route 的准确产品合同是“执行离线、提示词由用户配置”，不是“完全零配置”。即使未完成 VCPToolBox 提示词配置，人工 CLI 仍可使用；Agent 不会稳定地产生工具调用，Mobile 也不得偷偷补一份 system prompt。

### 4.3 vcpPlugin

```text
preflight:
  Distributed enabled
  credentials valid
  connection online(epoch)
  EnabledToolNames 含 VCPMobileCLI
        ↓
register_tools（仅一份 VCPMobileCLI manifest）
        ↓
VCPToolBox 拥有工具循环
        ↓
execute_tool → Mobile Distributed client
        ↓
同一个 MobileCliRuntime
        ↓
tool_result → VCPToolBox 续轮
```

此模式关闭 Mobile 的本地 turn parser/executor，只保留聊天流展示。不能因为 `/chatvcp` 断开而静默改成本地执行；用户选择的执行位置可能涉及不同文件、权限和安全边界。

### 4.4 未授权/offline

- `vcpPlugin + 未授权`：VCPToolBox 是否仍展示 manifest 说明由用户提示词配置决定；Mobile 不发布 manifest，收到直接执行请求时稳定返回 `user_disabled`，不得尝试执行。
- `vcpPlugin + connecting/offline`：不注册远端 manifest；若用户保留了手工说明，调用 preflight 返回 `remote_disconnected`，聊天本身仍可继续。
- 远端断开：在途 request 以 `remote_disconnected` 终结；已由本地 Runtime 启动的异步 Job 不因 WS 断开而被杀，可在重连后按 `job_id` 查询。

## 5. 本地模型续轮状态机

当前 VCPMobile 单次发送只请求模型一次。新增 coordinator 必须位于一次用户发送的 ActiveRequest owner 内，而不是递归调用顶层 send：

```text
TURN_ACTIVE(attempt_id, generation, step=0)
  → request model
  → stream/display partial
  → complete assistant frame
      ├─ no executable VCP block → FINAL_COMMIT
      └─ valid VCPMobileCLI block
           → digest + ledger claim
           → LocalVcpMetaProcessor capability/projection
           → dispatch run/list_skills/read_skill/poll/cancel/list
           → persist tool result
           → append assistant request + VCP_TOOL_PAYLOAD
           → step += 1
           → request model again
```

必须维护：

- `attempt_id + step_index + canonical_tool_call_digest` 唯一键；
- `claimed/running/result_ready/continuation_pending/continued/terminal` ledger；
- 最大工具 step 和最大总 wall-clock budget；
- 每次执行前与 commit 前的 generation/owner 校验；
- SSE replay、请求重试、WebView reload 和进程重启后的去重；
- shell 完成但模型续轮断网时保存 `continuation_pending`，网络恢复后只续轮，不重跑命令；
- finalizer 只由 turn owner exact-once 执行。

流式 parser 只有收到完整、位于 reasoning 外的闭合 block 后才能 claim；不对半截 delta 执行命令。

Group Chat 必须与单聊同时接入相同 coordinator；若未支持，Mobile 必须在能力状态中明确该路径不可执行并返回稳定错误。VCPToolBox 侧的全局 manifest 说明可能仍然可见，因此不能靠“Mobile 不注入提示词”掩盖 Group 缺少执行 owner。

## 6. Distributed ToolRegistry 显式扫描与授权合同

当前 ToolRegistry 逻辑是“未出现在 disabled 集合即启用”：注册新工具时先插入 disabled，但加载旧配置会用旧文件整集合替换。升级用户旧文件中没有新工具，新工具就会因取反逻辑被自动启用。

冻结修改为两层真源：

```text
ScannedToolCatalog = 每次启动扫描/静态构建得到的全量工具清单，不是授权配置
EnabledToolNames   = 用户逐个授权后持久化的 allowlist，默认空集

is_enabled(name) = catalog.contains(name) && enabled_names.contains(name)
```

- Registry 先显式扫描全部 OneShot/Interactive/Streaming 工具，扫描只代表“已发现”，不代表“已授权”。
- 复用现有 `DistributedView` 工具卡片/开关，UI 始终显示 catalog 中每个工具的名称、类型、权限/风险说明、可用性、`blocked_reason` 和独立授权开关；新扫描工具的开关必为关，不新建第二个工具管理页。
- 保存 API 从 `update_disabled_tools(disabled_names)` 改为 `update_enabled_tools(enabled_names)`；后端校验重复名与未知名，先原子持久化再替换内存策略。
- 无配置、旧 `disabled_names` 配置、破损配置和读写失败都 fail closed 到空 allowlist。不从旧取反集合自动推导任何授权；用户需重新确认。
- 加载新 schema 时，实际权限是 `persisted enabledTools ∩ scanned names`；已下架工具的 orphaned 名称不能生效，只记录可见警告并在下次成功保存时清理。用户保存 API 仍拒绝当前 catalog 之外的名称。
- `get_all_manifests`、placeholder 发布与 `execute` 共用同一 allowlist gate；UI 的 `enabled` 必须由后端显式返回，不得以缺字段默认 true。

建议持久化 fixture：

```json
{
  "schemaVersion": 2,
  "enabledTools": []
}
```

真实 VCP 路由下，只发布同时满足下列条件的 manifest：

```text
route == vcp_plugin
&& distributed.enabled
&& EnabledToolNames.contains("VCPMobileCLI")
&& runtime.available
&& connection is current online epoch
```

必须有升级测试：

1. 干净安装扫描到所有工具，但全部 `enabled=false`，`register_tools` 发布空集；
2. 携带旧 disabled-name 配置升级后不自动授权任何工具，并给用户一次“需重新授权”提示；
3. 新版本多扫描到一个工具时，已授权工具保持原值，新工具保持关闭；
4. 对 `VCPMobileCLI` 显式授权后恰好注册一份；撤销后重新注册不含该 manifest，UI registered count 同步清零；
5. 未授权工具即使被伪造 `execute_tool` 点名也必须拒绝；
6. 本地 route 不读取 Distributed allowlist，远端授权关闭不影响用户已选择的本地 CLI route。

## 7. 协议不变量

1. `manifest.name == commandIdentifier == tool_name`。
2. 两条 route 使用同一个参数 validator 和结果 normalizer。
3. 同一 turn 只有一个工具循环 owner。
4. 同一 tool call digest 最多执行一次；模型续轮可以重试，命令不可隐式重跑。
5. `requestId` 不是单独的信任边界；必须带连接 epoch 和目标节点身份。
6. manifest 只声明稳定工具合同；route 不可用时 Runtime 必须返回明确错误，不伪造执行成功。
7. 错误结果进入 Agent 可读 payload，但安全拒绝不会被模型绕过。
8. UI 来源标记不改变 Agent 所见工具名。
9. `ink/river/vref/archery` 先由 route 的 VCP meta owner 处理；保留字段不直接进入 Bash。本地合法 `river/vref` 能力不足时继续命令并提示 Agent，其他能力/安全错误仍返回 typed error。

# 设置接口与状态契约

以下 TypeScript 描述目标接口与语义，不是已存在的代码。Pinia 继续使用 Composition API；接口示意省略 Vue 自动解包细节，不要求引入额外 repository 类、依赖注入容器或通用状态机。

## 聊天偏好接口

P1 直接迁移既有类型、选项、归一化和 setter，避免同时改变公共行为。

~~~ts
export interface ChatPreferences {
  readonly presentationMode: ChatPresentationMode;
  readonly smoothStreamingEnabled: boolean;
}

export interface PresentationChangeResult {
  ok: boolean;
  changed: boolean;
  mode: ChatPresentationMode;
  error?: string;
}

export interface SmoothStreamingChangeResult {
  ok: boolean;
  changed: boolean;
  enabled: boolean;
  error?: string;
}

export interface ChatPreferenceCommands {
  setPresentationMode(value: unknown): PresentationChangeResult;
  setSmoothStreamingEnabled(value: boolean): SmoothStreamingChangeResult;
}
~~~

useChatPreferencesStore 是唯一状态入口。消费者可以直接读取只读偏好，通过这两个 setter 写入。model.ts 导出 ChatPresentationMode、CHAT_PRESENTATION_MODES、CHAT_PRESENTATION_OPTIONS 和 normalizeChatPresentationMode。

### 初始化和写入

1. 在 Store 创建时同步读取两个既有 key，按当前生产规则恢复。
2. 缺省仍为 bubble 和 false。无效缓存继续归一化；已识别的损坏值修复失败时保留可用内存值并记录问题，不阻断聊天。
3. setter 对新旧值相同的情况返回 changed=false，不写存储。
4. setter 写入成功后才发布新偏好；写失败返回旧值和 error。
5. 不使用组件挂载、深层 watch 或设置页打开动作启动持久化。
6. 不提供跨 key 批量原子更新承诺。将来出现必须一起提交的字段，再定义该领域事务。
7. 不保留 theme Store 到新 Store 的转发 getter；一次迁移全部生产消费者和相关测试。

设置页面可以按以下方式绑定，失败反馈留在实际交互入口：

~~~vue
<SettingsSwitch
  :model-value="preferences.smoothStreamingEnabled"
  aria-label="流式平滑动效"
  @update:model-value="onSmoothStreamingChange"
/>
~~~

onSmoothStreamingChange 调用领域 setter，并根据结果反馈；不能直接修改 Store 的持久状态。使用可写 computed 绑定同样必须经过 setter。

### 期望值和实际效果

smoothStreamingEnabled 只表示用户偏好。流式状态、AST 支持、页面可见性和减少动态效果等条件继续在真实渲染消费路径判断，不能被“设置为 true”绕过，也不持久化为第二份 effectiveEnabled。

主题明暗、主题文件应用和回滚仍通过 useThemeStore。聊天偏好不加载主题资产，不注册系统明暗监听。

## 本地持久化工具

P1 的聊天 storage.ts 封装自身 key 和编码。P4 有第二个实际领域使用时，提取窄 IO 工具：

~~~ts
export type LocalReadResult =
  | { ok: true; raw: string | null }
  | { ok: false; error: string };

export type LocalWriteResult =
  | { ok: true }
  | { ok: false; error: string };

export interface LocalPreferenceIO {
  read(key: string): LocalReadResult;
  write(key: string, value: string): LocalWriteResult;
}
~~~

该工具捕获实际存储异常，便于以失败存储验证行为。类型解码、默认值、修复决定和业务文案仍由领域定义。当前只有少量字符串和布尔值，不引入 schema 库或统一版本包络。

读取原文为 null 与读取失败不同：前者使用领域缺省，后者保留异常信息。写成功与读修复成功也不同，不能用默认值回退伪造一次用户修改成功。

若未来确实变更格式，迁移规则须包含旧格式读取、新格式校验、新写成功后才移除旧数据、失败保留可恢复原值，以及重复启动的幂等性。本次没有这种迁移需求。

## Rust 配置访问接口

保留 useSettingsStore 的现有方法形态：

~~~ts
interface SettingsAccess {
  readonly settings: AppSettings | null;
  fetchSettings(): Promise<void>;
  updateSettings(updates: Partial<AppSettings>): Promise<AppSettings>;
}
~~~

接口继续调用 read_settings 和 update_settings。更新是现有 Rust 顶层 patch，不是整对象写回，不是嵌套对象深合并。

提交契约：

- 调用入队前复制 patch 的值，避免队列实际执行时读取到已经变化的草稿或数组。
- Store 是唯一已提交快照所有者；页面不得将某个旧响应重新赋值给 settings。
- 成功只意味着持久配置已提交，连接和其他运行结果从对应所有者取得。
- 保留损坏恢复通知；现有成功 Toast 文案改为准确的“设置已保存”，不声称“同步成功”或所有效果均已完成。
- 本轮先保留既有调用方的通知行为，页面普通保存不另叠加成功 Toast；导入、导出等专用操作显示自身结果。
- 失败仍拒绝 Promise，保存会话在边界转换成可呈现结果；不为失败向后端反向写旧值。
- 不从默认字段对象构造可保存表单。首个正式快照未取得时，编辑会话处于未就绪状态。
- 已有合法快照时可以先建立会话，再通过原队列刷新；刷新失败保留现有快照和草稿，并显示失败，不把它们清空为默认值。

AppSettings 现有字符串索引不作为新表单扩展协议。页面用显式字段集合形成 Pick 类型，禁止新增任意字符串字段来绕过领域定义；本专项不强制一次删除现有 extra 兼容能力。

## 页面编辑接口

身份、连接、总结配置分别建立一个会话。P2 先在现有 SettingsView 装配中使用，P3 移入对应页面，任何时刻同一页面只有一个活动会话。

~~~ts
export type SettingsSaveResult =
  | {
      ok: true;
      changed: boolean;
      dirty: boolean;
      snapshot: Readonly<AppSettings>;
    }
  | { ok: false; error: string };

export interface SettingsEditSession<Fields extends object> {
  readonly ready: boolean;
  readonly draft: Readonly<Fields>;
  readonly dirty: boolean;
  readonly saving: boolean;
  readonly leaving: boolean;
  readonly error: string | null;

  edit<K extends keyof Fields>(key: K, value: Fields[K]): void;
  save(): Promise<SettingsSaveResult>;
  settlePending(): Promise<SettingsSaveResult>;
  prepareLeave(): Promise<boolean>;
  acceptImport(replacedKeys: readonly (keyof Fields)[]): void;
  dispose(): void;
}
~~~

settlePending 只等待已经请求的保存过程完整结算，不把原本没有请求保存的 dirty 字段额外提交；导入确认是它的实际消费者。没有活动保存时返回当前快照和 dirty 状态。

acceptImport 只用于已确认且成功的导入，且要求本页无 pending 保存。它从当前 SettingsStore 快照接受 replacedKeys，不重放可能落后的导入响应；普通外部快照使用内部 rebase，不能无条件重置用户草稿。组件通过 edit 或调用 edit 的 computed setter 修改草稿，禁止直接修改嵌套 props 绕过编辑计数。

### 内部状态

| 状态 | 含义 |
|---|---|
| base | 最新已知正式快照在本页字段的投影 |
| draft | 用户正在编辑的本页值 |
| editRevision[k] | 字段每次用户编辑递增；服务器响应不递增 |
| pending | 本批次的字段、提交值与捕获的 editRevision |
| saveRequested | 当前保存期间是否又收到一次显式保存要求 |
| activeSave | 单飞保存过程的 Promise |
| disposed | 本页访问已经结束，禁止迟到 UI 副作用 |

dirty 按 draft 与 base 的差异计算，不单独持久化。字段比较依据实际类型；当前三个页面投影都是字符串或枚举，不需要为此引入通用对象差异引擎。

### 新快照进入会话

对每个本页字段，先记录旧状态下是否 dirty，或者是否属于 pending；然后更新 base。只有既不 dirty 又不 pending 的字段跟随新快照更新 draft，其余保留用户意图。最后重新计算 dirty。

pending 不能省略。关键时序为：原值 0 → 改为 1 → 提交 1 → 保存期间改回 0。此时 draft 暂时等于旧 base，dirty 可能为 false，但 pending 与 editRevision 必须阻止响应 1 覆盖新的 0。

### 一批提交

1. 按当前 SettingsStore 快照重基；未就绪或已释放时不提交。
2. 捕获当前 dirty 字段和值，复制成顶层 patch，同时记录字段 editRevision。
3. 若 patch 为空，返回当前快照及 dirty 状态，不产生 IPC。
4. 标记 pending，调用唯一 SettingsStore.updateSettings。
5. 成功后使用当前 Store.settings 进行结算，不把较旧响应直接复制到页面。
6. 对该批字段，editRevision 未变化时接受当前正式值；有后续编辑时保留新草稿。
7. 清理 pending 并重新计算 dirty。返回成功不自动等于页面可以关闭。
8. 失败保留草稿和错误，清理 pending，不自动循环重试。

快照观察与结算顺序必须明确。实现可使用同步快照观察，并在 Promise 结算时再显式重基；不能让一个迟到 watcher 在结算后覆盖新输入。即使页面已释放，共享 Store 仍可接纳已经提交的操作结果；旧页面只停止自己的更新和导航。

### 保存合并和同字段竞争

save() 设置 saveRequested；若已有 activeSave，复用这一个保存过程。每批成功后，如果期间再次收到显式 save，则捕获最新 dirty 继续提交；没有新的保存要求就结束。普通输入只更新草稿，不自动要求无限追赶保存。

任一批失败即结束本次过程、清除待自动推进标记并反馈，用户可显式重试。不能简单地在 saving 时返回旧 Promise，却丢掉后一次保存意图。

当前 Rust 不提供字段条件版本更新。本方案防止回写未编辑旧值，但两个入口主动修改同一字段仍按现有提交顺序生效；不承诺跨入口冲突合并，不顺便引入 CAS。

### 离开时保存

prepareLeave 先将 leaving 置为 true，短暂禁止本页新编辑和新动作，再调用同一个 save 流程。已有在途保存被等待，之后补存最新 dirty。只有成功且 dirty=false 才允许离开；失败恢复可编辑状态并保留草稿。

正常保存允许继续输入，离开保存才冻结输入。若正在确认导入或原生操作，其关闭行为先由对应 modal/操作所有者处理，不能绕过它强行触发另一次提交。

## 依赖保存的操作

不再用 void 的 save-request 事件表达必须完成的前置步骤。页面直接组织动作，或向子区块提供一个明确可等待的提交函数。

~~~ts
type CommitSettings = () => Promise<SettingsSaveResult>;
~~~

| 操作 | 目标顺序 |
|---|---|
| 测试 Chat 连接 | 保存本页当前输入；失败则不测试；成功后从该次确认快照捕获端点参数并调用原测试命令 |
| 表情库重建 | 等待连接配置提交成功，再调用 regenerate_emoticon_library；结果仍属于本次任务 |
| 导出配置 | 等待保存成功，再对成功结果的确定快照应用原白名单，之后编码和导出 |
| 导入配置 | 原选择和解析 → 原确认 → 提交已验证 patch → 仅对被导入字段接受新值 |
| 打开同步面板 | 保留现有打开面板语义；不自动执行同步，也不因这是一个按钮就套上保存前置 |
| 清理缓存 | 保持已有独立操作，不保存无关表单字段 |

导出与诊断需要本次确定输入：启动动作时短暂冻结本页编辑，等待已请求保存结算后取得快照，再解除冻结并执行后续长任务。不能让导出在等待过程中悄悄混入未保存的新输入，也不能在文件导出全过程不必要地锁住表单。

导入确认应用时先独占本页动作并冻结编辑，阻止新的保存、诊断和导入，再调用 settlePending 等待已经请求的 activeSave 及其 saveRequested 批次全部结算。等待失败则中止本次应用并保留草稿；不能让旧保存循环在导入之后继续排入一个覆盖导入结果的 patch。

本页无 pending 后才提交导入 patch。成功后，acceptImport 从当前 Store 接受导入涉及的本页字段，未涉及的 dirty 字段保留；失败保留尚未被提交的编辑。最后解除动作和输入冻结。不能用新的 save() 替代 settlePending，导致原本未请求保存的其他字段被顺便提交。用户已确认的覆盖与普通外部快照更新采用不同规则。

原生选择、临时文件、取消和迟到结果仍沿 useConfigBackup/nativeFilePicker 现有生命周期；不因设置架构增加第二个文件操作所有者。正在执行的后端任务也不因页面离开被虚构为取消。

总结模型保持当前编辑触发保存、blur 兜底和模型选择后保存的用户效果，通过同一会话合并重复请求。模型选择器和相关状态在 P3 移入 AdvancedSettingsPage；重基更新不能再次被误认为用户输入而触发保存。

## 页面目录接口

~~~ts
import type { Component } from "vue";

export type SettingsPageId =
  | "identity"
  | "connection"
  | "theme"
  | "rendering"
  | "advanced"
  | "guide"
  | "about";

export interface SettingsPageEntry {
  id: SettingsPageId;
  title: string;
  description: string;
  component: Component;
  frame: "list" | "viewport" | "immersive";
}

export interface SettingsPageHandle {
  beforeLeave?: () => Promise<boolean>;
}

export interface SettingsPageProps {
  active: boolean;
}
~~~

component 在 catalog 模块级通过 defineAsyncComponent 建立稳定引用。active 表示设置可见且该页为当前活动页，供页面资源和动作生命周期使用；页面可发送 back 事件，由壳进入同一离开流程。

编辑页通过 defineExpose 暴露 beforeLeave，并调用自己的 prepareLeave。即时偏好、主题和纯展示页无需提供保存钩子。主题未应用草稿直接丢弃；已经点击应用的操作继续由主题所有者完成，不因离开页面反向回滚。

目录不保存 beforeLeave 函数，钩子属于当前组件实例。异步组件未加载时允许取消该次访问；页面明确加载失败时显示重试或返回，不让旧页面 ref 被当作新页面的钩子。

## 返回和隐藏协议

壳只维护当前子页、退场展示页、访问序号、加载状态和一个离开 Promise。它不维护另一份全局 modal 栈。

useModalHistory 只接受同步 boolean 或 void。存在异步保存的页面必须这样桥接：

~~~ts
registerModal(SUBPAGE_MODAL_ID, () => {
  void requestLeave();
  return false;
}, () => subpageSurface.value);
~~~

该示例只用于具有 beforeLeave 的异步分支，且完成关闭必须发生在本次回调返回 false 之后。无钩子分支同步关闭时应返回 true 或 void；不能同步注销后仍返回 false，否则 popstate 会补回已关闭的 entry。即使当前没有 dirty，异步分支也要先结束同步否决回调，再结算关闭。

requestLeave 的契约：

1. 头部返回、硬件返回、Escape 和页面 back 都调用同一入口。
2. 无保存钩子的已挂载页面可同步退出；有钩子的页面同步否决本次 modal 关闭，启动单次离开过程。
3. 等待钩子成功后，检查设置仍可见、页面 ID 和访问序号仍匹配，再清除当前子页。
4. 子页清除通过单一关闭路径调用 unregisterModal；失败保留页面和 history entry。
5. 浏览器返回时，返回 false 会使现有 ModalHistory 补回 entry；不要再手写 pushState。
6. 离开期间忽略重复返回；嵌套 ModelSelector、确认框等仍由现有栈先消费。
7. 只有从设置首页关闭，才向 FeatureOverlays 发 close。将来的直接关闭全设置入口也必须先结算活动页。

SettingsView 常驻，因此在 isOpen=false 时必须立即注销子页 modal、作废访问序号、阻止迟到导航并令 active=false。退场内容可保留到实际 transition 完成；清理时再次核对访问序号，避免旧动画回调销毁新打开的页面。

active=false 同时通知本页已有操作所有者，立即关闭 ModelSelector、AvatarCropper、导入确认等局部覆盖层，并清理其所属 modal；未交付 picker 作废该次访问并调用既有取消清理。不能等退场卸载后才处理，否则迟到结果可能在设置已经隐藏时打开裁剪层。复用现有文件操作清理函数，不建立第二份原生操作状态。

编辑会话在每次访问时建立，在成功离开或强制隐藏时 dispose；常驻的 SettingsView 不复用已经结束或 leaving=true 的旧会话。这一语义从 P2 就成立，P3 只迁移其挂载归属。

优先使用对应 transition 的 after-leave 清理；如果当前外层组件不能通知完成，再做精确的完成事件补充，不能新增另一套不一致的动画计时器。关于页背景在隐藏时停止活跃工作，保留退场画面所需资源后再释放。

外部 popToRoot、应用收尾或强制隐藏不走可等待保存协议。隐藏 watcher 和 onUnmounted 只清理，不启动保存；尚未提交的本页草稿随该次访问释放。已提交操作可完成，但不得重新打开旧页面或关闭新页面。

# 设置架构 Magi 审议与后续扩展

用户认可的方向是领域拥有设置、设置中心组织入口、共享基础负责可靠读写。以下记录三方审视对具体方案的取舍，作为实施时判断改动尺度的依据。

## Melchior 逻辑与系统

核心判断：现有 Rust 配置链路已经承担真正的串行化、持久化与运行时协调。前端重构应在这些边界之上收窄编辑范围，不能用 localStorage 或页面 watch 替代它。

采纳：

- 迁出聊天偏好，保留既有 key、同步恢复和先持久化后发布语义。
- 设置数据库继续使用现有顶层 patch；领域化通过明确字段类型和编辑会话实现。
- 以 pending 和 editRevision 保护保存期间的输入，以 saveRequested 保存后一次显式意图。
- 记录同字段主动竞争的能力边界，不把字段草稿重基描述为通用冲突解决。
- 异步返回通过现有同步 false 桥接，避免 Promise 被误认为允许退出。

风险取舍：不引入全局 revision/CAS、不增加新的 IPC、不拆数据库。若未来出现真正需要跨入口条件更新的产品需求，再以对应调用链设计。

## Balthasar 直觉与美学

核心判断：用户需要知道一次点击是在即时修改、编辑草稿还是执行操作；开发者需要知道该状态属于谁。统一控件不能抹平这些差异。

采纳：

- 用户分类可以汇集不同所有者的设置，不因此合并数据模型。
- 主题继续预览后应用，返回直接丢弃未确认预览；即时偏好返回无额外保存。
- 编辑配置失败保持当前页面和草稿，避免看起来已经完成。
- 设置壳、列表滚动、主题可用区域和沉浸关于页具有有限、明确的布局类型。
- 共享开关具备合适触控范围和语义，页面不再重复外包交互按钮。
- 正常离开与外部隐藏分开处理；常驻组件不能依赖卸载作为唯一清理信号。

风险取舍：不承诺一个页面无限扩容，不显示未来预留开关。内容增长时可以根据用户任务分组或增加专用页面，保持高密度线性表达。

## Casper 务实与交付

核心判断：应直接减少实际扩展阻力，同时限制重构引入的新概念。当前 settings Store 主要承担串行 IPC，并不是必须拆除的大对象。

采纳：

- 先完成聊天偏好纵向切片，再建立保存契约，最后搬动页面装配。
- 薄页面目录替代分类与模板分支的重复维护，但不建立万能表单 DSL。
- 只在第二个实际领域接入时提取公共 IO；自动检查更新提供这个有界实例。
- ThemePicker 保留原路径，现有原生操作和后端配置层保持，避免为目录对称进行无收益搬迁。
- 通过真实的消费行为和失败时序验收，不按创建了多少层、多少接口衡量成果。

风险取舍：P4 只收口自动检查布尔偏好，不顺带重写 OTA；新触感、折叠、搜索、同步都不绑定为本次完成条件。

## 综合决定

| 议题 | 本方案选择 | 原因 |
|---|---|---|
| 所有设置一个总 Store | 按真实所有者组织 | 避免第二个全局配置与生命周期混合 |
| 全部偏好单 key | 保留当前 key，按领域决定后续格式 | 单 key 本身不带来可靠性，当前无迁移收益 |
| 通用 setPreference | P1 保留既有领域 setter | 先稳定语义，未来重复模式出现再提炼 |
| 页面自动生成 | 薄目录加普通组件 | 现有复杂主题、诊断和备份有专用交互 |
| 配置草稿 | 明确字段会话和用户编辑记录 | 防止旧全量草稿无意覆盖 |
| 返回栈 | 复用同步否决与局部异步桥接 | 处理真实协议差异，避免全局导航重写 |
| 导入与在途保存 | 冻结输入，先结算已请求保存，再导入 | 防止旧保存批次在导入后覆盖新值 |
| 关于页背景 | 保留独立常驻宿主，内容按访问释放 | 保持既有 idle 编译和背景保活，不把 chunk 预载当作 GPU 预热 |
| 本地 IO 公共化 | P4 由两个实际领域驱动 | 限制抽象范围，保留领域解码规则 |
| 搜索或同步 | 后续需求单独接入 | 两者都有额外产品和生命周期语义 |

这些是本方案的具体实施建议，不代表新增产品功能已获实施授权。本次用户授权范围是制定并保存方案。

## 后续新增普通偏好的接入方式

以一个已明确产品行为的聊天偏好为例：

1. 在聊天 model 中定义类型、默认值和合法值；明确它表达用户意图还是实际运行状态。
2. 在领域 storage 和 Store 中建立可靠读写；已有用户数据受影响时提供明确迁移。
3. 在 ChatPreferencesPage 中放入对应分组，调用领域修改入口。
4. 在真实消费者中应用偏好，保留该功能已有的生命周期和运行条件。
5. 针对最可能失败的行为验证，例如写失败、双入口、流结束或重新挂载。

正常情况下不修改 ThemePicker、theme Store、SettingsView 或 Rust 配置。如果新字段实际由 Rust 消费，则使用现有 Rust 配置链路，而不是为了套用示例把它放入前端存储。

## 回复触感接入范例

未来明确新增回复完成触感时，需要先确定“完成”的业务事件、适用消息范围、默认值，以及现有发送和长按触感是否独立。当前报告中的默认 true 不能当作已批准产品决定。

偏好归聊天领域；触发时机归现有聊天完成路径；设备执行归实际平台能力边界。设置组件只表达和修改偏好，不能监听流结束后自行调用原生能力。

不为这一范例新增统一能力门禁、全局事件总线或另一份流完成状态。跨平台实现沿 docs/CROSS_PLATFORM_DEVELOPMENT.md，不能仅凭一个浏览器 API 存在就宣称两平台设备行为已验证。

## 工具折叠接入范例

未来新增流式工具折叠时，建议行为优先级为：

~~~text
用户对本块的明确展开或收起
    优先于当前阶段的自动默认策略
    再使用既有历史消息默认行为
~~~

偏好归聊天领域，人工选择归消息块交互状态。自动策略不能在流结束时收起用户正在查看的内容。实现前必须核对真实 block key、流式到稳定块的身份连续性以及默认值 watcher，不能只加一个 computed。

人工展开是否跨卸载保留、默认折叠是否作用于历史消息、开启后是否立即影响当前消息，属于该功能实施时需要明确的产品语义；它们不阻塞本次架构重构。

## 设置搜索与直接定位

当实际规模需要搜索时，可在已有页面 ID 上增加稳定条目 ID、关键词和定位目标。搜索只索引可导航信息，不持有配置副本，不在搜索时挂载全部页面或初始化业务。

当前页面目录不提前增加 unused keywords、权限表达式或字段 schema。真正有搜索消费者时再扩接口。

## 偏好同步与备份

保存到本机不自动意味着适合跨设备同步。排版、触感、更新、账号连接和运行记录具有不同语义；后续应逐项决定同步范围、覆盖规则和设备差异，再接现有同步所有者。

当前 .vcpcfg 仍是身份与连接配置备份。扩大到用户偏好需要明确版本和恢复范围，不通过本次目录重构隐式扩大。

## 后续设计评估标准

新增普通聊天偏好时，改动集中在聊天偏好定义、设置界面和实际消费者；主题、全局导航和无关业务配置不跟随修改。遇到复杂操作时，仍能指出唯一状态所有者、提交点、失败结果和清理路径。

只有真实需求突破这些边界时才扩大架构。一个通用接口无法准确描述现有行为时，优先保留清晰的领域接口，不通过新增隐藏规则维持表面统一。

# 04. 生命周期、后台、网络与同步策略

## 1. 核心裁决

iOS 不能复制 VCPMobile 当前 Android 的 Foreground Service、`:helper` 进程和 Wake/Wi-Fi Lock，但 iOS/iPadOS 26 提供了更接近本需求的公开能力。冻结目标是：

> **iOS/iPadOS 26 及以上，对用户主动发起的生成尝试 `BGContinuedProcessingTask`，由同一个 Rust SSE owner 尽力继续；系统拒绝、用户取消、资源回收或更早系统版本时，明确回退为“保持应用前台 + 生成期间屏幕常亮”。服务端不改造，因挂起而断开的请求不能伪装成可恢复。**

这仍不是“病毒级强保活”保证。它把能用的系统持续处理机会用到最大，同时让失败语义诚实、UI 有明确下一步，并避免用私有 API 或虚假进度欺骗系统与用户。

## 2. Apple 平台事实

Apple 的公开模型有五个关键边界：

1. 普通 App 进入后台后通常会被挂起；后台模式必须对应明确用途；
2. iOS/iPadOS 26 的 `BGContinuedProcessingTask` 面向用户发起、希望即刻开始并可继续较长时间的工作，可使用网络与 CPU；
3. 系统仍拥有 admission、调度、用户取消与资源终止权；任务必须报告真实 `Progress` 并处理 expiration，零进度或缺少进展的任务可能被降低优先级；
4. `beginBackgroundTask` 只为收尾提供有限、不可保证的延长时间，不是常驻许可；
5. background `URLSession` 适合系统管理的文件上传/下载，不会让任意 data task、SSE 或 WebSocket 永久运行。

依据：

- [Choosing Background Strategies for Your App](https://developer.apple.com/documentation/backgroundtasks/choosing-background-strategies-for-your-app)
- [Performing long-running tasks on iOS and iPadOS](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados/)
- [BGContinuedProcessingTask](https://developer.apple.com/documentation/backgroundtasks/bgcontinuedprocessingtask)
- [Configuring Background Execution Modes](https://developer.apple.com/documentation/Xcode/configuring-background-execution-modes)
- [URLSession](https://developer.apple.com/documentation/foundation/urlsession)

因此不得通过声明 audio/location/remote-notification 等 background mode 来伪装持续 SSE。未走 App Store 也不会改变这些操作系统调度规则。

## 3. 当前 Android 假设

[lifecycle_controller.rs](../../src-tauri/src/vcp_modules/infra/lifecycle_controller.rs) 当前进入后台后：

- 为 VCP Log 申请原生 foreground lease，并保留约 10 分钟；
- Distributed 保留约 5 分钟；
- 依赖 `ForegroundGuardian`、前台服务和 Android 进程生存语义；
- 回前台后取消 linger，并按断连标记恢复。

该 owner/epoch 设计值得保留，但时间承诺和原生 lease 不适用于 iOS。当前 `acquire_foreground_inner` 在非 Android 还会无操作返回 `Ok(())`，这会让 Rust 误以为保护已建立，必须先消除。

## 4. 推荐生命周期状态机

Swift 只聚合 scene/application 事实并管理 Apple task token；Rust lifecycle epoch 和 Chat attempt 仍是唯一业务 owner。`sceneWillResignActive` 可能只是控制中心、系统权限框或其他短暂打断，绝不能等同 `sceneDidEnterBackground`。Chat 与 Sync/Distributed 使用不同后台策略，lifecycle coordinator 不能再“一刀切”取消所有域。

```text
startup
  -> Rust 先订阅 native event
  -> 再读取 NativeLifecycleSnapshot(sequence, aggregate_state)
  -> 按单调 sequence 对账，补 listener 安装前的事件

ACTIVE(no generation)
  │ sceneWillResignActive
  ▼
INACTIVE
  ├─ 暂停 UI 动画/高频渲染
  ├─ 不破坏性取消 Chat/Sync/Distributed
  ├─ sceneDidBecomeActive ────────────────> ACTIVE
  └─ all scenes didEnterBackground
       ▼
BACKGROUND_CLOSING(rust_epoch, native_sequence)
  ├─ 冻结新 Sync/Distributed 工作
  ├─ 无 continued task 的 Chat：cancel + settle interrupted
  ├─ Sync generation invalidate + cancel + session join
  ├─ Distributed stop + child join
  └─ Rust 回执 closing outcome
       ▼
SUSPEND_SAFE
  │ sceneDidBecomeActive
  ▼
FOREGROUND_RECONCILING(new rust_epoch)
  ├─ 重新读取 native snapshot / 权限 / 网络 / capability
  ├─ 保留 completed/cancelled/interrupted 真实终态
  ├─ 服务端无 cursor，不自动假恢复
  └─ 不复活用户已手工停止的任务
       ▼
ACTIVE

用户在 ACTIVE 发起 Chat generation
  ├─ iOS/iPadOS 26+：提交 continued-processing request（优先 immediate/fail admission）
  │    ├─ accepted → CONTINUED_ACTIVE(attempt_id, rust_epoch, native_task_id)
  │    │    ├─ 前台：屏幕常亮；同一 Rust SSE 正常消费
  │    │    ├─ 后台：Chat 继续；Sync/Distributed 仍按上文收口
  │    │    ├─ completed/user cancelled → exact-once terminal + complete task
  │    │    └─ expiration → cancel Rust attempt + continued_task_expired；无回调强杀由下次启动 ledger 对账
  │    └─ rejected/unavailable → FOREGROUND_REQUIRED
  └─ iOS/iPadOS <26 → FOREGROUND_REQUIRED
       ├─ 保持主界面与屏幕常亮
       └─ 真进入后台 → cancel + interrupted；回前台允许显式重试
```

MVP 推荐不启用多窗口 Scene。若后续启用，native aggregate 必须按进程聚合：任一 scene active 则为 active；存在前台但无 active scene 则为 inactive；只有所有 connected scene 都在后台/断开时才进入 background closing。单个 iPad 窗口退后台不得关闭仍在使用的另一个窗口。

### 4.1 两类 Apple task 的回执协议

必须区分两个不可互换的 API：

- `BGContinuedProcessingTask`：仅 iOS/iPadOS 26+ 的用户发起生成续跑；拥有独立 task identifier、`Progress`、cancellation/expiration 和 completion；
- `UIApplication.beginBackgroundTask`：只给没有 continued task 的域做有界收尾，绝不能续跑整个 Chat。

单向 lifecycle event 不足以保证 token 被正确结束。冻结以下双向、epoch 化协议：

1. 发起生成时 Swift 先按系统版本尝试提交 continued request，并把 admission/identifier 绑定到 Rust `attempt_id + epoch`；提交失败立即返回 `foreground_required`，不能空操作成功；
2. task handler 获得系统 task 后只启动/附着既有 Rust attempt，不创建 Swift SSE client；若 attempt 已结束，立即完成 task；
3. Rust 每次真实 delta/usage/terminal 更新共享 `ProgressSnapshot`；Swift 只把快照映射给系统 `Progress`；
4. 正常完成、用户取消、Rust cancel 和 expiration 都经同一个 compare-and-complete owner exact-once 结束 task；旧 epoch/重复回调幂等忽略；
5. 没有 continued task 时，Swift 在聚合状态进入 background 获取短收尾 token，发送 `background_closing(sequence, deadline)`；Rust 收口各域并回执后 exact-once `endBackgroundTask`；
6. scene 重新 active 时创建新 Rust epoch；仍在运行且 task 有效的 Chat 继续，已过期/已中断的 attempt 不被复活。

Swift 持有的是系统 token，不是 Chat/Sync/Distributed session。所有 completion/expiration path 都必须释放 token；用户从系统界面取消 continued task 时必须取消对应 Rust attempt。

必须保持的并发不变量：

- 新 epoch 使旧 transition 失效；
- 各域在自身 owner 内先失效 generation/attempt，再 cancel，再 join/settle；
- commit 前重新检查 generation；
- terminal/deleted 不回退 pending；
- native snapshot/event sequence 与 Rust epoch 均单调，启动、WebView reload 和多事件可对账；
- background expiration、closing 回执与正常 foreground 回调幂等；
- Swift 不持有业务 session，不单独重连。

## 5. Chat 流式策略

### 5.1 MVP：iOS 26 尽力续跑 + 前台常亮回退

当前 [vcp_client.rs](../../src-tauri/src/vcp_modules/infra/vcp_client.rs) 已有单 attempt 的 UUID ownership、oneshot abort sender、RAII 删除、active-generation DB ledger 和前台 reqwest 流，但没有生命周期批量 cancel、`JoinHandle`、drain 回执或 deadline。服务端明确不可改，第一阶段冻结为：

- 前台保持现有 30 Hz 合帧、AST diff、partial/final contract；
- 在既有 owner 内增加 `cancel_all_for_lifecycle(epoch, deadline)` 与 join/settle receipt；
- iOS/iPadOS 26+ 在请求开始时提交 continued-processing task，accepted 后继续消费同一个 Rust reqwest stream；
- task expiration、用户取消或可观察的系统回收时，保存 partial 并持久化精确 terminal reason；进程无回调被强杀时只能依靠已持续落盘的 partial/active ledger，在下次启动写 `process_terminated_or_unknown`，不能伪造已执行 cancel；
- submission rejected、系统版本不足时，UI 明确提示“生成期间请保持本页打开”，并通过现有引用计数 owner 设置 `UIApplication.isIdleTimerDisabled`；
- 用户主动取消、生成 terminal、路由离开或 App 退出生成态时必须释放 screen-keeper；它只防自动锁屏，不增加后台 CPU/网络资格；
- 服务端无 cursor/helper cache，连接一旦断开只能标记 `interrupted` 并允许用户显式重试，不写 `recoverable` 承诺；
- 现有 `checkAndRecoverInterruptedStreams` 可保留为终态协调入口，但 iOS 不能制造不存在的 helper cache。

### 5.2 真实进度与系统契约

当前 stream 只稳定解析 `choices[].delta.content`，没有每个 delta 的真实 token usage。`max_output_tokens` 是最大输出预算，不是模型最终会生成多少 token，因此 `received / max_output_tokens` **不得命名为完成百分比**。

系统会把 continued task 的 title/subtitle/progress 显示在 Live Activity，并允许用户在那里取消；即使产品 UI 不需要百分比，也必须满足这份系统契约。冻结映射规则：

- 若协议提供可信的累计输出 token：系统 `Progress.totalUnitCount = max_output_tokens`、`completedUnitCount = min(received_tokens, max_output_tokens)`，文案只能写“已接收 N tokens / 输出上限 M”，不能写“完成 X%”；
- 若没有可信 token 计数：保持 `totalUnitCount=0`、`completedUnitCount=0`，使 Foundation 判定为 indeterminate；用 task subtitle 与应用内 UI 显示真实的字符数、UTF-8 字节数、delta/chunk 数与最后活动时间，不伪填 unit；
- 只有收到服务端 terminal SSE 并完成本地 commit 后才切换为 completed/100%；
- 不用定时器递增、不注入假 token、不用流逝时间伪造心跳；只有真实网络 delta、usage 或 terminal 才更新 activity；
- 若长时间无真实进展，可以显示“仍在等待服务器”，但不得假装任务有进度；系统若因此降低优先级是平台事实，不以造假规避；
- 系统取消回调与 App 内取消按钮进入同一个 Rust abort owner，最终状态均可追溯。

Apple `Progress` 支持 indeterminate 语义，参见 [Progress.isIndeterminate](https://developer.apple.com/documentation/foundation/progress/isindeterminate)。

### 5.3 服务端不变的直接后果

原先建议的 request ID/cursor/result-retention/APNs 恢复协议不进入本项目：服务端不可改、APNs 不做。于是必须接受：continued task 失效或进程被杀后，客户端既不能取回遗漏 delta，也不能证明服务器最终状态；本地 partial 必须以 `interrupted`/`continued_task_expired` 终结，用户显式重试可能产生新的服务端生成。用户从 app switcher 关闭 App 时，系统会取消 continued task，且应用收不到取消通知，只能在下次启动从 ledger 推断未正常结束。UI 应在重试前说明这一点。

### 5.4 明确不做

- 不把 Android `SseProxyService` 翻译成 Swift singleton；
- 不在 extension 或 notification service 中跑 Chat owner；
- 不依赖静默推送保证实时性；
- 不用 `BGAppRefreshTask`/`BGProcessingTask` 轮询长对话；continued task 只对应用户实际发起的当前生成；
- 不让 partial 消息在恢复时重复落库。
- 不声称用户强杀、系统重启、续签到期或 task expiration 后还能继续。

## 6. Sync 策略

[sync_service.rs](../../src-tauri/src/vcp_modules/sync/sync_service.rs) 已具有 session generation、CancellationToken、JoinHandle、write drain 和 owner commit lock，这些是 iOS 适配的优势。

### 第一阶段

- Sync 只在前台启动；
- 聚合状态进入后台后调用内部 `stop_sync_inner(deadline)` 一类 owner，不经 lifecycle 反调 Tauri command wrapper，也不保留 5/10 分钟假设；
- 目标关闭不变量为 generation invalidation → cancellation → producers 退出 → flush 已接受写队列 → await session → cache invalidate；这是需固化的内部协议，不是当前已经完全显式分层的调用序列；
- 回前台只恢复“设置启用且没有用户 stop intent”的 session；
- 将 loopback 诊断从 `is_android` 改为通用 `is_mobile`，iOS 也不能用 `127.0.0.1` 指向电脑。

现有 lifecycle controller 在 Distributed 已启用但 idle 时会提前 `return`。改造后唯一 coordinator 必须顺序调用 Chat、Sync、Distributed 等域并收集 outcome；任何单域都不得提前结束整个 transition。

### 后续候选

- 小型、幂等的后台文件 transfer 可分离给 background URLSession；
- Sync 协议正文、差异计算和 SQLite commit 不应迁入 Swift；
- BGTaskScheduler 只能做系统择机、短时、可取消的维护，不能作为准时同步 SLA；
- 每个后台入口必须在 expiration 时安全中止并可从 hash/session receipt 继续。

## 7. Distributed 策略

当前 [distributed/client.rs](../../src-tauri/src/distributed/client.rs) 有 session cancel 与 child task join，但还无条件注册 Android/sysfs 工具，并把非 Android wake lock 变成空操作。

首个实验产物不启动 Distributed；capability 写为 `support=supported/degraded`（按具体工具）、`implementation=not_implemented`、`runtime.policy=foreground_only`，而不是返回 mock 设备。未来若启用才执行：

- 前台建立 WebSocket；
- capability 过滤后注册工具；
- scene background 立即停止 session，close writer，等待 child tracker；
- 回前台按设置与 generation 重建；
- server 看到明确 offline，不继续向 suspended device 派发工具；
- 未授权 location/motion 不上报；Root/通知监听永不上报。

如果业务要求 iPhone 长期充当无人值守分布式节点，则与 iOS 调度模型冲突，应判 `NO-GO`。continued-processing task 只服务用户发起的当前生成，不扩大为 Distributed 常驻资格。

## 8. 网络状态与恢复

Swift 可用 `NWPathMonitor` 上报 path 变化，但它表达“当前路径是否可用/昂贵/受限”，不保证业务 endpoint 已连通。参见 [NWPathMonitor](https://developer.apple.com/documentation/network/nwpathmonitor)。

推荐事件 DTO：

```text
path_status: satisfied | unsatisfied | requires_connection
interface: wifi | cellular | wired | other | unknown
is_expensive: bool
is_constrained: bool
reason: nullable
observed_at
```

Rust 收到 network-restored 事件后仍要通过真实连接验证，不把 path satisfied 当成 VCP server reachable。

## 9. Local Network 与 ATS

VCPMobile 支持用户输入受信 LAN 的 HTTP/WS 地址。这在 iOS 同时触发两套边界：

### Local Network privacy

- Info.plist 必须有 `NSLocalNetworkUsageDescription`；
- 首次实际局域网访问可能弹系统授权；
- 后台且权限仍未决定时，系统可能直接拒绝而不弹窗；
- 没有可靠的通用“预查询并弹窗” API，应从实际 connection 状态和错误表达；
- 用户拒绝后提供系统设置引导和清晰 blocking reason。

TN3179 同时指出，直接源自 `WKWebView` 的流量不要求 Local Network privilege；但本项目核心 Chat/Sync/Distributed 连接主要由 Rust/native 网络栈发起，不能用该 WebKit 例外跳过用途说明与真机测试。任何未来把请求在 WebView 与 Rust 之间迁移的改动，都必须重新判定权限、ATS、CORS 与 owner，不能只为绕过提示改变网络 owner。

依据：[TN3179: Understanding Local Network Privacy](https://developer.apple.com/documentation/technotes/tn3179-understanding-local-network-privacy) 和 [NSLocalNetworkUsageDescription](https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSLocalNetworkUsageDescription)。

### App Transport Security 与 Rust 传输策略

- 默认优先 HTTPS/WSS；
- `WKWebView`、`URLSession` 等 Apple URL Loading 路径受 ATS/Info.plist 配置治理，不使用全局任意明文开关；
- Rust `reqwest/rustls`、`tokio-tungstenite`/socket 是否受某个 ATS 例外控制不能想当然，应由 Rust 自身 scheme/TLS allowlist fail-closed，并在最终 Apple binary 验证；真机状态保留为社区未验证；
- 如保留受信 LAN HTTP/WS，分别为 WebKit/URLSession 与 Rust transport 设计最窄策略，不能以一个 ATS key 声称覆盖所有路径；
- Local Network privacy 与 ATS/TLS 是独立维度；UI 明确标记明文 LAN 风险，不把 internet host 误放行；
- 实验产物说明解释用途、用户控制、transport 和数据范围；若未来转正式分发再另建审核材料。

依据：[Preventing Insecure Network Connections](https://developer.apple.com/documentation/security/preventing-insecure-network-connections) 和 [NSAppTransportSecurity](https://developer.apple.com/documentation/bundleresources/information-property-list/nsapptransportsecurity)。

## 10. Loopback 高速上传

当前非 Android 大文件路径会启动 `http://127.0.0.1` 临时服务，让 WebView 将正文以 64KB 流写入 Rust。它有较好的内存边界，但 iOS 仍需验证：

- WKWebView 对 loopback HTTP 的加载与 CORS；
- WebKit/URLSession ATS 与 Rust loopback scheme policy 分别如何作用；
- WebKit 流量的 Local Network 例外与 Rust/native endpoint 权限不能混为一谈；
- app suspend 时服务器/上传如何取消；
- 端口冲突、过期 ticket、重放和来源校验；
- 大文件过程保留现有字节/磁盘硬上限；iOS memory pressure 不做发布认证；
- iOS Simulator 与真机表现是否一致。

在 E3 证据前只能标记 `CANDIDATE`，不能假定 non-Android 路径天然兼容 iOS；E4 社区报告可补充，但不是产物发布门禁。

## 11. 失败语义

所有后台/网络结果至少区分：

- `completed`：服务器与本地 commit 都确认；
- `cancelled_by_user`：用户明确取消；
- `continued_task_rejected`：iOS 26+ 本次未获系统接纳，必须保持前台；
- `foreground_required`：系统版本或当前资格不支持后台续跑；
- `continued_task_expired`：系统终止已运行的 continued task，本地 partial 已收口；
- `background_suspended`：没有 continued task 时进入后台导致平台中断；
- `expired_before_close`：expiration handler 来不及完整收口；
- `network_lost`：网络失败；
- `unsupported_by_platform`：iOS 无能力；
- `unsupported_by_product_scope`：平台可能存在 API，但本实验产物明确砍掉该能力。

不要把“App 被挂起”归类成普通网络错误，也不要把空操作 lease 记成成功。服务端不可查询时不得写 `server_continues` 或 `recoverable`。

## 12. 验证门禁

### 纯代码可验证

- lifecycle 乱序 epoch；
- continued task admission/expiration/cancel 与 Rust attempt 的 exact-once 映射；
- foreground fallback 的 screen-keeper 引用计数与释放；
- 无 continued task 时的 background cancel+join；
- expiration 与 foreground race；
- partial/terminal 不回退；
- Sync stop 后无迟到 DB commit；
- Distributed child 全部 join；
- 真实 progress snapshot：无 token usage 时 indeterminate，有 token 时只表达 budget usage，terminal 才 completed；
- capability 过滤和 mobile loopback 诊断。

### Simulator 可验证

- Swift scene event → Rust → Vue round-trip；
- native scene event/snapshot sequence、Rust epoch 与 UI 响应；仅证明事件路径，不证明真实挂起或后台时限；
- iOS 26 availability guard、continued request/handler round-trip、系统取消映射；Simulator 结果不证明真实调度时长；
- NWPath event；
- HTTPS/WSS 和 loopback 基础连接；
- foreground Chat/Sync 旅程；Distributed 当前只验证 capability 不注册。

### 社区真机可补充、但不阻塞实验产物

- Local Network prompt/denial/retry；
- Wi-Fi/蜂窝/IPv6-only/VPN/热点切换；

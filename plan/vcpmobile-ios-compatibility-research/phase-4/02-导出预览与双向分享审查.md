# Phase 4：导出、预览与双向分享重构方案

> 2026-10-16，覆盖 P4-3 / P4-4，方案草案尚未实施。本文定义系统操作、文件寿命和跨进程持久交接；源码导航基线为 `7e4d645b`。范围依据 [路线图](../08-分期实施路线图与验收门禁.md)、[D8/D9/D12/D18](../09-Magi综合裁决与待决策清单.md) 和 [功能审批](../phase-2/09-功能权限与提示审议表.md)。

## 1. 目标体验与待定选择

用户导出配置或邮件附件时，在 Files 中选择目的地；查看文档时进入只读 Quick Look；分享同步日志或附件时选择系统分享目标。这三种操作各自有明确结果，由主 App 完成，不需要 Share Extension 或 App Group。

用户从其他 App 分享文字、链接或文件时，Share Extension 将内容保存到 App Group 收件箱。随后打开 VCPMobile，选择 Agent、查看预填内容并发送。扩展负责取得内容，主 App Rust 负责持久接收、附件登记和会话提交，Vue 负责选择、编辑与结果反馈。

**需要用户选择的主要差异是：是否接受“系统分享中保存 → 用户打开 VCPMobile → 选 Agent”的两段流程。** Apple 官方工程师说明 Share Extension 没有受支持的直接启动包含 App 的路径。不能将 `NSExtensionContext.open`、遍历 responder chain 或 URL scheme 写成可靠的自动唤起保证。自签目标没有 App Store 审核要求，也没有因此获得系统启动保证。[Apple Frameworks Engineer 说明](https://developer.apple.com/forums/thread/773342)

| 待定项 | 方案建议 | 用户可感知的影响 |
|---|---|---|
| 分享后如何进入会话 | 扩展提示“已保存，打开 VCPMobile 后继续”；主 App 启动/回前台取件 | 需要用户自行打开 App；这是本方案最主要的体验选择 |
| 多批分享如何处理 | 按接收次序逐批选择 Agent；关闭表示稍后处理，提供明确“丢弃”动作 | 内容不会因又分享一次而覆盖；未完成批次可从轻量待处理入口继续 |
| 部分文件失败 | 显示失败项并允许重试；用户可明确选择只继续文本与成功项 | 不自动省略附件，也不要求一个失败文件阻断所有已取得内容 |

这些是交互选择，不要求新增通用任务平台。其余技术边界可按本文实施建议推进，用户未批准实施前只记录方案。

## 2. 主 App 中的操作与结果契约

| 用户操作 | 系统呈现与处理 | 返回给页面的结果 |
|---|---|---|
| 导出配置 | 保存用户已编辑的配置，生成 `.vcpcfg` 工作文件，打开 Files 目的地选择 | 保存成功显示实际文件名并保留明文密钥提示；取消回到原页 |
| 保存邮件附件 | 邮件领域完成下载并生成受控文件，随后打开 Files | 下载错误与导出错误分别反馈；用户取消导出不报下载失败 |
| 查看附件 | 图片/文本使用相应查看器，适合 Quick Look 的文档以只读副本呈现 | 关闭返回原会话；不能预览时提供分享或导出动作 |
| 分享同步日志/附件 | 准备本次工作副本，系统活动面板选择目标 | 记录活动完成、取消或具体错误；不推断第三方的上传/接收结果 |

三项原生操作各自返回有消费者的结果，不压成一个成功布尔值。接口字段以实现时命名为准，建议契约如下：

```text
exportFile(operationId, ownedFile, anchor?)
  → saved { displayName, mimeType, size, destinationLabel? } | cancelled

previewFile(operationId, ownedFile, anchor?)
  → closed | cannotPreview

shareFile(operationId, ownedFile, anchor?)
  → completed { activityType? } | cancelled

cancelPresentation(operationId)
  → request accepted；最终结果仍由原操作返回
```

`ownedFile` 是主 App 已验证、为该操作持有的本地文件描述，不是 provider 临时 URL 或大块字节数组。真实 IO/provider/呈现故障返回操作错误。`operationId` 贯穿文件准备、展示、取消和清理，页面离开后迟到结果只释放本次资源，不回填另一页面。

文件预算按配置、邮件、附件各自的产品用途统一制定，覆盖下载/准备、复制和导出完整链。具体最大字节数、批量数量和空间余量随 P4-1 预算收敛，所有层按同一用途预算接收与处理文件。

## 3. P4-3 推荐实现

### 3.1 Files 导出

使用 `UIDocumentPickerViewController(forExporting: [ownedURL], asCopy: true)`。配置序列化和邮件下载分别在所属业务入口完成；Rust 准备受控工作文件，Swift 只接收文件描述和呈现参数。内容按路径交接，数据解码与复制计入同一次操作预算。[Apple 导出构造器](https://developer.apple.com/documentation/uikit/uidocumentpickerviewcontroller/init(forexporting:ascopy:))

面向 Vue 的结果表达 `saved` / `cancelled`，只有 `saved` 才携带实际文件名、MIME、字节数及可选目的地说明。成功表示用户选定目的地的导出操作完成；iCloud/File Provider 返回位置不作为长期访问凭证，也不据此报告云端同步完成。

主 App Swift 持有 picker、delegate 和 Invoke 到最终回调，结束后向 Rust 请求释放该 operation 的工作文件。展示失败、用户取消、provider 错误和显式取消最终只结束一次；交互取消回到页面，错误由发起页面反馈。临时文件的清理不依赖页面仍然挂载。

### 3.2 Quick Look 与“其他应用打开”

为附件建立保留原文件名的只读预览副本，复制失败不呈现；使用 `QLPreviewController.canPreview` 判断实际支持情况，编辑模式设为 disabled。副本保持到控制器结束再释放，磁盘预算计入这一份复制；CAS 原件不被编辑或移动。[Apple Quick Look 支持范围](https://developer.apple.com/documentation/quicklook)、[编辑模式](https://developer.apple.com/documentation/quicklook/qlpreviewcontrollerdelegate/previewcontroller(_:editingmodefor:))

无法 Quick Look 预览时，返回 `cannotPreview`，页面保留附件并提供“分享给其他应用”和“导出到文件”。图片、文本与消息内 HTML 继续由对应查看器呈现，文档外部交接通过系统活动面板完成。

### 3.3 Outgoing share、结果与资源释放

`UIActivityViewController` 传递文件 URL，避免将整个日志/附件转成 `Data` 后跨层重复缓冲。面板的 `completionWithItemsHandler` 区分用户取消、系统/活动错误和所选活动完成；“活动完成”不等于第三方已上传成功或对方已读。[Apple completionWithItemsHandler](https://developer.apple.com/documentation/uikit/uiactivityviewcontroller/completionwithitemshandler-swift.property)

系统面板显示期间保持工作文件可读，最终 callback 到达后释放。原同步日志、CAS 附件和配置来源不属于该操作的清理范围。取消静默返回；所选活动完成时可反馈“已交给所选应用”，错误说明实际活动失败。呈现成功只用于退出 loading，不提前报分享完成。

### 3.4 iPad、Scene 与异步调用

Files、Quick Look、活动面板共用一个主队列 presentation owner，关联实际 `WKWebView.window.windowScene` 和可展示控制器。每次操作依次经历 `preparing → presenting → waiting → finished`；重复请求返回 busy，显式取消按 operation ID 定位正在准备或呈现的那一次。这个 owner 同时供 P4-1 picker 使用。

iPad 活动面板必须配置有效 popover 锚点。调用按钮能给出矩形时传点击瞬间的 `getBoundingClientRect()` 与视口坐标信息，由 Swift 转换到当前 WKWebView / sourceView 的 points；不能把 CSS px 乘设备像素比。旋转、分屏、键盘或页面滚动导致矩形失效时，在当前可见 WebView 的有效区域使用明确的保底锚点。若入口已经卸载，不能继续用陈旧 DOM 位置。[Apple popover 定位规则](https://developer.apple.com/documentation/uikit/displaying-transient-content-in-a-popover)

Rust 在独立原生等待任务中保持响应 receiver，直到 Swift 最终 resolve/reject；Vue 离开只取消页面消费。显式取消通知真正持有控制器/文件准备任务的 owner，原等待仍接收终态。WebView 替换或 Scene 失效时，owner 结束呈现并释放资源；临时 inactive（例如权限弹窗）不直接取消操作。[Tauri 2.12.1 主 App 插件入口](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.1/crates/tauri/mobile/ios-api/Sources/Tauri/Plugin/Plugin.swift)

工作文件放在按 operation ID 划分的临时目录，创建未完成时不提供给 UIKit。正常关闭即清理；进程被终止时允许留下孤立副本，下次启动清理没有活动 owner 的过期目录。系统面板尚在使用的文件不参与回收。关闭回调后的删除失败不改写已经完成的用户结果，记录为下次待回收文件。

## 4. 接收分享的完整流程与持久状态

```text
其他 App 的分享面板
  → Share Extension 获取文字/文件
  → App Group 内完成文件与 manifest，原子发布 ready 批次
  → 用户打开 VCPMobile
  → Rust 拉取并建立 delivery receipt，导入附件到 CAS
  → 用户选择 Agent
  → 原子创建目标话题与分享专用预填记录
  → 用户检查/编辑后发送
  → 同一数据库事务提交消息、附件引用、delivery 的 sent 状态
  → 清理共享收件副本；后续响应交给正常聊天流程
```

`deliveryId` 标识用户这一次分享，`itemId` 标识其中一个输入项。文件 hash 标识内容，可用于 CAS 复用；相同内容出现在两次分享中仍保留两次独立意图。展示中的 `operationId` 与 `revision` 负责取消和迟到回调，不承担持久去重。

主 App Rust 持有一份分享领域 receipt，最小字段为：`deliveryId`、manifest 摘要、接收顺序、状态、各项导入结果、目标 Agent/topic、分享预填内容与修订号、最终 message ID。共享目录只存输入，业务状态只写主 App 数据库。

| 状态/提交点 | 持久事实 | 此时允许清理什么 |
|---|---|---|
| 扩展 `partial` | 内容尚未对主 App 发布 | 本批取消或失败可删；过期残片经协调后回收 |
| 扩展 `ready`、Rust `received` | 整批原始输入已发布；Rust 已接受或可在下次扫描接受 | 只能清导入失败留下的本次临时文件；保留收件原件 |
| Rust `prepared` | 每项成功/失败及已登记附件可复查，尚未选 Agent | 保留收件原件，用户可重试、稍后处理或丢弃 |
| Rust `draft` | 目标话题及分享预填已持久绑定 | 可删已完成的上传 staging；收件原件继续承担重启恢复 |
| Rust `sent` | 一条用户消息、其附件引用和本次 delivery 的提交在同一事务完成 | 可删除收件原件与专用草稿内容，保留去重凭据及 message ID |
| Rust `discarded` | 用户明确放弃整批 | 可删除收件原件和专用草稿，保留足以完成幂等清理的凭据 |

文件复制和数据库事务不能跨进程合并成一个原子动作，所以采用“先保留输入、再写业务提交、最后清理”的顺序。中断可能留下可重试的输入副本或已经登记的 CAS；不能出现已删除唯一输入但业务提交尚未完成的窗口。

## 5. P4-4 推荐交接方案

### 5.1 扩展只做获取与提交

建立独立 UIKit Share Extension target，`NSExtensionPointIdentifier = com.apple.share-services`，activation rule 列出实际处理的文字、URL、图片和文件类型/数量。界面只显示本批摘要、保存进度、取消和结果；图片转换与文档解析由主 App 在导入阶段处理。

输入使用 `NSExtensionItem` / `NSItemProvider`，一份 attachment 选择一种适合的 representation，避免同一 provider 的 URL、文本和文件变体被重复导入。文本/网页 URL 作为文本预填；文件优先 file representation 并流式复制，不在扩展内解码整张 UIImage、大图缩略图、文档解析或调用模型。`loadFileRepresentation` 返回的临时 URL 在 completion handler 返回后可能被删除，必须在该生命周期内完成到自有目录的复制。[Apple NSItemProvider 文件有效期](https://developer.apple.com/documentation/foundation/nsitemprovider/loadfilerepresentation(fortypeidentifier:completionhandler:))

每批生成随机 `deliveryId`，每项生成 `itemId`。扩展在 App Group 专用 `IncomingShare/<deliveryId>.partial/` 内流式写入文件，同时计算实际字节数和内容摘要；manifest 记录版本、批次 ID、文本、项 ID、相对叶文件名、字节数、摘要与类型。所有文件写入、关闭并完成持久化步骤后，写入 manifest，最后在同容器内原子 rename 为 ready 目录。发布后内容不可变，扩展才向用户显示“已保存”并结束请求。

主 App 只读 ready 目录，先验证 manifest 版本、文件包含关系、实际长度与摘要，再接受 receipt。取消/provider 失败清理本批 partial；迟到回调不得重新发布取消批次。原子 rename 保证主 App 不会读到半批，文件持久化用于降低正常崩溃后的数据丢失风险；它不构成断电、磁盘损坏或系统移除数据时的绝对保证。

复制并发先设为 1，文件和文本边读边计量，磁盘余量覆盖本批未完成复制；provider 返回未知长度也执行同一预算。文件数量、单文件/整批字节、收件箱占盘与复制期限作为新的统一预算确定，提前在扩展显示会影响选择的限制。`Progress.cancel()` 与 operation 状态共同处理取消，错误区分 provider、容量和超限。Apple 没有为所有 Share Extension 承诺统一的内存或运行时额度。[Apple 扩展资源约束](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionCreation.html)

### 5.2 主 App 拉取，事件只作为提示

主 App 在 Rust 初始化/启动清理完成且 Vue READY 后、Scene 回到 active 时，以及用户进入待处理入口时检查 ready 批次。可增加跨进程变化通知供正在运行的主 App及时刷新，但它只是检查提示，不保证启动或唤醒进程；拉取结果以磁盘 manifest 和 receipt 为准。

冷启动、暖启动和 WebView 重建共用同一个拉取入口。Rust 以 `deliveryId` 唯一约束执行接收：首次插入 `received`，重复拉取返回同一记录；同 ID 的 manifest 摘要改变则报告损坏，不覆盖既有内容。一次导入一批，重复请求附着到同一活动操作，不重复启动导入。

导入时从 ready 原件复制到主 App 本次 staging，经过 P4-1 的校验、CAS 登记和派生处理后，把每个 item 的结果写入 receipt，最后成为 `prepared`。staging 可在中断后清掉，ready 原件保留。重启后逐项核对实际 CAS 文件与登记，缺失项重新导入；仅有旧路径或 hash 不能当作文件仍可用的证据。纯文本批次执行同样的 receipt 流程，只省略文件导入。

### 5.3 目标话题与可恢复预填

用户选择 Agent 时，Rust 在一个写事务内创建目标 topic、绑定 `deliveryId` 并保存初始分享预填，状态变为 `draft`；重复命令返回同一 topic。若目标 Agent 已不存在，保留批次并重新选择，不建立无效绑定。

Vue 取得 `{ deliveryId, topicId, revision, text, items }` 后，只在该目标会话仍是当前意图时挂载。切换页面不删除草稿，回到目标话题或待处理入口可以继续。收到新分享时列入待处理批次，不覆盖用户正在编辑的这一批。

分享输入中的文本编辑、移除附件和明确跳过失败项，按递增 revision 写回这份分享专用草稿；Rust 仅在状态为 `draft` 时接受更新的 revision，返回已持久化版本。发送或丢弃提交后的迟到编辑不重开草稿。重启恢复最后确认的版本，输入框已出现但尚未持久化的最后几个字符不保证恢复。原始收件内容仍保留，用户可以重新取回；本流程的持久状态限定在分享内容内。

### 5.4 发送提交、重试与清理

点击发送时，Vue 携当前最终文本、所选附件、revision 和 `deliveryId` 交给 Rust。Rust 校验目标与附件仍可用，并在事务内裁定 revision：请求早于已持久版本时返回冲突供页面刷新，接受的最终版本连同用户消息、消息附件引用和 receipt 的 `sent`/message ID 在**同一写事务**提交。并发双击或提交后响应丢失时，重复请求返回既有 message ID，不再创建第二条消息。写事务失败则保留 draft 和 ready 原件，允许用户继续。

本方案的“消费成功”指上述本地持久提交完成。网络请求、模型生成和服务器重试仍由聊天领域处理；它们失败时保留已经提交的消息，不把 delivery 重新预填并发送。由此保证同一批交接在本地至多产生一次提交，不宣称外部模型调用具有 exactly-once 语义。

事务提交后再删除 ready 原件与专用草稿正文。清理失败只留下可重试副本，receipt 仍为 `sent`，下次扫描只继续清理；不得重新导入。`discarded` 同样先写用户决定，再删除文件。终态凭据至少保留到相关共享目录确认清理完成；凭据存在期间重复投递返回原终态。

关闭 Agent 选择器/输入页表示稍后处理；显式“丢弃”才置 `discarded`。单项失败保留原件，重试只处理未完成项；用户选择部分继续时，把选定项和明确跳过项一并记入草稿，最终发送/丢弃后处理整批清理。已登记 CAS 的清理交给附件引用管理，不因丢弃本批而删除可能被其他消息使用的文件。

收件箱容量受统一预算约束：满时拒绝新批并说明，已接收 draft 不因时间流逝自动失去原件。partial 可用短期限回收；尚未取件的 ready 若要自动过期，保留时长与告知属于产品选择，未确定前只提供用户主动清理。跨进程提交、占用和清理使用文件协调或短锁，保证清理不会碰到正在写入或正在导入的批次。[Apple 共享容器与并发访问说明](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionScenarios.html)

### 5.5 可靠性承诺的边界

目标是在文件与数据库完好的条件下，面对扩展/主 App 进程终止、WebView 重建、重复扫描及最终 IPC 响应丢失，仍能继续处理同一批内容，并避免重复话题和重复本地消息。扩展发布前终止可以留下未接收残片，用户没有收到成功承诺；发布后至本地提交前，ready 原件是恢复来源；本地提交后，消息和附件引用是结果来源。

卸载 App、重签造成容器身份变化、用户主动删除数据、存储损坏和 provider 在发布前撤回内容，不在该持久交接保证内。遇到缺失或摘要不匹配时保留 receipt 并报告哪一项无法恢复，不伪造成功。恢复流程的正确性以中断点验证，不仅以正常分享一次能完成来判断。

## 6. 自签与 App Group 的交付条件

2026-10-16 实查 Apple 官方 [Supported capabilities (iOS)](https://developer.apple.com/help/account/reference/supported-capabilities-ios/)：`App groups` 一行在 ADP、ADEP、Apple Developer 三列均为支持；文档将 Apple Developer 定义为不付费的 Apple Agreement 账号。可以基于免费开发能力设计共享组，最终仍须验证用户选用的重签工具生成并保留所需身份。

本方案的实际运行条件是主 App 与扩展最终签名中的 App Group entitlement 指向同一个可用共享容器，两个 target 的 bundle ID/profile/签名相容。`containerURL(forSecurityApplicationGroupIdentifier:)` 真正返回目录才可接收；失败就解释本次安装的共享容器不可用，不能转写扩展私有路径后向用户报已交接。[Apple capability 与 profile 配置规则](https://developer.apple.com/help/account/identifiers/enable-app-capabilities)

| 产物/身份情况 | 能做什么 | 不能声称什么 |
|---|---|---|
| 未签 device archive | 检查主 App 嵌入 `.appex`、目标架构、最低版本、Info 与 entitlement 输入 | 不能证明安装成功、App Group 获授权或系统分享列表可用 |
| 用户重签工具保留并正确配置双 target + group | 可走本方案完整系统分享接收 | 仍不保证扩展直接唤起主 App |
| 工具剥离 `.appex` 或 group、profile 不支持实际组 | 说明此安装的系统分享接收不可用，指导核对重签输入；主 App 内文件选择不受此条件影响 | 不能将缺失扩展或共享组的安装认定为完整分享产物 |

Phase 6 提供工具无关的双 target / group 改写清单，再按用户采用的工具记录结果。正式付费 Team 和签名服务仍不在项目范围内。

## 7. 工程输入与分段实施建议

工程生成输入包含主 App 插件与独立 Share Extension target，主 target 显式嵌入 `.appex`。扩展只链接 extension-safe 的获取/文件交接代码，保持独立入口与资源；共享的数据协议可复用小型 Swift 文件或模块。

| 步骤 | 可独立审查的产出 | 必须随步骤闭合的边界 |
|---|---|---|
| A：P4-1 基础稳定后实现 Files/Quick Look/活动面板 | 一个 Swift presentation owner；真实导出/预览/分享命令与消费者 | iPad anchor、取消结果、一次完成、临时资源持有、配置/邮件/同步日志文案 |
| B：接收协议与小扩展 | 受限 manifest、原子发布、轻量 UIKit target、activation rule | provider 临时 URL、取消、资源预算、独立进程、无 Rust/Vue 副本 |
| C：主 App 收件与会话提交 | READY/active 拉取、持久 receipt、staging/CAS、目标 topic/专用草稿、发送事务 | cold/warm/reload 去重、逐项重试、最后持久 revision、消息与 receipt 同一提交、幂等清理 |
| D：阶段诊断与 P6 输入移交 | 可重放 XcodeGen overlay，主 target embed extension，Info/entitlements/资源与身份清单 | 主 App/扩展最低 iOS 26.0；Xcode 26.2；`APPLICATION_EXTENSION_API_ONLY=YES`；扩展不链接含 App-only API 的 Tauri 主插件 |

P6 输入至少包含：主 bundle ID、扩展 bundle ID、共同 App Group ID、两份 entitlement 与 profile 关系、扩展 activation rule、嵌入位置与源资源、自签改写位置。P4 完成可重放生成与未签 archive 结构检查，P6 接收这些输入并核对用户产物。

## 8. 验证与交付边界

实现时重点覆盖以下中断点与用户结果：

- Files 取消返回原页、重复点击只出现一个面板，Quick Look 只读副本和分享文件保持到系统操作结束。
- 扩展分别在文件复制、manifest 写入、ready rename 前后终止；主 App 只接受完整批次，发布后的重复扫描返回同一 receipt。
- 主 App 在 CAS 登记、topic/草稿事务、消息/receipt 事务前后终止；恢复后没有重复话题/消息，未提交内容仍可由 ready 原件恢复。
- 数据库提交成功但 IPC 响应丢失、清理只完成一部分；重试返回原 message ID 并继续清理，不重新预填。
- 编辑 revision 乱序、选择 Agent 时关闭界面、下一批到达或会话切换；迟到结果不覆盖当前会话，重启恢复最后确认的草稿版本。
- 容量不足、provider 撤回、部分文件失败、用户明确部分继续/丢弃；各结果对应同一批资源所有权。

预算与目录校验可通过有意义的文件 fixture/状态测试取得执行证据；Vue/Rust 跨层变更运行 `pnpm check`，Android 共用命令变化须保留目标检查。手动 G1 在固定 Xcode 26.2 上取得 Swift/extension 编译链接和 archive 嵌入证据，后续 G2 记录自签输入与产物边界。

本项目不建设 iOS 实机测试体系。因此 provider 的真实系统 UI、iPad 锚点表现、第三方分享目标行为、用户重签工具及扩展安装/容器授权，在没有实际观察时只能记为未验证；Windows 静态检查、host 测试、无签 archive 均不能替代这些结论。

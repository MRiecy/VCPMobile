## 1. 第四阶段要形成的使用体验

用户可以通过 Files、照片库和相机添加内容，在聊天中查看、发送和保存图片，将文件导出或分享给其他 App，也能将外部内容交给 VCPMobile 后继续对话。所有入口共享清晰的取消、失败、恢复和完成语义；iPhone/iPad 在各自窗口中获得正确的键盘布局、原生弹层和富消息交互。

| 任务 | 目标设计 | 专题方案 |
|---|---|---|
| P4-1 文件/照片导入 | Files/PHPicker 取得受控副本；Rust 完成校验与 CAS 登记；整个操作可取消、可清理、可关联到本次附件意图 | [文件导入与图片处理](./01-文件导入与图片处理审查.md) |
| P4-2 相机/保存/图像 | 原件留在 CAS，列表/全屏显示、头像工作副本和发送用图分别派生；ImageIO 返回真实格式，PhotoKit 使用 add-only 写入，AVCapturePhotoOutput 获取静态照片 | [文件导入与图片处理](./01-文件导入与图片处理审查.md) |
| P4-3 导出/预览/配置与对外分享 | Files exporter/原生选择器、只读 Quick Look、系统分享各自报告实际结果；配置导入导出均走各自平台原生能力（彻底移除 HTML input）；文件以路径交接，覆盖配置、邮件、附件和同步日志消费者 | [导出预览与双向分享](./02-导出预览与双向分享审查.md) |
| P4-4 接收分享 | 只维护当前一次分享，新分享覆盖旧分享；Extension 发布当前内容，主 App 选择 Agent 并预填；发送、丢弃或被替换后清理 | [导出预览与双向分享](./02-导出预览与双向分享审查.md) |
| P4-5 缓存/交互/渲染 | 精确清理浏览缓存；根应用与全屏浮层统一消费可用矩形；文本选择、焦点、触控及富消息资源各有明确规则 | [WebKit 缓存与交互](./03-WebKit缓存与交互审查.md) |

三份专题展开数据流、接口、状态迁移、系统 API 和实施步骤；本总览规定跨专题共用的职责与依赖。

## 2. 职责与数据流

| 所有者 | 承担的工作 | 对外结果 |
|---|---|---|
| Vue 功能层 | 创建用户操作、展示进度、取消、选择目标会话、消费最终结果 | 本次操作意图与页面/会话身份 |
| Rust 文件与分享领域 | 校验输入、协调导入取消、CAS/数据库提交、当前分享恢复与替换 | 已登记附件、当前分享内容、真实错误 |
| 主 App Swift 适配 | 系统选择器、文件访问、图像处理、相机/相册、原生呈现与 WebKit 几何 | 受控文件及元数据、系统操作结果、几何快照 |
| Share Extension | 接受新分享并替换槽位、有界复制、按 generation 发布完整内容 | 独立于主 App 运行状态的当前一次分享 |

导入链为“用户操作 → 原生系统选择器取得受控副本（双端全面原生化，彻底移除 HTML `<input type="file">` 选文件入口及大文件 XHR 本地通道） → 本次 staging → Rust 校验与 CAS 登记/配置恢复 → Vue 附件/配置生效”。保存与导出链为“已选内容/导出数据 → 本次导出文件 → 原生系统操作（Files 导出 / 相册保存 / 原生分享） → 完成后释放”。两条链根据用户目的选择终点，纯导出只持有临时文件；大文件与二进制传输全部采用原生磁盘路径交接，避免数据跨 WebView IPC 反复中转。

分享接收链为“Extension → 当前分享槽位 → Rust 当前记录 → 绑定 Agent/topic → 当前预填 → 消息持久提交”。2026-10-16 用户明确只维护一次分享；新分享使旧 generation 失效，旧导入与未发送预填被覆盖，不建设多批队列或分享历史。一次分享可以包含多个文件，hash 负责内容去重。

## 3. 共用的生命周期设计

### 文件所有权与提交点

| 文件类别 | 放置与持有 | 释放时点 |
|---|---|---|
| 外部 provider 文件 | Swift 在系统允许的访问窗口内持有，复制为应用副本 | 复制完成、失败或取消时释放 scope/句柄 |
| 本次导入 staging | cache 中按 operation 隔离；由 Rust 导入协调者跟踪 | CAS 提交成功，或提交前失败/取消 |
| CAS 原件 | Application Support，由文件领域管理内容与持久引用 | 依据消息/附件引用回收，与单次 UI 关闭解耦 |
| 显示/模型派生 | cache 中按原件身份、用途和处理参数识别；使用期间由消费方持有 | 使用结束后按缓存策略回收，可从原件重建 |
| 预览/导出副本 | 本次原生操作持有，只读提供给系统 | 系统结束读取后释放；中断遗留由定向清理回收 |
| 分享收件原件 | App Group 中按 generation 隔离的当前内容 | 消息提交、明确丢弃或新分享替换后，待持有者释放再清理 |

导入状态围绕 `selecting → acquiring → staged → committing → registered` 组织。取消与提交由同一 Rust 操作协调者裁定：提交前停止传输并清理临时文件；提交已经生效则保留附件记录，淘汰过期页面回填，由引用管理决定后续回收。每条调用产生一次最终结果。

仅当前分享保留可恢复内容。新分享替换、话题绑定和发送按同一身份裁定顺序执行：替换先发生则旧发送失效，消息先提交则保留聊天结果。发送时将消息、附件引用和当前分享终态纳入同一业务提交。重启只恢复当前槽位，旧文件仅用于清理，旧回调不得重新发布或清空新内容。

### 原生响应、页面与生命周期

每次系统操作携带 operation ID。Swift 持有该操作的 controller、delegate、provider Progress、工作文件与 Invoke；显式取消发送到这个 owner。Rust 桥保持接收者直到原生最终 resolve/reject，迟到响应仍完成清理，页面只接收属于当前意图的结果。

主 Scene 配备一个轻量 presentation owner，同一时刻呈现一个本插件发起的模态操作。它处理重复点击、呈现失败、交互关闭、旋转及 WebView 替换。`inactive` 是独立生命周期状态，选择器和权限交互期间继续持有本次操作；真正后台中断按各资源的取消与恢复规则收尾。

### 平台接入与权限

共享页面按运行时平台选择原生操作。命令 DTO 服务于具体文件、分享和几何消费者，ACL 随实际入口配置。PHPicker 采用系统用户选择模型；相机在点击拍照时申请授权；保存相册使用 add-only。用途描述、请求、拒绝后的恢复动作和最终反馈作为同一交付片段完成。

本阶段覆盖文件/图片、相机、相册、双向分享及 WebKit；语音、视频抽帧和后台运行资源继续按各自阶段范围管理。

## 4. 已确认的用户体验选择

### A. 接收分享后的进入方式

**建议流程：扩展保存并提示 → 用户打开 VCPMobile → 选择 Agent → 查看待发送内容。** 主 App 在启动和回到前台时读取当前一次分享；关闭可以稍后继续，新分享则覆盖尚未发送的内容，已发送消息保留。Apple 的支持范围决定这里需要用户打开主 App；Share Extension 没有受支持的直接启动主 App API。[Apple 官方说明](https://developer.apple.com/forums/thread/773342)

本轮按上述两段流程实施。扩展与主 App 通过 App Group 交接；最终重签应一致处理主 bundle ID、扩展 ID、group ID、entitlement 与 profile。免费开发身份具备 Apple 表列的 App Groups 能力，具体重签工具须正确装配这些输入。[Apple capability 表](https://developer.apple.com/help/account/reference/supported-capabilities-ios/)

### B. 拍照入口使用最小取景页

采用 `AVCapturePhotoOutput` 最小拍照页，输出尺寸、编码、镜头、方向和中断归同一原生 owner。按设备支持的输出尺寸选择上限，预览与编码另计资源；具体参数见实施记录，不承诺精确进程峰值。

图片以原件和用途派生组织：CAS 保留所选内容，列表与全屏查看按显示需求生成图像，模型发送生成静态主图派生，透明图使用 PNG，HDR 派生输出 SDR。PHPicker 使用当前静态文件表示，不取得 Live Photo 视频配对资源。

图像质量、一次分享的文件数量/总字节和部分失败反馈已按专题方案收敛，具体工程取值在实施记录集中维护。

预算按用途确定：显示目标依据窗口与可见细节，模型派生依据接收格式/尺寸和累计请求大小，Canvas 导出依据长边、总像素与编码字节，分享依据文件数、单批字节和总占盘。候选数值在专题集中维护，首批实现前收敛；解码缓冲、编码输出和跨层副本分别计入预算。系统 codec 内部开销仍作为证据边界记录。

## 5. 建议的分段实施顺序

实施沿用 P4-1–P4-5 编号和下面的依赖关系；实际交付结果见实施记录。

1. **P4-1 导入协议与资源管理。** 交付 operation、状态迁移、取消/提交裁定、staging 生命周期及文件元数据 DTO，连接各字节入口与 CAS。
2. **P4-1 Files/PHPicker。** 交付主 Scene 呈现、scope/provider 获取和应用副本，接入聊天与头像的用户流程。
3. **P4-2 图像、拍照与相册。** 交付按用途的 ImageIO 处理、格式/预算契约、选定相机及 PhotoKit 保存，覆盖显示、模型发送和图形导出。
4. **P4-3 导出/预览/对外分享。** 交付 Files、Quick Look、系统活动面板及各自结果类型，覆盖配置、邮件、附件、同步日志和 iPad 呈现。
5. **P4-4 单次分享交接。** 交付扩展、当前槽位/generation、目标话题/预填、覆盖与发送裁定、恢复及定向清理；工程与重签输入同时交给 Phase 6。
6. **P4-5 布局与富消息。** 交付统一可用矩形、输入/选择/焦点规则、限定缓存操作、有界文本/图像/Canvas 路径及强渲染覆盖。几何协议和缓存操作可与前几批并行，原生面板接入后完成交互联审。

## 6. 验证与交付条件

每个实施片段交付可追踪的输入、最终结果和资源释放。专题中的接口与参数属于设计草案；生产代码接入后再记录实现与执行证据。

实施后按改动范围运行 `pnpm check`、相关 Rust/前端领域验证；涉及 Android 共享契约或原生修改时检查实际 Android 目标。重点选择能够暴露问题的事件序列：取消与 CAS 提交交错、provider 迟到、批次重复取件、会话创建期间新分享、导出关闭与清理竞争，以及图片实际编码/尺寸/MIME。几何计算可用明确输入推演，但不能据此宣称键盘或触控已在 iPhone/iPad 验证。

Apple 编译沿用阶段性手动 Actions：最低 iOS/iPadOS 26.0，Xcode 固定 26.2；工具链与既有构建证据统一引用 [Apple 工程记录](../../../src-tauri/ios/README.md)。

Phase 4 实现后按需以 `phase-4` 标签检查当前完整应用，收集实际归档与扩展资源；G2 仍负责后续 release/用户产物集成。无签名构建不能证明用户的共享组授权或最终重签安装可用，也不替代原生交互观察。本阶段不建设 iOS 实机测试体系。

# 双端音视频附件处理

> 2026-10-17。用户批准 Android 音频使用 Media3、优化现有视频抽帧，iOS 使用原生接口补齐音视频处理，图片保持现状，并修正格式标记和失败反馈。源码基线为 `794ae8dc`（上一轮视觉恢复独立存档）。本轮检查、测试和平台构建继续按用户要求延后。

## 范围与协议

本轮处理已经导入 CAS 的音视频文件，不接入录音、语音聊天或麦克风权限，不增加播放器，不改变图片派生或 SSE 保活音频会话。

音频保留既有 16 kHz、单声道、32 kbps 的压缩目标，统一使用 AAC-LC 编码、M4A 容器、`audio/mp4` MIME。原生按路径返回 `path/mime/codec/container/sampleRate/channels`；Rust 核对结果后组装 `image_url.url = data:audio/mp4;base64,...`。

此协议来自实际项目消费链：VCPChat `modules/chat/singleChatRequestOrchestrator.js` 把媒体 Data URI 放入 `image_url`；VCPToolBox `Plugin/ImageProcessor/image-processor.js` 通过 `data:(image|audio|video)/...` 识别媒体并执行配置的多模态翻译。两处只读核验，未修改参考工程。旧 Mobile 的 `input_audio` 不进入这条翻译链，且非 AAC 一律填 MP3 与原始编码不符。本轮不将 M4A 冒充 ADTS AAC，也不声称这个 VCP 契约等于所有模型提供方的标准 OpenAI 音频接口。

三方审查结论：系统视角优先消除逐块重采样、复制和 EOS 处理错误；交互视角要求用户知道哪个附件未能送达，停止不报失败；交付视角保留既有请求、CAS、finalizer 与平台资源职责，避免新增第二套聊天任务状态。

## 原生处理

| 平台 / 用途 | 实现 | 资源与语义 |
|---|---|---|
| Android 音频 | Media3 Transformer，PCM 格式转换、声道混合及 Sonic 重采样，系统 AAC 编码和 MP4 封装 | 沿现有 1.3.1 依赖，按锁定版本源码核对 API；专用 Looper 管理 Transformer，不在 UI 线程处理文件，不保留手写 PCM 算法 |
| Android 视频 | API 27+ `getScaledFrameAtTime`；API 26 保留原尺寸取帧后缩放 | 1280×720 包络，约 2 秒间隔与长视频最多 300 帧；直接计算有界时间表，不为整段长视频预建无限时间戳列表 |
| iOS 音频 | AVAudioFile 读取、单个 AVAudioConverter 持续转换，AVAudioFile 写出 M4A | 分块、复用缓冲、EOF drain；关闭输出完成文件头后返回；不配置 AVAudioSession |
| iOS 视频 | AVAssetImageGenerator 按时间逐张生成，ImageIO 编码 JPEG | maximumSize 与方向变换、允许时间容差、实际时间去重；取消生成后释放图像与部分结果 |

平台解码能力取决于实际输入容器、编码和系统支持；扩展名白名单不代表所有同名文件可解码。缩放 API 约束应用持有的帧尺寸，不承诺系统内部从不解码原尺寸画面。

## 所有权与取消

共享入口位于 `media_processor/`，原生只管理媒体作业资源：

1. Rust 创建本次独立 `media-work` 工作目录和 operation ID。
2. `prepareMediaOperation` 登记原生资源槽；成功后才调用 `processAudio` 或 `processVideo`。
3. `cancelMediaOperation` 撤销待执行槽或取消实际处理。迟到的 process 不得重新建立已经撤销的槽，也不留下永久取消 ID 集合。
4. 媒体 worker 等待原生最终回调并清理目录；原请求的取消和业务终态仍归 ActiveRequest / finalizer。

锁定 Tauri 的原生回调不能在取消时丢弃接收端。Rust 请求可以结束等待，但持有原生 receiver 的作业继续取消和收尾；不 abort 正在接收回调的任务，不让迟到 callback 写入已释放接收端。

原生失败或销毁清理自己持有的部分产物，Rust 最终释放整个工作目录；启动维护清理上次进程终止遗留的 `media-work`。原始 CAS 附件不作为临时文件删除。

## 预算、缓存与反馈

- 单音频派生文件上限 16 MiB；整次请求（含历史）音频 Data URI 累计上限 24 MiB。32 kbps 目标保留压缩收益，但不再以旧 3500 秒循环条件静默丢弃尾部。
- 单视频 JPEG 文件总量上限 12,000,000 字节；编码结果继续计入现有整次请求 16 MiB 图像预算，包含其他图片和历史视频帧。最多 300 张采样图不等于读取全部帧。
- 超限、无可用帧、文件不可读或转换失败返回明确错误，不返回成功的截断媒体，也不把音视频替换为仅有文件名的文本继续请求。
- 多模态缓存保留 `{hash}.json` 路径以复用既有回收规则，内容增加 schema/type 信息；旧的无类型字符串数组不被当作本轮结果复用。
- 用户消息和原附件按既有流程已经保存。准备失败沿原有 durable error finalizer 显示附件名及失败原因；群聊停止本轮后续成员，避免相同坏附件引发连续报错。主动取消走正常取消终态，取消与失败同时到达时以取消为准。

## 复审与证据

当前依据为生产调用链、锁定依赖源码及官方 API；源码接通不代替目标编译或运行证据。本轮未运行 `pnpm check`、Rust/前端测试、Gradle、Apple 构建或设备测试，未引入 iOS 实机测试体系。

三条实现分工和独立复审均已完成，根代理沿调用链再次核对。复审修正了 iOS URL 资源属性缓存可能令动态文件大小检查失效的问题（改为实时文件属性）、Android 抽帧为空仍继续的问题、Media3 1.3.1 非空异常参数，以及原生桥接失败后尚未消费的预约槽清理。`git diff --check` 仅检查补丁空白，不作为类型、编译或运行通过的证据。

取消遵循实际系统能力：音频在处理块边界或 Media3 取消收尾后结束；Android MediaMetadataRetriever 没有取消单次解码的接口，停止可能等待当前帧返回。iOS 会取消已登记的图像请求，登记与取消交错时可能等当前一帧返回后丢弃。两端都在原生处理终结后再由 Rust 删除工作目录，不将停止按钮等同于可立即打断系统解码。

后续检查重点是：两个原生 selector/DTO 与 Rust 一致、取消先于执行/执行中/完成交错、输入无音轨或无视频帧、输出格式与真实容器一致、预算边界、原生关闭与临时产物释放，以及群聊准备失败只结算当前发言者并结束当轮。

# 01. 架构现状与跨平台改造边界

## 1. 总体判断

当前 VCPMobile 的多数 Rust 业务模块从静态调用链看值得作为复用候选，但 Apple compile/link 前不能标记为已复用。工程不能通过“打开 iOS target”直接获得 iOS 产品；真正的改造边界应放在**单一平台能力适配层**，而不是复制业务系统。

推荐架构：

```text
Vue / Pinia
  │ 稳定、平台中立 IPC
  ▼
Rust 既有业务 owner
  ├─ Lifecycle epoch
  ├─ Chat attempt abort ownership + active-generation ledger
  ├─ Sync session generation + cancel + join
  ├─ Distributed session owner
  ├─ Attachment CAS / DB
  └─ Android Update service（iOS capability disabled）
        │
        ▼
PlatformCapabilities + MobilePlatform adapter
  ├─ Android Kotlin plugin
  ├─ iOS Swift plugin
  └─ host-test explicit Unsupported stub
```

核心原则：**跨平台共享状态放 Rust，平台事实放 Kotlin/Swift，前端只消费能力与结果。** 产品 target 仅为 iPhone/iPad；macOS 只运行 GitHub Actions/Xcode，不新增 Catalyst 或桌面业务分支。

## 2. 可复用资产

| 资产 | 当前证据 | iOS 价值 | 限制 |
|---|---|---|---|
| Rust library crate | `staticlib/cdylib/rlib` | 符合移动端嵌入形态 | 必须在 Apple target 实际编译链接 |
| JNI target gate | `jni` 只在 Android target | 避免 JNI 污染 iOS | 仍需检查所有间接依赖 |
| Vue 单应用 | UI/Store 未按设备复制 | iPhone/iPad 可共享 | 要移除散落 UA 与 Android 文案 |
| Lifecycle epoch | 已处理乱序 transition | 可保留恢复所有权 | 缺 Swift 事件生产端 |
| Chat attempt/ledger owner | Rust 管理 `attempt_id`、abort sender 与 active-generation DB ledger | 保留唯一请求 owner | 当前没有生命周期批量 cancel+join/drain 回执，非 Android resume 会失败终止 |
| Sync owner | generation + `CancellationToken` + `JoinHandle` | 正是 iOS suspend 前收口所需 | 必须把 iOS lifecycle 接入 stop/join |
| Distributed owner | 有 session 与子任务收口 | 可定义前台运行模式 | 当前工具无条件注册且遥测 Android 化 |
| SQLite/WAL/恢复 | app 目录 + WAL + recovery | 可继续使用 | 沿用既有硬上限；iOS memory pressure 标记 `NOT-EVALUATED`，不作实验产物门禁 |
| 附件 CAS/Hash | Rust 侧统一存储和登记 | Swift 可只做 staging | 当前根路径含 Android 假设 |
| 响应式 UI | 按当前窗口宽度，而非机型 | 适合 iPad 分屏和旋转 | WebKit/手势仍需验证 |

## 3. 当前 iOS 阻断

### 3.1 原生插件只有 Android

[插件 build.rs](../../src-tauri/plugins/vcp-mobile/build.rs) 只调用 `.android_path("android")`；[插件入口](../../src-tauri/plugins/vcp-mobile/src/lib.rs) 只在 Android 保存 `PluginHandle` 并注册 Kotlin 插件。仓库没有：

- `ios/Package.swift`；
- Swift `Plugin`；
- `.ios_path("ios")`；
- `ios_plugin_binding!`/`register_ios_plugin`；
- Apple generated project、Info.plist、entitlements、privacy manifest。

Tauri 的正确扩展方式见 [Mobile Plugin Development](https://v2.tauri.app/develop/plugins/develop-mobile/)。

### 3.2 生命周期只有接收端，没有 iOS 发送端

[src-tauri/src/lib.rs](../../src-tauri/src/lib.rs) 已在 Android/iOS cfg 下监听 `vcp-mobile://lifecycle`，但当前只有 Kotlin `LifecycleBridge` 能产生事件。iOS 又被 desktop window-focus fallback 排除。因此按现状生成 iOS 壳后，Rust 可能长期把 App 视作前台。

建议：Swift 监听 `UIScene`/`UIApplication` 状态，提供“先订阅、再读取 snapshot、按单调 sequence 对账”的桥；Rust 继续拥有业务 epoch 和状态迁移。`sceneWillResignActive` 只代表暂时 inactive，不能直接触发 Chat/Sync/Distributed 破坏性收口；只有聚合后的 background 才能进入 closing。MVP 应明确采用单 Scene；若启用多 Scene，必须在 Swift 聚合所有 connected scene，不能由单个 scene 的后台事件关闭全进程 Rust owner。参见 [Apple Scenes](https://developer.apple.com/documentation/uikit/scenes)。

Swift 可以持有 Apple background-task token，但只能按 Rust epoch 建立映射；它不拥有业务 session。iOS/iPadOS 26 及以上优先尝试 `BGContinuedProcessingTask`，更早版本或系统拒绝时仅保留前台执行；token 的获取、expiration、用户取消和 exact-once 结束必须与 Rust terminal receipt 形成闭环，详见 [04-生命周期后台网络与同步策略.md](./04-生命周期后台网络与同步策略.md)。

### 3.3 `not(android)` 不是 iOS 实现

当前大量分支把 desktop mock 和 iOS 混为一类：

| 现状 | 例子 | 风险 |
|---|---|---|
| 假权限 | 全部 `true`、通知监听 enabled | UI 跳过必要授权或声称不存在的能力可用 |
| 假设备数据 | 10/100GB、满电 25°C、127.0.0.1 | 用户与服务端收到虚假事实 |
| 假传感器 | 固定北京坐标及固定运动/环境数据 | Distributed 工具协议欺骗 |
| 空操作成功 | wake lock、网络监听、通知、剪贴板写 | 调用者误以为平台保证已建立 |
| desktop 行为落入 iOS | 打开 APK、`process::exit(0)` | 错误产品语义和审核风险 |

目标 cfg 必须显式分成：

```text
target_os = "android"  -> Kotlin 实现
target_os = "ios"      -> Swift 实现或结构化 Unsupported
not(mobile)             -> 明确的 host-test stub，不进入生产能力声明
```

不能再用 `not(android)` 表达“其他平台都可用”。

## 4. 单一 owner 不变量

### 4.1 必须继续由 Rust 拥有

- Chat request ID、attempt ownership、active-generation ledger、partial/final/terminal 状态；当前仍需在此 owner 内补生命周期 cancel-all、join/settle receipt；
- Sync session generation、cancel、join、commit-time generation check；
- Distributed session 与工具 registry；
- 生命周期业务状态与恢复决策；
- 附件 hash、CAS、DB transaction 和清理；
- Android Update 状态与平台路由；iOS 对外能力恒为 disabled，不建立第二套更新 owner；
- 平台 capability 快照的权威聚合。

### 4.2 Swift 只做

- 请求和读取 Apple 权限；
- 监听并聚合 scene/application、网络和键盘等平台事件，提供带 sequence 的 snapshot；
- 按 Rust epoch 持有和 exact-once 结束 Apple background-task token；
- 文件选择、照片写入和必要的图片 staging/转码；
- 返回 Apple 公开、真实且可解释的数据；
- 遇到不支持能力时返回结构化错误。

### 4.3 明确禁止

- 在 Swift 新建 SSE client 作为第二 owner；
- 在 Swift 复制 Sync/Distributed session 状态机；
- 前端独立决定后台任务重启；
- 以无操作 `Ok(())`、固定 `true` 或 Mock 数据表示成功；
- 为 iOS 复制一套 Pinia store 或组件树；
- 为“常驻”滥用 audio/location background mode。

## 5. 推荐平台能力契约

新增一个 backend-owned 快照，供 UI、Rust service 和 Distributed registry 共同使用。建议至少包含：

```text
platform: android | ios | host_test
support: supported | degraded | unavailable_by_platform | unknown
implementation: not_implemented | partial | implemented
authorization: not_applicable | not_determined | granted | denied | restricted
runtime:
  policy: foreground_only | system_managed | system_scheduled | unrestricted
  state: active | inactive | background | offline
  eligible_now: bool
reason_code: stable machine-readable code
user_message: plain-language explanation
details: nullable, platform-specific factual metadata
```

`not_implemented` 不能写成 `unavailable_by_platform`；同理，平台支持、需要授权且只能前台运行可以同时为真。实现成熟度、平台支持、用户授权、运行资格与 CI/设备证据分别治理。

关键用法：

1. 活跃 UI 根据 capability 生成按功能触发的步骤，不在模板中散落 `isIOS`；现有未挂载的 Android PermissionGate 不为 iOS 复活；
2. Settings 只展示可用或有解释价值的入口；
3. Distributed registry 只上报真实支持且已授权的工具；
4. keepalive 返回 `ContinuedTaskAccepted / ForegroundRequired / Unsupported`，而不是无操作成功；
5. 更新服务只在 Android 暴露 APK 路径；iOS UI、IPC capability 和自动检查均禁用；
6. host tests 必须显式表明 mock 来源，不得进入产品 UI。

## 6. Rust 核心风险

### 6.1 Chat SSE

当前前台非 Android 可走 Rust reqwest 流，但现有 `ActiveRequests` 只有单 attempt 的 abort ownership，没有生命周期批量 cancel、`JoinHandle`、drain 回执或 deadline；非 Android 恢复又会在没有 Android helper cache 时标记失败。服务端明确不改造，iOS 第一版应：

- 前台使用现有 Rust owner；
- 在既有 owner 内补有界 cancel-all + join/settle receipt，不在 Swift 新建 owner；
- iOS/iPadOS 26 及以上提交 continued-processing task；被系统接纳时继续同一个 Rust SSE attempt，并处理用户取消/expiration；
- 更早版本、系统拒绝或 task 终止时，要求用户保持应用前台并用现有 screen-keeper 防自动锁屏；一旦连接被挂起且服务端无 cursor，只能落为明确 `interrupted`；
- 不用 `max_output_tokens` 伪造完成率；有真实 token 计数时只表达“已接收/上限”，否则使用 indeterminate 和字符/字节/chunk 活动事实。

### 6.2 Sync

现有 generation/cancel/session join 是正确基础。iOS 需要把聚合后的 scene background 接入内部 `stop_sync_inner(deadline)` 一类 owner。以下是目标不变量，不是当前已经完整实现的显式关闭序列：

- 先失效 generation，再 cancel；
- join 后才释放 session；
- DB commit 前再次检查 generation；
- terminal/deleted 不回退 pending；
- 用户手动停止的会话前台恢复后不被自动复活。

当前 lifecycle controller 在 Distributed 已启用但 idle 时存在提前 `return`；以后不能把 Chat/Sync 收口简单追加在其后。唯一 coordinator 应顺序调用各域 owner、收集每域 outcome，单个域不得提前结束整个 lifecycle transition。

### 6.3 Distributed 与遥测

当前所有工具无条件注册，并深度依赖 Android JNI、`/proc`、`/sys`、Root。iOS 必须在 registry 层过滤：

- 可支持：有限 battery、network path、thermal state、location/motion（需授权）；
- 需重定义：CPU thermal 只能是系统热压力，GPU load 不可等价；
- 不支持：Root shell、Magisk manager、跨应用通知、Android sysfs 细粒度指标；
- 未授权或不可用能力不得被 server 看到。

### 6.4 文件、数据库与内存

| 风险 | 当前模式 | iOS 处理 |
|---|---|---|
| 附件目录 | `document_dir()` 后 `pop()` | 显式区分 app data、cache、temporary；首期无 App Group；设计迁移 |
| 外部文件 | Android picker 返回路径 | security-scoped URL 立即复制到 staging，再交 Rust hash/CAS |
| 大文件上传 | `http://127.0.0.1` 临时服务 | WKWebView/ATS/loopback 先做 Simulator；真机保持社区未验证 |
| SQLite | WAL、5 连接、256MB mmap、memory temp | 不扩大现有限额；iOS 运行表现记为 `NOT-EVALUATED`，社区报告触发修复 |
| 图片 | 小图有跨平台 fallback，≥5 MiB 当前会拒绝 | iOS 用 ImageIO/CoreGraphics 转换到 staging；沿用字节上限，避免 Swift/JS 双份 Base64 |
| 音频 | 当前 Android 录音也不可用，Whisper 扩展名/MIME 不一致 | iOS 首期隐藏语音入口，不请求麦克风权限、不移植 |
| 视频 | 仅 Android，多帧 Base64 | 首期明确不支持；后续若需要再评估 `AVAssetImageGenerator` |
| 文本 | 50 MiB 级输入文件、最多千万输出字符 | 沿用硬上限；性能不认证，异常由社区报告驱动修复 |
| 预渲染 | 最多 12 blocking workers | 沿用既有 Rust owner；不设 iOS 性能发布门禁，不宣称已验证 |

### 6.5 更新契约

当前 updater DTO 依赖 `download_url`、`apk_size` 和 arm64 APK 校验。Android 保持现有 APK owner；iOS 不提供版本检查、下载、通知、安装或 Store/TestFlight 导航，capability 固定返回 `unavailable_by_product_scope`，相关 UI 完全隐藏。GitHub Release 上的新未签名资产只供用户手工发现、下载与自行重签，应用本身不得形成自动更新链。

## 7. 插件与 capability 改造顺序

1. 先引入 `PlatformCapabilities`，消灭假成功；
2. 再初始化 iOS plugin 和最小 command/event round-trip；
3. 将插件状态从 Android-only 扩为 mobile handle；
4. 同一个命令按 Android/iOS 注册不同 native method；
5. 权限文件按平台拆分；已迁移的 Root/helper/autostart 等命令不授权给 iOS；仍需兼容旧调用的短暂迁移期则保留最小授权，并由 handler fail-closed 返回结构化错误，二者不得混用；
6. guest-js 与前端直接 invoke 统一走稳定 typed facade；
7. 最后逐能力增加 Swift，不预建空壳 command。

注意：新增/删除插件命令仍需遵守仓库的 handler、`build.rs`、permissions、guest-js 契约，并补 Kotlin/Swift selector 测试。

## 8. 架构退出条件

若产品要求以下任一项，等价 iOS 迁移应判定 `NO-GO`：

- Android `:helper` 独立进程持续 SSE；
- Root shell、Root manager 或 jailbreak 等价；
- 监听其他 App 的通知；
- 物理 Wake/Wi-Fi Lock 和长期 FGS 等价；逻辑 facade 只能返回 continued/foreground 实际模式；
- 程序化退后台或自我重启；
- 由应用自身从 GitHub 下载、重签或安装 IPA；用户在应用外下载实验产物并自行重签不在此禁项内；
- 在服务端不可改且无 cursor 的前提下仍要求断线自动恢复或结果必达；
- GitHub macOS/Xcode CI 未通过却宣称 Apple binary 可编译。

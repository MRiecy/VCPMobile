## 2. 初次确认的问题与后续处理（历史发现）

### R1 已处理：移除拒绝真实依赖的多余门禁

初次复现涉及当时的 Swift 锁定脚本、工程校验器和应用 Cargo 依赖清单，问题可由下述调用链触发。

初次复审时的允许集合和最终证据集合都仅包含 `Tauri`、`tauri-plugin-opener`、`tauri-plugin-vcp-mobile`。实际应用还依赖并注册 `tauri-plugin-log 2.9.0`，其发布源码 `build.rs` 调用 `.ios_path("ios")`，`ios/Package.swift` 声明独立静态包 `tauri-plugin-log`。

真实构建链为：log build.rs → tauri-plugin mobile build → tauri-utils `link_apple_library` → swift-rs `SwiftLinker` → 在 log 包目录执行 `swift build --build-path`。它也会进入现有 shim。[锁定 swift-rs 构建源码](https://github.com/Brendonovich/swift-rs/blob/fd82965ee1a55b2777122a9ac42a581c613327ac/src-rs/build.rs)在 Xcode 26.2 分支仍使用该调用方式。

**已取得本地复现：**以实际 log 2.9.0 的 `ios/Package.swift` 所在目录为工作目录，给现有 shim 传入 `build --build-path unused`，返回退出码 1、`SwiftPM input gate: Unaudited Swift build root: …/tauri-plugin-log-2.9.0/ios`。拒绝发生在运行 Swift 或写入包目录之前；没有更改 registry。

影响是 G1 在开始构建该包时直接失败。只补 allowlist 仍不够，最终 archive 核验的三元素集合会再次拒绝第四份证据。既有 8 项 Python 回归全部通过也不能发现这一遗漏，因为没有覆盖生产依赖根的完整集合。

**实际处理：**用户指出这套人工包清单及重复核验属于同源冗余验证，要求清理整个 G1 的同类门禁。已删除 Swift shim、包白名单、集中 lock 预置/迁移、最终 root 集合比较及相应测试，保留真实日志插件和正常工具链构建。原先“补第四个 root”的建议撤回。该拒绝路径已消除，后续仍需真实 G1 编译结果，详见 10。

### R2 P1 单 Scene 退出与主窗口重建缺口（已按 12 修复）

**项目位置：** [lib.rs](../../../src-tauri/src/lib.rs) 第 126–146 行，iOS 事件全部落入 `_ => {}`；没有 `RunEvent::SceneRequested` 的消费者。

触发条件是 UIKit 回收后台 Scene，但进程仍保留，随后重新连接该 Scene。Apple 明确允许为回收内存断开 Scene；这不同于普通切后台，也不以允许多窗口为前提。[Apple sceneDidDisconnect 说明](https://developer.apple.com/documentation/uikit/uiscenedelegate/scenediddisconnect%28_%3A%29?language=_6)

当前锁定源码链如下：

1. `tao 0.37.1 / ios/scene.rs:88–97`：`sceneDidDisconnect` 对该 Scene 的窗口发送 `Destroyed`。
2. `tauri 2.12.1 / app.rs:2709–2714` 清理窗口 manager；`tauri-runtime-wry 2.12.1 / lib.rs:4256–4271` 移除运行时窗口。
3. 最后窗口销毁会请求退出，项目没有处理这个 `ExitRequested`。runtime-wry 因而设置 `ControlFlow::Exit`；`tao / ios/app_state.rs:411` 先 `take_state()`，第 462–466 行的 iOS Exit 分支只恢复 control flow，没有 `set_state()`，留下 `app_state=None`。后续读取状态会进入 `bug!("AppState previously failed a state transition")`。这里存在事件循环状态错误风险，不能由“Exit ignored”注释推断应用能安全存活并自动恢复。
4. 即使拦截上述退出、让同一进程继续，Scene 重连时 `tao / ios/app_state.rs:519–549` 已经设置 `did_first_scene_connect`，不再运行首次 app-ready/setup，而是发出 `SceneRequested`。
5. runtime-wry 第 4344 行和 Tauri app.rs 第 2805 行只转发事件；项目忽略它，没有创建新的 `main` 窗口及 WebView。

依据：[tao Scene delegate](https://github.com/tauri-apps/tao/blob/tao-v0.37.1/src/platform_impl/ios/scene.rs)、[tao AppState](https://github.com/tauri-apps/tao/blob/tao-v0.37.1/src/platform_impl/ios/app_state.rs)、[Tauri runtime](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.1/crates/tauri-runtime-wry/src/lib.rs)、[Tauri app](https://github.com/tauri-apps/tauri/blob/tauri-v2.12.1/crates/tauri/src/app.rs)。已直接对照本地锁定包。

**源码结论与条件：**断开回调须枚举到仍登记在 runtime 的最后窗口，才会进入上述退出分支；同进程重连且没有待绑定窗口时，才会进入 `SceneRequested` 分支。两段是需要分别处理的条件路径，不能断言每次切后台都会完整经过它们。满足条件时，可能先触发框架事件循环状态错误；即使防止退出，重连仍缺少主窗口恢复入口，Swift `load` 的 WebView 替换处理也没有机会执行。P1 按潜在影响定级，发生频率和实际表现未测；未观察到 Apple 白屏、黑屏或崩溃。

**需闭合的职责：**一是 tao 退出分支的状态完整性，二是应用与 Tauri 的单主窗口恢复策略。当前应用只有声明式 `main` 配置，没有已经实现的窗口恢复 owner；不能预先断言“两处 app 回调补丁”就是最终方案。后续应分别评估框架修正和应用接入，以 Tauri 窗口注册表、实际 Scene 请求和原配置为事实源，决定是否需要整理窗口资源职责，不另建镜像存活状态，也不把窗口管理塞入业务 Swift 插件。恢复需复用 Rust 领域状态和长期 Channel，并核对重复请求、迟到事件及 WebView attach；仅拦截退出不能补回窗口。06 的保留项已有源码证据进入修复清单，但不因此阻止能取得编译事实的 G1。

### R3 P2 订阅迟到结果与失败提示缺口（已按 12 修复）

**位置：** [ios.rs](../../../src-tauri/plugins/vcp-mobile/src/ios.rs) 第 106–115 行；[lifecycle_manager.rs](../../../src-tauri/src/vcp_modules/infra/lifecycle_manager.rs) 第 338–344 行；[events.rs](../../../src-tauri/plugins/vcp-mobile/src/events.rs) 第 90–119 行；[useNotificationProcessor.ts](../../../src/core/composables/useNotificationProcessor.ts) 第 153–166 行。

当前 5 秒超时只停止等待，底层 receiver 仍保活，这是必要的安全处理。但 bootstrap 把超时和真正 reject 一律记为 `events` 失败；迟到完成结果随被丢弃的 JoinHandle 失去消费者，后续成功事件不会纠正该失败提示。这里确认的是条件成立时的代码行为，尚未在 Apple 环境观察到超过 5 秒的注册。

| 分支 | 当前结果 | 用户实际需要知道 |
|---|---|---|
| 原生主队列超过 5 秒，随后注册成功 | 生命周期/网络 Channel 已建立，失败提示不会因订阅成功自动撤回；手动清除或 WebView 重建等仍可能使其消失 | 尚未完成不能等同于失败；若展示等待状态，应随真实结果更新 |
| 注册真正 reject，未建立首个快照 | 本进程不重新订阅；iOS 首个 phase 门禁持续阻止中断流恢复 | 需关闭并重新打开应用，单纯保持前台不能修好 |

实际文案是“无法可靠接收应用前后台状态变化，后台保活可能受影响。请保持应用在前台使用。”它不足以表达 iOS 的故障影响与恢复办法。`BootScreen` 的 iOS“重试启动”只重新执行前端 bootstrap/能力查询，不会重新安装原生订阅。

**重新评估后的方案方向：**能力查询是前端等待的短请求；订阅注册在核心 READY 后由独立任务持有，不阻塞 bootstrap 返回，两者没有共用 5 秒终止等待策略的必然理由。优先评估订阅持续等待唯一一次真实 resolve/reject、能力查询保留有限等待，让结果始终回到现有订阅 owner。保留单在途和底层 receiver 保活；若调整 helper，应按实际调用语义拆分等待策略。当前没有足够理由先增加三态协议、成功撤警事件或重新注册机制。真实 reject 仍需准确告知恢复方式；建议文案：“原生状态监听未能建立，部分恢复功能暂不可用。请关闭并重新打开应用。”本轮只修订设计判断，未实施该方案。

另外，Swift 运行期 `failSubscription` 目前只清理资源并写日志，能力快照也不会自动刷新到 UI。不过当前 `Channel.send` 只有 JSON 编码能抛错，现有载荷仅字符串、Bool、UInt64，未找到正常输入的具体失败触发。仅记录这一不确定性，不据此立项增加新的故障协议，也不另算已复现运行缺陷。

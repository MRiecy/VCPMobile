# 05. 文件、媒体、分享、通知与设备能力

## 1. 总体原则

iOS 原生层的职责不是接管附件业务，而是把系统资源安全地交给现有 Rust owner：

```text
Apple picker / camera / photo / share extension
  -> bounded staging file + factual metadata
  -> Rust validate path/type/size/hash
  -> existing attachment CAS + DB commit
  -> cleanup ticket
```

任何 Swift 路径都不应绕过 Rust 的路径、大小、hash、所有权和清理边界。

## 2. 数据目录重构

当前附件根目录通过 `document_dir()` 后 `pop()` 推导，带有 Android 路径结构假设。iOS 施工前应按数据性质明确目录：

| 数据 | 推荐容器 | 备份/清理语义 |
|---|---|---|
| SQLite、用户设置、聊天/日记正文 | app support/data | 持久、迁移、受保护；是否备份需产品决策 |
| 附件 CAS 原件 | app data 或明确 documents | 持久；按用户数据策略备份 |
| 可重建缩略图/预渲染 | caches | 不备份，可被清理，必须可重建 |
| picker/camera 临时导入 | temporary/staging | 有 ticket、超时和异常清理 |
| Share Extension 交接 | App Group container | 最小数据、短生命周期、host 消费后清理 |
| background URLSession 文件 | 系统/受控 download staging | completion 后原子移入，失败可重试 |

必须设计 Android 既有路径到跨平台目录的迁移，不能在 iOS 上简单改变函数后让 Android 数据失联。

## 3. Files 与 security-scoped URL

[attachmentStore.ts](../../src/core/stores/attachmentStore.ts) 已有非 Android HTML `<input>` fallback，但它只是候选路径，不等于完整 iOS 文件系统集成。对于系统 Files provider，建议 Swift 使用 `UIDocumentPickerViewController`。参见 [Apple Document Picker](https://developer.apple.com/documentation/uikit/uidocumentpickerviewcontroller)。

推荐流程：

1. 用户显式发起 picker；
2. Swift 获得 URL 后在授权窗口内协调访问；
3. 检查文件是否为 regular file、大小上限、UTType 和可读性；
4. 流式复制到本 App staging，避免长期持有 provider URL；
5. 返回 `ticket/path/name/size/declared_type`；
6. Rust 重新 canonicalize、探测真实 MIME、计算 hash、注册附件；
7. 成功或失败都按 ticket 清理。

不要：

- 把外部 security-scoped URL 当永久内部路径存库；
- 在 Swift 一次性读完整大文件再 Base64 穿过 IPC；
- 只相信扩展名/UTType；
- 为方便测试扩大 asset protocol scope。

## 4. 相机与照片

### 4.1 相机输入

HTML `<input capture="environment">` 可作为低成本候选，但具体呈现、元数据、HEIC、方向和内存都依赖 WKWebView。若核心旅程要求稳定相机体验，应使用 Swift/AVFoundation 或系统 picker，并保持输出进入 staging。

必须覆盖：

- `NSCameraUsageDescription`；
- first ask、denied、restricted、Settings 恢复；
- HEIC/JPEG、方向、色彩空间和 Live Photo 是否接受；
- 超大原图的缩放/编码预算；
- 用户取消不视为 error toast；
- 模拟器只能验证权限/UI 流，真实质量需真机。

参见 [Requesting Authorization to Capture and Save Media](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media)。

### 4.2 照片选择与照片库访问

照片能力至少拆成四条，不能共用一个 `limited/denied` 状态：

| 能力 | 系统路径 | 授权事实 |
|---|---|---|
| 拍照 | 相机/AVFoundation 或系统 camera UI | camera authorization 独立 |
| 用户选择照片 | `PHPickerViewController` 候选 | 系统私密选择通常不要求 App 先取得整个照片库 read/write 权限；返回项仍需 staging/大小/MIME 验证 |
| 只保存到相册 | PhotoKit add-only | 记录 requested access level 与该 level 的 authorization status；不能无条件套用 `limited` |
| 直接浏览/管理照片库 | PhotoKit read/write | 只有产品确需时请求；此时才处理 limited library 范围与选择变化 |

参见 [PhotoKit privacy guidance](https://developer.apple.com/documentation/photokit/delivering-an-enhanced-privacy-experience-in-your-photos-app)。

### 4.3 保存照片

`save_image_to_gallery`/`save_image_from_path` 可用 PhotoKit 做 add-only 实现：

- 使用最小照片写入权限和用途说明；
- 分别记录 add-only access level 与其 `notDetermined/authorized/denied/restricted` 等实际状态；若另有 read/write 能力，再单独处理 limited library；
- 先验证 sandbox path、UTType、文件大小和实际图像解码；
- 返回真实 local identifier/结果，不伪造 Android URI；
- 保存失败不删除原始附件。

参见 [PHPhotoLibrary](https://developer.apple.com/documentation/photos/phphotolibrary)。

## 5. Outgoing Share 与 Incoming Share

两者是不同产品能力，不能共用“分享”一个勾选框。

### 5.1 Outgoing Share

从 VCPMobile 分享文本、图片或文件可使用 `UIActivityViewController`：

- iPhone 模态呈现；
- iPad 必须提供正确 popover source；
- 大文件用 file URL/item provider，不先转 Base64；
- completion 只表示系统 sheet 结束，不一定表示目标 App 成功处理；
- capability 可在 MVP 中独立实现。

参见 [UIActivityViewController](https://developer.apple.com/documentation/uikit/uiactivityviewcontroller)。

### 5.2 Incoming Share

从其他 App 分享到 VCPMobile 需要独立 Share Extension，不是普通插件 command：

```text
Share Extension process
  -> validate input count/type/size
  -> copy to App Group staging
  -> atomically write immutable manifest/ticket
  -> complete extension request; do not assume it can open host App
Host App
  -> claim ticket once on its next normal/approved activation
  -> Rust validate/hash/CAS/DB
  -> mark consumed + cleanup
```

Apple 的 extension 生命周期边界只允许 Today widget 请求系统打开 containing App；Share Extension 不能靠 `openURL` 强拉主 App。首期交接必须允许“分享已暂存，主 App 下次正常打开后导入”，不得使用 responder-chain 等非公开绕行。若产品要求分享后立即进入主 App，需要另行核验当期公开的系统入口，不能把它作为既定能力。参见 [Understand How an App Extension Works](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/ExtensionOverview.html)。

所需新增面：

- 第二个 Bundle ID；
- Extension target；
- host/extension 一致的 App Group entitlement；
- 独立 provisioning profile；
- 激活规则、超时、内存预算；
- 多文件/大文件、冷启动/热启动、重复投递测试；
- ticket generation、claim owner 和过期清理。

Extension 不应启动 Rust Chat 核心、写主 SQLite、连接 VCP server 或持有长期状态。参见 [Apple Share Extension](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/Share.html)。

建议：incoming share 不进入前台 MVP，除非用户明确把它列为首发硬需求。

## 6. 录音、语音识别与音频附件

当前 Web 录音会探测 `audio/webm`、OGG、MP4、WAV，但附件和 Whisper 上传固定 `.webm`。这在 iOS 上是 P0 数据契约缺陷。

建议统一 recorder result：

```text
bytes/path
actual_mime
container
codec (if known)
duration_ms
suggested_extension
```

规则：

- 文件名从实际容器派生；
- Rust 再用魔数/解码器验证；
- 服务端 STT multipart 使用真实 MIME 和扩展名；
- 录音权限拒绝、音频 route 中断、来电/锁屏中断有独立 terminal reason；
- 长录音避免整段 `Uint8Array -> Tauri IPC -> Base64 JSON` 多次复制；
- Phase 0/3 必须冻结最大录音时长、最大累计字节和预计峰值内存；当前每 250ms 产生 chunk 仍会把 chunks 留在数组并在结束时整体 `arrayBuffer()`，不能把 timeslice 当作内存问题已解决；
- 超限、用户取消、音频 route 中断、后台中断都必须停止 recorder、释放 track、删除未提交 staging；超过 Web 路径预算时采用原生文件/分块 staging；
- Web Speech API 只能 feature-detect，不能作为 iOS 产品承诺；云端 Whisper 是明确的 fallback。

真机必须验证：

- WKWebView `MediaRecorder` 实际 MIME；
- 蓝牙/听筒/扬声器 route；
- 中文听写与第三方键盘；
- 锁屏/来电/切后台；
- 麦克风指示与资源释放；
- 服务器对 MP4/M4A/WebM 的接收。

## 7. 图片、视频与文档处理

### 图片与附件预算

当前不是一个统一的“5 MB 图片上限”，而是多条不同路径：

- 附件 import 的 WebView IPC 小文件路径约束为 `<2 MiB`，更大文件另走本地 XHR/受控路径；
- 非 GIF 图片附件还有约 10 MiB 的前端约束；
- Rust 多模态图片转换的非 Android 整文件 Base64 fallback 使用 5 MiB 级预算，它不代表整个附件导入链；
- HEIC 等格式的候选转换仍应输出受控 staging，由 Rust 管理，而不是放宽某一条 Base64 IPC 上限。

施工时必须把 import、multimodal conversion 与 extractor 三套预算分别写进 capability/test，不得把 MB/MiB 或一条 fallback 外推为全链上限。

### 视频

当前视频抽帧只有 Android 实现。首期有两种诚实选择：

1. `unsupported/deferred`，附件仍可作为文件发送但不做视觉抽帧；
2. Swift AVFoundation 抽帧到 staging，每帧设像素、数量和总字节上限。

不应在内存里构造一批约十几 MB 的 Base64 字符串再跨 IPC。

### Office/PDF/文本

Rust file extractor 静态看来是复用候选；当前边界包括 50 MiB 级输入文件上限与一千万输出字符上限。PDF/Office 解析和并发预渲染必须进入 iOS memory pressure 测试，Apple compile/link 与真机 jetsam 证据前不能写“已复用”。

## 8. 通知能力分层

| 能力 | iOS 结论 | 说明 |
|---|---|---|
| App 内 Toast/通知中心 | 复用 | Vue/Pinia 现有能力 |
| 本 App local notification | 可实现 | UserNotifications；按上下文请求权限 |
| remote notification/APNs | 可选二期 | 需服务端 token、环境、隐私和恢复协议 |
| notification click/deep link | 可实现 | 缓存本 App response，交现有路由 owner |
| Android ongoing download notification | 不等价 | 默认用 App 内进度；Live Activity 是独立 ActivityKit 产品能力，不是普通通知替身，需单独的系统版本、生命周期和价值门禁 |
| 监听其他 App 通知 | 不支持 | iOS 无 NotificationListenerService 等价 |
| 读取系统通知历史 | 不支持 | `get_pending_notification` 只能表示本 App 待处理 response |

权限应在用户启用相关功能时请求，先查询当前状态并提供拒绝后的 Settings 路径。参见 [Asking Permission to Use Notifications](https://developer.apple.com/documentation/usernotifications/asking-permission-to-use-notifications)。

## 9. 屏幕常亮、电池、网络和热状态

### 屏幕常亮

`UIApplication.isIdleTimerDisabled` 可近似实现屏幕常亮，但必须：

- 继续由现有引用计数/owner 控制；
- App inactive/background 时收回；
- 异常退出或最后 owner 释放时恢复；
- UI 不把它描述为后台保活。

参见 [UIApplication.isIdleTimerDisabled](https://developer.apple.com/documentation/uikit/uiapplication/isidletimerdisabled)。

### Battery

可获得有限的电量和充电状态，并可观察 Low Power Mode；普通 App 没有当前 Android DTO 中“电池温度 25°C”的公开等价。温度字段必须 nullable/unsupported，不能以固定值填充。

### Thermal

`ProcessInfo.thermalState` 返回 nominal/fair/serious/critical 等系统热压力，用于降载，不是 CPU 摄氏温度。DTO 和 UI 必须改名。参见 [ProcessInfo Thermal State](https://developer.apple.com/documentation/foundation/processinfo)。

### Network

`NWPathMonitor` 可提供连接路径、接口、昂贵/受限状态；它不保证 VCP endpoint 可达，也不保证稳定获得本机 IP 或链路速度。

## 10. 传感器与 Distributed 工具

| 当前工具/数据 | iOS 候选 | 产品结论 |
|---|---|---|
| Location | Core Location | 只在用户明确用途下请求；后台另行审核 |
| Motion | Core Motion | 前台候选，按设备 capability |
| Barometer | Core Motion/altimeter | 设备可能无硬件，nullable |
| Ambient light | 无普通 Android TYPE_LIGHT 等价 | MVP 不支持 |
| CPU temperature | 无公开等价 | 用 thermal state 替代并改名 |
| GPU renderer/load | Metal device name 部分可取 | 不声称 GPU load；字段重定义 |
| Root/Shell | 无 | 永不广告 |
| Clipboard | UIKit/Tauri 官方插件候选 | 只在用户操作中读写；未实现不广告 |
| System local notification | UserNotifications | 只代表本 App 发出的系统通知；与 Vue Toast/通知中心及 APNs 分开 |

Distributed registry 必须消费同一 `PlatformCapabilities`：

- 平台不支持：不注册；
- 设备无硬件：不注册或标 unavailable；
- 用户未授权：不注册，或只注册显式请求授权的安全动作；
- 当前后台：整个 Distributed session offline；
- 所有结果返回真实时间、来源和可用性，不返回演示数据。

参见 [Core Motion](https://developer.apple.com/documentation/coremotion/)。

## 11. 剪贴板与隐私体验

当前非 Android **native/Distributed clipboard command** 读返回 placeholder、写入无操作成功；普通 Vue 交互中另有多处直接使用 `navigator.clipboard`，两者不能混为“整个前端剪贴板不可用”。iOS 必须对两条路径分别选真实实现与 feature-detect：

- 用户点击“复制”时写入剪贴板；
- 用户明确点击“粘贴”时读取；
- 或使用经过审计的 Tauri 官方 clipboard 插件；
- 不在后台/启动时自动读取；
- 不实现时返回 unavailable，不能返回假内容。

## 12. 能力候选池（不替代 MVP manifest）

本节只列出可选能力和依赖关系。[08-分期实施路线图与验收门禁](./08-分期实施路线图与验收门禁.md) 中由 Phase 0 产出的版本化 MVP manifest 才是某个 Beta 的范围真源。未被选中不等于技术否定，也不得因为出现在本列表就默认阻塞核心 Beta。

### 可由 Phase 0 选入首个 Beta 的独立 slice

- Files picker + staging；
- camera（HTML/system 候选）；
- PHPicker 照片选择；
- PhotoKit add-only 图片保存；
- 外部打开/outgoing share；
- MIME 正确的录音/Whisper；
- 系统 local notification（不包括现有 App 内 Toast/通知中心，也不包括 APNs）；
- screen awake；
- battery/network/thermal 的有限事实；
- Distributed capability 过滤。

每个 slice 都必须单独列 owner、授权状态、真机门禁和失败降级；不能把上述项目捆成一个“媒体 MVP”。

### 推荐默认延期

- incoming Share Extension；
- background URLSession；
- APNs；
- Live Activity；
- 视频抽帧；
- location/motion/barometer；
- 更丰富的 clipboard/haptics。

### 永不对等

- Root、Root manager；
- 跨 App 通知监听；
- Android Wake/Wi-Fi Lock；
- OEM auto-start/battery whitelist；
- 程序化退后台；
- APK/IPA 自安装更新。

# 08. 分期实施路线图与验收门禁

## 1. 路线原则

本路线以“前台核心客户端”为首个可交付目标，不以 Android 功能逐项复刻为目标。实施时必须遵守四条边界：

1. Vue/Pinia、Rust 业务 owner 和现有生命周期 generation/cancellation 机制继续作为唯一事实源；
2. Swift 只实现平台适配、权限、文件桥接与原生事件，不创建第二套 Chat、Sync、Distributed 状态机；
3. 平台支持度、当前实现度、用户授权和运行资格必须是独立事实，禁止非 Android fallback 继续伪成功；
4. 每一阶段都按证据等级退出，Linux 静态检查、macOS 编译、Simulator、真机与 TestFlight 不得互相替代。

在任何产品代码施工前，还需遵守仓库的重构存档协议：先确认工作区既有修改的 owner 和范围；若将新增模块目录、拆分大文件或修改跨模块调用链，先建立可恢复存档。存档不等于替用户提交，未经授权不得 commit 或 push。

## 2. 总体路线

```text
Phase 0  产品契约冻结
   ↓
Phase 1A 平台中立能力契约
   ↓
Phase 1B macOS/Simulator 构建尖峰
   ↓
Phase 2  前台核心 MVP ───────────────→ Phase 5A 上传候选/内部 Beta
   ├─→ 被 MVP manifest 选中的 Phase 3 slices ─┘
   └─→ 可选 Phase 4A/4B/4C 项目 ─────→ 后续 Beta
Phase 5B 外部 Beta → Phase 5C App Review/发布
```

Phase 0–2 是“纯文本前台核心”的最短实现主线。这里的“工程 Beta”只表示 Phase 2 指定设备开发签名验证；“平台服务 Beta”表示并入了被选中的 Phase 3 slices；“TestFlight Beta”必须再取得 Phase 5A/5B 的分发证据。Phase 0 若把附件、系统 local notification 或媒体列入某个 Beta，相应 Phase 3 slice 才成为该 Beta 的必经项；Phase 4 的三个项目都不是前台核心 Beta 的默认前置条件。Phase 5 是递进的分发状态，不是一次性总门禁。

## 3. Phase 0：冻结产品与合规契约

### 输入

- 本专项 00–09 文档；
- 41 条命令矩阵；
- 服务端是否支持 request ID、游标、结果补取与 APNs 的事实；
- 最低系统/设备/Bundle ID 的候选范围，以及 Apple 资源当前库存与获取计划。

### 工作项

- 对 [09-待决策清单](./09-Magi综合裁决与待决策清单.md) 的 P0 项逐项签字；
- 冻结 iOS MVP 功能表，明确 15 条 `X` 是从 iOS capability 移除，还是仅在旧调用迁移期由 compatibility handler fail-closed；
- 冻结“前台优先 + 确定性收口 + 有协议才恢复”承诺，不使用“后台常驻”“Android 等价”等表述；
- 确认 LAN HTTP/WS、incoming Share、APNs、iPad 多窗口是否进入首发；
- 指定 Apple 发布、隐私说明和设备验收 owner。

### Phase 0 必须产出的 MVP manifest

以下表格是推荐初始值，不是替用户完成决策。每个 Beta 都必须保存一份带版本和 owner 的实例，后续范围变化走显式变更记录。

| 范围层 | 推荐初始内容 | 进入该 Beta 的条件 |
|---|---|---|
| 核心必选 | 启动/配置、Chat、Diary、Settings、SQLite、现有 App 内 Toast/通知中心、前台网络与 Sync、生命周期确定性收口、Android-only UI 退出 | Phase 2 全部门禁通过 |
| 按决策并入 | Document Picker、camera、PHPicker 照片选择、PhotoKit add-only 保存、外部打开/outgoing share、录音、系统 local notification、screen awake、有限设备事实、Distributed | 逐项选择 Phase 3 slice，并通过该能力的授权/真机/隐私门禁；“附件/相册/导出/通知”不得作为含糊总项 |
| 独立可选项目 | Chat 服务端 continuation、APNs、incoming Share Extension | 分别进入 Phase 4A/4B/4C；不因“Phase 4”名称互相捆绑 |
| 推荐延期 | background URLSession、Live Activity、视频抽帧、位置/运动/气压计、丰富 clipboard/haptics | 有明确用户旅程、协议和合规依据后另行立项 |
| 永不对等 | 15 条 `X` 对应的 Android-only 语义 | 从正常 capability 与 UI 退出；不得用假成功补位 |

### 退出门禁

- [ ] 有一份版本化的产品能力表，每项都分别填写 `support`（supported/degraded/unavailable_by_platform/unknown）、`implementation`（not_implemented/partial/implemented）、`authorization`（not_applicable/not_determined/granted/denied/restricted）和 `runtime.policy/state/eligibleNow`；
- [ ] 同一版本的 MVP manifest 已把每项标为核心必选、按决策并入、独立可选或延期，并记录 owner；
- [ ] 15 条 `X` 均有唯一 UI/API 迁移行为，稳定态不授权与迁移期 handler 方案不混用；
- [ ] 最低系统、设备与 Bundle ID 已形成 spike 候选；Mac、签名/Team、真机与发布资源分别有 owner 和最晚到位阶段；资源尚未到位不阻止纯契约的 Phase 0/1A；
- [ ] 服务端恢复能力已确认，不把未知项写成客户端承诺；
- [ ] 对是否进入 Phase 1 有明确 `GO / HOLD / NO-GO`。

### 此时允许的声明

“iOS 产品范围已经冻结。”不得声明“iOS 已实现”或“能够构建”。

## 4. Phase 1：平台中立能力层与 macOS 构建尖峰

Phase 1A 可在现有环境开始设计和测试；Phase 1B 必须在 macOS 上完成，但 Simulator spike 不要求先取得 distribution 证书、付费 Team 或真机。二者都通过才可进入 MVP 施工。

### Phase 1A：收紧共享契约

- 引入 typed `PlatformCapabilities`，拆分 support、implementation、authorization 和 runtime policy/state/eligibility；
- 建立 `MobilePlatform`/facade 边界，Vue 不直接通过 UA 猜测命令；
- 把非 Android 的权限、硬件、通知、文件删除、剪贴板等伪成功改为 fail-closed 的结构化结果；
- 在现有 Rust Chat、Sync、Distributed、lifecycle owner 内补生命周期 cancel/join/settle 与回执，不复制状态机；
- 明确 updater 在 iOS 只提供 Store/TestFlight 版本提示，不走 APK 安装；
- 为 Android 现有语义补回归契约，避免平台抽象破坏生产目标。

### Phase 1B：最小 Apple 工程尖峰

- 在受控 macOS 上安装完整 Xcode、CocoaPods 和 Rust Apple targets；
- 执行 `pnpm tauri ios init`，审查生成树后再决定哪些文件纳入版本控制；
- 建立最小 Swift 插件骨架，证明同步 command、异步 command、错误和事件四种通路；
- 验证 SQLite、网络、Rust TLS、Tauri plugin 集合和现有依赖能为 Apple target 编译与链接；
- 显式设置 deployment target、Bundle ID、Info.plist、entitlements 和 capabilities；
- 未实现命令要么不进入 iOS capability/授权，要么仅在旧调用迁移期由 compatibility handler 返回 `unavailable_by_platform`；不复用开发 fallback。

### 退出门禁

- [ ] macOS 分别完成 device `aarch64-apple-ios` 与 runner 对应 simulator target（Apple Silicon 通常为 `aarch64-apple-ios-sim`）的 locked check；最终 target 以当期 Tauri/Xcode 工具输出冻结；
- [ ] 无 distribution 签名的 Simulator Debug build 成功；device target 至少完成编译/链接可达性检查，具体命令按冻结的 Tauri/Xcode 版本记录；
- [ ] iPhone 与 iPad Simulator 至少各启动一次，并完成 Rust↔Swift↔Vue smoke；
- [ ] 生命周期、网络和错误事件不会重复注册或丢失 owner；
- [ ] Android 的 `pnpm check`、前端测试、Rust 测试和插件契约测试通过；
- [ ] 41 条命令在 iOS capability 表中无“未知默认成功”。

### 失败退出条件

若关键依赖无法支持 Apple target、必须大规模 fork Tauri/核心依赖，或最小 command/event 通路不能稳定建立，应暂停并重新评估技术路线，不得直接扩展 Swift 功能面。

### 此时允许的声明

“Apple Debug 工程可构建并完成 Simulator 桥接 smoke。”仍不得声明真机兼容、后台可靠或可提交审核。

## 5. Phase 2：前台核心 MVP

### 目标用户旅程

1. 首次启动完成真实 capability discovery 与用途解释；不批量请求可选权限，也不复活 Android PermissionGate；
2. 配置服务器，进入核心 Chat/Diary/Settings；
3. 前台发起、流式接收和取消会话；切后台时确定性收口，无服务端 cursor 时返回明确 interrupted；
4. 前台执行 Sync，切后台后安全收口，返回时按本地 generation/设置决定是否重建客户端 session；
5. 若 Phase 0 已选定基础附件，则完成对应 Phase 3 Document Picker/staging slice；
6. 正常冷启、热启、短暂 inactive、锁屏、旋转、分屏和内存压力后不产生重复 owner。

### 关键施工

- Swift 提供聚合 scene snapshot + monotonic sequence，并与 Rust lifecycle epoch 对账；MVP 不启用多窗口 Scene；
- Apple background-task token 与 Rust drain outcome 建立 exact-once 回执；
- 动态 CSS safe-area 与 `visualViewport`/原生键盘候选分别进入现有 Insets owner，只有设备证据支持时才用原生值覆盖 CSS；
- 先在 Tauri/Wry spike 证明是否存在原生返回手势，再与应用横滑抽屉仲裁；无论结果如何都取消全屏误触入口；
- 设置输入与核心触控命中达到已冻结的可访问性标准；
- 若 D11 允许页面缩放，同时治理 viewport meta 与全局 `touch-action`；viewer 自定义 pinch 只做局部声明；
- modal/sheet 补焦点进入与恢复、背景 inert、键盘关闭闭环；装饰 WebGL 在 hidden/reduced-motion 时停 rAF，并处理 context loss/restore；
- Chat 在既有 attempt owner 内补 lifecycle cancel/join/settle；只有 Phase 0 已证明的服务端 cursor 才启用补取，否则明确终止；
- Sync 保留现有 epoch/generation/cancel/join 结构；
- 若 MVP manifest 选中 Distributed，则只注册 iOS 真实 capability，前台运行且默认不承诺后台；
- 文件路径全部限定为 app container 或经授权后复制的 staging。

### 退出门禁

- [ ] 核心旅程在 iPhone/iPad Simulator 通过自动化或可复现 smoke；
- [ ] 至少一台受支持 iPhone 真机完成安装、冷启、网络、键盘和生命周期测试；附件只在被选入时阻塞；
- [ ] 若 D5 把 iPad 纳入该 Beta 声明，至少一台 iPad 真机或经批准的外部设备完成布局、modal focus、键盘与可访问性旅程；
- [ ] 后台超过系统容忍时间后，返回前台给出明确终态；只有已验证 server cursor 路径才允许恢复，且不出现永远 pending；
- [ ] 所有 `X` 能力在普通 UI 中无误导入口；
- [ ] Android 生产关键旅程无回归。

### 此时允许的声明

“iOS 前台核心工程 Beta 候选已完成指定 development-signed 设备验证。”必须同时列出设备、系统版本和未支持能力；取得 Phase 5A 证据前不能写成 TestFlight Beta，更不能泛化成“全面兼容 iOS”。

## 6. Phase 3：文件、媒体、通知与平台服务

按真实需求从下列能力中选择，不默认全做：

| 能力 | 推荐顺序 | 主要门禁 |
|---|---:|---|
| Document Picker + staging | 1 | security-scoped URL、超限、取消、重复导入 |
| Camera | 1 | 独立 camera authorization、取消、EXIF/方向、内存峰值、用途说明 |
| PHPicker 照片选择 | 1 | 不预申请全库权限、provider staging、EXIF/HEIC、取消 |
| PhotoKit add-only 保存 | 1 | requested access level/status、重复保存、授权变化；不混入 read/write limited library |
| 外部打开/outgoing share | 1 | Quick Look/UIActivityViewController、iPad popover、敏感文件清理 |
| 系统 local notification | 2 | UserNotifications 授权、deep link、前后台行为；与 App 内 Toast 和 APNs 分开 |
| 录音 | 2 | 真实 MIME/扩展名、最大时长/累计字节/峰值内存、取消清理、服务端接受格式 |
| background URLSession 文件传输 | 3 | 系统重启/进程终止后的 delegate 恢复与幂等提交 |
| 运动/定位/气压计 | 需求驱动 | 用途、权限、数据最小化、后台资格 |

### 退出门禁

- [ ] 每项能力都有 capability、授权拒绝、撤销授权和平台限制测试；
- [ ] 所有临时文件都有 owner、大小上限、清理时点和 canonical containment；
- [ ] 音频/图片/视频 MIME、扩展名和服务端 Content-Type 一致；
- [ ] Info.plist/PrivacyInfo 与实际代码路径一致；
- [ ] 真机峰值内存、相机取消、低存储和锁屏路径有记录。

### 此时允许的声明

只能逐能力声明，例如“相册写入已在列出的设备与授权状态通过”，不得以一个能力外推整个媒体链。

## 7. Phase 4：恢复型后台、incoming Share 与 APNs

该阶段包含三个独立项目，不应捆绑成一个“大后台功能”：

### 4A. Chat 服务端 continuation 与 Sync 协议恢复

- Chat 若需设备挂起后继续生成，由服务端持有 generation continuation/result owner；客户端用稳定 request ID、游标或结果版本补取；
- Sync 会话 owner 仍是 Rust `SyncState`；服务端只提供 hash、receipt 与协议状态，不能再建立第二套客户端执行 owner；
- 进入后台时提交有限收尾任务，超时即停止本地工作；
- 返回前台后按各自 owner 对账，不盲目重放副作用请求。

### 4B. APNs 可选唤醒/结果通知

- APNs 只用于通知用户或提示拉取结果，不承诺静默推送必达或持续执行；
- token、环境、用户解绑和 deep link 有明确 owner；
- 未授权通知不影响前台核心功能。

### 4C. incoming Share Extension

- 独立 Extension target、Bundle ID/profile 与 App Group；
- Extension 只做最小 staging 和元数据记录；
- 主 App 通过幂等队列导入，不让 Extension 承担数据库/网络长任务；
- 失败、重复、过大文件和共享容器清理均有契约。

### 退出门禁

- [ ] 后台恢复测试覆盖进程挂起、杀进程、断网、重复通知、重复回调；
- [ ] 服务端幂等和结果保留窗口有可验证契约；
- [ ] APNs 或 Extension 的签名、App Group 和隐私配置有独立 CI/人工清单；
- [ ] 没有使用 background mode、silent push 或 Extension 规避平台限制；
- [ ] 不再沿用 Android FGS/helper/WakeLock 术语向用户承诺。

## 8. Phase 5：递进式分发与发布门禁

### Phase 5A：上传候选与内部 Beta

- Archive、签名、导出和上传链在干净 macOS runner 可复现；
- 上传成功与 App Store Connect 处理成功分别记录；首次上传不以前一轮 TestFlight 成功作为前置条件；
- 内部 TestFlight 设备完成冻结的核心旅程，崩溃和 WebKit reload 可查询；
- 只有被该 Beta manifest 选中的 Phase 3/4 slice 才阻塞这一阶段。

### Phase 5B：外部 Beta

- 外部测试所需的 Beta App Review、测试说明与出口合规状态完成；
- 外部组覆盖冻结的设备/系统范围，而不是笼统要求“所有 iOS”；
- 反馈按 build SHA、设备、系统、网络和 capability state 回流。

### Phase 5C：App Review 与发布

- App Store Connect 中隐私问卷、截图、年龄分级、审核备注和支持链接齐全；
- 账号、LAN server、加密/明文模式与特殊硬件均向审核人员提供可复现说明；
- protected Git tag/checkout SHA、源码 marketing version、archive 实际 `CFBundleShortVersionString`、单调 `CFBundleVersion` 与 IPA SHA-256 可追踪；
- 审核通过后才取得 `APP-REVIEW-APPROVED`；一次拒绝只是整改证据，不是发布门禁通过。

### 最终发布门禁

- [ ] 所有 P0 缺陷关闭，或相关能力/发布声明已从本版本下架；只有 P1 才可经书面风险裁决延期；
- [ ] `DEVICE-VERIFIED(scope)` 已按冻结矩阵取得，不以单设备外推未覆盖设备族；
- [ ] `APP-REVIEW-APPROVED` 已由审核通过事实取得；
- [ ] Release UI 不展示 Root、通知监听、OEM 权限或 APK 更新入口；
- [ ] Android Release 与现有 CI/CD 未被 iOS 分支破坏；
- [ ] 发布说明明确前台/后台、LAN、Share、通知与设备能力边界。

## 9. 资源与周期粗估

下表是工程量的 `person-week` 粗估，不是日历工期或发布日期承诺。假设一名熟悉现有 Vue/Rust/Tauri 的主力工程师，有兼职 Swift/发布支持；首次 Apple 平台集成误差建议按至少 `±50%` 管理。账号开通、设备采购、TestFlight 处理和 App Review 是独立外部 lead time，不包含在工程量里，也不能由代码仓库保证。

| 范围 | 粗估 | 主要不确定性 |
|---|---:|---|
| Phase 0 | 0.5–1 person-week | 产品范围与服务端事实确认 |
| Phase 1A+1B | 1–2 person-weeks | Apple target 依赖、生成工程、Swift bridge |
| Phase 2 | 3–5 person-weeks | WebKit、生命周期确定性收口、iPad、Android 回归 |
| Phase 3 选定 slices | 合计 2–4 person-weeks 起 | 只在 manifest 冻结后按真实集合重估 |
| Phase 4A Chat continuation | 2–4 person-weeks 起 | 服务端协议、结果保留、幂等与移动端对账 |
| Phase 4B APNs | 1–3 person-weeks 起 | provider、token 环境、deep link、运维与隐私 |
| Phase 4C Share Extension | 2–4 person-weeks 起 | 新 target、App Group、staging 与签名矩阵 |
| Phase 5 工程工作 | 1–2 person-weeks 起 | 自动化、材料与缺陷修复；外部等待另计 |

因此只能在 Phase 1 spike 后，结合选定 slices 与可并行人数换算日历计划；本文不再用“6–10 周”把工程量、账号/设备到位和 Apple 外部处理时间混成一个发布日期。

## 10. 回滚与停止规则

任一阶段出现以下情况，应停在当前 evidence state，不得用产品文案掩盖：

- 必须使用私有 API、越狱能力或不真实 background mode 才能满足核心承诺；
- 不接受 15 条 `X` 的不可用语义；
- 服务端无法提供恢复/幂等，但产品仍要求后台持续生成必达；
- 无 Apple Team、合规 Mac runner 或受支持真机，却要求 Release 结论；
- 平台抽象要求复制 Chat/Sync/Distributed owner；
- iOS 改造持续破坏 Android arm64 生产路径且没有可隔离修复。

停止不等于项目失败，而是将结论保持为 `RESEARCHED`、`MACOS-BUILD-PENDING` 或对应阶段，等待产品范围、资源或外部系统发生真实变化。

## 11. 完成定义

本专项最终完成不以“存在 `gen/apple`”为标准，而以以下闭环为标准：

```text
产品承诺
  = capability 真值
  = Vue 可见状态
  = Rust 单一 owner 行为
  = Swift 公开 API 行为
  = CI/Simulator/真机证据
  = Info.plist/PrivacyInfo/App Review 声明
```

## 结论

这三个部分需要作为同一次群聊能力升级设计，但不需要重写聊天生成或整个同步系统。推荐先建立完整的群配置与同步契约，再完成顺序配置和群设置重构，随后接入 JEV 服务及持续会话编排。

**同步插件当初有考虑 DTO 的集中抽取与白名单复用，但没有形成覆盖 JS、桌面 Rust 数据服务和 Mobile 的单一契约。** 新增字段并非只改 `dto/group.dto.js`：默认值、新建配置、双向应用、CDS 投影、Mobile 类型、SQL 装配、hash 和升级迁移都参与。可以收拢这些入口，保留现有传输框架。

目前已确认的主要问题：

| 发现 | 实际影响 | 证据性质 |
|---|---|---|
| `modeSettings` 未进入同步投影 | 只调整 JEV 参数或顺序不改变群 hash；新建同步群不携带这些配置 | 源码与生产 JS 函数内存探针 |
| 自然随机有 nested 权威字段及旧 flat 镜像 | 手机回推旧 flat 字段后，桌面仍可能使用 nested 旧值 | 完整读写调用链 |
| legacy JS DTO 已包含群上下文窗口，Mobile 严格 DTO 不接受 | legacy 群下载存在反序列化失败；CDS 路径则没有传递该能力 | 源码，未运行真实双端同步 |
| 新 schema 的默认值与 hash 不是普通用户编辑 | 不处理首次补齐和时间戳，可能覆盖桌面既有新配置或手机离线修改 | 基于现有整实体 LWW 的迁移风险推导 |
| 同步插件锁未覆盖桌面正常群配置保存 | 同步目录内的条件写可改善已检测冲突，但不能宣称所有桌面同时编辑都严格无丢失 | 双方实际文件 writer 与锁关系 |
| Mobile 当前群轮以固定计划执行，运行中同话题不能再抢租约 | JEV 需要向现有会话投递输入、插队和取消，不能只新增选人分支 | 核心与语音实际调用链 |
| VChat 与 Mobile 的“停止”含义不同 | JEV 的停止后续不能替换语音挂断、插话及立即停止的取消语义 | 双端生产代码 |

VChat 保留 `sequential`、`naturerandom`、`invite_only`，新增 `jev`。新顺序功能是**独立的成员发言排列**，不是带重复成员、次数或循环轮次的流程编辑器。JEV 是独立结构化决策接口，选人后仍使用现有 Agent 的模型、流式输出与工具链。

## 已取得与尚未取得的证据

四路并行审计分别覆盖 Melchior 的协议/生命周期、Casper 的核心与交付、Balthasar 的交互、独立同步契约复核；主代理核对交叉风险并整合方案。

主代理对插件现有 `extractGroupDTO`、`applyGroupDTO`、`createGroupConfig`、`computeDtoHash` 执行纯内存输入验证，未读取用户群数据或启动服务。结果如下：

```json
{
  "newSettingsAffectHash": false,
  "contextWindowAffectsHash": true,
  "createPreservesModeSettings": false,
  "applyAcceptsNewModeSettings": false,
  "applyPreservesExistingModeSettings": true
}
```

这里的 `newSettings` 是仅修改 `modeSettings.sequential.speakerOrder` 与 JEV 嵌套参数的合成配置。最后一项尤其重要：**旧插件对既有桌面配置通常是忽略新字段，并非每次回推都会直接删除整个 `modeSettings`**；新建丢失、投影遗漏及旧镜像遮蔽是不同问题。

JEV 子审计另执行了实际生产解析函数的内存探针，发现空/弱类型答案可能被当作自然结束或强制继续结果，详见 01。

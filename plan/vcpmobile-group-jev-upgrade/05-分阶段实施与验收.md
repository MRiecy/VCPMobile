## 1. 施工顺序与范围

三个工作部分的依赖关系是：群配置语义先明确，数据契约先闭合，JEV 持续会话最后接入现有生成链。推荐阶段如下：

| 阶段 | 交付 | 依赖 | 对应用户任务 |
|---|---|---|---|
| P0 | 产品差异裁定与升级样例 | 本审计 | 三部分共同输入 |
| P1 | 类型化群配置、持久化、三端 canonical 投影与首次迁移 | P0 | 新群组结构、同步 DTO |
| P2 | 同步端到端接入与版本切换 | P1 | VChat 同步插件及 CDS |
| P3 | 原三模式群设置重构、顺序排列、成员上下文窗口 | P1；跨端验收依赖 P2 | 新群组重构 |
| P4 | Rust JEV 客户端与全局设置 | P0；可与 P1–P3 部分并行 | JEV 适配 |
| P5 | JEV 会话编排、移动交互、语音与恢复集成 | P2、P3、P4 | JEV 与新群聊 |
| P6 | 迁移、混合版本、运行和平台验收 | P1–P5 | 完整交付 |

可并行的是接口明确后的 JEV 网络层与群配置/同步；同一群轮 owner、迁移事务和最终集成必须串行收口。不将“DTO 可以传输”当作“JEV 已可运行”。阶段之间以源码及检查验收，不在本任务中自动发布半成品。

## 2. P0：确定有限的产品差异

按 06 的 D1–D7 确定停止动作、语音接入、全局 JEV 配置、群成员窗口、首次同步冲突处理、重新生成范围和桌面并发写入保证的边界。其他常规实现选择采用推荐方案，不逐项增加审批。

在写代码前固定以下真实业务样例：

1. 桌面群已有 `speakerOrder=[B,A]` 和非默认 JEV；手机旧群最近改了名称，尚未同步。
2. 桌面和手机都已升级；手机离线明确改了 JEV 阈值，桌面同时改了另一群名称。
3. 同一群从自然随机切换 JEV 再切回，退群/重新加群后标签和风格遵循明确的保留规则。
4. JEV 正在仲裁时用户补充消息；成员已经开始回复时用户补充消息或点击停止后续。
5. 语音插话/挂断期间，JEV 仲裁和当前回复分别如何结束，以及已落盘的回复仍关联哪一条真人消息。

这些样例用于发现未知行为与约束，不用预先写死的测试反向决定产品。

## 3. P1：群配置与 canonical 契约

### 3.1 建议的数据所有权

- `members` 只描述群成员身份；`modeSettings.sequential.speakerOrder` 描述顺序。规范化时去重、过滤非成员并按成员原顺序补齐，不能靠改变 `members` 隐式表示排列。
- 群共享行为配置采用显式 Rust 类型：顺序、自然随机、邀请、JEV。前端类型沿实际 IPC 配对；不让任意 JSON 直接进入执行器。
- 持久化可用类型化读写的 `mode_settings` JSON 列承载模式配置，减少未来每个参数都散落 SQL 列的修改；通用字段、成员上下文窗口仍有明确字段和校验。JSON 存储不意味着跳过输入类型检查。
- Mobile 只保留一个模式配置权威来源。旧 flat 字段在迁移时单向归一；VChat 仍有真实旧字段消费者，镜像转换留在同步适配边界，并与 nested 权威原子更新。
- 桌面 `modeSettings.game` 等不在本轮共享契约内。共享投影只抽取支持的模式字段；桌面应用补丁保留其他模式分支和已支持模式内不属共享契约的 key，不能整个覆盖 `modeSettings` 或 JEV 对象。
- 未支持的 `mode` 保留原值并明确不可执行，不能在反序列化、编辑或保存时默默变成 sequential。

### 3.2 收拢 DTO 扩展点

目标不是让跨语言变更变成“只改一行”，而是让变更入口有限且可核对：

| 端 | 推荐收口 | 避免保留的重复 |
|---|---|---|
| JS 插件 | 一个群共享配置 normalizer/projector；extract、create、apply、hash 都消费其结果 | 白名单、默认构造、嵌套镜像和 hash 各自定义语义 |
| CDS Rust | 一个群投影函数承接导出与 hash；与 JS 共用代表性输入样例 | DTO 输出与 cached hash 使用不同字段集合 |
| Mobile Rust | `GroupBehaviorSettings` 等明确类型、一个 canonical DTO 构造、数据库读写复用 | `GroupConfig -> DTO`、manifest、SQL writer、hash 手抄不同集合 |
| Vue | 类型与模式专属编辑器，保存后消费 Rust canonical 结果 | UI 自建第二份默认/执行规则 |

跨语言保留轻量契约说明和共享 fixture，不为一次升级建设通用 schema DSL、运行时插件系统或全仓代码生成框架。新增字段将来仍需处理它的真实 UI/运行消费者；只调整未被消费的 DTO 不算完工。

canonical 规则必须明确 missing/null/空数组/空对象、ID 顺序、成员删除、历史标签、字符串与数值。对 JEV 阈值统一有限数字输出，尤其是 `0`/`0.0`、`1`/`1.0`；不能套用现有仅针对 `temperature` 的局部格式特判后就假定群 hash 一致。保留用户实际存储的提示词，缺失默认值另行统一，不能为了统一默认把已有文本改写。

### 3.3 首次升级不能制造用户编辑

必须处理两个独立问题：

1. **hash 投影版本变化**：重新计算 cached hash，保留业务 `updated_at`。现有 CDS 重扫和 Mobile 旧缓存都需要显式审查，不能靠“扫过一次”保证 LWW 安全。
2. **旧手机从未拥有新字段**：迁移生成的 UI 默认值不能被当作用户显式配置回推。wire 升级、重新计算 hash、保留时间戳均不能单独解决这一点。

推荐一次性的、可重入的群升级流程，而非永久增加一套字段同步引擎：

1. 迁移既有群时保留原字段和值，记录新配置部分尚未取得的来源状态；仅用于展示的默认值不等于已持久化用户选择。新建群从创建时即有完整配置。
2. 用户在首次连接前明确编辑的新配置，保留临时 dirty 叶路径/补丁；关闭页面或只改群名不应将其他字段标为已编辑。只改 `speakerThreshold` 不能把尚未取得的 `navigatorPrompt/memberStyles` 默认值一并当作用户选择。原有 flat 标签迁入 nested 属于已拥有的共享值，不属于“从未取得的新字段”。不要求给所有历史字段建立永久版本。
3. 先经现有 `PHASE_START` 门禁完成桌面 reconcile，取得带配置版本与删除状态的已提交 owner 快照，再暂缓普通整实体写入进行补齐。两端都存在的旧群吸收本机未取得字段，旧共有字段保留原有冲突规则；远端墓碑继续遵循原删除规则，不能把拉取失败或墓碑当作“桌面没有此群”并重建。
4. 若新配置字段在两端都存在明确修改且不能判定先后，呈现具体差异供选择，不静默用默认值覆盖。确认和提交都绑定所见版本；对端变化则重读/重新合并，不能把过期确认直接写回。离线仅在本机存在、且没有远端删除记录的新群按完整新契约创建。
5. 本地配置、来源标记、canonical hash 在同一事务完成，保留真实业务修改时间；中断重试得到同一结果。跨端写回需取得对应版本条件的提交结果后，才完成该群的升级流程。本地事务不代表跨端原子性；未完成补齐的群不得上传伪装完整的新 DTO。
6. 合并完成后回到单一整实体同步路径；迁移标记不进入日常执行，也不扩展为永久双写协议。

该流程是推荐方案，具体临时字段补丁与提交顺序由 P0 样例确定；不得通过禁止用户离线编辑来回避真实数据合并问题。

**现有接口缺口**：owner manifest 的动作结果和 owner pull DTO 不提供完整的对端 `configHash/updatedAt` 版本快照，当前 owner push 也没有 `expectedConfigHash` 条件。P1/P2 因而需要在现有实体读取/写回边界增加迁移所需的版本数据与条件提交，不能假定新增 `modeSettings` 后上述流程自然成立。客户端再次 GET 后 POST 仍有检查与写入之间的窗口；条件必须在实际提交边界复验。

**已经确认的限制**：插件锁不覆盖桌面正常群编辑。同步锁内条件检查、最新完整文件合并、提交后重读与 CDS 确认，只能对可观察到的竞争拒绝/重试，不能消除所有外部 writer 的窗口；共享 configHash 也不覆盖 topics/头像等专有字段。严格无丢失需要桌面所有相关 writer 加入共同持久化 owner，这超出当前可写目录。P0 按 D7 明确保证范围，不能以不可能在本范围实现的全局保证作为已达成条件；具体证据见 03 §5.4。

**退出条件**：旧数据可读，新增/编辑/落盘/重读保持规范化值；三端代表性投影与 hash 相同；迁移重跑不改业务时间、不覆盖未取得的新字段、不丢未知桌面配置。

## 4. P2：双后端同步闭环

修改范围包含 JS DTO/defaults/entity/manifest 真实消费者、CDS `sync.rs`/导入与缓存更新，以及 Mobile `sync_dto`、`sync_hash`、`db_write_queue`、群读写和迁移。精确入口见 03。

- legacy 与 CDS 分别验收，不能只验证默认 CDS 就宣称旧路径兼容。
- 新字段参与双向下载、上传、新建、更新、manifest hash；桌面 natural nested 与 flat 镜像同一次写入。
- 利用现有严格 wire 等值机制升级协议。实施时选择新 wire 号；本轮不改 app/package 版本或发布流程。
- 握手只保护实际受它约束的链路。HTTP owner 写入也要消费同一 DTO 校验与版本语义，不能接受旧形态完整覆盖后宣称已受 WS 升级保护。
- 为首次升级补齐扩展 owner 版本快照与条件提交，分别校验共享版本与完整物理文件快照，并如实保留上述外部 writer 限制。新插件配旧 CDS 的形态/能力不匹配也要在写入前被识别，外部 wire 相同不能替代内部配套检查。
- 协议升级的 owner 重投影必须在首份新 manifest 之前完成，并保持真实修改时间。CDS 已有 reconcile 可复用，不能为此清空或全量重建用户数据库。
- 旧端获得明确版本不匹配结果，不能尝试移除 `deny_unknown_fields` 来掩盖契约缺失，也不长期维护双 wire。

**退出条件**：legacy/CDS 双向新建、更新、删除后重建和第二次无变化同步均收敛；混合版本在实际数据写入前停止；纯 schema 升级不赢得 LWW；旧手机新群字段补齐样例通过。

## 5. P3：群设置与原模式闭环

- 群设置按基础信息、成员、模式专属设置、模型与上下文组织，复用现有页面、返回与主题原语。
- 独立顺序列表提供编号与上移/下移。拖动可作为增强，不是唯一移动操作。
- 自然随机 Tag 和匹配方式只在该模式显示，切换模式不删除其他模式草稿。
- 顺序执行只消费 canonical `speakerOrder`；成员增加稳定追加，移除后不执行悬空 ID。保留旧自然随机、手动邀请的实际行为。
- 建议纳入群成员模型上下文窗口：仅裁剪交给成员模型的历史，不删消息、不影响历史浏览和总结，不能用 JEV `historyWindow` 代替。
- 群配置保存失败保留草稿并阻止误判已保存；不得因页面已经关闭而只能 Toast 后丢弃编辑。

**退出条件**：四模式数据均可保留，原三模式按真实配置运行；编辑、同步、重启后顺序一致；窗口仅影响模型输入；JEV 未接运行时有明确状态而不假装已完成。

## 6. P4：JEV 服务与配置

JEV 使用独立 Rust 决策客户端，不调用普通 chat completion 路径来伪造概率答案。复用项目已有 HTTP/TLS、取消与诊断设施；具体网络协议、provider 规则和重试边界见 01。

建议全局 `jev` 配置领域承载连接、提供商、模型、密钥、可靠性及可选代理/应用信息；这属于现有 `settings_manager` 的领域配置与显式 TS 导出链，不把它塞进群 DTO 或复制成 Vue localStorage 配置。当前八领域及导出器/备份策略的扩展点需成套调整。

- 群 `modeSettings.jev` 只放群行为参数和成员风格；账号密钥不进入群同步。
- 一次请求绑定配置和选定 key，有限重试不切换身份；取消能中断请求与退避，迟到结果不恢复群轮。
- 明确区分停用、未配置、认证错误、超时、可重试错误和无效答案。
- 对每个 question/option 的答案进行实质校验；协议错误不是自然收敛。并列、强制继续、无候选和 fallback 的结果有确定规则。
- 不将服务测试按钮的成功当作真实群聊、流式回复和工具处理均成功。

**退出条件**：受控 HTTP fixture 能证伪请求格式、响应校验、key 选择、重试和取消；设置草稿/提交/重启读取一致，日志和错误不含密钥；真实 JEV 服务测试另取得经用户配置的网络证据。

## 7. P5：单一群会话 owner

### 7.1 复用与扩展

保留 `ActiveGroupTurns` 对 `TopicKey` 的排他关系、现有 speaker runner、模型/工具链、落盘终结、输出恢复与 TTS 归属。扩展现有群会话状态和命令输入；不在 Vue、新 timer 或另一份 map 中建立竞争性的业务 owner。

会话接纳的意图包括：用户新消息、发起、继续、手动排入成员、停止后续、立即取消。运行中的新消息递交给当前 owner，并沿现有消息仓储落盘；不是重复抢一次群轮租约。

状态至少能区分仲裁、队列、成员发言、停止后续等待当前收尾、终态；UI 根据后端快照及 revision 更新。没有流式气泡不等于会话空闲。

### 7.2 必须闭合的竞态

- 仲裁取历史快照与 revision；期间用户消息落盘，旧结果作废并按最新输入重新裁决，不能把过期人选再排进队。
- 手动插队能发生在仲裁或发言期间，去重与当前发言者的规则固定，不能让自动结果覆盖真人已接纳的意图。
- stop-after-current 中止尚未开始的仲裁和队列，允许已经开始的回复正常终结；取消整个会话同时取消当前 child、仲裁和待发队列。若单独开放“停止当前后继续”，须等该请求真实结算后才调度下一位；首期推荐保持 Mobile 单条硬停止结束本次接力的既有行为，不自动引入这种变化。
- 推荐停止命令只作用于当时的 run；在等待当前回复收尾期间明确接纳的新消息先落盘，在旧回复真实结束后触发下一 run。不能接受发送后仅在 finally 中清掉其触发意图。语音插话/挂断按其真实取消作用域执行。
- 仅在 idle→running 接纳一次新 run 时重置自治预算。运行中普通补充不重置预算；之后用户明确继续或新消息启动下一 run 才重置，避免话题终身计数与无限续预算两个极端。
- 每次 speaker 请求绑定不可变的 `originUserMessageId`/语音策略，后来的输入不能改写已经开始回复的来源。新裁决使用哪个输入作为来源需在 P0 明确；不能简单把整个会话的 origin 改成 latest。
- 每个语音回复作用域还要有可识别的完成/取消通知，并等待对应模型与播放收尾。现有 `ChatFeed` 通过 `turnId + group_turn(active=false)` 结束群朗读且忽略群成员 request_activity，TTS 又按 origin 筛选；不能只在长会话结束时对最新 origin 发一次终态。该作用域是同一调度 owner 的输出关联，不是第二个群执行器。
- 推荐运行中普通文本补充保留已排自动队列，仲裁期间使旧裁决失效；已开始回复固定配置快照，下一位发言前核验最新成员，下一次仲裁读取新配置。相关历史编辑、成员删除、模式变更推进 revision，不能混用旧队列与新成员表。
- 群/话题删除须发现并取消没有活动消息行的仲裁阶段；未结算请求仍由原 owner 收尾。重新生成范围按 D6，在支持前继续保持历史截断前拒绝，不能仅放开 mode 检查。
- 同进程 WebView 重接恢复真实活动快照；进程死亡后仅恢复已持久化消息和已有请求事实，不自动重放尚未执行的 JEV 队列/仲裁，用户可明确继续。后台行为按实际移动资源边界验收。
- 队列/继续轮数/历史窗口均有明确上限；不为等待仲裁无限持有数据库锁或创建无界任务。

### 7.3 移动入口

JEV 模式提供发起、继续、成员插队；生成期间仍能发送真人消息，并以独立动作控制停止。紧凑状态行说明仲裁/当前发言/终态原因，不写成伪造聊天消息。旧模式控件和语音取消保持原意，不能只改通用按钮文案却混用后端操作。

**退出条件**：用户补充、插队、取消、收尾、恢复与语音来源在同一会话中成立，单 Agent 与原三模式未回退；没有因新增 JEV 复制持久化或工具执行链。

## 8. P6：验证矩阵与证据范围

| 不确定性 | 应取得的证据 |
|---|---|
| 三端数字/默认/嵌套对象 hash | 生产投影函数消费同一组业务输入，比较 canonical 内容和最终 hash；含 Unicode、0/1、小数、空值及多余字段 |
| legacy/CDS 漂移 | 两套真实后端分别与 Mobile 导入/导出链往返，同步第二轮不继续产生差异 |
| 升级覆盖 | 旧手机仅改名称或单个 JEV 阈值、桌面已有其他新字段；远端墓碑；确认期间桌面再编辑；条件提交失败/中断重试；重算 hash 不改变业务时间 |
| 并发写入范围 | 在读取、检查、rename 前后插入同步与桌面业务写入；分别验证同锁写入、可检测外部冲突和未统一 writer 的剩余窗口，不把测试通过外推为全局 CAS |
| 严格协议 | 旧 Mobile/新插件、新 Mobile/旧插件、HTTP 旧形态上传分别取得明确拒绝且不写入 |
| JEV 结果可信度 | 非法/缺失/重复答案、并列、无活跃成员、全员静默、强制继续、429/超时/取消、迟到响应 |
| 会话竞态 | 仲裁中补充消息、发言中补充、重复插队、删成员/群/话题、停止后续、停止收尾中接纳新输入、立即取消、继续预算重置 |
| 持久化/恢复 | UI Channel 缺席、前后台切换、同进程 WebView 重建与进程死亡分别验证；当前回复正常/失败终结；重连不重复发言；未支持的重跑不截断历史 |
| 语音关联 | 插话/挂断取消正确任务；每个 origin 的完成通知与播放收尾均可到达；TTS 不消费旧来源、不会重播或把新消息覆盖已有回复 origin |
| 编辑闭环 | 四模式切换、顺序移动、保存失败、同步更新与本地草稿冲突、重开与重启 |
| 移动交互 | 具名 Android Debug 设备上的触控、键盘、返回与状态显示；仅操作 `com.vcp.avatar.debug` |
| iOS | 共享源码与 host 检查；需要时按既定 G1/G2 手动 Actions 取得 Apple 构建证据，不建设 iOS 实机体系 |

每次涉及核心或跨层的阶段完成后运行 `pnpm check`，先修复静态错误；运行与本阶段真实风险相称的 Rust、Vue、JS 测试。通过后不为增加数量重复无关测试。生产事实发生变化时更新这些文档及代码地图。

所有阶段完成前，分别报告源码审查、静态检查、host 测试、外部网络、双端同步、Android 运行和 Apple 构建结果；未取得的证据不能互相替代。提交、push 和发布仍需用户明确授权。

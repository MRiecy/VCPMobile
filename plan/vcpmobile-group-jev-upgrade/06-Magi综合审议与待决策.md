# Magi 综合审议与待决策

日期：2026-10-19。审议基于本轮当前生产代码，结论是推荐方案；本轮授权范围为审计与规划。

> 后续已获分阶段实施授权。用户最新裁定为本地差异化群配置、不改同步 DTO、模式独立、群停止直接中断全部及语音接入；实施期三方审议与记录见 [07](07-实施裁定与进度.md)。原同步扩展相关待决策不再构成本轮前置条件。

## 1. 三方意见与综合判断

| 视角 | 主要论点 | 对方案的影响 |
|---|---|---|
| Melchior：逻辑与系统 | JEV 是决策 API；持续仲裁与运行中新消息超出现有固定 speaker plan。必须约束历史 revision、取消、队列、预算、origin 和迟到响应 | 在 Rust 原群会话 owner 上扩展编排，复用模型、工具、持久化与输出链；严格区分无效答案与自然结束 |
| Balthasar：交互与美学 | 增加一个模式按钮不足以使用 JEV。手机需要独立排序、发起/继续/插队、生成期间发送，以及明确的停止语义 | 高密度线性模式设置，后端驱动的紧凑运行状态；保留返回/草稿闭环；不复制桌面视觉容器 |
| Casper：务实与交付 | 重写整个聊天核心会破坏已解决的后台、语音和终态；只在旧 policy 增加分支又无法表达持续会话 | 保留稳定 runner，重构配置边界与编排；先完成数据/顺序，再接 JEV；阶段分别验收 |
| 同步独立复核 | 已有 DTO 模块但不是三端单点契约，且存在真实漂移；首迁移的默认值与 hash 会影响整实体 LWW | 同步是前置依赖；收拢投影，使用严格版本切换、保时间重投影和一次性补齐，避免永久双协议 |

这些观点互相约束：以小改动为名跳过迁移会留下数据问题；以完整架构为名重写稳定生成链会扩大回归范围。推荐尺度是**群配置契约 + 群会话编排 + 必要移动入口**。

## 2. 推荐直接采用的工程选择

1. 原三种模式保留，默认顺序不变；JEV 为第四种模式，不自动替换自然随机。
2. 顺序配置是去重成员排列，新成员稳定追加；不增加循环次数或重复节点编辑器。
3. 全局 JEV 连接与账号配置归本机全局配置；群 DTO 只携带群行为参数。现有同步没有全局设置同步，本次不扩大范围。
4. JS、CDS、Mobile 各保留一个明确群投影入口，以相同业务输入验证三端一致；不建通用元编程框架。
5. `modeSettings` 是共享行为的权威；桌面旧镜像因为仍有真实消费者而保留在 adapter，不能让 Mobile 也永久双写。
6. 保留桌面不属于本轮的模式和其他配置。游戏模式不移植，不在同步回写时误删。
7. Mobile 的 JEV 回答校验应比上游弱类型解析明确：无效数据报决策错误，不假装自然结束；不复制已发现的自治预算生命周期问题。
8. 上移/下移是顺序编辑的基础操作，拖动为可选增强；未知模式保留数据并说明状态。
9. 同进程重接从 Rust 快照恢复，前端不拥有 JEV 调度；进程死亡不自动重放未执行队列。不把未完成仲裁写为聊天内容。
10. 新群 `fallbackPolicy` 默认 `stop`，首期不新增选择器；同步/导入的合法 `top_speaker` 保留并由后端按明确算法执行。修改群名或其他字段不能把已有值强制改成 `stop`。
11. 自治预算按一次 idle→running 的 run 计算，运行中补充不重置。普通文本补充保留已排队列，但使尚未接纳的旧裁决失效；已开始回复固定快照，下一次调度/仲裁刷新相关成员和配置。
12. 优雅停止作用于当前 run；等待当前回复结束期间接纳的新消息保留为下一 run 的触发，不能在收尾时悄悄丢弃。

## 3. 实施前应确定的产品决定

以下只列会影响用户行为或数据取舍的选择。推荐项尚未被用户逐项批准。

| 编号 | 问题 | 推荐 | 其他选择及代价 |
|---|---|---|---|
| D1 | JEV 的停止按钮是否跟随 VChat？ | JEV 主群控制使用“停止后续”，当前回复完成；同时保留独立的立即停止路径。原模式和语音取消不改变含义 | 只提供立即停止较简单，但不能复现 VChat 当前自然收尾行为；把所有取消都改成等回复结束会破坏语音 |
| D2 | JEV 是否本轮覆盖语音通话？ | 完整集成现有语音 owner：保留真实插话/挂断取消，给每次发言固定来源；把实现和验收纳入 P5 | 文本先行需明确 JEV 群语音不可用的过渡范围，不能仍允许进入却在后端抢租约失败 |
| D3 | JEV 全局配置和备份范围？ | Mobile 本机直连、独立配置；复用现有显式备份机制并明确密钥是否导出，群同步不含账号配置 | 桌面代理调用依赖在线桌面，属新增架构；自动同步账号配置是另一个产品范围，不应随 DTO 升级引入 |
| D4 | 是否同时补齐群成员模型上下文窗口？ | 纳入本轮：当前已是桌面群配置，且 legacy DTO 已包含，修复契约时一起完成运行消费者 | 仅存储/传输可先保持数据，但 Mobile 模型上下文仍有行为差异，需要明确提示和后续阶段 |
| D5 | 首次升级遇到新字段冲突如何处理？ | 未取得的新字段先吸收桌面已有值，保留手机旧字段编辑；两边明确修改无法判断时展示具体差异让用户选 | 统一桌面覆盖或手机覆盖容易实现，但分别可能丢手机离线编辑或桌面新配置；不能静默选择 |
| D6 | JEV 的“重新生成”是否首期开放？ | 首期保留截断历史前明确拒绝；提供继续与成员点名。单成员重试和从某条消息重跑整场另行明确后再开放 | 直接复用原历史截断路径可能删除连续讨论并重复其他成员；若本轮要求开放，需要同时定义重跑范围和取消/语音关联 |
| D7 | 是否要求桌面编辑与同步任意交错都严格无丢失？ | 当前任务继续遵守仅同步目录可写；实现版本检查、完整配置合并及可检测冲突的拒绝/重试，明确不承诺全 writer 原子性 | 如要求严格保证，需要另行授权改造 VCPChat 的全部相关群配置 writer；仅改插件或 CDS 无法让现有桌面直接文件写自动参加同一锁 |

D3 的“是否导出密钥”按项目现有备份产品约定选择，不应为了本任务突然引入另一套加密或账号管理体系。备份与跨设备实时同步是两种不同动作。

D2 还需在 P0 细化一个关联规则：若真人在当前成员回复期间发送新消息，已经开始的回复保持原 `originUserMessageId`，后续由新历史触发的成员回复关联对应新输入。一次会话容纳多次输入后，不可再用一个可变的 origin 字段同时代表全部回复。每个语音回复作用域必须获得独立的完成/取消通知并等待实际播放收尾；固定 origin 而不改现有只等待整群 turn 结束的 feed，仍不构成完整适配。

D1 的后台意图应明确区分，界面不一定呈现三个按钮：

| 意图 | 当前成员回复 | 后续队列/仲裁 | 语音 |
|---|---|---|---|
| 停止后续 | 自然完成 | 当前 run 不再开始新工作 | 当前有效来源继续朗读至实际完成 |
| 停止当前回复 | 硬取消并等待结算 | 首期建议维持 Mobile 取消后结束本次接力；“停当前、继续下一位”不是默认行为 | 停止该回复对应朗读，通知其来源终结 |
| 取消整个会话/通话回复 | 取消属于该作用域的当前请求 | 清除对应排队并取消仲裁，等待真实清理 | 取消对应回复/播放；不得误取消别的通话或话题 |

D5 需要的不只是 UI 选择：现有 owner 接口缺少对端版本快照与条件写，实施须在同步提交边界补齐，重新核验确认期间发生的桌面编辑；本地事务不能被宣称为跨端原子提交。D7 是进一步的物理写入边界：插件已有锁与桌面业务写不共享，即使条件检查通过仍可能与另一 writer 交错，详见 03 §5.4。

## 4. 已辨明的风险不应被误写成新产品需求

- 发现上游对空答案和类型转换过宽，不代表要增加用户可调的十几个“安全参数”；在真实响应边界校验即可。
- Mobile 需要显示仲裁/结束状态，是为了使用和恢复该功能；VChat 当前事件消费者并没有完整队列可视 UI，不能声称只是照搬现成界面。
- 现有 wire 握手提供版本拒绝机制，不代表所有 HTTP 写入自动受到同一保护；应沿实际链路落实一致契约，不另建无消费方的能力门禁。
- legacy 存在字段漂移不等于默认 CDS 同步全面失效；两条路径分别记录和验收。
- 旧插件忽略新配置不等于它每次都删除新配置。需要分别解决 hash 不可见、新建丢失、nested 镜像遮蔽及首迁移覆盖。
- 代码审计发现潜在不一致，不等于用户现有数据已经损坏。本轮没有访问实际用户群库进行损坏判定。
